## Denoising A/B

- **Denoising A/B** (evaluate any precision/recall lever BEFORE shipping): `node benchmark/denoise-ab.mjs --save before.json` (control) → apply the change → `node benchmark/denoise-ab.mjs --compare before.json` (verdict). Runs the precision hard-negative, vocab-mismatch paraphrase, AND cjk_mixed suites so a lever's precision gain and recall cost are weighed on one screen — the split that let an OR-BM25 floor ship-then-revert (2026-06-29). Behavioral probes ride the same screen (multiscript guard + cross-source direction + deferred reachability + events end-to-end pipeline); any probe failure overrides the verdict to PROBE-FAIL and exits 1 — "A/B NEUTRAL ≠ safe" on faces the metric suites can't see. Verdict: REJECT / TRADEOFF / NET-POSITIVE / NEUTRAL / PROBE-FAIL.


## error-recall LIVE replay

- **error-recall LIVE replay** (`node benchmark/error-recall-live-replay.mjs [--dump f.json] [--shapes f.json]`): the ruler that closed D#167, and the one to reach for FIRST on this face. No fixture at all — inputs are real failing commands with their real stderr read out of `~/.claude/projects/**/*.jsonl` and filtered through the surface's own `detectBashSignificance().isHardError`; corpus is the live DB, every project with ≥20 rows. Reports the share of injected rows that match NO error term (i.e. admitted on command vocabulary alone) and the share of cases where such a row is TOP-1. **A/B it by flipping `CLAUDE_MEM_ERROR_RECALL_RERANK=off`, not by editing it**, and pass the same `--shapes` file to both arms — the transcript sample grows every session, so a re-extraction between arms silently changes the denominator. It carries a self-check that the membership predicate can return FALSE, because the first version of it could not (see the FTS5 note below) and reported the defect as 0.0%.


## citation per-face LIVE replay

- **citation per-face LIVE replay** (`node benchmark/citation-live-replay.mjs [--split ISO] [--since ISO] [--project s] [--dump f] [--corpus f] [--by-project] [--by-scope] [--json]`): every injection FACE's cite-rate re-derived from real transcripts through the **shipped** extractors (`extractInjectedBySurface` / `extractCitationsFromTranscript` / `collectSubagentSurface`). **Reach for this before `citation-stats`** when a face's row count looks too small to decide on: `citation_surface_log` is only as old as the METER, and the meter is routinely younger than the behaviour — it held n=8/2.1d for `task_imperative` while this replay gave n=34 over the corpus. It is not `benchmark/cite-recall.mjs` either: that one buckets by hook EVENT using its own hand-copied markers (a twin of `SURFACE_MATCHERS`) and unions cited ids across a session, the caliber that credited `subagent` for cross-agent citations until v3.81.0. Caliber here: denominator = **(session, id) pairs**; numerator = that id cited as `#NN` in the session's own main-thread text, or for `subagent` in the **receiving** agent's own text. **Never diff two runs taken at different times** — the corpus grows, and a +38 delta measured that way was +22 in a same-corpus pass; use `--split`, which cuts ONE walk into two arms. `keyctx` is declared unreachable rather than silently omitted, and a face added to `SURFACE_MATCHERS` that this script cannot reach makes it throw. **The LIVE corpus on this machine now walks 85 session transcripts / 79 injection-bearing sessions (measured 2026-09-01T20:24Z; it read 77/72 on 2026-08-31, and the walk grows every session — including the one writing the note that quotes it; 235 `.jsonl` at all depths, of which the replay walks the session level). Why it is an order of magnitude under the frozen baseline was NOT established — pruning, rotation and a different walk depth are all consistent with what was measured, and none was verified — so the only safe rule is that any figure must say which of the two corpora it came from.** A 2026-08-31 reviewer report in `tasks/` quotes "1122 transcripts" for its own walk; that is not reproducible at any depth here and is close enough to the frozen 1116 to look like the baseline being restated. Its PAIR counts did reproduce independently, so treat that report's corpus-size line as the unreliable part, not its findings. Baseline, quoted from the FROZEN corpus below so it is reproducible rather than a moving number (1116 transcripts / 87 injection-bearing sessions / 9 projects): pretool 39.5% (562/1424) · subagent 24.5% (12/49) · task_imperative 45.7% (16/35) · fyi 11.3% (32/284) · ups 8.1% (20/246) · error_recall 6.2% (44/709). A fresh walk reads a little higher on every face within the same day — that is corpus growth, not drift, and it is exactly why a cross-time subtraction is banned above. Frozen corpora for a later same-denominator A/B live in `benchmark/results/`, gitignored and never to be committed — but for **different reasons, so do not copy one justification onto the other**: `citation-corpus-2026-08-25.json` holds no transcript text at all (its longest string is a project path; a record is `{project, session, ts, anyCite, faces:{face:{inj,hit}}}`) and is excluded for the session UUIDs and absolute paths, while `error-recall-shapes-2026-08-25.json` genuinely carries real commands and their stderr. The latter is the `--shapes` file to pass to BOTH arms when re-measuring v3.79.0's error-recall rerank once n is large enough (at the v3.79.0 split the after-arm was 35 pairs, CI [0.5, 14.5]% — fully overlapping the before-arm, i.e. nothing decidable yet). **`--by-scope` is the ruler that closed D#153**: it re-buckets each face's pairs by `observations.scope`, which is what `CLAUDE_MEM_SCOPE_FILTER` keys on. On `pretool` — the face that filter gates — `environment` cites at **47.5% (67/141)**, the highest bucket, against `project` 44.3% (293/661), `file` 40.0%, `(gone)` 37.1%, `module` 36.5%, `(null)` 34.9%, face overall 41.0% (623/1519). The environment/project CIs OVERLAP, so "environment leads" is not established — what is refuted is that it is the class to suppress, and the down-weight redesign was NOT built. Caliber: the six buckets sum to exactly 1519 because 498 ids whose row has since left the table are reported as `(gone)` rather than dropped — a scope table whose buckets do not sum to the face's pair count is comparing rates over a population that is not the face. Those gone ids are an old cohort from bands that are ~81% `(null)`-scope, so they cannot be environment-heavy; the head-to-head is not era-confounded, but `(null)` and the face-overall comparator are. **`--mentions` is D#179's prerequisite measurement**: it re-splits each face's NUMERATOR into ids named in a model response that also called a tool, and ids named only in prose, keyed by `requestId` — one model response, which is the granularity that matters, since a whole user-to-user exchange nearly always contains some tool call and bounding on user turns would classify everything as applied. Measured 2026-09-01T20:24Z over 79 injection-bearing sessions (85 transcripts): **`pretool` 76.4% mention-only (420/550)**, fyi 61.9%, ups 61.5%, task_imperative 66.7%, error_recall 42.9%. **Quote the ratio, stamp the counts**: three runs the same evening read `pretool` 75.3% → 75.6% → 76.4% as n grew, and the corpus grows partly BECAUSE of the work being measured — the session that writes a release note is itself a transcript the next walk reads, which is the self-reference D#179 exists to describe. Stated in one currency, since a share of hits and a change in a rate are not comparable and the draft set them side by side: **403 of `pretool`'s hits are prose-only against 149 hits contributed by the ten document-shaped sessions**, so the contamination is NOT confined to those sessions. **Neither column is a bound, and a first draft of the docblock wrongly called `mentionOnly` a floor**: co-occurring with a tool call is not evidence a lesson was followed, and acting in one response then citing in a later summary lands in `mentionOnly`. `subagent` is declared unavailable rather than omitted — its hits come from the receiving agent's transcript, which this classification does not walk.


## episode-flush LIVE replay

- **episode-flush LIVE replay** (`node benchmark/episode-flush-replay.mjs [--since ISO] [--project p] [--json]`): the ruler for D#178 and the only thing that can price a change to the episode flush path. No fixture: it replays every real tool call in `~/.claude/projects/**.jsonl` through the **shipped** batcher (`isRelatedToEpisode` / `EPISODE_BUFFER_SIZE` / `EPISODE_TIME_GAP_MS` / `planEpisodeFlush` / `explainSignificance` / `buildImmediateObservation` / the two write-side noise gates), so the flush decisions cannot drift from production. **Its middle self-check is the one that matters**: the live `episode_significance` metric rows measure the same share the replay models, and the two must agree within 15pp or the run exits 1 (measured 2026-08-25: meter 40.7% insignificant over n=938, replay 37.1% over n=1305, gap 3.6pp). It reports SKIP — not PASS — on a machine that never set `CLAUDE_MEM_METRICS=1`, because there the flush model is unchecked. Known under-count, in one direction: `<session>/subagents/*.jsonl` is one level below the walk, so tool calls made inside a dispatched agent — which do fire PostToolUse and do append to the same reads file — are missing. **Correct a premise before quoting it**: D#178 was filed saying ~92–96% of flushes are insignificant; the meter says **40.7%** (n=938 over 3 active days). Standing result (2026-08-25, 1122 transcripts, 3819 flushes, 1627 distinct reads consumed): **42.2% of the Read paths a flush consumed are destroyed by an insignificant flush**, 72.7% of significant flushes carry no reads at all, and the fix delivers ×1.68 more (72.7% → 66.1% empty). Staleness is **per delivering flush and of the OLDEST read in each** — median 1.7m, p90 10.1m — so it overstates the typical read's wait and understates nothing. Observation-level, past the two write-side gates and NOT modelling DB dedup (so an upper bound): 10 → 17 of 47 landed rows carry a read. **The delivery multiple is a UNION, not a sum**: production collects with `new Set(...)`, so a path read in two carried-over windows is delivered once; summing per-flush counts published a figure 2.9% high until both pre-tag reviews caught it independently.


## error-recall calibration

- **error-recall calibration** (`node benchmark/error-recall-suite.mjs [--scores|--sweep|--compare]`): denoise-ab **structurally cannot see the error-recall face** — its suites are query→document, while that face's input is a failed command plus its stderr, so a lever there reads NEUTRAL Δ=0 no matter what it does. This is its ruler. `--sweep` is the one to calibrate against: a floor only affects rows that reach the injection cap, so the `--scores` distribution overstates the achievable gain. **Four invariants the suite enforces on itself, each one earned:** (1) every case must pass the real `detectBashSignificance().isHardError` — a case that cannot fire measures a path that does not exist (#10731); (2) the fixture must carry enough filler to keep FTS5's IDF non-degenerate (a small all-one-topic corpus scores every row 0.00, and any floor then removes everything); (3) `--scores` must probe at `floor: 0` and self-checks that it can see below the calibrated value — it once inherited the shipped default and reported the post-gate remnant as the population, making the calibration table unreproducible from its own tool; (4) cases are split into **servable** (the corpus can explain the failure → judged on hit-rate) and **unservable** (it cannot → judged on staying quiet), because with only servable cases present a set-level gate scores identically at every threshold and reads as a no-op. **Standing result (v3.78.0): the |bm25| floor is built, calibrated at 10.5, and OFF by default.** Measured on the live DB at that threshold (8 projects × 9 shapes, 69 firing cases): floor off = 201 injected rows; **set-level = 126 (−37%), 39% of firings silenced**; per-row = 97 (−52%), 38% silenced. Loss concentrates in projects under ~500 observations, which `corpusFloorScale` is documented not to see (it normalises over the whole table, correct for IDF, deliberately project-blind). **The fixture reports the set-level form as a no-op and is wrong** — its hard negatives are constructed to score above 10.5, so it cannot see this cost; two review rounds each caught one level of this same "fixture number standing in for a live one" error. Command words dominating BM25 is a semantic defect and no magnitude gate reaches it → D#167. **D#167 is now closed, and it was filed against the wrong culprit.** Measured over 52 real failing commands (real stderr, pulled from 1110 transcripts, filtered through the real `isHardError`) replayed across 15 live projects: 28 of the 52 name their failure (`ModuleNotFoundError`/`ENOENT`/`JSONDecodeError`) and **25 of those 28 (89.3%) never got that name into the query** — the six-term budget went to the Python banner `traceback,most,recent` and to path fragments (`mnt,data_ssd,dev`). Downstream, 39.2% of injected rows and **42.3% of TOP-1 rows** (the row inlined verbatim into context) matched no error term at all. Two independent defects, and **fixing terms alone does not touch injection**: naming the failure moved cmd-only rows 39.2% → 40.2% (more specific terms match fewer rows, leaving the flat OR *more* room to fill slots with command vocabulary). Shipped: `ERROR_NAMER_RE` (positive pattern for the signal, never a boilerplate stop-list — that enumerates forever) + an error-first rerank that **reorders and never removes** → 22.4% rows / 21.5% top-1, row count unchanged; suite precision 23.1%→34.6%, hit-rate 85.7%→100%. The mandatory-error-term form was rejected on the same sample (−22.4% rows, 21.5% of cases injecting nothing, concentrated in small projects — the floor's failure mode relocated). **Two ruler defects worth remembering:** (1) `SELECT 1 FROM observations_fts WHERE rowid = ? AND fts MATCH ?` **silently drops the rowid constraint** on SQLite 3.53.1 — it is an always-true membership test, and it reported the defect as 0.0%; pull each term's rowid set instead. (2) `ERROR_NAMER_MAX` shipped at 2 on an argument (chained tracebacks) and swept to 1 on data. Residual: the cap evicts the *last* term, which is often the most specific one (a filename lost to a class name) — **that was D#169, and it was built, measured and rejected**: an identifier-first cap (`[._-]`) moved cmd-only rows 22.6% → 35.8% and top-1 21.3% → 33.4% on the live DB, because `[._-]` conflates "discriminative" with "unique to this invocation" — it promotes this run's own filenames (IDF so high they match nothing) and evicts `enoent`/`syscall`, which are exactly what the explaining memories contain. Any retry needs real document frequencies, and `planErrorRecall` is pure with no corpus to count. The negative result lives in the cap's docblock in `bash-utils.mjs`.


## error-recall rerank same-corpus A/B

- **error-recall rerank, same-corpus A/B (settled 2026-09-01)**: the measurement debt v3.79.0 opened is closed on the MECHANISM and still open on the OUTCOME. Both arms over the frozen `benchmark/results/error-recall-shapes-2026-08-25.json` run back to back (64 shapes, 885 firing cases, **2413 injected rows in both arms**, with identical per-project row counts in all 15 projects — equal TOTALS alone would be necessary and not sufficient, since a transform that drops one row and admits another keeps the count; even the per-project agreement is counts, not set identity), flipping `CLAUDE_MEM_ERROR_RECALL_RERANK=off` rather than editing code, 2026-09-01T19:58Z: rows matching NO error term **39.7% → 21.7%**, TOP-1 such rows **38.8% → 20.5%**. The SHAPES are frozen; the DB they replay against is not, so the off-arm read 39.8% / 38.9% six hours earlier while the on-arm was identical to the digit — stamp these too. That confirms v3.79.0's shipped claim. The OUTCOME arm does not: `citation-live-replay --split 2026-08-24T18:00:15Z` (one walk, both arms) puts `error_recall` cite-rate at **9.0% [6.0, 13.2]% (22/245) before → 5.2% [3.4, 7.9]% (20/383) after**. **On a date split only the BEFORE arm is reproducible** — it is a closed past window and read identically six hours apart, while the after arm grew 374 → 383 pairs; a "before" figure can therefore be quoted flat and an "after" figure cannot. The after-arm is no longer under-powered (35 pairs at release). **The robust reason this is "unestablished" is the shorter one: the two CIs OVERLAP** ([6.0, 13.2] vs [3.4, 7.9] share 6.0–7.9), so the difference is not significant however the period is treated; separately `pretool` moved 34.0% → 39.9% over the same boundary, so a period effect is present and a date split cannot attribute either direction. But do not read "unestablished" as "uninformative" — the only outcome evidence available points AGAINST the rerank (a difference-in-differences over those two faces would read about −11pp); computing it is declined because nothing supports parallel trends between faces with different content, so the honest label is adverse-and-confounded. Standing verdict: mechanism confirmed, cite-rate benefit **not demonstrated and not refuted**.


## rerank-pool LIVE replay

- **rerank-pool LIVE replay** (`node benchmark/rerank-pool-replay.mjs [--sample N] [--baseline-same n] [--baseline-cross n] [--cross-arm] [--cost] [--json]`): the ruler for the `fyi` face's candidate-pool bounds (`RERANK_POOL_SAME_PROJECT` / `RERANK_POOL_CROSS_PROJECT`, audit ALGO-3). **`benchmark/denoise-ab.mjs` is structurally blind to this face** — its suites drive `search-engine.mjs`, nothing imports `hook-memory.mjs` — so a NEUTRAL Δ=0 there says nothing about a change here. Replays every real row of `user_prompts` through both the shipped module and a twin carrying different pool constants. **The default is the WHOLE corpus and that is deliberate**: v3.85.0's first draft quoted 11.9% / 4.0% off a newest-1200 sample filtered to `LENGTH(prompt_text) BETWEEN 20 AND 2000`, the pre-tag review could not reproduce it under nine sampling configurations, and the harness turned out to be right — **the sample predicate was the entire disagreement** (1200-row samples of this one table span 11.9%–20.2% by predicate). `--sample N` therefore prints a warning. **Never diff two runs taken at different times**: the table grows every session (11279 on 2026-09-01 morning, 11289 that evening), so run every arm of a comparison back-to-back. Standing result (n = **11289**, 2026-09-01, 10/5 → 30/15): 15.9% of prompts get a different injected set, 6.7% a different top-1, 2497 rows newly reachable / 1252 displaced, empty 6587 → 6362, **delivered rows 9650 → 10895 (+12.9%)** with the per-set cap unmoved (size-3 sets 1966 → 2521 — the fill changed, not the cap). **Decomposed, the headlined clause is not the one that acts**: cross-project `LIMIT 5 → 15` alone gives 12.6% / 5.3% and **214** of the 225 empty→non-empty prompts, against 3.6% / 1.4% / **9** for same-project `10 → 30` alone. `--cost` measures the whole function, both arms, arm order alternated across two passes: **+5% to +16% across calibers, +6% to +10% with this one**. Six whole-corpus `--cost` runs on one machine gave **1.058–1.102** — same code, same corpus — against 1.054–1.065 with the arm order held fixed and 1.063–1.156 with each arm alone in its own process (closest to production). **Quote the range, re-measure, and never quote the absolute ms/prompt**: they moved 3.04 → 1.80 across those same six runs while the ratio held. Pairing the arms per prompt does let the second call reuse the first's pages and alternating cancels only about half of it, which makes this the lowest-VARIANCE caliber, not the unbiased one. Timing the SELECT alone reads ~1.00× and misses the JS scoring the widened pool feeds, so that caliber answers a different question. Five self-checks, each verified able to fail (and `--cost` runs the determinism one too, since v3.85.1 — it used to `exit(0)` above it, so the mode producing the most contested number was the only one that never checked the replay was reproducible): the twin patch must apply and must differ from shipped; the handle must reject a write (`searchRelevantMemories` bumps `injection_count` on every row it returns, so a writable handle would move the very noise signal being measured *and* let arm A's writes change arm B's scores); shipped-vs-shipped must report zero; and **`nonEmptyToEmpty` — the counterexample to the superset argument — must stay 0 or the run exits 1** (`emptyWide ≤ emptyNarrow` does NOT establish this: two prompts moving off empty hide one moving onto it). And, since v3.91.0, **the metric sink must not grow**. That fifth one exists because the other four all held while the ruler wrote 1.5 million rows into a series this project reads. **`searchRelevantMemories` has TWO sinks and the readonly handle only shuts one of them**: it also appends an `inject` row to `$DB_DIR/metrics/YYYY-MM-DD.jsonl`, which a readonly *database* handle does nothing about. On a machine with `CLAUDE_MEM_METRICS=1` (this one), whole-corpus runs plus six `--cost` passes wrote **204,499,386 B / 1,543,630 lines on 2026-09-01, of which 1,541,442 are `inject`** — against **15 / 17 / 26** on the three clean days in the same window (08-31 / 08-29 / 08-27) — and **`claude-mem-lite doctor --metrics`** (the plain `doctor` has no metrics section — the reader is behind that flag) consequently reported `inject · n=1543363 · 2 / 8 / 19 (ms)` over its 7-day window, i.e. **at least 99.87%** of that row is benchmark traffic and the three percentiles are in-process replay timings, not injection latency. **All four of those figures are now unreproducible from disk, and the reason is NOT corpus growth**: the 2026-09-01 shard was surgically repaired in v3.91.0 — its 1,541,442 `inject` rows filtered out, its 2,188 genuine rows kept, 204,499,386 B → 279,021 B — so the same command now reads `inject · n=149 · 9 / 45 / 74` (2026-09-02T17:4xZ, after BOTH days were repaired — see the 09-02 paragraph below) over the same window. A reader who does what this file tells them to do (re-measure rather than carry) cannot reconcile 1,922 with 1,543,363 by any amount of real-prompt growth, and "stamp the n" alone would have handed them a false mechanism; it governs the LIVE `inject` count, not this retired one. The repair cost that day's genuine `inject` rows too — on the order of 15–25 by the clean-day rate — because nothing in a metric row records which process wrote it. **"At least", because 09-02 is not the clean comparator it looks like**: it read **1,863 at 2026-09-02T15:5xZ and 1,864 minutes later** — 09-02 is the *current* day, so that half is still accruing and must be stamped — with **1,794** of them in two UTC hours (11:00–12:59), which is stable because those hours are closed. That window is that day's ad-hoc D#215 measurement. So a second day is contaminated by a *different* tool — an uncommitted one-off harness, which no guard in this repo can reach. The rule that does reach it: **any ad-hoc script that calls `searchRelevantMemories` passes `{ counterfactual: true }`**, for the same reason the committed ruler does. **09-02 was repaired too, and on a sharper predicate than 09-01's** — that day the two populations separate with nothing in between: clustering its 1,879 `inject` rows at a 5s gap gives 88 runs, of which **2 hold 1,788 rows in 4 and 5 seconds** (≈200 rows/s) and the other 86 hold **91 rows, largest run 3**. So only the two bursts were dropped and all 91 genuine rows kept, where 09-01 had to lose its ~15–25. Post-repair per-day `inject`: 26 / 17 / 15 / **0** / **91** (08-27 / 08-29 / 08-31 / 09-01 / 09-02), summing to the `n=149` above. **The finding to carry is what happened to the PERCENTILES, because it runs opposite to the intuition that pollution inflates**: `2 / 8 / 19` → **`9 / 45 / 74` ms**. The replay's in-process calls are *faster* than production injection, so 99.9% benchmark rows were dragging p99 down by ~4×; a poisoned latency series can understate as easily as overstate, and reading the old row as "injection is fast" would have been the wrong conclusion in the safe-looking direction. **`mem-cli stats` was unaffected in its VALUES and not in its cost** — the distinction matters if anyone later reads it as "the pollution had no reach into `stats`": it never displays `inject` (it reads `file_intel` / `reread_warn` / `pretool_recall` / `error_recall` / `enrich_save`), but `aggregateMetrics(DB_DIR, 7)` and `readMetrics(DB_DIR, 7)` walk **every** row in the window, so it was parsing a 204 MB file to print the same figures. Every arm invocation now goes through `callArm()`, which passes the shipped `{ counterfactual: true }` (it skips the bump *and* the emit); the guard forces the sink ON, lets `recordMetric` NAME the shard in a throwaway dir and watches that basename in the real one, and **fails if the probe call never reached the metric block**. State that invariant as "**returns without calling `_emit`**", not as "returns above it": there are **three** such paths, not two (`!db || !userPrompt`, the length floor, and `!ftsQuery`), and the third sits *below* `_emit`'s definition inside the `try` and simply never calls it — the positional phrasing is wrong today and would rot on any reorder. **The probe alone was NOT enough, and the pre-tag review proved it with a running counterexample.** It establishes that `callArm` carries the flag; that every arm invocation GOES through `callArm` was left to a source-text case, and four bypasses defeat a regex — aliasing the handle (`const d = db; narrow(d, …)`), `narrow.call(null, db, …)`, aliasing the function inside `costCompare`'s timer, and a newly exported helper calling an arm directly. All four survived the suite, and the aliasing one over 300 real prompts **appended 992 metric rows while the run printed a full report and exited 0** — this release's own defect, reopened through a form the text guard cannot match. So the guarantee is now stated at the level that matters: not "the helper carries the flag" but **"THIS RUN wrote nothing"**. `metricsDirSize` + `runLevelGrowth` take a whole-`metrics/`-directory baseline and re-check it from a `process.on('exit')` handler — which covers every exit path including the two `process.exit(0)` modes and any mode not yet written, and which fires AFTER the report prints, so a false positive (a live hook writing during a multi-minute run — indistinguishable, and the message says so) costs a scary message rather than the run's output. Measured on the same bypass: **exit 1, 992 rows named, report intact**. Directory-total rather than one shard also closes the UTC-day-rollover hole (a run started at 23:59 writes into tomorrow's shard). **One stated limitation**: with `CLAUDE_MEM_METRICS` unset a bypassing call writes nothing, so the run-level gate passes — correctly, no harm occurred, but it is then silent about call FORM; the probe, which forces the sink on for its own duration, is what covers that case. The two are complementary, not redundant. **Ten mutations, ten killed**, and re-run in a quiet tree: the first round was taken while a reviewer was mutating the same file, its backup captured the OTHER agent's mutated state, and neither harness could have detected it (`feedback_parallel_builders_shared_tree`). End-to-end, a 500-prompt run under `CLAUDE_MEM_METRICS=1` grew the shard by **0 bytes / 0 lines**; with `CLAUDE_MEM_DIR` redirected to a sandbox, 0 rows and 0 files. Two things to carry: this file's own docblock said "IT CANNOT POLLUTE THE CORPUS, and proves it rather than promising it", which was true of the corpus and read as if it covered the file — **a guard is only as wide as the sinks it enumerates** — and v3.90.0 fixed this exact shape in `lib/patha-exclude-meter.mjs` while quoting *this* ruler's write-guard as the precedent, so the rule was cited in the same release in which it was being violated elsewhere. **Swept over FUNCTIONS CALLED, not modules imported** — say which, because two committed benchmarks do import metric-emitting modules and both are benign: `benchmark/patha-exclude-report.mjs` takes only the `PATHA_EXCLUDE_EVENT` constant out of `lib/patha-exclude-meter.mjs` and only the read side out of `lib/metrics.mjs`, and `benchmark/rerank-pool-replay.mjs` now imports `recordMetric` deliberately, to name a shard in a throwaway dir. ## path-A exclude meter

- **path-A exclude meter** (`lib/patha-exclude-meter.mjs`, wired into `hook.mjs handleUserPrompt`, **off unless `CLAUDE_MEM_METRICS=1`**; rows land in `<dbDir>/metrics/YYYY-MM-DD.jsonl` under `event: "patha_exclude"`): the ruler for D#216 (re-filed from D#215/D#214/D#213/D#212/D#193). It is the one ruler here that is **not** a replay, and deliberately so. The obvious route — persist the marker at write time and replay it later — buys a corpus that still has to be run against a database that has drifted, which is the shape this file bans on three other faces ("never diff two runs taken at different times"). Instead both arms run **at the read**, one process, one DB state: arm A is the set just delivered, arm B is the same `searchRelevantMemories` call with the path-A ids coerced to numbers. **ORDER AND SIDE EFFECTS ARE THE CONTRACT, and the caller owns both — this is the finding of the v3.90.0 pre-tag review, reproduced with probes.** `searchRelevantMemories` is not a read: it `UPDATE`s `injection_count` on every row it returns, a column feeding `noisePenaltyClause`, `demotePinned`'s `injection_count >= N AND cited_count = 0` predicate, and the `injection_count = 0` GC gate. The first version handed it the live writable handle and ran it AFTER the delivery, so rows nobody saw were credited, the `inject` meter double-counted, and — worst — **the ruler manufactured its own delta**: arm A's own bump pushed a row across the `>= 4` noise gate before arm B scored, reporting `refilled: 1, setChanged: true` on a prompt where the honest answer was zero. CLAUDE.md already carried that rule for `rerank-pool-replay` ("the handle must reject a write"); the new ruler quoted it and broke it. Now: arm B runs FIRST with `{ counterfactual: true }` (skips both the bump and the metric emission), so both arms see one state by ordering rather than isolation, and arm B carries its OWN imperative pick instead of arm A's. `tests/patha-meter-counterfactual.test.mjs` pins the behaviour AND the wiring — including source-position ordering, because the flag with the wrong order leaves the delta defect intact; six mutations, six kills. **`suppressed` is exact, not estimated** — arm A's exclude is inert, so its result IS the unexcluded search, and intersecting it with the coerced marker names precisely the rows a working exclude would drop. **The column that decides D#216 is `refilled`, not `suppressed`**: the ledger's open question is whether a freed slot gets refilled from the pool or is simply lost, and a suppression count alone cannot answer it. `net` is reported beside `setChanged` because a one-for-one replacement is net zero while the delivered SET moved — a net-only reading would call that "no change". **Isolation:** coerced ids are ADDED to `contextExclude` rather than replacing it, so the Key Context half (a different mechanism with its own history) is byte-identical in both arms. **`inert` is per PROMPT and keyed on the right predicate** — a prompt's exclude is inert when an id it COULD have matched arrives as a string, not merely when some string is present. The looser rule shipped in a draft on the premise that only a PreToolUse emission turns the union into strings; **that premise is false and the counterexample is the writer itself** — `scripts/user-prompt-search.js` emits `P<id>` (prompt corpus) and `D<id>` (deferred) on its own legs, and the deferred leg merges `prevIds.map(String)`, stringifying whatever was already in the file with no tool call involved.
