## Findings

### P2-1 c3833d9 reopened, for every non-Bash-output field, the private-span cut that 0791b9d had (utils.mjs:287-293)
`unpairedPrivateMarks` ran inside `scrubTruncate`, and `scrubTruncate` is shared by the Bash **command**
(utils.mjs:343), Edit old/new_string (:341), NotebookEdit (:345) and the **Grep** result (:356). c3833d9 deleted it
from `scrubTruncate` and moved a strict cut into `privateSafeHead`, which only the Bash *output* reaches. None of
these other fields are in the commit body. Every one of them is part of the stored `desc` (hook.mjs:746), and the
outer `scrubSecrets` there cannot help, because stripPrivate leaves an unclosed opener alone.
Repro: `node probes/grep.mjs`:
```
head   Search "pin" → notes.md:3:<private>bank pin 4412 notes.md:9:pin rotated
head   grep -rn "<private>pin 4412" notes/ → no match here, exit 1
r0791  Search "pin" → notes.md:3:
r0791  grep -rn " → no match here, exit 1
v6180  (same as head)
```
Also `node probes/fields.mjs`: on HEAD, Edit, NotebookEdit and Grep each show `<private>FIELDLEAK…`, and a key
longer than 4096 characters shows `-----BEGIN RSA PRIVATE KEY----- FIELDKEYAAAA…`. All of these are `ok` on 0791b9d.
The Grep shape is ordinary use: grep prints the line that holds the opener, and the closer sits on a line that did
not match. This is not a regression against v6.18.0, which shows the same text, but it breaks the contract, and it
undoes a fix that already existed in the unreleased 0791b9d. No test covers these fields, which is why the removal
stayed green.
Fix: give `scrubTruncate` the same strict head (stripPrivate over the whole string, then cut before the first
remaining `<private>` or key BEGIN, gated on the same cheap marker test), so every field gets it. Add one Grep case
and one Edit case.

### P3-1 A remaining closer still exposes the text before it: nested spans, closer-first, a key's body+END only (utils.mjs:310-315)
`privateSafeHead` cuts only at an OPENER. Repro: `node probes/leak.mjs`:
```
nested private      c → [redacted]NESTEDLEAK</private> ok          (input <private>a<private>b</private>NESTEDLEAK</private> ok)
stray closer first  c → CLOSERLEAK</private> then
closer before opener c → x CLOSERLEAK2</private> y
key body+END only   c → MIIEKEYBODYLEAK0123456789abcdef morebody -----END RSA PRIVA…   (e.g. `tail key.pem`)
```
v6.18.0 and 0791b9d leak the same text (pre-existing). The contract names both "nested" and "cut off".
Fix: search `/<\/?private>|-----(BEGIN|END) [A-Z0-9 ]*PRIVATE KEY/i` in the stripped window. If the first hit is a
closer, drop the head entirely; if it is an opener, cut before it as now.

### P3-2 A JWT glued by a hyphen to more than 40 characters of [\w-] still leaks; v6.18.0 caught it (secret-scrub.mjs:196)
Repro: `node probes/fp.mjs`:
```
head  cookie: session-3f2a9c1e-8b4d-4e2f-9a1b-7c6d5e4f3a2b-eyJhbGci….eyJzdWIi….sigSIGsig
v6180 cookie: session-3f2a9c1e-8b4d-4e2f-9a1b-7c6d5e4f3a2b-***
head  path /tmp/aaaa(52 a)-eyJ… (unscrubbed)          v6180 …-***
```
The `session-<uuid>-` prefix is 44 characters. The comment "is a start too, as `\b` allowed" is MISLEADING: `\b`
allowed any length. 21a09fd narrowed this regression from 1b93b69 but did not close it. The makeEntryDesc probe
("JWT glued to >40 hyphen words") shows the whole JWT in the Bash description as well.

### P3-3 Prose that names two key headers still loses the text between them (secret-scrub.mjs:210)
`RSA keys start with -----BEGIN RSA PRIVATE KEY----- and EC keys with -----BEGIN EC PRIVATE KEY----- …` becomes
`RSA keys start with ***PEM_KEY***-----BEGIN EC …` on HEAD and on 0791b9d. v6.18.0 kept the sentence
(probes/fp.mjs). This is the same class as the certificate case 21a09fd fixed (delta P3-2), with a key header as
the second header. It has been present since 1b93b69. One possible tightening: accept an END-less termination only
when the next key BEGIN starts a line (`(?<=\n)`). Prose mentions sit mid-line, and concatenated keys start their
headers on a new line.

### P3-4 (out of diff range, a release-level change from #37) A JWT longer than ~4050 characters shows its signature in the tail
Repro: `leak.mjs` case "long JWT crossing tail window": `…bbbbbbbb.SIGLEAKsigcccc…`, on HEAD and on 0791b9d.
v6.18.0 shows no tail. The tail window starts mid-token, so the JWT pattern never sees `eyJ`. Oversized access
tokens (large group claims) exist in the wild. What leaks is a signature fragment, which is not usable on its own,
but the contract says "never show a secret scrub would catch".

### P3-5 The marker gate is case-sensitive, and the opener cut is case-insensitive (utils.mjs:320, :307)
`str.includes('PRIVATE KEY')` misses `-----begin rsa private key-----\nLOWERKEY`, so the output takes the
head+tail path and shows `-----begin rsa private key----- LOWERKEY`. 0791b9d cut it (PRIVATE_MARK_RE had /gi). This
is not a real PEM label and scrubSecrets does not catch it either, so the impact is low. The problem is that the two
halves of one rule disagree.

### P3-6 (pre-existing since v6.18.0) The head window can split a fixed-length secret, and trim then shows the fragment
`' '.repeat(4080) + 'ghp_' + 'A'*36` gives `c → ghp_AAAAAAAAAAAA…*** done`. The window sees 12 of the 36 characters,
the pattern's length gate fails, and normalizeInline's trim puts the fragment first. All three trees show it
(`leak.mjs`). An `sk-ant-api03-` key at the same edge is caught.

## Other checks (no defect)
- Placements that are clean on HEAD (`leak.mjs`): opener at 4096-5, an opener split by the window edge, a BEGIN split
  by the edge, a closed span crossing the window after a whitespace head, a key with no END crossing the window, a
  key with no END followed by a certificate, an opener inside a key, an unclosed span holding a key, several spans
  with the last unclosed, a private span only in the tail (the head is clean and there is no tail), and mixed-case
  `<PrIvAtE>`. `<private >` is not a tag anywhere in the system (stripPrivate and both gates use the same exact tag),
  so it is consistent by design and not a leak under the system's own definition.
- Cost of the whole-output gate, stripPrivate and the search (`probes/perf.mjs`, 8 MiB, mean of 3, HEAD / 0791b9d):
  plain 4.0/0.4 ms, `<a ` dense 2.9/0.1, marker at end 6.9/0.2, 0.9M openers 46.5/0.5, 0.44M pairs 56.8/0.4,
  closers 39.7/0.6, `PRIVATE KEY` dense 1.6/0.2, BEGIN dense 6.8/0.2, mixed case 9.7/0.2. The cost is linear.
  Hook stdin is capped at 256 KiB (utils.mjs:170 MAX_HOOK_STDIN_BYTES), so the real cost is about 2 ms at most.
- No regression on output without markers: 19,608 random 10-12k-character slices of README/CHANGELOG/source
  without a marker gave 0 differences between HEAD and 0791b9d from `makeEntryDesc('Bash')` (`probes/eqv.mjs`; 392
  slices had a marker and were skipped).
- Linearity (`probes/lin.mjs`, HEAD growth per doubling from 100k to 200k, and time at 1M): 12 shapes gave
  1.60x-2.08x and 10-32 ms at 1M. The shapes: dashes, `a-` runs, 39-character words plus a dash, hyphen words
  before eyJ, dotted JWT chains, a key then fake key labels, a key then long END labels, a key then END with
  `PRIVATE KE` repeated, a key then headers without dashes, alternating headers, certificates then a key. Benign
  text was 11 ms at 1M. v6.18.0 shows the known quadratics (hyphenEyJ 22.7 s at 1M, keyHdrsAlt 1.26 s).
- JWT false positives: the wider lookbehind matches only where a full `eyJ….eyJ….x` follows, so it adds no
  prose false positives.
- PEM simplification (not a defect): the body's `(?!-----BEGIN [A-Z0-9 ]*PRIVATE KEY)` guard is redundant. With a
  lazy body and the `(?=-----BEGIN …PRIVATE KEY)` terminator, the body can never cross a key BEGIN anyway. Dropping
  the guard (mutation M8) passes all 26 tests, and 200,000 random fragment strings gave 0 output differences.
- eslint exits 0 and prettier --check passes on the five touched files. utils, secret-scrub-linear, search-core
  and private-strip tests pass: 365/365.
