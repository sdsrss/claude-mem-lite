## 0. 摘要

**一句话**：插件最实在的作用仍是"显式写、跨会话读"（待办账本、主动存教训）。自动注入一侧量大、命中少，但没有发现误导。本轮最大的新问题不在注入，而在交接：本机汇报格式改成"汇报 / 变更 / 验证 / 遗留"之后，确定性摘要几乎什么都取不到。于是 182 条手打消息里有 52 条（28.6%），是你把上一轮的"遗留"段手动粘回来。

1. **有作用的部分（已证实）**
   - 待办账本持续在用、能闭环。窗口内新建 193 条，完成 78 条，78 条都关联到了完成它的那条记录。
   - 非本项目的 50 个会话里，模型主动写记忆 146 次、读 87 次。
   - 跨会话接续的因果证据仍只有 09-29 的沙箱 A/B（插件组 26/28，对照组 5/12）。真实会话没有对照组，本轮无法复测"效率提升了多少"。
2. **R4 判定（Q1/Q2）：按事先登记的原文，两个杠杆都"采纳"；但补上评审看不到的那部分后，两个都不满足（已证实）**
   - S2(a) 每会话只留前 22 个 pretool 块：去掉组适用 2/30，对照组 4/30，去掉的字节占 48.2%；
   - S2(b) 只给有 lesson、importance ≥ 2 的 bugfix / decision：去掉组适用 2/30，去掉的字节占 44.1%；
   - 但 78 个样本里有 19 个被判为 UNCLEAR，全都是"只给编号、不给正文"的 Read→Edit 提示块。这类块占 pretool 块的 29.5%。补上模型在 Read 那一刻看到的原文后复评，两个去掉组都变成 **3/30**，超过 ≤2/30 的门槛。

     - 它取回"变更"（Done）0 份；

4. **其他已证实的问题**
   - 有记忆写错了项目：模型在同一条命令里先 `cd` 进 Claude Code 自带的记忆目录，再运行 `cli.mjs save`。daagu 的 4 条 bugfix 教训和 1 条待办因此落在 `-home-ai-dev-daagu--memory` 下，daagu 按项目过滤的自动注入（pretool、SessionStart 待办）不会选到它们。

### 5.4 补充分析：UNCLEAR 全是评审看不到正文的提示块（事后加做，已证实）

- 19 个 UNCLEAR 的理由一模一样：块里只有 `[mem] ⚠ Lessons #X were shown when you Read <文件> — apply each lesson…`，没有教训正文。模型在先前 Read 时见过正文，评审没见过。

- **做法**：
  - 从同一会话里，找到这些编号在先前 Read 块中的原文（19/19 都找到，逐字取自 transcript），附到样本上；
  - 交给第三个不知道假设的子代理，标签和规则不变，只说明 `earlierShownLessonText` 是模型当时看到的。
- **结果**：19 个中 APPLICABLE 2、TOPICAL 16、IRRELEVANT 1。

| 组 | 原读数 | 补上原文后 |
|---|---|---|
| A | 2/30 | **3/30** = 10.0% [3.5, 25.6] |
| B | 2/30 | **3/30** = 10.0% [3.5, 25.6] |
| C | 4/30 | 4/30（C 组的 5 个 UNCLEAR 补评后无一适用） |

- 两个新增的适用块：
  - S57（B 组）：`#1615`"改 `INDEX_VERSION` 会让所有用户重建索引"，随后代理正好碰到索引版本守卫，选择不再升版本；
  - S77（A 组）：一条"文案扫描测试只限产品自己写的文字"的教训，正是下一步编辑要守的边界。
- **读法**：
  - 原判定的"通过"，A、B 都刚好卡在门槛上（2 = 2）。它靠的是评审看不到近三成的块。
  - 补上正文后，两个杠杆都不满足条件 1，但仍满足条件 2（3 ≤ 4）。
  - 这次补评是**看过数据之后加做的**，不能替代事先登记的规则，所以两种读数并列报告，由你决定采用哪一个（§11）。

### 5.5 规则挡不住的东西：去掉的部分值不值

- **功效**（照抄事先登记）：真实适用率为 10% 时，30 个样本里出现 ≤ 2 个的概率约 41%。3/30 与 4/30 的区间几乎完全重叠，**这批数据分不出去掉组和对照组谁更切题**。
- **代价**（估算）：
  - 按补评后的 3/30 外推，S2(a) 去掉约 86 个适用块（856 × 0.1），每个会话约 1.6 个；S2(b) 约 80 个，每个会话约 1.5 个。区间很宽（A 组 Wilson 下限 3.5% 对应约 30 个，上限 25.6% 对应约 219 个）。
- **收益**（估算）：
  - 两个杠杆各省约 3.1–3.4 KB/会话的注入。
  - 插件全部注入约占输入 token 的 0.64%–0.85%（§7.1），pretool 的这一半约为其中的 22%。所以省下的约是全部输入 token 的 0.1%–0.2%；A 去掉的是会话后段的块，被重读的次数更少，实际还要低一些。
- **误导**：三组合计 MISLEADING 0/97 次判定（78 个样本加 19 个补评）。没有证据表明这些不适用的块造成了错误操作。

## 8. 本轮新发现的问题

### 8.1 确定性摘要读不到现行汇报格式（P1，已证实）

- **现象**：`lib/summary-extractor.mjs` 的标题识别是：
  - 英文 `Done | Not done | Failed | Uncertain`；
  - 中文 `剩下 / 剩余 / 还剩 / 未完成 / 下次 / 待做 / 未做`。
  - 它不认"汇报 / 变更 / 验证 / 遗留"，也不认英文的 "Changes / Verification / Open items"。
- **复现**：把冻结语料里每一份带 `## 汇报` / `## Report` 标题的助手消息（162 份）喂给发布的 `extractStructuredSummary`（`tasks/r4/scripts/extract-probe.mjs`）：
  - `done` 非空 **0/162**；
  - 含"遗留"段的 158 份中，`notDone` 非空 **17/158**。这 17 份都是命中了正文里的中文标题词（剩下的 11、还剩 2、剩余 1、下次 3），取到的是那一行，不是"遗留"段本身。
- **格式何时变的**：活目录里还在的 transcript（最早 10-24）中，每天带"汇报"标题的消息都有十几到几十条，带 Done / Not done 标题的全期只有 5 条。也就是说，至少一个月里，确定性的那条摘要路径在本机等于没在工作。
- **后果链**：
  1. 提取器取不到 → `remaining_items` 只能来自模型摘要（`hook-llm.mjs`）；
  2. 模型摘要的质量参差，例如"Only the single observation is recorded, so the full scope of the leftover work is not visible"；
  3. SessionStart 再把它截到 120 字符；
  4. 你在 28.6% 的手打消息里手动粘回"遗留"段（§6.3）。
- **相关的在途工作**：D24、D25 的读数写着"`completed` 来源为模型 28–29 个、报告 1–2 个"，与这里一致。D27（D#850，12-09 冻结）的 D 臂用的是"每一轮报告的 Done"。在提取器认不出"变更"的情况下，这一臂对每个"汇报"格式的轮次都会退化成"回复开头 ≤120 字符"。**D27 的前提受这条影响**，需要先决定先后顺序（§11 Q2）。
- **适用人群**：这条只对使用这份汇报规范的用户成立（本机，以及使用 claudemd 规范的用户）。按记忆 `feedback-premise-from-own-convention`，不能据此推断其他用户。不过只是加认几个标题，对其他用户没有影响。

### 8.2 CLI 写入落错项目：项目 id 来自记忆目录（P2，已证实）

- **现象**：副本里 `-home-ai-dev-daagu--memory` 名下有 4 条 bugfix（3 条在窗口内，1 条在今天）和 1 条待办。它们都属于 daagu，但 daagu 的 pretool 召回、SessionStart 待办列表都按项目过滤，不会选到它们。
- **机制**（从 transcript 逐条核对了写入命令）：
  1. 模型在一条 Bash 命令里先 `cd ~/.claude/projects/-home-ai-dev-daagu/memory`，用 python 改 `MEMORY.md`；
  2. 同一条命令接着运行 `cli.mjs save "…"`；
  3. `project-utils.mjs` 的 `inferProject()` 取 `CLAUDE_PROJECT_DIR || PWD || cwd`，CLI 子进程里 `PWD` 是记忆目录，于是得到 `-home-ai-dev-daagu--memory`。
- 这正是 §6.2 的"重复写"场景（同一条命令写两套记忆）带出来的。R3 §7.4 的 `worktrees--agent-*` 等 7 个非项目 id 仍在。

### 8.3 待办缺一个"修改"操作，查用法的往返没降下来（P3，已证实）

- CLI 的 `defer` 只有 `add` / `list` / `drop`，加上 `save --closes-deferred`；MCP 只有 `mem_defer` / `mem_defer_list` / `mem_defer_drop`。没有改标题、改说明、改优先级的办法。
- 后果：
  - 窗口内 41 次 drop 是"先删后建"。日程项从 D#849 起被重建了 5 次（D#849 → 858 → 874 → 876 → 882 → 888），记忆 `project-dated-work-calendar` 也写着"drop 再 re-add"；
  - 查用法时，模型的 grep 目标里有 `defer (update`、`edit)`。
- O6 未达标的原因：help 调用 grep 的目标按次数为：
  - `defer` 22、`save` 11、`close` 11、`^  defer` 10、`closes` 5、`supersede` 2、`--reason` 1……
  - 也就是在找"怎么用 CLI 关闭待办、怎么 drop、怎么改、怎么 supersede"。而 O6 写进常驻说明的是 `defer add` 和 `save --files`。

### 8.4 `change` 类仍占一半（P3，已证实，延续 R3 §7.2）

- 活跃 1,453 条中，change 728（50.1%）。它们被注入过 86 条、被引用过 2 条；bugfix 502 条，被注入过 267 条、被引用过 69 条。
- 窗口内新写的 341 条中，change 201 条（58.9%）。
- R3 的 S3（不注入 change 类）已因盲评撤回。本轮 B 组（S2(b) 去掉的块）补评后的 3 个适用块，注入的**全是** change 类（`#1480`、`#1500`、`#1615`）。所以仍**不建议**按类型一刀切。
