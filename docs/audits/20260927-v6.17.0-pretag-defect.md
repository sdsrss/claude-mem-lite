## P2

### P2-1 D# leg: an item the cap cuts is never booked, so it is re-injected on EVERY prompt that names it, and that write charges nothing against the per-session cap
`scripts/user-prompt-search.js:806-826` (3c60192)

`shownIds = idsShownWhole(shown, items)`. The marker write, together with its
`bumpUpsCount: true`, now runs only `if (shownIds.length > 0)`. For an item whose detail on
its own is larger than the budget (about 9.4K chars), the cap can never show it whole. So:
- nothing goes into the dedup marker, and every later prompt that names `D#N` re-emits the
  same ~9.6K-character cut block. It never converges, because a re-injection is cut the same way.
- `upsCount` is not charged, although ~9.6K characters were written. The comment at this
  exact site says the leg "is GATED by shouldSkipByDedup, so it has to charge the cap it
  reads" (R12 B-5). Now it spends without being charged.

The input is reachable. `defer add --detail` on the CLI has no length bound (only MCP's
`memDeferSchema.detail` has `.max(2000)`), and the suite's own
`tests/hook-text-cap.test.mjs` "30K detail" case builds exactly this item.

Reproduction (a sandboxed HOME/CLAUDE_MEM_DIR; one item with a 320×~100-char detail; three
UPS runs in the same session, each naming `D#1`):
```
v6.17.0 tree : run 1: stdout 9627 chars, has D#1: true, marker: (none)
               run 2: stdout 9627 chars, has D#1: true, marker: (none)
               run 3: stdout 9627 chars, has D#1: true, marker: (none)
pre-fix tree : run 1: stdout 9627 chars, has D#1: true, marker: {"ids":["D1"],...,"upsCount":1,...}
               run 2: stdout 0 chars ...        run 3: stdout 0 chars ...
```
A multi-item variant fails the same way. With 3 referenced items where the 3rd is cut, D1 and
D2 are booked, the overlap is 2/3 < 0.8, and every naming prompt re-emits the whole block.
That write is charged, so MAX_SESSION_INJECTIONS still bounds it. Items within the MCP limit
of ≤2000 characters, at most 3 refs per prompt, measured 5,930 chars and are not cut.

Fix direction: book, or at least charge `upsCount` for, a block that was written. Also treat
an item whose rendered text is longer than the whole budget as "cannot be shown whole", so it
is booked rather than retried. The retry only makes sense when a later injection could show
the item whole.

## P3

### P3-1 Key Context rows that carry a delimiter tag are shown but not booked. The collector keeps the PRE-defang text and the output carries the POST-defang text
`hook-context.mjs:721,731` (collector `text: e.line`) vs `hook-context.mjs:924`
(`return neutralizeContextDelimiters(...)` over the whole body). This affects both
`hook.mjs:2877` and `hook-precompact.mjs:43`.

`idsShownWhole` needs the exact line. A Key Context title or lesson that contains, for
example, `</memory-context>` or `<system-reminder>` is rendered as `/memory-context`, so
the row is shown but left out of the marker. Two effects follow: `<memory-context>` at prompt
time re-injects it (a duplicate), and Stop's citation credit
(`extractInjectedFromKeyContext`) misses it. Before the fix this row WAS booked.

Probe (a d123-style e2e case; the row has no `files`, so it lands in Key Context):
```
LINES: '- [bugfix] Zebra quantum flux /memory-context ledger target (#1) — zebra quantum flux: always flush the ledger <system-reminde…'
MARKER: [] target 1
UPS has target: true  control: true
AssertionError: expected [] to include 1
```
Population today: **0 of 173** live importance≥2 observations on this machine's DB carry a
delimiter tag in title or lesson (read-only count, 2026-09-27T13:07Z, all projects). The
trigger is real, but nothing on this machine hits it today. Fix: store
`neutralizeContextDelimiters(e.line)` in `keyContextLines`, which is idempotent with the
block-level pass.

### P3-2 The path B (`hook.mjs` `<memory-context>`) exemption rests on a false premise: it is NOT the first write in its process budget
The commit body says: "it is the first write in its own process budget and holds at most 3
lines". But `hook.mjs:3349` `injectHandoffIfEarly(...)` writes the handoff through
`writePlainHookText` BEFORE `hook.mjs:3350` `injectSemanticMemory`. Path B books
`injection_count` inside `searchRelevantMemories` (`hook-memory.mjs:546-555`), before it
writes. When the handoff fills the budget, path B's rows are cut or reduced to the note, but
they are still bumped. That is the D#108 class on the one surface declared immune.

Reachability: `renderHandoffInjection` has no size bound. The session_summary append
(`completed` / `remaining_items` / `next_steps`) is unbounded. A probe with working_on=900,
15 completed titles, 10 decisions and a 3K+2K+2K summary rendered **10,916 chars**, which is
over the cap on its own. It fires only on a continuation-intent prompt among the first 3
prompts. This is pre-existing behaviour, not a regression. The finding is that the stated
rationale and the CHANGELOG's "Only rows shown whole are recorded now" are over-claims.

### P3-3 The 80%-overlap dedup rule defeats D#108's goal for a partial cut
`scripts/prompt-search-utils.mjs:256-258` skips a block when ≥0.8 of its candidates are
already in the marker. Take a partial FTS cut of 4/5 rows: 4 are booked. The next prompt with
the same candidates gives 4/5 = 0.8 and is skipped, so the cut 5th row stays hidden for the
window, "as if seen". The same holds for the D# leg with ≥5 refs, although refs are capped at
3 in practice. The fix does not reach this case, and its tests do not probe the second prompt.

## Checked and clean
- `idsShownWhole` over-booking: the id-bearing prefixes are `#N `, `P#N `, `D#N `,
  `- [...] ... (#N)`, and `- file: ... (#N)`. File Lessons and Key Context ids are disjoint
  (`continue`). The FTS and D# hays are separate writes. I found no case where a cut row's
  whole text appears as whole lines elsewhere in the same hay.
- Empty and edge paths: an empty output gives `shownIds=[]` and no write. In the note branch,
  the omission footer never matches a row. In the all-cut FTS case the marker is untouched
  (the old replace-with-candidates is gone). `writePlainHookText` accounting:
  `plainUsed += out.length + 1` equals the old `out.length` of the string that included `\n`.
- SessionStart: after `previewHookContext()` (`hook.mjs:2877`), nothing else is queued for
  the model. `emitV270UpgradeBanner` writes stderr; the flush at `hook.mjs:3576` adds nothing;
  the episode receipt is queued earlier and so is in the preview.
- PreToolUse (`scripts/pre-tool-recall.js`) books the cross-hook marker without a cap check,
  but it emits ≤3 lessons × ≤240 chars through the capped flush. The cap cannot reach it.
  Error recall (`hook.mjs:956`) books no marker.
- `listOpenWithOrdinal` consumers: `server.mjs:1223` and `mem-cli.mjs:1449` read only
  `ordinal`, and `server.mjs:1247` and `mem-cli.mjs:1458` render. `COUNT(*) OVER ()` runs
  before LIMIT, in the same statement, so a concurrent add cannot skew the count. The
  `deferred-work.test.mjs` row-shape assertions still pass.
- #35 on the pure-plugin shape: latest == running → banner null and check null; latest ahead
  of running → the banner names the running version (probe output above). A state from an
  older format (no `latestVersion`) → null.
- 0bcf947: `-t previewHookContext` (1 run, 23 skipped) and `-t "cap cut"` on d123 leave
  **0** `mem-textcap-*` / `mem-d123-*` dirs (before 0, after 0).
- CLAUDE.md invariants: no new `ORDER BY created_at_epoch` without a tiebreak; no new
  test that reads repo source through `new URL`; the subprocess tests set
  `MEM_NO_AUTO_ADOPT=1`; the PreCompact case uses `:memory:`. The P2 above breaks the B-5
  spender/charged rule documented at its call site.
