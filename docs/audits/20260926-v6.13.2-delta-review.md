## FALSE claims

### FALSE-1: "Ctrl-C" clears the stamp (commit msg; scripts/green-stamp-reporter.mjs:69-71)
Claim: "a run that ends 'interrupted' (--bail, Ctrl-C) clears the stamp like a failed one".
vitest 5.0.0 produces 'interrupted' only via cancelCurrentRun: --bail, or the keypress handler, which is
registered only when `stdin.isTTY && config.watch` (node_modules/vitest/dist/chunks/cli-api.LUtK11-x.js:354).
Under `vitest run` (which is what `npm test` is, package.json:30) a SIGINT goes to the logger's onExit
(dist/chunks/index.B89dZ0-N.js:14091-14099), which calls process.exit() and never reaches onTestRunEnd.
Reproduced: fixture with the shipped reporter + globalSetup, green run → stamp written; then
`GS_FAIL=1 GS_SLOW=8000 vitest run`, a.test fails at once (log shows "× env"), SIGINT at 4 s → exit 130,
stamp PRESENT, and `checkStamp()` → `{"reuse":true,"reason":"full suite passed on this exact tree ..."}`.
So a red run cut short with Ctrl-C still leaves the older green reusable by pre-commit. The --bail part is TRUE
(mutant M1 below is killed by the --bail case, so that case really reaches 'interrupted').
Gap is pre-existing; the claim that it is closed is new. Fix direction: clear at run START (onInit /
onTestRunStart) and let the passing end re-record, or write an "in progress" marker checkStamp refuses.
(This conflicts with "a partial run that loads the reporter keeps the stamp"; one of the two has to give.)

### FALSE-2 (reasoning; the population number is TRUE): "The dropped character was always a literal, so no verdict changed"
Population check TRUE: reverting only the two escaped-copy fixes (strip + split, the exact old
`x += cmd[k++]; x += ch`) changes 0 of 15,730 Bash results in this project's transcripts (main + subagent,
read 2026-09-26 ~07:10Z), both for the read-only verdict and for isHardError.
Reasoning FALSE: a dropped literal can be whitespace, and whitespace is what classifySimpleCommand
tokenises on. Old vs new:
  `x="a\ b" grep TypeError f`       old READ → new RUN

bash runs grep here, so the new verdict is the wrong one (the conservative direction). It is the same
defect the parser already has for `x="a b" grep` (tokens are split inside quotes), which the old drop
happened to mask. The sentence should say "no verdict changed on the replay population", not "always".

## P3 defects

### P3-1: new O(n²) in stripNonCommands' arithmetic copy (bash-utils.mjs:222-231) — the one super-linear path left
Every unquoted `((` / `$((` calls closingParen, which scans to end of input when it never closes; the loop
then advances one character and tries again. Timings (node 22, this machine), `'grep x ' + '(('.repeat(n/2)`:
  5 KB 44 ms · 10 KB 129 ms · 20 KB 462 ms · 40 KB 2,458 ms · 80 KB 9,819 ms (parent a04f292: 5 ms at 100 KB).
100 KB of unclosed `$((` → 7.3 s; `(( a ` repeated → 3.7 s. detectBashSignificance runs synchronously in
hook.mjs:677 under a 5 s PostToolUse timeout (hooks/hooks.json:62), so from ~55 KB the hook is killed and
the event is dropped. Needs unquoted, unclosed parens in the agent's own command, so adversarial-only.
Fix: after the first -1, stop trying arithmetic for the rest of the string.
Other 100 KB shapes are linear: nested `$(` ×25k closed 19 ms (the parent threw RangeError after 827 ms),
nested `$((` 15 ms, sibling substitutions 13 ms, 25k heredoc markers 20 ms, 10k-line unquoted heredoc 10 ms,
`$'…'` 5 ms. The depth cap works as stated: `depth > 32` means 33 levels, past that 'other'.

### P3-2: an unquoted heredoc body line ending in `\` breaks the `: "<line>"` wrapper (bash-utils.mjs:261)
The escaping doubles a backslash only when a `"` follows it, so `foo \` becomes `: "foo \"`, which escapes
the closing quote. Two effects:
 (a) regression, read → RUN: `cat <<EOF | grep x\nfoo \\\nbar\nEOF` is READ at a04f292 and RUN at 1d6ccaa
     (the line no longer parses, so it is 'other'). Continuation lines are common when an agent writes a
     shell script through `cat > x.sh <<EOF`, though output is usually empty then.
 (b) contrived hide: a brute force over 10,277 five-line bodies found 1 body with a live `$(npm test)` that is
     still READ: lines `a\`, `it's`, `$(npm test)`, `it's`, `a\`. bash runs the substitution (checked with
     `$(echo SUBST-RAN >&2)`: printed). The parent was READ as well, so this is not a regression.
Fix: escape a trailing backslash too (`/\\$/`), or join backslash-newline the way bash does in an
unquoted body. Replay impact on the corpus: 0 results (parent→1d6ccaa newly firing = 0).

### P3-3: `$((cmd) …)` is taken as arithmetic, but bash runs it as a command substitution (bash-utils.mjs:322-328)
bash tries arithmetic first and re-parses as `$( (cmd) … )` when that fails:
`bash -c 'echo "[$((echo SUBSHELL-RAN >&2) | cat)]"'` prints SUBSHELL-RAN. takeSub marks it arithmetic,
the body `(npm test) | head` contains no `$(` or backtick, so nothing is judged:
`grep x $((npm test) | head) f` → READ (the parent too; not a regression). The commit's
"a substitution inside arithmetic is judged" does not cover this. Fix: if an arithmetic body parses as a
command list whose first element starts with `(`, judge it.

### P3-4: the "nested parens" test cannot say NO (tests/bash-utils-signif.test.mjs:295)
Mutant M33 deletes `else if (ch === '(') depth++;` from closingParen and the whole file stays green. Both
cases in that test miss it: the first expects RUN, and an early close makes the body unparseable, so it
is 'other' = RUN anyway; the second's parens are inside double quotes. A READ-expected case kills it:
`grep x $(echo $((1+2))) f` → new READ, M33 RUN. The commit lists "nested parens" among the six surviving
mutants now covered; for the depth counter itself, that is not so.
