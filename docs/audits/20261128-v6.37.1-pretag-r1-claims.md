# v6.37.1 pre-tag review — claims lens (candidate 9b16f159, HEAD verified)

Severity: P1 = false in the CHANGELOG; P2 = the evidence a CHANGELOG claim rests on is false; P3 = over-broad or edge. No P0/P1.

## Findings

**F1 · P2 · the test named as the guard does not exist.** Commit 80729ce2 body, line 28: "The re-import case fails when the stripped-text keys are removed." This is false at 9b16f159. I removed `lib/import-jsonl.mjs:427` (seenPrompts stripped key) and `:457` (countStored stripped key) in a copy. Result: `tests/import-jsonl.test.mjs` 33/33 pass, and all 24 test files that mention import-jsonl pass 1205/1205. The keys still matter in practice. With them removed, re-importing a transcript that v6.37.0 imported adds a copy of a short block-bearing prompt with no timestamp (8 → 9 rows). After a v6.12.1 import, a re-import adds 4 rows instead of 2. So the CHANGELOG re-import sentence (CHANGELOG.md:19-20) holds for the shipped code, but no test guards the stripped-key half of it. The timestamped "row stored with the block" test passes through `legacyKey` (:238) instead. Missing case: a short line with no timestamp over a legacy block row.

**F2 · P3.** CHANGELOG.md:14-15: "at about 4 KB it filled the prompt-time search query by itself, so none of the typed words were searched". The same claim appears in 80729ce2 line 15, `lib/host-blocks.mjs:9-10` and `scripts/user-prompt-search.js:782-783`. It is true of the FTS query: `nlp.mjs:385` cuts the raw text at 2000 characters. But at v6.37.0 the D#N lookup, the file-path recall and the error-signature search read the whole prompt. I ran v6.37.0 `user-prompt-search.js` with a 4150-character block in front of the typed text:
- "D#1 approved…" injected "D#1 🟡 [P2] Platypus migration follow-up".
- "please look at src/kangaroo/cache.ts…" returned only "#3 Kangaroo cache invalidation reworked". The block cannot match that row, and a fallback would have listed all three rows.
- "fix the ledger export…" did not find #1; the first run returned only a block-word match (#2). This confirms the main point.

Suggested wording: "…so the typed words never reached the full-text search."

**F3 · P3.** CHANGELOG.md:17-18: "an unclosed `<private>` inside the block no longer redacts the typed text after the block." This holds only for 1–16 unclosed openers (`MAX_PRIVATE_RESCANS = 16`, host-blocks.mjs:54). From 17 on, the typed text is redacted. I ran `hook.mjs user-prompt` end to end in a sandbox: with 16 openers the stored text was "typed words sixteen"; with 17 it was "[redacted]". The candidate's own test pins this (tests/host-blocks.test.mjs:117-121). It is harmless in practice; only the wording overclaims.

**F4 · P3 (defects lens should weigh it).** `lib/host-blocks.mjs:19-23` says the start-only rule "is a safety property", because a typed pair "would otherwise disarm" fail-closed redaction. 80729ce2 line 44 adds that a mid-prompt pair "cannot disarm a <private> region". Both are true mid-prompt only. A pair the user types at the start still disarms it, with or without a host block. Example input: `<browser_instruction><private></browser_instruction> my password is hunter2`. Through stripPrivate, v6.37.0 stores `<browser_instruction>[redacted]`; the candidate's stripPromptBlocks gives `my password is hunter2`. This also makes two unchanged texts over-broad for the prompt path: `lib/private-strip.mjs:17` ("an opener with no close redacts to the END") and README.md:493 / README.zh-CN.md:355 (the 6.21.0 upgrade notes). The input is contrived.

**F5 · P3.** CHANGELOG.md:19-20: "Re-importing a transcript that an earlier version already imported adds no second copy". It holds for v6.37.0 stores. Two transcripts (14 lines covering timestamped and untimestamped, short and long, an unclosed `<private>` in the block, private regions, a plain twin and a block-only prompt) added 0 rows over two re-imports. It fails for stores written by v6.12.1 and earlier. Those versions capped then scrubbed, `scrubSecrets(text.slice(0, 10000))`, until 21068af7 (first shipped in v6.12.2). A long block prompt with a `<private>` region gains a copy (8 → 10 rows). This is not a regression: v6.37.0 re-importing the same store adds 3, and a block-less transcript also gains copies (2 → 4). The tests model legacy rows as today's `scrubSecrets(joined).slice(0, 10000)`, which is the v6.12.2+ shape. Suggested wording: "a transcript 6.37.0 imported".

**F6 · P3, unverified premise.** CHANGELOG.md:10-11 and host-blocks.mjs:3-7 (VS Code, 4 KB, "its own text part, the first one") rest on PR #62 alone. No user message in 580 transcripts (depth ≤4) contains the tag. The 3 files that mention it are this release's own sessions, in tool output. All 146,074 entrypoint markers in the depth-2 transcripts are "cli". "The first one" is not in the PR; the PR says only "its own text part". The importer depends on it: a block behind another part is not at the start and stays.

**Note (not falsified).** CHANGELOG.md:23-24 ("cd'd into another repository") rests on PR #61's single observation.
