### Findings (most severe first)

**F1. P1 by the rubric (real text lost beyond what the CHANGELOG states). Regression. A public key, cache key, partition key or idempotency key at a line start inside a JSON string is erased.**
- Where: secret-scrub.mjs:407 (the D#690 pattern) and its exclusion `(?<!(?:^|[^A-Za-z0-9])(?:public|…|host))`.
- Mechanism: in escaped text a line start is `\n`, `\t` or `\r`. So the name reads `nPUBLIC_KEY`, the letter before `PUBLIC` defeats the word anchor, and the exclusion does not apply. The decoded reading keeps the value, but the final whole-text pass erases it. When another label in the same string was erased, the literal is rewritten, and the token masking at :1665-1670 removes the whole `NAME=VALUE` token, name included (output `token: ***\n***\n`).
- Repro at scrubSecrets level: `node probes/pubkey2.mjs`. For `{"content":"NODE_ENV=production\nPUBLIC_KEY=<b64>\n"}`, base keeps the value and cand erases it. The same holds for CACHE_KEY, PARTITION_KEY, IDEMPOTENCY_KEY and a tab-indented line. These keep their value on both trees: VAPID_PUBLIC_KEY, VITE_SUPABASE_ANON_KEY, `  cache_key:`, ssh_host_key, and raw text.
- Repro end to end through import-jsonl (it scrubs the joined JSON text, lib/import-jsonl.mjs:150): `cp probes/zz-review-probe.test.mjs cand/tests/ && ./vt.sh cand tests/zz-review-probe.test.mjs`. The input is a Write of `/w/.env` holding `NODE_ENV=production\nPUBLIC_KEY=<b64>\nCACHE_KEY=<hex64>\n`. Cand prints `PUB: false HEX: false` (1 failed). The base tree with the same test prints `PUB: true HEX: true` (1 passed).
- Repro on the hook path: `node probes/hookpath.mjs`. makeEntryDesc of `cat config.json`, whose JSON holds that .env: base keeps the public key, cand drops it.
- This contradicts CHANGELOG.md:31-35 ("under `CACHE_KEY`, `PARTITION_KEY`, … `PUBLIC_KEY` … it is kept") and the comment at secret-scrub.mjs:398-400.
- The shape is real (an .env or config line other than the first, inside any JSON string). Frequency: the D#690 pattern changes 0 of 136,643 real texts from other projects (probes/claim-p44.mjs), and none of the real-corpus losses were these names. The impact is losing public or non-secret values when the shape occurs.

**F2. P2. Regression. scrubSecrets throws `RangeError: Maximum call stack size exceeded` on one long double-quoted literal.**
- Where: secret-scrub.mjs:1632 and :1658. The body `(?:[^"\\\r\n]|\\[^\r\n])*` of ESCAPED_LITERAL_RE overflows irregexp's backtrack stack. `node probes/stacksite.mjs` shows the regex alone throws.
- Repro: `node probes/stackbisect.mjs` (same thresholds on `$N22`). It throws from a one-line literal of:
  - 8,500,871 chars holding one escape (8,375,873 is fine)
  - 11.25M chars of repeated `ab\n`
  - 12.22M chars of a JSON-encoded file content
  - 9.95M chars of minified JSON in a string
- v6.30.13 returns on all of these (83 ms at 12M chars, `node probes/robust.mjs`).
- Reach: import-jsonl scrubs whole tool parts before its 4000-char cut, inside one `db.transaction` with no per-pair catch (lib/import-jsonl.mjs:474-534). One such string therefore aborts the import of the whole file. The PostToolUse description scrubs 4-8 KB windows, so it cannot reach the threshold. The prompt sits under the 8 MB payload cap, just below the lowest threshold.
- Not seen in real input here: the longest string in 704,715 transcript lines is 311,104 chars (`node probes/maxlen.mjs`). The shape class is real; the size is constructed.

**F6. P3. Regression, constructed. Leak-direction regressions appear only when a literal boundary falls inside a private key.**
- Repro: differential fuzz `node probes/fuzz.mjs <seed> <n> <out>`, about 211,000 cases over 26 seeds. Every regression is a key-body window, for example `node probes/classify-reg.mjs out/f1.json out/f2.json out/f3.json` gives `{ 'pem-body': 550 }`. Inspect cases with `probes/inspect.mjs` and `probes/context.mjs`.
- The regressions need one of these inputs:
  - a stray `"`, `'` or `\\"` inserted inside a key held in nested JSON
  - JSON whose ASCII letters are written as `\u00XX` (seeds 11-14: 35 regressions in 24,000 cases)
  - text cut at an arbitrary start point (seeds 61-64: 14 in 24,000)
  - two keys in one text, with one of them 4-5 levels deep in a one-string-per-line shape (out/f7.json case 0, out/f54.json case 16: the only 2 regressions in about 100,000 default cases without insertions)
- Mechanism: the rewrite erases one end of a key inside a literal, so the whole-text key passes no longer pair the BEGIN and END around it.
- Zero regressions in:
  - 24,000 PHP `\/` cases and 12,000 Python ensure_ascii / Go-escaped cases
  - key shapes at depths 0-6, whole and cut: JS concatenation, Python implicit concatenation, arrays, notebook, util.inspect, C (probes/keylines.mjs, probes/keydeep.mjs, probes/keycut.mjs)
  - cut key tails in JSON strings (probes/keytail.mjs)
  - six stray-quote placements in a single-level JSON string (probes/strayquote.mjs)
  - the real-transcript differential (0 tokens, 0 twelve-character windows)
- Reach: the hook path and import-jsonl both cut before the first BEGIN or END. Only whole-text callers, such as the prompt, could reach these shapes.

**F7. P3. Valid JSON in, invalid JSON out: an existing defect now reached in more places.**
- The values of pattern 30 (DSN) and pattern 24 (Authorization) eat the `\` of a following `\"`. v6.30.13 does the same at depth 2 and deeper (`node probes/dsn.mjs`: `dsnDepth2` is invalid on both trees).
- New: PHP json_encode output (`postgres:\/\/…`). v6.30.13 stored that password; the candidate erases it but leaves invalid JSON. This happened in 55-70 of 6,000 PHP-wrapped fuzz cases (`node probes/jsonreg-classify.mjs out/fp21.json …`: dsn 33, Authorization 1).
- Real corpus: 0 JSON-validity regressions.

**F8. P3. A rewritten literal re-encodes its whole body.**
- Repro: `node probes/bytes.mjs`. Once a literal is rewritten, `\x1b` becomes `\\x1b` and `\$` becomes `\\$`. An escape JSON does not know is decoded as written and then has its backslash escaped, so it now reads as a literal backslash. Also `\/` becomes `/`, `\u00e9` becomes `é`, and `\u003c` becomes `<`.
- Literals with nothing erased keep every byte (confirmed, row `untouchedSameText`).

**F9. P3. Text that the decoded reading now drops inside JSON strings (existing text-reading false positives, now reached).**
- Real corpus from other projects, JSON population: 47 texts lose 54 tokens compared with base (`node probes/corpus.mjs out/x.json other`). Examples:
  - `"session_id":"<id>"` and `"token":"<value>"` in escaped JSON inside Bash commands (test fixtures)
  - `grep -E "^DEEPSEEK_API_KEY=" backend/.env` loses `backend/.env | …`, because pattern 9 takes the text up to the next quote
  - `"SecretString"` values erased whole
  - the `***PEM_KEY***` marker replaced by `***`
- This repo's own transcripts: 105 texts lose 418 tokens, including markdown prose after `` `PRIVATE_KEY="-----BEGIN…` `` erased across lines up to the next quote.
- The CHANGELOG's "decoded and scrubbed as text" covers the mechanism but names none of these.

### Claims to falsify
- **"rewritten only when the scrub changed it" / "a string with nothing to erase comes out byte for byte" (c049a78d):** holds for literals the scrub leaves alone. What counts as "nothing to erase" is decided by the text reading, which erases F9's text.
- **"every token that the patterns erase in the escaped body is also erased in the rewritten literal" (c049a78d):** false. `node probes/claim-tokens.mjs`: for `password=abc12345\npath\/to\/<S>` and `…\nkey\u002d<S>`, the escaped body's reading erases `<S>` but the rewritten literal keeps it, because re-encoding joins it into a token the body does not have. The final whole-text pass erased it in both cases.
- **"The name is read as the env-variable patterns above read `NAME=VALUE`, with their nouns" (ebe041ce):** false for PGPASS, SUPABASE_KEY and SUPABASE_SERVICE_ROLE_KEY (F4).
- **"A key the name says is an identifier or public (…) holds a hash, an id or a public key, and stays" (ebe041ce):** false at an escaped line start (F1).
- **"on 198,303 real texts 796 and 3,667 ms on Node 22, against 121 (Node 26: 760, 123, 114)" (ebe041ce):** reproduced in shape on 136,643 texts (`node probes/claim-p44.mjs`, and with `$N22`).

  | Form | Node 22 ms | Node 26 ms |
  |---|---|---|
  | shipped | 125-130 | 130-135 |
  | name-first | 883 | 880 |
  | leading lookbehind | 4,052 | 137 |

- **"The quote is matched before that count is checked: Node 22 runs a leading lookbehind at every position" (2bd0ac3d):** confirmed (`probes/claim-2bd0.mjs`). The old regex takes 5,166 ms on a 200,000-backslash run on Node 22 and 0 ms on Node 26. The shipped regex takes 0 ms on both. Both give the same matches on 20,000 random strings.
- **"A text the first round leaves as it is is a fixed point already, and is not scrubbed again" (a8b48eee):** true. scrubText is deterministic, and removing the early return survives all 863 scrub tests (an equivalent mutant).
- **"Started at the name, it tried every word of the text, and with the name check before the key segment Node 22 ran that check at every position" (ebe041ce):** consistent with the table above. The name-first form costs 6.8x the shipped form on both Nodes; the lookbehind-first form costs 31x on Node 22 only.
- **CHANGELOG "keeps nothing in them that 6.30.13 erased":** holds on my real populations (see Verification).
