## P1 and P2 findings

### F1 — P1 — repair-db drops rows SQLite can read through the log, and says SQLite could not read them

Where:
- lib/db-repair.mjs:176-198 (openOld) with :156-168 (storeTables).
- The main-alone fallback at :643-657. The warning at :778-782.

Claims it falsifies:
- Notice and doctor note, lib/db-unusable.mjs:220: "repair-db copies every row SQLite can still read into a fresh file". It
  is printed under every `✗ Database:` line (D4) and in the SessionStart notice (N3).
- lib/db-unusable.mjs:173-175: "it reads what SQLite still can, with writable_schema when the schema will not parse and from
  the main file alone when the log is what breaks the store".
- Commit: "with writable_schema when its schema will not parse and from a copy of the main file alone when the log makes the
  store unreadable".
- lib/db-repair.mjs:17: "When the store does not read at all with its log, the main file alone is read".
- README:1001-1003, as to the trigger.
- The output line itself: "SQLite could not read the database together with its log (database disk image is malformed); the
  rows were read from the database file alone".
- tests/db-unusable.test.mjs comment: "repair-db reads what it can".

Evidence: E-8x and SWEEP.
- On these 8 plants the plain open fails, and openOld retries with writable_schema. storeTables' full scan of sqlite_master
  throws, so openOld rethrows the plain error, and the build falls back to the main file alone.
- The same read-only handle with writable_schema reads all 241 observations, the 41 log rows included, identical to the
  unplanted store.
- The output says SQLite could not read the database together with its log. It then says "The store as found is kept as
  <A> and <A>-wal — delete them once you no longer need it."
- Same 8 plants in both arms.

Why P1: a user who takes the warning at its word ("SQLite could not read ... with its log") and follows the next line
deletes the only files that hold 41 readable observations. Round 1's P1-2 had the same shape: readable rows dropped, the line
calls them unreadable, and the next line invites deleting the kept file.

Mitigating facts the owner may weigh:
- The kept files and the "go back" command are printed.
- Doing nothing also loses these 41 rows: the next session's ensureDbWithWalRecovery deletes the log.
- The archive's C3w copy had the same limitation (24/46 vs the 31/46 a plain per-table read gets).

Population: 8 of 869 single-page plants, which is 8 of the 46 `✗ Database` plants (17%).

### F2 — P2 — doctor first, then repair-db (the documented order) loses rows repair-db alone recovers

Where:
- install.mjs:3117-3159: the FTS check opens read-write, and its close checkpoints the log into the main file.
- Then :3163-3188, the integrity line with INTEGRITY_REMEDY.

Claims it makes misleading:
- README:991-993: "When `doctor` prints `✗ Database integrity:` ... run ... repair-db".
- README:1006: "Rows on a page SQLite cannot read are lost either way".
- INTEGRITY_REMEDY: "it copies every row SQLite can still read".

Evidence: SWEEP, p5-v0 and p5-v1 (observations root page).
- Before doctor, the main file alone reads 200 observations.
- Arm D: doctor prints `✗ FTS5 rebuild errors` and `✗ Database integrity: Tree 5 page 5 ...` with repair-db. The log is
  0 bytes after doctor. repair-db prints "SQLite cannot read <db>: no observation could be read ... Nothing was written to
  the database", then the set-aside.
- Arm P, the same plant with no doctor first: repaired, 200 observations, with the main-file-alone warning.

So "lost either way" is false for these rows: doctor's own write is what made them unreadable. The doctor behaviour predates
this commit; v6.30.3's doctor folds the frame in the same way. The new text routes the user through it.

Population: 2 of 869. The 196 integrity plants are all post-doctor, so the main-alone fallback is never available on them
in arm D.

### F4 — P2 — "refuses ... when no observation can be read" is false when the main file alone reads an empty table

Where: lib/db-repair.mjs:643-657. A main-alone build counts as `ok` with 0 observations when the table is readable and
empty. The guard at :495-499 applies only to errors.

Claims it falsifies:
- Commit: "It refuses, writing nothing to the store, when ... no observation can be read".
- lib/db-repair.mjs:17 (as F1).

Evidence: E-T3. No observation reads through the log, and the main file alone has none. Outcome repaired, exit 0. The store
now holds 0 observations; "Copied 2 rows". The aside and the go-back command are printed.

Reach: any store whose observations live only in an un-checkpointed log (for example after a crash before the first
checkpoint) when a log frame of the observations tree is damaged. Not in the 869 sweep, where the main file always holds 200.

- The line: "rows there that no index lists may be lost". The next line invites deleting the kept file.

### F7 — P2 — the store is written outside the backup, and a throw after the probe deletes the copy of the store as found

Claims it falsifies:

- Output: "SQLite cannot write into <db>": the probe's checkpoint did write into it.

Evidence:

  connection checkpointed, as probeExclusive's own docstring says.
