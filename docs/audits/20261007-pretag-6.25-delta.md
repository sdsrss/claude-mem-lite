## O-1 (outside the delta, pre-existing since a1e11148 2026-06-29) — a throw during cleanup after a smoke rollback deletes the restored install
`hook-update.mjs:1107-1112` and `:1199-1201`. Smoke fails → `rollbackInstall` puts the old files back → then
`rmSync(stagingDir)` throws (EBUSY / EPERM / EACCES; `force` does not suppress those) → the catch calls
`rollbackInstall(installed, backedUp, …)` **again**. The first call reversed both arrays in place and the second
reverses them back, so it deletes every `installed` path, which now holds the *restored old* files. The backups were
already renamed back, so nothing is restored. Probe (scratch copy of the barrier test, one-shot EBUSY on the staging
`rmSync`):
```
throw arm  : hook.mjs exists: false  server.mjs exists: false  marker: false
control arm: hook.mjs exists: true   server.mjs exists: true   marker: false
```
The marker part of the brief's question is fine: no path leaves it set. `package.json#os` includes `win32`, where an
EBUSY/EPERM on a freshly npm-installed dir is ordinary. Not introduced by 6.25.0, so it does not block this tag.
Suggest a deferred item: guard the catch with a `rolledBack` flag, or move the cleanup `rmSync`s out of the try.

  no in the published numbers (P3-6).
