## 2. 架构与关键流

子系统由三块组成，共享一个 `resource-registry.db`，但触发路径互不相同：

```
                       ┌─ resource-registry.db (独立于主库) ─┐
                       │                                      │
 install (npm 路径)  ──┤  15 repos / ~150MB clone → scan → upsert
   install.mjs:1560    │
                       │
 UserPromptSubmit ─────┤  L1 显式名指针 matchRegistrySkillName → stdout 提示
 user-prompt-search.js │  L2 意图推荐 recommendSkill ────────→ JSONL（仅日志）
                       │
 PreToolUse:Skill ─────┤  pre-skill-bridge.js → additionalContext 注入技能正文
                       │
 CLI / MCP ────────────┘  registry list|search|import|enrich · mem_registry · mem_use
```

**关键前提**：三条运行时路径（L1、L2、桥接）全部以 `existsSync(REGISTRY_DB_PATH)` 为门。库不存在 = 三条全部静默 no-op。

## 3. 核查结果

### 3.1 已证实

#### `A20260906-R9-P1-1` — 推荐引擎按构造零产出，且其标定指标结构上算不出来

**优先级**：P1（关键功能失效）

**位置与证据**：

1. `registry-recommend.mjs:4-7` 自述 Phase-1 invariant：「the engine only LOGS. It never emits to stdout」。`live` 模式落进 `RECOMMEND_MODE_UNIMPLEMENTED`（:23），`getRecommendMode()` 降级为 `shadow`（:39-46）。CHANGELOG:5585 确认 Phase 2 从未建成。
2. 消费者反查：`recommendSkill` 唯一调用点 `scripts/user-prompt-search.js:1138`，**返回值被丢弃**；影子日志唯一读者是诊断命令 `registry recommend-stats`（`mem-cli.mjs:2703`）。无任何路径通向用户或 agent。
3. 实测积累量（本机，2026-09-06）：

   ```
   /home/ai/.claude-mem-lite/runtime/recommendations/
     2026-09-05.jsonl: 2 行 · 2026-09-06.jsonl: 1 行
     全部 kind:"adopt"；kind:"reco" = 0
   ```

   v3.12.0 发版于 2026-06-24（`85e5f53`），至今 **74 天，0 条推荐记录**。
4. 成因：L2 门在 `existsSync(REGISTRY_DB_PATH)`（`user-prompt-search.js:1124`），而 `/home/ai/.claude-mem-lite/resource-registry.db` 不存在（`find /home/ai -maxdepth 4 -name "resource-registry.db*"` 零命中）。本机是 plugin-only 安装（`doctor` 原话），而建库的 `installPreinstalledResources()` 仅在 `install.mjs:1560` 被调用，属 npm `install` 路径；`scripts/setup.sh`（plugin 通道的 SessionStart 引导）中 `registry|preinstalled|clone|scan` 四词零命中。
5. **最致命的一条 —— 沙箱实测**：

   ```
   STORED: [{ name:'superpowers/brainstorming', invocation_name:'' }, …]
   Skill slug "superpowers:brainstorming" -> NO MATCH
   Skill slug "superpowers/brainstorming" -> { name:'superpowers/brainstorming' }
   Skill slug "humanizer"                 -> { name:'humanizer' }
   ```

   `resource-discovery.mjs:123,140` 以 **`plugin/skill`** 造名；Skill 工具传的是 **`plugin:skill`**；`invocation_name` 仅 GitHub 导入路径从 frontmatter 填（`registry-importer.mjs:523`），扫描器根本不写该列。于是 v3.12.1 声称修好的 matched-precision join（`registry-recommend.mjs:408` 的 `top.invocation_name || top.name`）对命名空间技能**仍恒为 0%**。

**影响**：Phase 2 的放行判据（lift > 1 + per-session PASS 密度）依赖 matched precision，而该数字对主流技能形态在结构上无法产生。这不是待办，是死锁：**引擎在等一个它自己造不出来的数字**。

**最小修复**：删除 `registry-recommend.mjs` 及其接线。

**验收标准**：`grep -rn "recommendSkill\|registry-recommend" --include=*.mjs --include=*.js . --exclude-dir=node_modules` 零命中；全套测试绿。

**改动风险**：低。用户可见行为损失为零（它本就不产生输出）。

**前置依赖**：无。

#### `A20260906-R9-P1-2` — Skill 桥接对命名空间技能匹配不上

**优先级**：P1（关键功能失效）

**位置与证据**：`scripts/pre-skill-bridge.js:74-85` 的 `WHERE status='active' AND (name=? OR invocation_name=?) AND local_path LIKE ?`。与 P1-1 第 5 点同一沙箱实测：`superpowers:brainstorming` → **NO MATCH**。只有裸名扁平技能（`managed/skills/{skill}`，`resource-discovery.mjs:84-92`）能命中。

**影响**：对当前主流的 plugin 命名空间技能，该钩子是每次 Skill 调用都要付一次进程启动 + 一次 `existsSync` 的 no-op。对能命中的少数扁平技能，它做的是把 Claude Code 马上要自己加载的正文再注入一遍。

**附带**：这是本项目唯一自动注入第三方仓库内容的面，2026-08-14 M-4 为它专门写了三重 defang（`neutralizeSkillBridgeDelimiters` + `neutralizeSkillDelimiters` + `neutralizeContextDelimiters`）。移除它同时移除该攻击面。

**最小修复**：删除 `scripts/pre-skill-bridge.js` + `hooks/hooks.json` 的 `PreToolUse:Skill` 条目 + `install.mjs:1057` 的孪生条目。

**验收标准**：`tests/audit-silent-20260814.test.mjs`（钩子集合 diff 守卫）绿——它会强制两处同改。

**改动风险**：中。两处钩子注册必须同改，CLAUDE.md 已把这条列为「Invariants that bite」。

**前置依赖**：无。

---

#### `A20260906-R9-P2-1` — registry 管理面与 Claude Code 原生 plugin 体系职能重叠

**优先级**：P2（结构性 / 可维护性）

**位置与证据**：

1. `registry/preinstalled.json` 的 15 个仓库含 `obra/superpowers`；而 superpowers 此刻正作为原生插件位于 `~/.claude/plugins/cache/claude-plugins-official/superpowers`。该功能会再 clone 一份、再索引一遍——且这份 shallow clone 冻结在导入时刻，原生插件那份会自动更新。
2. 默认 plugin 安装从不建库（见 P1-1 第 4 点）。npm 路径建库要付 15 次 clone / ~150MB，`install.mjs:1195` 自己在打印这个代价警告。
3. `mem_registry` / `mem_use` 在 `tool-schemas.mjs:846,866` 均为 `hidden: true`，不进 `tools/list`——agent 只能靠精确记住名字够到。

**影响**：3,779 行产品码 + 对应测试，维护一个与宿主平台竞争且已落败的二级包管理器。每轮审计都要重新覆盖这片不受信任输入边界（R6 就为此花了一整轮）。

**最小修复**：删除 9 个模块 + 清单 + `commands/tools.md` + CLI 三个命令族 + 两个隐藏 MCP 工具 + `schema.mjs:16` 的 `REGISTRY_DB_PATH`。

**验收标准**：全套测试绿；`claude-mem-lite help` 不再列 `registry`/`import`/`enrich`；`tools/list` 数量不变（本就 hidden）。

**改动风险**：**高——这是破坏性 Δ-contract**。CLI 命令与 MCP 工具消失，属"已发布产物用户可见默认行为变化"，按 §2 为 L3，需 major 版本 + CHANGELOG 迁移说明 + 回退路径（pin 前一版本）+ 一次性可发现性信号。

**前置依赖**：P1-1、P1-2 先落地（它们是本项的子集，先删可缩小 P2-1 的爆炸半径）。

### 3.2 待验证疑点

- **`invocation_name` 空列是否影响 registry 的其它面**：本轮只证实了它对桥接匹配与 shadow join 的影响。`formatRegistryListLine`（`registry.mjs:664`）在渲染时也读它，渲染缺失不影响正确性，未测。
- **npm 安装路径下 L1 显式名指针的实际命中率**：`matchRegistrySkillName` 走的是另一条匹配逻辑（`prompt-search-utils.mjs`），本轮未读其实现，不对其命中率下结论。
- **本机是 n=1 总体**：使用率证据取自作者自用机（plugin-only 安装）。"其它用户用得多吗"本轮答不了。但 P1-1 的三条结构性结论（Phase 2 未建成、`live` 降级、slug 错配）与安装形态无关，在任何机器上成立。

## 6. 明确不建议做

- **不建议修 slug 错配**（`plugin/skill` → `plugin:skill`）。修好只会让一个已判定要删的子系统开始产生数据，属反向投资。若最终决定**保留** registry，则此项立即升为 P1。
- **不建议保留 registry 只删推荐**。管理面的存在正是三条运行时路径的开关（`existsSync(REGISTRY_DB_PATH)`）；留着库就留着每 prompt 一次开库的代价。
- **不建议顺手重构 `registry-retriever.mjs` 的 BM25 打分**。它随子系统一起删，重构是浪费。
