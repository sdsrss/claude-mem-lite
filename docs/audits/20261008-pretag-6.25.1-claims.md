## FALSE

### F1. "nothing rolls a release back once its check has passed" — CHANGELOG.md v6.25.1 bullet 1
Same claim, in code comments: lib/doctor-stale-temp.mjs classifyUpdateResidue docblock "A backup dir that still holds its
journal is a swap whose updater was killed … A swap that is over removes its journal before anything else"; and the doctor
line it drives, install.mjs "Unfinished update: … an update was interrupted, or is running right now (run: node install.mjs
cleanup — it finishes an interrupted one …)".

Mechanism (code, HEAD hook-update.mjs discardBackupDir + recoverInterruptedSwaps): if `rmSync(<backup>/.swap-journal.json)`
throws, discardBackupDir returns and leaves the journal AND the complete backups ("so a replay restores one whole release").
recoverInterruptedSwaps replays any journal it finds. Since 5baef3d3 it runs not only at the next update entry but also from
`install`, `repair` (via the downloaded installer) and `cleanup`.

Evidence (my probe, HEAD tree, harness copied from tests/hook-update-rollback-barrier.test.mjs, smoke passes, ONE EBUSY on
the journal path, then the next entry):
```
PROBE-COMMIT {"after1":{"ret":true,"faultFired":true,"pkg":"{\"version\":\"1.1.0\"}","hook":"// new hook",
  "cli":"#!/usr/bin/env node\n","left":[".update-backup-1791458716074-3952260"]},
  "after2":{"recovered":1,"pkg":"{\"version\":\"1.0.0\"}","hook":"// old hook","cli":null,"left":[]}}
```
The committed 1.1.0 (installExtractedRelease returned true) is rolled back to 1.0.0 by the next recovery. [A] reproduced the
same independently, and showed classifyUpdateResidue calls the leftover 'unfinished-swap', so doctor sends the user to
`cleanup`, which now performs that rollback and prints "Finished an interrupted update". Before 5baef3d3 cleanup DELETED that
dir (keeping the new release); so 6.25.1 adds a path where the doctor-recommended `cleanup` downgrades the install.
Self-update / plugin sync re-install right after recovery, so there it is transient; after `cleanup` it is not.
(Not measured: whether the downgraded code then meets a DB the newer release migrated — the schema-skew lockout.)

The project already knew: docs/audits/…-r1.md P3-7 ("已提交的 swap 会被'延迟回滚'") and its "需要证伪的主张：结论" item 2
("提交后任何清理失败都不能回滚它：不能立即回滚，但删 journal 失败会在下一次入口被延迟回滚"), and …-r2.md F10 ("'nothing that
throws afterwards may roll it back' is true only within the call"). Both are dispositioned "→ D#289", and the release commit
says D#289's remainder is D#292 — i.e. not fixed, yet the CHANGELOG states the opposite as a universal.
Side point in the same docblock: "A swap that is over removes its journal before anything else" is also literally wrong —
discardSwapDirs removes the STAGING dir first, then the journal (hook-update.mjs discardSwapDirs); a kill there leaves a
committed swap's journal too (r1 Q1 table row "已提交，删 journal 前被 kill（含 staging rm 期间）→ OLD，延迟回滚").

Corrected: "Once its check has passed, an update no longer rolls itself back in the same run. If the journal of a finished
update cannot be deleted (EBUSY/EPERM on Windows) or the updater is killed before it is, the next update, install, repair or
cleanup replays it and puts the previous release back." The docblock/doctor line should say a journal-holding backup dir is
"a swap that was interrupted OR whose journal could not be removed after it finished".

### A-F1. "nothing rolls a release back once its check has passed" (CHANGELOG v6.25.1, bullet 1)

discardBackupDir() returns early when rmSync(<backup>/.swap-journal.json) throws, deliberately leaving the
journal AND the complete backups ("so a replay restores one whole release"). recoverInterruptedSwaps()
replays any journal it finds — and since 5baef3d3 it is also run by `install`, `repair` and `cleanup`.
Probe (copy of tests/hook-update-rollback-barrier.test.mjs harness in the HEAD tree; smoke passes; ONE
