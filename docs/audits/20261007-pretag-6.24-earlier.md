## P2

### P2-1 — doctor's new follow-up line is false when an update was already detected (e47d272c)
`install.mjs:2510` (HEAD `:2529`):
`'Until a lookup succeeds no update is announced, and self-update / repair cannot fetch a release.'`

The failure branch keeps the cached detection (`hook-update.mjs:111-117` spreads `...fresh`, so
`updateAvailable` / `latestVersion` survive), and the SessionStart banner reads that cache. In
plugin mode the cached flag stays until the plugin is updated, and a rate-limited lookup (403/429)
also sets `lookupError`, so this is reachable for a default plugin user.

Evidence (sandbox HOME/CLAUDE_MEM_DIR, state
`{"latestVersion":"99.0.0","updateAvailable":true,"lookupError":"HTTP 400","lookupFailingSince":"2026-10-06T00:00:00Z"}`):
```
  ⚠ Update state: last check: 2026-10-07T18:23:07.990Z, latest: v99.0.0, update pending — the last release lookup failed (HTTP 400, failing since 2026-10-06T00:00:00Z)
  Until a lookup succeeds no update is announced, and self-update / repair cannot fetch a release.
banner: "\n📦 claude-mem-lite: v99.0.0 available (current: v1.0.0) — plugin mode only checks for updates; reinstall/update the plugin to apply it\n"
```
The same doctor line says "update pending" and "no update is announced". The second half
("self-update / repair cannot fetch a release") predicts from one past failure. This is the class
the commit exists to remove (a doctor line that misreports the update check), and the fix is one
string, e.g. "no newer release can be detected until a lookup succeeds".

### P3-2 — wrong SQLite mechanism in the comment and commit message (96665883)
`lib/search-telemetry.mjs:162-164`: "once the holder committed, that snapshot was stale, which
SQLite answers with SQLITE_BUSY_SNAPSHOT at once". Probe: a child holds BEGIN IMMEDIATE for 80 ms
and inserts one row, and the contender runs read-then-write with busy_timeout 250:
```
deferred threw SQLITE_BUSY after 1 ms
immediate ok after 95 ms
deferred threw SQLITE_BUSY after 0 ms
immediate ok after 102 ms
```
The deferred transaction fails while the holder still HOLDS the lock, with plain SQLITE_BUSY and
no wait: SQLite does not run the busy handler when it upgrades an open read transaction to a
write. The test's holder never writes, so no snapshot can go stale there. The deferred mutation of
the test fails with `SqliteError: database is locked` at 130 ms. The conclusion (`.immediate()`)
is correct; only the explanation is wrong. A claude-mem-lite bugfix note from this fix (#446)
repeats the BUSY_SNAPSHOT explanation and needs superseding.
