## P2

### P2-1 CHANGELOG.md:63-64: "the purge of 15,000 rows took 180 ms, not counting the snapshot" is contradicted by the measurement it comes from

f7c0f3f8 added "not counting the snapshot". The number comes from 35eb39db's message:
"Timing on a 44k-row file DB with 15k candidates: this tree purges 15000 in 180 ms; HEAD purges
1000 in 65 ms per run." Every HEAD run also snapshotted first ("every run first wrote a full
database snapshot"). Purge cost grows with the row count, so the two points solve for a fixed
per-run cost: s + p = 65, s + 15p = 180 gives p of about 8.2 ms per 1000 rows and s of about 57 ms.
- The per-1000 cost matches a purge alone. Re-measured on a synthetic 44k-row file DB with 15k
  pending rows, run twice: one 1000-row batch took 7–8 ms, and the full 15k loop took 106 ms.
- The fixed cost has the size of a snapshot: `snapshotDb` took 86 ms here. `runMaintainOps`
  with the snapshot took 211 / 215 / 217 ms, and a HEAD-shaped run (snapshot plus one batch)
  took 96 / 106 / 112 ms.
So the 180 ms almost certainly includes the snapshot. Purge-only would be about 120 ms. The
ratio 180/65 = 2.8 cannot come from a purge-only timing, where 15k/1k gives 15x.

Evidence (probe scripts in the scratch dir, now deleted):
```
{"purged":15000,"purgeMs":106,"snapshotMs":86,"left":29000}
{"runMaintainOpsWithSnapshotMs":211,"headShapeRunWithSnapshotMs":96,"oneBatchNoSnapshotMs":7}
{"runMaintainOpsWithSnapshotMs":217,"headShapeRunWithSnapshotMs":106,"oneBatchNoSnapshotMs":8}
{"runMaintainOpsWithSnapshotMs":215,"headShapeRunWithSnapshotMs":112,"oneBatchNoSnapshotMs":7}
```
Fix: say "including the snapshot", or re-measure with split timing and quote both numbers. Caveat:
my DB is synthetic. The original DB was not available. The inference rests on the two figures
in 35eb39db.

## P3

### P3-1 lib/native-binding-hint.mjs:95: the new guard never fires on its only production path, and :156 re-creates the data dir first

`formatHookError` (native-binding-hint.mjs:123) is the only shipped caller of
`nativeBindingHintDue`. It is called from hook.mjs:4005 (top-level catch). It first calls
`recordNativeBindingBreakage(runtimeDir)` (:129), and that function runs
`mkdirSync(runtimeDir, { recursive: true })` with no guard (:156). Only then does it call
`nativeBindingHintDue` (:135). By then the dir exists, so the guard added at :95 passes and the
hint marker is written too. Probe: a worker env, a removed data dir, and an ERR_DLOPEN_FAILED error.
```
worker env: 1 dataDir exists before: false
line returned: true
dataDir exists after: true [ 'native-binding-broken', 'native-binding-hint-last' ]
```
(recordHookError at lib/hook-telemetry.mjs:87 guards before its own call to
recordNativeBindingBreakage, so that path is fine.)
Reachability from a real worker is narrow. A native-binding error reaches hook.mjs's catch only
from `new Database()` (schema.mjs:1322), which runs after ensureDb's guard (schema.mjs:1289). So
it needs a broken binding and a removal inside that sub-millisecond window. Once it happens, it
cascades: every later guard sees the dir again. (I saw the same cascade when I reverted the
proc-lock guard: auto-maintain then re-created runtime/ AND a fresh claude-mem-lite.db.)
Claims affected:
- CHANGELOG.md:56-57 "its later writes (... logs and markers) are skipped". The breakage marker
  is not skipped.
- f3cd6d4c's message: "The rate-limited native-binding hint marker ... gets the same check", and
  "finds no other site a worker reaches". Site :156 is reached through the same catch.
Fix: guard `recordNativeBindingBreakage`, or `formatHookError` before :129. One line. The sink test
(tests/worker-data-dir.test.mjs `nativeBindingHintDue skips a missing dir…`) tests the function
alone and cannot see the order.
