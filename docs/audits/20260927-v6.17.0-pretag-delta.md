## Q2: The new D# booking rule (scripts/user-prompt-search.js:804-812)

The rule books `D<id>` when the item's first line (`D#N 🟡 [Pn] title`) appears as a whole line in
what was written.

| Path | Result |
|---|---|
| Single item, no detail | Head = whole item → booked; a second naming is suppressed. Probe P2: marker `["D1"]`, 2nd run suppressed. Correct. |
| Single item, detail over budget | Head booked. This is the first block (`resetPlainHookText()` at :707; no earlier write), so re-injection is cut identically. Correct. This was the P2-1 fix. |
| Head line cut mid-line | Cannot happen. `capHookText` cuts mid-line only when `kept.length === 0`, i.e. the header line `[mem] Deferred work …`. Any later line that does not fit is dropped whole (loop `break`). The final `safeSlice` cuts only the tail, and kept lines are ≤ cap-RESERVE. The note-only branch of `writePlainHookText` cannot run for the first write. |
| Head dropped | Unbooked. The `dpair` test pins this. |
| Dedup 0.8 overlap | `MAX_DEFERRED_REFS = 3` (prompt-search-utils.mjs:278). With ≤3 ids, overlap ≥ 0.8 means **all** referenced ids are booked, so no partial overlap can suppress an unbooked item. Probe P4 (5 refs) confirmed only 3 are read. |
| Per-session charge | `bumpUpsCount: true` whenever `shownIds.length > 0`. The first item's head always fits unless a CLI title is ~9.4K chars (MCP caps titles at 200, tool-schemas.mjs:547). Removing `bumpUpsCount` reds `user-prompt-search.test.mjs > D#N … > charges the injection cap it is gated by`. |
| **Item cut by a sibling, later named alone** | **Over-booked. See P3-1.** |

### P3-1: an item whose detail was cut by an earlier sibling is booked, then suppressed when named alone

The code comment (:804-808) and the CHANGELOG justify the rule with "an item the cap cut is cut
the same way on every re-injection". That holds only for the **first** item. A later item's cut
depends on the siblings ahead of it in the same prompt.

Repro (subprocess, sandbox HOME/CLAUDE_MEM_DIR, same harness as tests/hook-text-cap.test.mjs):

- A = 55 detail lines (~5K). B = 65 detail lines, which fits whole alone: 6,324 chars in a fresh
  session.
- `ups('s1', "D#1 and D#2 please")` → 9,531 chars. B's head is shown, **42 of 65** detail lines
  are shown, and the footer reads `23 more line(s) not shown` with no id. Marker
  `ids:["D1","D2"]`.
- `ups('s1', "ok continue with D#2 now")` → **0 chars**: overlap 1/1, suppressed. B's last 23
  lines never reach the model.

Why this is P3:

- It is **not a regression versus the released v6.16.0**, which booked every referenced id
  (`git show v6.16.0:scripts/user-prompt-search.js:780-800`: `mergeInjectedMarker(…, dedupIds…)`).
  It regresses only against the unreleased 3c60192.
- The model can still fetch the item with `defer get` / `mem_get`.

How long the suppression lasts: until the marker goes stale. `ts` is refreshed by **any** hook's
write (lib/injected-ids.mjs:145-148, :171), and D ids are carried under union mode until
`MAX_MARKER_IDS` evicts them. So in a tool-active session it can outlast the nominal 5 minutes.

A tighter rule exists and passes the current tests: book the first item on its head, and every
other item only when shown whole:

```js
idsShownWhole(shown, items.map((e, i) => (i === 0 ? { id: e.id, text: e.text.split('\n')[0] } : e)))
```

Applied in the tree, tests/hook-text-cap.test.mjs stays **26/26 green**, and the P1 probe then
re-injects B whole (6,324 chars). No existing test separates the shipped rule from this one.
