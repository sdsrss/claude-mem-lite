## Findings

**P1: none.** 3232 ground-truth leaks were found, and in 0 of them does the scrubber flag the raw reply (as
written or with `|*removed). So the floor adds no leak for a shape the raw-reply check caught; every leak below
is a scrubber-coverage gap, except P3-a.

**P2 (adjacent to this commit, pre-existing since at least v6.17.0, outside 7f9fe16's diff): the Done / Not done /
Failed / Uncertain paths still scrub the whole section before truncating.** `clean()` = scrub → truncate, and
extractStructuredSummary does not cap a section. Measured with extractStructuredSummary + writeStopSummary:
- `'Done: ' + "'" + 'secret'.repeat(33000)` → 2215–2326 ms (Uncertain: 2209 ms). The same text with no report → 20 ms.
- `'Done: ' + chain + ' ' + '"' + 'password'.repeat(12500)` (100k chars; chain = 40 alternating `token: abcdefgh` /
  `secret: abcdefgh`, which drives scrubSecrets to its 32-pass cap) → **27 970 ms**, far past Stop's 5 s timeout.
  scrubSecrets alone on the 200k version: 110 s.
The commit's P2-1 fix bounds only the floor; the same DoS still works through a report section.

**P3-a: a PEM block whose END lies past the 8000-char window is stored partly.** Reply =
`'Here is the key: -----BEGIN RSA PRIV'+'ATE KEY-----\n' + body(L) + '\n-----END …'`. Floor is empty for
L = 1000 / 3200 / 7800. For L = 7950 / 8100 / 12000 it stores
`Here is the key: -----BEGIN RSA PRIVATE KEY----- MIIJKAIBAAKCAgEA…` (about 70 chars of the key body), even
though scrubSecrets flags the raw reply. The code comment "8000 covers a PEM block that starts inside the stored
head" does not hold for bodies of about 7.9k chars or more. My estimate is that this means RSA-16384 (about 12.5k)
or large PGP key blocks; I did not generate one. The stored prefix is armor plus the key header and modulus start,
which is probably public material.

**P3-b: the stored text is not exactly the checked text; the 120-char cut plus `…` can complete a scrub shape.**
`normalizeInline` only maps `\n` to a space and trims, and flat has neither, so the cut is the only step after the
checks. I ran boundary probes with a pad of 60..118:
- `password=<26 letters+digits>(x)` (function-call veto removed by the cut): the stored text is flagged in 26/59.
- `the password: <14 letters> is set` (the prose letters-only lookahead is defeated by `…`): 10/59.
- `AK + 'Q…'` (the trailing `\b` is satisfied by `…`): 1/59.
In every case the full text was not flagged. Effect: the stored floor is not a fixed point of scrubSecrets, so a
later re-scrub rewrites it. The letters-only prose password is a ground-truth secret, and that gap predates this
commit.

**P3-c: the `lined` view is load-bearing, but no test guards it.**
- Mutant `!carriesSecret(flat)` only (lined check dropped): 57/57 tests pass. The fuzz then leaks 164 cases that
  the raw reply's scrub DOES flag, e.g. `'Staging creds\npassword: hunterxyz\nDone'` →
  `Staging creds password: hunterxyz Done`. Joining the lines moves the label into prose position.
- The commit message and the carriesSecret comment say "each alone catches every case found (0 of 56 differ)".
  That is true for the flat view (mutant: 0 differences over 10 829 cases) and false for the lined view.

The 15-per-family leaks are prose position: `<word> token|secret|bearer: v`, plus a letters-only password of 15
letters or fewer. Examples: `__password__=V`, `| password | V |`, `password is V`, `{"GH_TOKEN": "V"}`,
`Staging creds token: V done.` are all stored verbatim. These gaps belong to the scrubber and hit every scrubbed
field, including the Done path. The underscore/tilde emphasis cases fall into the same class that carriesSecret's
stripped arm covers for `*`, and that arm does not strip `_` or `~`. Fuzz artifact: my GCP key was malformed
(gt = 0), so GCP was not tested.
