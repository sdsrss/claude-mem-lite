## Questions
- **Is 9da56038 limited to the two reply branches? Yes.**
  - 288/288 reply prompts are exactly `parent.system + " " + SUMMARY_COMPLETED_ORDER`: the sentence appears once and the user part is unchanged.
  - The no-reply case is covered under claim 1.
- **Is the shipped prompt equal to e51a8c69's arm Q? Yes, for every session with a usable reply.**
  - 144/180 sessions are identical, covering 1 reply, 2 replies, 15 replies, long replies and secrets.
  - The other 36 are sessions with no usable reply. There, e51a8c69's arm Q appended the sentence after `key_decisions`, and the shipped prompt (correctly, per contract) does not.
  - D26's population requires at least one non-empty recorded reply (summary-events-ab.mjs:585), so these sessions were outside it. One exception: `stopEvents` keeps a whitespace-only assistant text (`if (text)`, no trim). That case is constructed.
  - The ruler's guard is exact: it throws precisely when HEAD's arm would differ from e51a8c69's arm.
- **Callers of `buildSessionSummaryPrompt`:**
  - The worker (hook-llm.mjs:1940) serves both the Stop spawn (hook.mjs:1959) and the /clear spawn (hook.mjs:2517). Each gets the sentence whenever at least one reply was recorded. Recorded replies are trimmed and never empty (turn-replies.mjs:42, :70).
  - Nothing throws except P, Q and Q2. The rulers' change of meaning is F-1.
- **Downstream effects of a longer `completed`. No misbehaviour found.** Store figures come from a copy of the store, 45-day window, 330 summary rows. By provenance: model n=180 (median 338, p90 602, max 1335 chars); report n=64 (cut at 600); tail 77; titles 9.
  - **Storage:** the model's `completed` is stored without a cap (fast-summary.mjs:549/579). `FAST_SUMMARY_LIMITS` applies only to the Stop and SessionStart writes.
  - **Merge with a report's Done:** the report's Done is kept (fast-summary.mjs:578), so D26's ordering never reaches those rows (64/330 here). The ruler lists this as not modelled; it is not a code defect.
  - **SessionStart line:** `truncate(…, 120)` at hook-context.mjs:978, so the injected size does not change.
  - **Key Context budget:** hook-context.mjs:266 charges session rows for request + completed + next_steps, although `summaries` is never rendered. Probe on the store copy, 28 projects, the model's `completed` inflated by 47%:
    - observation selection changed in 0/28 projects
    - Recent table changed in 0/28 projects
    - unrendered summaries selected: 47 → 45
  - **Continuation handoff:** hook-handoff.mjs:1192 injects the full `completed`. The only cap is the 10,000-character per-hook cap (hook-text-cap.mjs:22), shared with the `<memory-context>` written after it in the same UserPromptSubmit (hook.mjs:3698, then :3920).
    - Handoff rows (n=47) raw: median 1726, p90 3474, max 5198 chars.
    - With 1335 × 1.47 ≈ 1960 added, this stays under the cap's 9,500-character content budget (10,000 minus a 500 reserve).
    - Growth is about D26's mean of +301 characters per continuation injection. No ruler measures it; injection-budget reads a frozen corpus.
  - **Keyed legs:** lib/llm-call.mjs:36 sets `maxTokens: 2000`. A reply cut at max_tokens is treated as a failure and falls back to the CLI (haiku-client.mjs:747, :365-375). D26 measured the CLI leg only.
    - Estimated summary JSON on the 180 model rows with `completed` +47%: max 1474 tokens with the repo's estimator, 1914 assuming 1 CJK character per token. 0/180 rows exceed 2000.
  - **Display:** server.mjs:608 and mem-cli.mjs:645 use `completed` only when `request` is empty, cut to 80.
  - **Dedupe / compare:** no production code compares or dedupes `completed`.
