## P2

### P2-1 Scrubbing first can SPLIT a secret that the old order caught (lib/fast-summary.mjs:283-287)
The first scrub on the raw reply matches only a prefix of a token that markdown splits. It redacts that prefix to `***`. Flattening then removes the backtick or pipe, but the suffix is no longer attached to its prefix, so the second scrub cannot see it. Scrubbing after flattening (138c20b's order) joined the token and redacted all of it.
```
| Authorization: Bearer | Zq9xw7LkPq3mZq9xw7Lk |      (a table row)
  => "Header Value --- --- Authorization: Bearer *** Zq9xw7LkPq3mZq9xw7Lk"   (Bearer's value class eats the lone "|")
Your key: sk-ant-api03-Ab`9Zq9xw7LkPq3mRtYu` (keep it private).
  => "Your key: ***9Zq9xw7LkPq3mRtYu (keep it private)."    (sk-ant-<8+> matched "api03-Ab")
old order on both: "... Bearer ***" / "Your key: *** ..."
```
Fuzz: 10 secret shapes × a mark (`` ` `` ** * | \n __ _) at every position × 8 prefixes = 41,680 inputs. The new pipeline leaked in 3,144 cases where the old one did not, and the old one in 624 where the new one did not. Most of the 3,144 are unpaired `**` / `__` inside the KEY (`p**assword=…`, `api_**key:`). Those are the cost of keeping identifiers (P2-2's trade), not of the ordering. **312** are the split shape shown above: backtick, paired bold or pipe inside the token.
Fix direction: fail closed when the two orders disagree. Compute `scrub(flattenReply(raw))` as well, and if it redacts a span the stored text still carries, store titles instead of the tail. Or add that span to the redaction.
