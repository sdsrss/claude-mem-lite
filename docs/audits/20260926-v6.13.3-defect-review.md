## Q1 — are the new SQL orderings right for the rows that reach them?

Writers of session_summaries:
- lib/fast-summary.mjs:20 INSERT (Stop baseline hook.mjs:1131, guarded by "no row for this
  session"; SessionStart /clear prev-session hook.mjs:2170, NOT guarded -> a session can hold >1
  fast row; /exit-restart hook.mjs:2271, guarded).
- hook-llm.mjs:1560 INSERT (when no `notes='fast'` row exists).
- hook-llm.mjs:1520 UPDATE of the `notes='fast'` row: rewrites `created_at_epoch = now` and KEEPS
  the row's id.

So for INSERT-only rows id order = write order (AUTOINCREMENT, schema.mjs:255), and `id DESC` is the
right tiebreaker. For UPDATE-upgraded rows, id is NOT recency — the same property findings.md uses
to reject a rowid tiebreaker for session_handoffs.

Live population (read-only, 2026-09-26T07:5xZ, ~/.claude-mem-lite/claude-mem-lite.db):
  rows 452; notes: fast 371, '' 58, llm 14, other 9; sessions with >1 row 86 (max 37)
  same-session pairs with id order != epoch order: 0; same-project pairs: 0
  project+epoch tie groups: 0; min gap between consecutive same-project rows: 3019 ms
  session_handoffs (contrast): 53 rows, 0 tie groups, rowid-vs-epoch inversions 48/1378 pairs
So id order agrees with epoch order on every summary pair that exists today, while handoffs
really are inverted by the UPSERT — the two decisions are empirically consistent. See P3-1 for the
one constructed shape where the new tiebreaker picks the less-recent write.

### P3-3 — the wait loop and "still going" premise read only exitCode; a signal-killed child hangs the case, and failure paths never kill the child
tests/green-stamp.test.mjs:351-356. A child killed by a signal has `exitCode === null` and
`signalCode` set, so (a) the loop at :351 keeps polling a dead child for the full 40 s, and (b) the
premise at :355 ("the run was still going") PASSES for a dead child; `child.kill('SIGINT')` is then a
no-op and `await new Promise((r) => child.on('exit', r))` at :357 registers after 'exit' already
fired, so the case hangs to the 60 s test timeout. Repro (test copy with
`child.kill('SIGKILL'); await sleep(500)` inserted before the premise):
  PROBE exitCode=null signal=SIGKILL
  Error: Test timed out in 60000ms.   Tests 1 failed | 33 skipped (34)   elapsed 61s
Also, when the ready premise (:354) or the 60 s timeout fails the case, nothing kills the child:
it keeps running (20 s sleep) against a fixture afterEach has already disposed.
Fix shape: loop/premise on `child.exitCode === null && child.signalCode === null`, and kill the
child in a finally/afterEach. The exitCode-only premise predates this range; the new loop inherits
it. Budget note: setup (2 child vitest runs) + 40 s loop cap sits inside the 60 s timeout only while
setup stays under ~20 s.
Pre-existing, measured on the PASS path too (not introduced here): after SIGINT the killed vitest's
fork worker is orphaned (ppid=1) with its cwd in the deleted fixture: seen 07:49:04.850, last seen
07:49:09.697, outer test run exited 07:49:04.857 (~4.8 s past the run). The ba01408 version orphans
it as well (last orphan seen 1.25 s past outer exit). No recreated fixture dir was observed
(private TMPDIR listing after the run: only 3 vitest ssr id dirs + node-compile-cache).
