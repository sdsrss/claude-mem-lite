The entry names exactly two families: "header lines that each hold a BEGIN over a few blank lines,
repeated" and "quoted BEGINs at many escape depths in turn". Against the release a user upgrades
from, only the removed-line (`-Comment: -----BEGIN …` over `-` lines) variant is faster (0.25-0.38x
at 50k/200k/400k); the context-line, escaped, spaced-grep and backslash-grep variants of the first
family and both depth cycles are slower (1.22-2.54x). The speed-up the entry reports is the
recovery of a slowdown introduced inside this same unreleased range (dc747922..1eef3c18: D#614
A1/A2/A3 and D#641). The absolute costs stay linear (ratio constant over 50k-400k) and below
0.6 s at 400k, so this is a wording finding, not a hang. Commit 83cb4e0f itself compares only with
1eef3c18 and says so; the CHANGELOG drops the baseline.

### P2-3 (C1, omission) "Nothing to run" without saying that keys stored before the upgrade stay stored

C1's literal statements hold (below). But the entry is a security note saying 6.30.9 stored these
keys, and the upgrade note says only "nothing to run". No code path re-scrubs stored rows: callers of
`scrubSecrets` at ea5dcc1e scrub new writes, LLM rewrites (hook-optimize.mjs) and `restore`
(cmdRestore, mem-cli.mjs:2585-2589); nothing rewrites existing observations. A user who had a cut key stored by
6.30.9 or earlier still has it after upgrading, and the entry neither says so nor names a way to find
it. The project has stated this before (v6.8.2: "existing rows are not rewritten"); v6.30.9's entry
has the same omission.

### P3-1 (C7) "code over 4,096 characters" counts the stored line, prefix and escapes included

`probes/longcode.mjs` (code of L characters before `'''-----BEGIN`, 4 line shapes, 4 wraps, 4 key
types, cut after every line) and `probes/longcode-dq.mjs`:
- 6.30.9 keeps from L = 250 code characters in Read output (`     4\t` + 250 = 257 > 256) and grep
  JSON; ea5dcc1e erases through L = 4,000 in every escaped shape. C3's 256 -> 4,096 holds.
- ea5dcc1e keeps everything at L = 4,080 under a grep prefix (`src/conf.py:3:` + 4,080 > 4,096),
  and in a JSON string inside another at L = 3,000 source characters when the code holds double
  quotes (each becomes `\\\"`). Raw and CRLF text: 0 kept at every L up to 20,000 in both trees.
So the limit is 4,096 characters of the escaped stored line from its start, not 4,096 characters of
code.

### P3-2 (C7) "an encrypted key … first 40 characters" is narrower than what is kept

`probes/firstline.mjs`, `probes/midline.mjs` (the release-note diff set cut at every 3rd character
