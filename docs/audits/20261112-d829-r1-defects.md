## Findings

### F1 — P2 — introduced — the D#815 line hides that the store is still there
- Where: install.mjs:2008-2012 (`Could not remove everything in ~/.claude-mem-lite (${e.code || e.message}); what it could not remove stays there.`)
- Mechanism: on Node 24 and 26, `rmSync` is the C++ binding. It stops at the FIRST failing entry, and `e.path` is the top-level dir, never the failing child (measured, see below). So everything it had not reached yet stays too, the store included. The line puts the blame for what is left on "what it could not remove". It does not name the store and does not say that running it again (after the fix) finishes the job. Exit 1 and "the purge is incomplete" are correct. No false "Done!".
- Evidence (Node 26, the same on 24): a sudo-style locked subdir `runtime/locked` (0555), 11 files seeded (6 code, db, -wal, runtime/ep-flush-1.json, a metrics shard, locked/inner.txt). `node q3-d815.mjs new 26 'locked subdir, mem unset'`:
  ```
  ⚠ Could not remove everything in ~/.claude-mem-lite (EACCES); what it could not remove stays there.
  ✗ Uninstalled, but the purge is incomplete: see the lines above.
  - home/.claude-mem-lite/runtime/ep-flush-1.json        <- the ONLY entry removed
  ```
  10 of 11 files stay, including claude-mem-lite.db and claude-mem-lite.db-wal, and only 1 of them (inner.txt) is one it could not remove.
  A concurrent writer (a hook of another running session writing runtime/) gives the same result. `race-e2e.sh`, 4 attempts: 3 printed `Could not remove everything in ~/.claude-mem-lite (ENOTEMPTY); what it could not remove stays there.` with `db=yes` (the store stayed, and nothing blocked its removal). 1 attempt finished cleanly.
  Direct rmSync object (errshape.mjs, Node 24/26): `{"code":"EACCES","syscall":"rm","path":"<top dir>"}`; order-dependent survivors: `left: claude-mem-lite.db locked locked/f`.
- How common: real. The code base itself names a "sudo run left it root-owned" shape (install.mjs:3839), and a second session writing runtime/ during uninstall is ordinary use. Judged from those comments and from the 3/4 race reproduction rate with one writer.
- Spec says "没删掉的留在原处" (what was not deleted stays). The English line narrows that to "could not remove", and that narrowing is the false part.

### F2 — P2 (P1-class impact, uncommon shape) — NOT introduced (same in 79374f2d) — a link INSIDE a real ~/.claude-mem-lite
- Where: install.mjs:2006-2007 (unchanged lines inside the new try)
- Mechanism: lstat of ~/.claude-mem-lite says "directory". `rmSync` unlinks links inside it without following them, prints "Data purged" and "Done!" and exits 0, while the store the link pointed to stays. This is the D#811 defect class one level down.
- Evidence: `node q4-regress.mjs new 26 'inner links'` (db → $C/ext/store.db, runtime → $C/ext/rt, node_modules → $C/ext/nm):
  ```
  ✓ Data purged (~/.claude-mem-lite/)
  Done!                                   exit=0
  - home/.claude-mem-lite/claude-mem-lite.db (l:$C/ext/store.db)   <- link gone, ext/store.db untouched
  ```
  The base tree gives the same output.
- How common: uncommon. The documented relocation is CLAUDE_MEM_DIR (README:1254), and the README never suggests symlinking. Linking the whole dir (D#811) is the likelier user move. Not following node_modules/scripts links is CORRECT for dev installs (install.mjs:620-632 creates such links), so a fix must stay limited to data entries.

### F3 — P3 — introduced — CLAUDE_MEM_DIR naming the default dir by another spelling + a removal failure: false "Relocated data purged" / "Kept … not claude-mem-lite's"
- Where: install.mjs:2008-2013 (the catch now continues) → 2022 (`MEM_DATA_DIR !== homeDir` is a string compare, and `resolveDataDir` returns the raw spelling) → 2072-2084
- Mechanism: before, the throw ended the run (stack trace, exit 1). Now the relocated purge runs on the same directory and classifies claude-mem-lite's own code as foreign.
- Evidence (`node q3-d815.mjs new 26 'mem = default'`):
  ```
  CLAUDE_MEM_DIR=$C/home/.claude-mem-lite/ , 0555 dir in node_modules/
  ⚠ Could not remove everything in ~/.claude-mem-lite (EACCES); what it could not remove stays there.
  ✓ Relocated data purged from $C/home/.claude-mem-lite/
  ⚠ Kept 4 entries there that it does not recognise as claude-mem-lite's: lib, node_modules, package.json, server.mjs. Remove them yourself if intended.
  CLAUDE_MEM_DIR=$C/home/.claude-mem-lite/ , 0555 dir in runtime/
  ⚠ Left runtime in $C/home/.claude-mem-lite/: claude-mem-lite's own, but the directory also holds entries that are not, so a file of yours may be inside. ...
  ⚠ Kept 6 entries there that it does not recognise as claude-mem-lite's: cli.mjs, install.mjs, lib, node_modules, package.json, server.mjs. ...
  ```
  Exit 1 in all of them. It removes only claude-mem-lite's own files, so no user data is lost. The false parts are "entries that are not [claude-mem-lite's]" and the ✓ line next to a failed default purge.
- How common: constructed. It needs CLAUDE_MEM_DIR set to the default path spelled differently (`…/` or `…/.`) AND a removal failure.

### F4 — P3 — introduced — Node-version-dependent: EBUSY prints no code and a malformed message
- Where: install.mjs:2010 (`e.code || e.message`)
- Mechanism: on Node 24.22.0 and 26.8.1, the C++ rmSync throws `{code:"", errno:-4094, message:", Unknown error: Device or resource busy '<abs path>'"}` for EBUSY (measured with a bwrap bind mount). The line becomes:
  ```
  ⚠ Could not remove everything in ~/.claude-mem-lite (, Unknown error: Device or resource busy '/…/home/.claude-mem-lite'); what it could not remove stays there.
  ```
  EACCES gives `EACCES` and ENOTEMPTY gives `ENOTEMPTY` (both measured on 24 and 26). Node 22 was not run, and its rmSync may be the JS rimraf with different codes and paths (unverified).
- How common: on Linux, a mount point at or inside the dir, which is constructed. On Windows, a file held open by a running MCP server could map to this branch, which I could not check.

### F6 — P3 — introduced, cosmetic — a target ending in "." is glued to the sentence's full stop

## Answers to the questions

1. Deletion with a link: none. 25 shapes (absolute, relative, chain, dangling, to a file, to HOME as `.` and absolute, to HOME's parent, self-loop, two-link loop, to `/`; CLAUDE_MEM_DIR = link, link/, link/., link/.., link/runtime/.., //link, target, target/, inside the target with a db, above the target with a db, an unrelated dir with a db, an alias link to the target and alias/, dangling + unrelated). On Node 26 and on Node 24: 25/25 exit 1, 25/25 no filesystem change anywhere in the case dir, 0 "Done!"/"purged" lines. The baseline gave exit 0 + "Done!" in 20/25 and left the store behind the link in all of them.
   Undetected "effectively a link" shapes: a bind mount or mount point (F7). A link inside a real dir (F2). HOME itself a link with a real ~/.claude-mem-lite is purged correctly; HOME a link with ~/.claude-mem-lite also a link is detected; HOME with a trailing slash is detected (q1b-home.mjs).
2. Output truth: F1, F3, F4, F6, F8. I found no shape where this change produces "Done!" or exit 0 with claude-mem-lite data left. The only Done/0-with-data-left shape is F2, which is the same in the baseline.
3. D#815: the relocated purge still runs after EACCES, ENOTEMPTY and EBUSY (reloc db removed in each). The message names the code for EACCES and ENOTEMPTY. It does not name a code for EBUSY on 24/26 (F4), and it understates what is left (F1). Node 24.22.0 and 26.8.1 behave identically on the filesystem. Node 22 was not run (no binary on this host; only node-gyp headers 22.23.4).
4. Non-link regressions vs 79374f2d (q4-regress.mjs): none. Same output and the same filesystem effect for: real default dir; real default + reloc; default absent with and without reloc; default a file with and without reloc; real default + CLAUDE_MEM_DIR=default/; inner links. Exit 3 (MCP still registered): real default gives the same result on both trees. A link gives exit 3 with the link warning and no "purge is incomplete" line (the summary line is pre-existing exit-3 precedence). A D#815 failure + reloc gives exit 3 (the base tree crashed with exit 1).
5. Tests: all 9 new tests fail on 79374f2d's install.mjs (9/50 failed). Per-site mutations, each asserted applied, on Node 26:
   M1 detection off 8 killed · M2 link branch not incomplete 8 · M3 relocated ignores link 5 · M4 readlink→realpath 2 · M5 catch not incomplete 1 · M6 catch rethrows 1 · M8 "included" never 5 · M9 link unlinked 8 · M10 unlink + relocated (the first attempt's shape) 8 · M11 lstat→stat 8 · M13 "Data purged" before rmSync 1 · M14 message without code 1 · M15 relocated skipped after failure 1 · **M7 "included" always: 0 (survives, F5)**.
   The unmutated test file passes 50/50 on Node 26 and 50/50 on Node 24. eslint and prettier --check are clean on both changed files.
