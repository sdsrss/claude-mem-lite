## Findings

### F1 · P3 · CONFIRMED mechanism, PLAUSIBLE reachability — an older kept dir is replayed while a newer unfinished one cannot be read; the only copy of a file is then lost
- hook-update.mjs:1098 (comment) "they are undone like a stack: newest first, and none older while a
  newer one is unfinished"; commit 626aa00e: "none older while a newer one is unfinished".
- Not true. A newer dir whose journal cannot be read right now (read error other than ENOENT, or
  JSON lacking the arrays) is skipped with `continue` (hook-update.mjs:1072-1092) before the
  sort/break at 1101-1110, so it is outside the stack and older dirs are replayed under it. The code
  itself plans for that state ("a journal it cannot read right now", installExtractedRelease comment).
- Evidence: scratch vitest probe in the 73fb919d tree (deleted). State built from a reachable sequence:
  update A rolled back but could not put server.mjs back (A holds "R0 server", seq 1); update B (seq 2)
  then swapped R1 in and was killed (B holds "R0 hook"); B's journal chmod 000.
    recoverInterruptedSwaps #1 -> A replayed and discarded, B left: tree {server:"R0 server", hook:"R1 hook"}
    chmod 644 B's journal; recoverInterruptedSwaps #2 -> tree {server:null, hook:"R0 hook"}, residue []
  Probe output: `REVIEW-PROBE {"afterFirst":{"tree":{"server.mjs":"R0 server","hook.mjs":"R1 hook"},
  "A":false,"B":true},"afterSecond":{"server.mjs":null,"hook.mjs":"R0 hook"},"residue":[]}`
  server.mjs is gone with no backup dir left: the outcome D#293 exists to prevent.
- Same root, reasoned only (not run): nextSwapSeq skips an unresolved dir whose journal cannot be read,
  so a swap started then can get the SAME seq as that dir; if both are later kept, their order falls
  back to readdir order, against "regardless of directory listing order".
- Reachability needs three rare events (a restore that cannot put a file back, a later swap killed, a
  transient journal read error such as EIO/EMFILE). repair recovers the install. Hence P3.

  extra.js was still "new" afterwards: 1000-1 was never tried, and nothing in it is held.

### F4 · P3 · CONFIRMED — doctor with ANY live install.lock holder: "✓ Stale temp files: none", an earlier interrupted update hidden, and the wrong holder named
- install.mjs:3073 "An update holds install.lock right now; its staging and backup dirs in X are not
  counted"; comment install.mjs:3027 "which is that update's own staging and backup dirs".
- lockHeld() is true for any live holder: install, repair's child, rebuild-binding (hook-launcher runs it

  the "Unfinished update" warning and the line goes green. (A real update first runs
  recoverInterruptedSwaps, so with an update holding the lock the leftovers are its own plus any kept dirs.)
- Evidence: sandbox with two unfinished backup dirs. With no lock, doctor printed
  "⚠ Unfinished update: 2 backup dir(s) ...". With install.lock = {pid of a `sleep 600`, ts now}:
    ✓ Stale temp files: none

  and no Unfinished-update line. Behaviour matches cleanup (which also skips). The finding is the green
  ✓ on a count that did not look, and the attribution.
