## P1

### P1-1: CLAUDE.local.md ships in the user's npm package (and in any packager that ignores .git/info/exclude), with the user's absolute home path
- lib/local-steering.mjs:117-129 and :158. adopt-cli.mjs:261-273. The whole protection is `.git/info/exclude`.
  git honours it. `npm pack`/`npm publish` does not (npm reads .npmignore/.gitignore/`files`). A Docker build
  context also ignores it (reasoned, not run). So does any zip or rsync deploy.
- The file is auto-written, unasked, into the git top-level of every repository the user opens. The block
  names the detail doc by ABSOLUTE path in the user's home (adopt-cli.mjs:269
  `buildClaudeMdBlock({ detailDocRef: ensureSteeringDetailDoc() })`), for example
  `/home/<user>/.claude-mem-lite/plugin_claude_mem_lite.md`.
- Repro (sandbox HOME, clone @ 80335a4): a repo with package.json + index.js + .gitignore(node_modules), then
  silentAutoAdopt, then:
  `{"ok":true,"action":"local","written":"created"}` · `git status: []` ·
  `npm pack files: CLAUDE.local.md, index.js, package.json` ·
  block contains `→ \`/tmp/.../h.d8Ta/.claude-mem-lite/plugin_claude_mem_lite.md\``.
- Why P1: the plugin writes a file into the user's tree that their own release tooling then publishes. A
  registry publish is effectively irreversible. `git status` stays clean, so the user gets no signal (the
  one-time note says "git never sees or commits it"). The WIP in the working tree switches the path to `~`.
  That fixes the path leak but not the shipped file.

## P2

### P2-1: Worktrees share one info/exclude, so unadopt/adopt/--disable in one worktree exposes the other worktree's CLAUDE.local.md to `git add -A`
- lib/local-steering.mjs:131-143 (removeExcluded) with :104-108 (`--git-path info/exclude` resolves to the
  COMMON dir). adopt-cli.mjs:54-57, :162, :320, :563.
- Repro (main + `git worktree add`): SessionStart in both, then `unadopt` in the worktree:
  `[main-local-still] true` · `[status-main-after-wt-unadopt] "?? CLAUDE.local.md"`.
  It stays dirty until the main tree's next SessionStart, and indefinitely under
  CLAUDE_MEM_NO_TEMPLATE_REFRESH=1, because the early return at adopt-cli.mjs:267 skips ensureExcluded.
  This is the exact failure 9-A set out to remove: a plugin file swept into the next commit.

### P2-2: A CLAUDE.local.md symlinked into another repository gets our block written into that repository's TRACKED file
- lib/local-steering.mjs:152 checks only whether the PROJECT repo tracks the path. writeBlockAt → atomicWrite
  writes THROUGH the symlink (lib/atomic-write.mjs, by design for CLAUDE.md).
- Repro: `dotfiles/CLAUDE.local.md` committed there, `proj/CLAUDE.local.md -> dotfiles/CLAUDE.local.md`
  (untracked in proj), then silentAutoAdopt:
  `{"action":"local","written":"created"}` · `status-proj ""` · `status-dotfiles "M CLAUDE.local.md"`.
  The shared file then steers every project that links it.

### P2-3: CLAUDE_CONFIG_DIR users lose their `adopt --disable` opt-out on upgrade, and auto-adopt writes into the repo they opted out of
- memdir.mjs:82 now resolves the memdir under $CLAUDE_CONFIG_DIR. The `.mem-no-auto-adopt` sentinel was written
  by every earlier version under `~/.claude/projects/<enc>/memory/`, and nothing migrates it.
- A/B, same env (HOME sandbox, CLAUDE_CONFIG_DIR=$HOME/cfg, sentinel at the old path):
  main → `{"action":"disabled","reason":"disabled-by-sentinel"} local file: false`;
  80335a4 → `{"action":"local","written":"created"} local file: true`.
- The legacy memory-dir residue under ~/.claude/projects is orphaned the same way (P3 part).

### P2-4: `adopt --disable --all` does not disable projects that have no memory/ dir, so their CLAUDE.local.md comes back next session
- adopt-cli.mjs:319 removes the local block for every KNOWN project, but :325 writes sentinels only into
  EXISTING memdirs (listAllMemdirs, adopt-cli.mjs:72-86, requires `projects/<enc>/memory/`). Claude Code
  creates that dir only when auto-memory is used.
- Repro: known project, no memdir:
  `[adopt --disable] …/proj/CLAUDE.local.md → removed` · `[adopt --disable] no memdirs found` ·
  `s2 {"action":"local","written":"created"} local exists: true`.

### P2-5: `unadopt`, or deleting CLAUDE.local.md by hand, is undone by the next SessionStart, while the note and README say otherwise
- adopt-cli.mjs:261-273 rewrites whenever no block is present. It has no memory that it wrote the file before.
- Repro: `s1 created` → unadopt → `after unadopt exists: false` → `s2 … created, exists: true`;
  user `rm` → `s3 … created, exists: true`.
- The one-time note (hook.mjs:2675) says "`claude-mem-lite unadopt` removes it". README.md:596 says "A block you
  remove by hand is not written back". commands/unadopt.md does carry a caveat, but the systemMessage and
  README do not. The WIP (uncommitted) adds a per-repo "created" state to fix this.

### P2-6: Sessions started in a subdirectory flip-flop with a CLAUDE.md block at the repo root: double steering, plus a rewrite on every alternation
- adopt-cli.mjs:261 checks the block in `<cwd>/CLAUDE.md`, but the local file goes to the git top-level
  (:263), and adopt-cli.mjs:276 / :162 drop the top-level local whenever the cwd has a block.
- Repro (root CLAUDE.md adopted and committed, subdir `pkg/`):
  `session-in-subdir {"action":"local","written":"created"}` · `root-has-local true` ·
  `root-has-claudemd-block true` · `session-at-root already-adopted` → `root-has-local … false` →
  `session-in-subdir-2 … created`.
  Claude Code loads ancestor CLAUDE.md and CLAUDE.local.md (documented behaviour; not run against a live
  CLI), so subdir sessions get the block twice. Each 'created' also injects a third copy once.
  Every older auto-adopted project (6.19.4 wrote `<cwd>/CLAUDE.md` everywhere) is exposed whenever a session
  starts in one of its subdirectories.

### P2-7: MEM_NO_AUTO_ADOPT=1 does not stop steering that is already written; the spec says it means "no steering at all"
- lib/quiet-scope.mjs:38-40 states it: "MEM_NO_AUTO_ADOPT only stops new writes". Every CLAUDE.local.md that
  auto-adopt has already written keeps loading. The spec's constraints say "MEM_NO_AUTO_ADOPT=1 and the
  per-project sentinel keep meaning 'no steering at all' (neither file nor injection)". The README table
  says it "stops the per-SessionStart steering across all projects". The only way out is `unadopt --all`,
  which the user is not told about.

### P2-8: The upgrade rewrites 3 tracked files in every previously adopted repo, while the README says auto-adopt "never writes anything git tracks"
- This range changes the block text (b6416ed, 9aca6cc). For projects that carry a committed block (every
  project 6.19.4's auto-adopt touched), silentAutoAdopt refreshes on the next session (adopt-cli.mjs:278-288).
- Repro (adopted by main's silentAutoAdopt, committed, then 80335a4): `{"action":"refreshed"}` ·
  `M .claude/.plugin_claude_mem_lite_state.json`, `M .claude/plugin_claude_mem_lite.md`, `M CLAUDE.md`.
- Refreshing is by spec (non-goals: "Existing blocks keep being refreshed as today"). The defect is the
  claim in README.md:170 and :590 ("without touching anything git tracks" / "never writes anything git
  tracks"), and that users hit it on this very release.

### P2-9 (item 7, from review-item7.md F1): a red node:test run reads as green when another summary in the same output says "fail 0"
- bash-utils.mjs:674-684. Real node 22 output with one green and one throwing run piped through `tail`:
  HEAD `{"isError":false,"isHardError":false}` vs main `{"isError":true,"isHardError":true}`. A timeout-only
  failure (`fail 0` + `cancelled 1`, exit 1) reads green too. Error recall and significance are lost for
  those runs.

## P3 (items 1-5)

1. Negated ignore (`!CLAUDE.local.md` in a tracked .gitignore, file untracked): ensureExcluded appends the
   exclude pair, the verification fails, the file is refused, and the pair is NOT removed. It repeats every
   session: `exclude-pairs 3` after 3 runs (local-steering.mjs:117-129). The growth is unbounded but small.
2. A repo whose `.git/info/` is missing (e.g. `git init --template=`) is always refused ('exclude-failed')
   instead of the dir being created (local-steering.mjs:122-124).
3. Concurrent starts: 8 simultaneous silentAutoAdopt calls left 4 exclude pairs (harmless, removal takes them
   all). Only one session gets 'created' and the one-time injection. The other 7 started before the file
   existed, so they run with no steering at all.
4. Exclude lines are left behind when the user deleted CLAUDE.local.md before unadopt, because dropLocalSteering
   gates on the block being present (adopt-cli.mjs:56). They are also left when an editor re-saved the
   exclude file as CRLF (local-steering.mjs:136 matches LF only). Repro: `exclude-after-unadopt` still holds
   the pair in both cases.
5. A dangling CLAUDE.local.md symlink is silently replaced by a regular file ('created').
6. A user's own untracked CLAUDE.local.md becomes git-ignored while adopted, so it is hidden from `git add -A`.
   Unadopt restores it byte-identically (`"my notes\n"`, `?? CLAUDE.local.md`).
7. Unadopt collapses every run of 3+ newlines anywhere in a user's CLAUDE.local.md (removeBlockAt, shared with
   CLAUDE.md; pre-existing there, new exposure for a file the user never asked us to touch).
8. An orphan-only local block (the user deleted the end marker) is skipped silently by unadopt/--disable. No
   residue line is printed, unlike CLAUDE.md, whose path reports 'partial'.
9. A tracked CLAUDE.local.md that contains our block (the user force-added it) is refused, then 'inject' → the
   steering is loaded twice, and the /adopt offer says "nothing is written to your repository".
10. If the DB is unusable, SessionStart returns at hook.mjs:2869-2885, before the steering is pushed (:2929-2944).
    'inject' projects then get no steering, and a 'created' session misses its one-time copy, while
    effectiveQuiet stays true (quiet-scope.mjs:56-59).
11. isAdoptedHere reads `<cwd>/CLAUDE.local.md` (quiet-scope.mjs:40), not the top-level one. It only matters
    under MEM_NO_AUTO_ADOPT=1 in a subdir: the block loads, but the project is treated as verbose.
12. The one-time note says the file "is listed in the repository's .git/info/exclude" (hook.mjs:2675). That is
    false when it was 'already' ignored by .gitignore or core.excludesFile, and the path differs in
    worktrees/submodules.
13. `adopt --status` prints "not a git work tree" when the top-level is $HOME or `/` (adopt-cli.mjs:396-399).
14. The worst case is 5 sequential git calls with a 5 s timeout each (25 s), against a SessionStart hook
    timeout of 15 s (hooks/hooks.json). Only a hung git reaches it.
15. CLAUDE_CONFIG_DIR: a relative value is ignored (data-paths.mjs:44,54). The CLI (2.1.284 binary, grepped)
    uses `CLAUDE_CONFIG_DIR ?? join(home,'.claude')` with no resolve, so a relative value diverges. The
    global state file is `.claude${VK()}.json`, i.e. `.claude-custom-oauth.json` etc. for non-prod OAuth,
    but claudeStatePath hardcodes `.claude.json`. lib/plan-reader.mjs:12 still reads ~/.claude/plans, while
    task-reader moved.
16. Stale LLM-visible docs: the commands/adopt.md description still says auto-adopt writes <cwd>/CLAUDE.md.
    commands/unadopt.md does not mention CLAUDE.local.md, and its "Aftermath: returns to verbose mode" is now
    false (quiet stays on via isSteeringInjectedHere). The detail doc (adopt-content.mjs) says the trigger
    table "由 SessionStart 注入", which is stale after r3.
17. The tests do not isolate the global git config (no GIT_CONFIG_GLOBAL). On a developer machine whose
    core.excludesFile lists CLAUDE.local.md, the "writes the block, excludes the file" test
    (tests/local-steering.test.mjs:98) fails.
18. Project-key collisions (inferProject = parent--base) share the one-time note/offer markers between
    different paths (pre-existing key scheme).

Item-2 note: not a defect. SessionStart context on 4 real projects (a copy of the live DB) measured
3191-4976 chars with the injected block included, well under the 10,000-char cap that would trim it from
the end.

## Item 3: SessionStart branches (hook.mjs:2755-2775, 2929-2944)

Correct: 'inject' injects plus a one-time offer. 'local' injects once only on 'created' (also when the block
was appended to a pre-existing user file, which is right because the host loaded it without the block).
'disabled' and MEM_NO_AUTO_ADOPT inject nothing. CLAUDE_MEM_NO_TEMPLATE_REFRESH freezes an existing local
block but still creates a missing one (same as CLAUDE.md). MEM_NO_ADOPT_HINT silences both notes. The markers
`.adopt-offered-` / `.local-steering-noted-` are in GC_PRESERVED_MARKER_PREFIXES and in no GC list, so they
never age out (hook-shared.mjs:262-268; sweepStaleProjectMarkers deletes only gc-listed prefixes).
Defects: P2-5, P2-6, P2-7, P3-10, P3-12.

## Item 4: unadopt / unadopt --all / adopt --disable [--all] / adopt

What holds: only the slug block is removed; user text is restored byte-identically; the user's own exclude
line survives (`exclude-after "CLAUDE.local.md\n"`); a symlink is emptied, not unlinked.
What fails: P2-1 (worktrees), P2-4 (--disable --all), P2-5 (regrowth), P2-6 (explicit adopt in a subdir
drops the root local), P3-4 (exclude residue), P3-8 (orphan-only local block).

## Item 6: event-edge prune (summary of review-item6.md)

No P1 or P2. It never removes an event's last hub edge (maintain-core.mjs:1039). It runs only in the locked
auto-maintain worker. It is idempotent and marker-gated. On a VACUUM INTO copy of the live DB, run 1
changed 1185 events (1831 edges) in 51 ms, and run 2 did nothing.
P3:
- A failed snapshot does not stop the pass, which still sets its marker (maintain-core.mjs:1069-1077).
  Repro: `snapshot:null`, the edge is removed, the marker is set.
- There is no date or source bound, so user-written `activity save --files` hub edges are narrowed too.
- A project under /tmp/claude-N loses its own edges (2 events on the live DB).
- "Bounded" is not enforced.
