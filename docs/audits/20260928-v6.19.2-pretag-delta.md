## F1 — P2 — The opening-quote walk takes an apostrophe for the string's opening quote (JSON / Python-repr text)

`secret-scrub.mjs:601-618` (`cutOffKeyEnd`, the new walk). The walk now crosses escaped breaks and stops at the nearest unescaped `"` or `'` before the BEGIN. In a double-quoted JSON string, an apostrophe in prose on an earlier escaped line ("Here's", "Don't") is unescaped, so it wins over the real opening `"`. `nextLine` then scans with quote `'`: the closing `"` no longer ends the string, and any `'` inside the key's lines does.

Two consequences, both cut-off keys in escaped text where an apostrophe precedes the BEGIN in the same string:
- F1a: when the string is followed by more fields (Claude Code's Bash `tool_response` puts `stdout` first, then `stderr`, `interrupted`), the last body line absorbs `","stderr":...`; a last line under 40 characters is then OTHER and is stored (up to 39 base64 characters; ≤15 when it is a SHORT line).
- F1b: an armor header value containing an apostrophe (`Comment: Alice's key`) ends the "string" in mid-header, the scan stops with `longs === 0`, and the WHOLE cut-off key (BEGIN, headers, every body line) is stored.

Output (tip):
```
F1a "{\"stdout\":\"Here's the head:\\n***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\",\"stderr\":\"\",\"interrupted\":false}"
F1b "{\"stdout\":\"Here's it:\\n-----BEGIN PGP PRIVATE KEY BLOCK-----\\nComment: Alice's key\\n\\nlQdGBFXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVy\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVyXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVy\",\"stderr\":\"\"}"
```
f2 and rel, same inputs:
```
F1a "{\"stdout\":\"Here's the head:\\n***PEM_KEY***\",\"stderr\":\"\",\"interrupted\":false}"
F1b "{\"stdout\":\"Here's it:\\n***PEM_KEY***\",\"stderr\":\"\"}"
```
Control: the same F1b input with `Here it is:` (no apostrophe before the BEGIN) is fully scrubbed by all three versions.

Mechanism check (mutation, on a copy of the tip): adding `if ((ch === 'n' || ch === 'r') && isEscBreak(backslashesBefore(text, k - 1, 0), u)) break;` to the walk (the pre-repair stop at an escaped break) restores `***PEM_KEY***` for both F1a and F1b. That mutation is not a fix, because it would undo the F3 Python-repr repair (`{'stdout': '$ head id\n-----BEGIN…`, which tip now scrubs fully and f2 did not). A fix has to decide between `"` and `'` some other way than "nearest unescaped quote" (in JSON an apostrophe never delimits a string; in a Python repr the string opens with `"` exactly when it contains `'`).

Regression: yes vs f2, yes vs rel.
Severity: P2 because it needs escaped text + an apostrophe earlier in the same string + a cut-off key (no END). F1b leaks the full key body.

## F2 — P2 — A tail whose END line has a prefix containing spaces is no longer scrubbed

`secret-scrub.mjs:744-749` (`keyTailSpan`). `sentence = /\S\s+\S/.test(trimmed)` sets `shape = null` for any END-line prefix with inner whitespace. The intent is "words before the END". But common line prefixes contain spaces: `docker compose logs` (`web-1  | `), syslog/journalctl (`Sep 28 12:00:00 host app[1]: `), Python logging (`2026-09-28 12:00:00,123 INFO `), a nested mail quote (`> > `). With `shape = null` the lines above keep their prefix, classify as OTHER, and the tail is stored in full.

Output:
```
tip: F2 "web-1  | Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVy\nweb-1  | Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVy\nweb-1  | abc=\nweb-1  | -----END RSA PRIVATE KEY-----\nweb-1  | listening"
f2 : F2 "web-1  | ***PEM_KEY***\nweb-1  | listening"
rel: (same as tip, stored)
```
The same holds for syslog, Python logging and `> > ` prefixes (checked: tip and rel store, f2 scrubs).

Regression: yes vs f2; no vs rel (rel stored these too).
A narrower sentence test would close this, e.g. deciding "sentence" only when the prefix shape does NOT match the line above. (Complete BEGIN…END blocks under these prefixes are still taken by the block pattern; only a headerless tail is affected.)

## F3 — P2 — A headerless tail of one 16-39 character line is kept (`tail -n 2 key.pem`)

`secret-scrub.mjs:759`. The new evidence gate needs `longs >= 2 || longest >= 40 || crc || KEY_MAGIC_RE`. `tail -n 2` of a PEM whose final line is 16-39 characters gives exactly one such line over the END, so it is kept.

```
tip: F3 "Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\n-----END RSA PRIVATE KEY-----\n"
f2 : F3 "***PEM_KEY***\n"
rel: F3 "***PEM_KEY***\n"
```

Regression: yes vs f2, yes vs rel. This is the documented F7 trade-off (an identifier over an END in prose), but it contradicts the contract's "a tail without header". The exposure is ≤39 base64 characters (≤29 bytes) of the key's final bytes.

## F4 — P2 — An armor header outside the new named list stops a cut-off key

`secret-scrub.mjs:378`. `ARMOR_HEADER_RE` now lists only `Proc-Type|DEK-Info|Version|Comment|Hash|Charset|MessageID`. RFC 1421 also defines `Content-Domain`, `Originator-ID-*`, `Key-Info`, `MIC-Info` and others, and tools emit `X-*` headers. When one of these comes before the body, the scan hits OTHER with `longs === 0` and the whole cut-off key is stored.

Output:
```
tip: F4 "-----BEGIN RSA PRIVATE KEY-----\nProc-Type: 4,ENCRYPTED\nContent-Domain: RFC822\nDEK-Info: AES-128-CBC,ABCDEF0123456789\n\nMIIEpAIBAAKCAQEAu1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gun\nMIIEpAIBAAKCAQEAu1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gun"
f2 : F4 "***PEM_KEY***"
rel: F4 "***PEM_KEY***\nContent-Domain: RFC822\nDEK-Info: …\n\nMIIE…(both body lines stored)"
```
`X-Custom: foo` before the body: tip and rel store the key, f2 scrubs it.
Regression: yes vs f2. Vs rel: rel also stored the body lines, so the only extra thing tip stores is the BEGIN and `Proc-Type` line. Complete blocks are unaffected, because the block pattern takes them.

## F6 — P3 — A BEGIN line with a short chunk before a 16+ chunk skips the key body below

`secret-scrub.mjs:579`. The F9 repair returns -1 for the whole key when a non-last chunk on the BEGIN line is under 16 characters. The following lines, which are key body, are then never scanned.
```
tip: F6 "-----BEGIN RSA PRIVATE KEY----- see configurationFile\nMIIE…\nMIIE…\n"   (body stored)
f2 : F6 "***PEM_KEY***\n"
rel: F6 (stored, same as tip)
```
Regression: yes vs f2; no vs rel.
Pre-existing in all three versions: `-----BEGIN RSA PRIVATE KEY----- copied from vault\n<64>\n<64>` stores the cut-off body, because every word is under 16 characters. Trailing words on the BEGIN line disable body scanning entirely.

## F7 — P3 — The block pattern's new stop at `***PEM_KEY***` leaves fragments that the line scanners cannot read

## F8 — P3 — The new CUT rules erase prose or identifiers that start the line after a BEGIN or a body

More tip-only erasures vs f2 (rel matches tip):

- a `sha256sum` line after a BEGIN line;

## Q4 — Throws

0 throws across 4 × 50,000 random token compositions (3-28 tokens each), 8,000 long compositions (3-303 tokens) and every crafted family above at up to 800k characters. Tokens: BEGIN/END for RSA, PGP and OPENSSH; base64 runs of 15/16/39/40/64; real, escaped and double-escaped breaks; CR; quotes and backticks; `</a>`; `<`, `[`, `…`, `...`; named and unnamed armor headers; `***PEM_KEY***`; Read/grep/quote/diff prefixes; JS concatenation; lone backslashes; `token:`; `eyJ`; `<private>`. ## Q5 — Idempotence

For every fuzz input (208,000), `scrub(scrub(x)) === scrub(x)`. The pass count, from replicating the loop over the exported `SECRET_PATTERNS`, maxed at 2. Fuzz reach: in 7,519 of 50,000 inputs (seed 11) the output gained a `***PEM_KEY***` that the input lacked, so the key scanners were exercised. I found no construction that chains passes through the new rules: a sentence-kept END line leaves `***PEM_KEY***` above it, which classifies OTHER on the next pass, and a CUT scrub keeps the rest of its line, which never starts a base64 run.
