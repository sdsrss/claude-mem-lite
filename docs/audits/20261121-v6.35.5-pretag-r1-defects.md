## Findings

### F1 — P3 — when the check of a compiled addon cannot run, the addon is treated as dead and moved, even if it works
- `lib/binding-probe.mjs:261-267` (`addonLoadsInFreshProcess` returns `!r.error && r.status === 0`) and `:300` (`.filter((f) => existsSync(f) && !addonLoadsInFreshProcess(f))`).
- One predicate is used in two directions. For the prebuild (`:303`), "no" is the safe answer: nothing gets moved. For the
  compiled addon, "no" is the answer that MOVES it. A spawn error (EAGAIN/ENOMEM), the 10 s timeout, or a crash on exit
  all count as "will not load".
- Repro (constructed): a working compiled addon (a copy of the prebuild in `build/Release`), the first probe stubbed to
  fail (`'probe timed out'`, as in test 2 of the D#928 block), and a preload that fails only the bare-require check child:
  ```
  NODE_OPTIONS="--require probes/flaky-check.cjs" node probes/ensure-w.mjs cand/lib <tree>
  → before: OPENS via …/build/Release/better_sqlite3.node
  → {"ok":true,"action":"restored","setAside":[".../build/Release/better_sqlite3.node"]}
  → after:  build/Release/better_sqlite3.node.unusable; OPENS via …/prebuilds/linux-x64.node
  ```
- Expected: an inconclusive check leaves the file alone, which is the promise in the comment at `:287`. Seen: the working
  addon is renamed. The user's custom SQLite build is silently replaced by the stock prebuild.
- Real or constructed: constructed. It needs the first probe AND the compiled check to fail for reasons other than
  dlopen (timeouts under heavy load, or a transient spawn failure) while the prebuild check and verify succeed.
- v6.35.4 never moves a compiled addon.

### F2 — P3 — the guard asks whether the prebuild loads, not whether the next file in the load order loads
- `lib/binding-probe.mjs:301-303`. A dead `build/Debug` is set aside only when the prebuild loads. Under 13.2.0, though,
  `build/Release` is what loads next.
- Repro: `build/Debug/better_sqlite3.node` = junk, `build/Release` = a working addon, prebuild = junk:
  ```
  node probes/ensure.mjs cand/lib <tree> '{"sourceBuild":false}'
  → {"ok":false,"error":"…/build/Debug/better_sqlite3.node: file too short"}   (nothing moved)
  moving build/Debug/better_sqlite3.node by hand → OPENS via …/build/Release/better_sqlite3.node
  ```
- Expected: a rename heals this tree, which is the whole point of the step. Seen: the SessionStart path fails and writes
  `.deps-broken`. `rebuild-binding` then does a full source compile (~41 s, needs a toolchain), and `node-gyp clean`
  deletes the good `build/Release` before compiling.
- Real or constructed: constructed. `build/Debug` exists only after `npm run build-debug`, so this is a developer tree.
  The install-message text has the same blind spot (F6).
- v6.35.4 with 13.0.3 (prebuild first) ends the same way: compile.

### F3 — P3 — the source-build branch can now quarantine a prebuild that loads, and the message calls it unloadable
- `lib/binding-probe.mjs:444-449` (quarantine on existence alone) and `install.mjs:4901` ("the shipped prebuild would not load — moved aside").
- Under 13.0.x, reaching this branch with a prebuild present meant the prebuild itself had failed, because it loaded
  first. Under 13.2.0 the branch is also reached when a compiled addon shadows a GOOD prebuild and set-aside did not act:
  the addon dlopens but cannot be used (F1's predicate is "dlopen succeeds", which is weaker than the probe), a rename
  failed, or set-aside's verify failed.
- Repro (constructed: a foreign N-API addon in `build/Release`; real probe and verify; npm stubbed; the compile stubbed as
  `node-gyp clean` plus a good addon):
  ```
  build/Release/better_sqlite3.node = lightningcss.linux-x64-gnu.node   → FAILS addon.initialize is not a function
  bare require of it: loads; prebuild: loads
  node probes/ensure-q.mjs cand/lib <tree> tmp/good-addon.node
  → {"ok":true,"action":"compiled","quarantined":".../prebuilds/linux-x64.node"}  (prebuild now linux-x64.node.unusable)
  ```
- Expected: a prebuild that loads keeps its name, and no message says it "would not load". Seen: it is renamed, and
  `rebuild-binding` would print the false line. On a Ctrl-C during the compile, the tree is also left with no addon.
- Real or constructed: constructed. v6.35.4 with 13.0.3 opens this tree from the prebuild and never reaches the branch.

### F4 — P3 — two of the four callers rename a file inside `node_modules` without naming it
- `scripts/launch.mjs:172` prints only for `'rebuilt'`. `install.mjs:741` prints `better-sqlite3: restored`, and `:758`
  prints nothing for `'restored'`. `install.mjs:4897-4899` states the rationale itself: "A silent move inside a dependency
  is the kind of thing that reads as corruption six months later".
- The real shape where this matters: an architecture switch at the same Node version (macOS Rosetta x64 → arm64, or a home
  directory moved to another machine). `process.versions.modules` does not change, so setup.sh's marker
  `node_modules/.mem-binding-ok-$NODE_ABI` (`scripts/setup.sh:326`) stays present and the SessionStart probe is skipped. The
  MCP launcher (`launch.mjs`, under the lock) is then the likely path that heals, and it heals without saying so.
- The CHANGELOG names only `rebuild-binding` and the SessionStart probe, and that statement is accurate. This is about
  consistency, not a false claim.
- v6.35.4 has no move to report.

### F5 — P3 — the new step's time budget is fixed at 10 s per spawn, and the hook-capped caller cannot tighten it
- `lib/binding-probe.mjs:253`, `:264`. `scripts/binding-probe-cli.mjs` caps its own probes at 8 s and its npm step at 20 s,
  under the 30 s SessionStart cap (`hooks/hooks.json`). The new step adds up to 4 × 10 s plus an 8 s verify before the npm
  step. The old worst case already exceeded the cap (8 + 20 [+20] + 8 s).
- Measured cost on the target shape: 108 ms (`ensure`, shape A) and 204 ms (whole `setup.sh`, shape A, sandbox HOME).
  It only matters if a dlopen or a node start hangs. Constructed.
- If the hook is killed mid-step, the renames are atomic and either state is loadable or unchanged. I found no corruption.

## Answers to the brief's questions

1. **Which addon each install shape loads.** Both 13.0.3 and 13.2.0 ship `gypfile: false` and no install script, and
   `binding.gyp` is byte-identical between them. The only resolver change is in `lib/binding.js`: 13.2.0 checks `build/Debug`,
   then `build/Release`, then `getPrebuildPath()`, and musl is detected from `/proc/self/maps`. `src/` changes add only the
   fd-VFS path. SQLite goes from 3.53.4 to 3.54.1.
   - npm 11.19.0, offline install of the 13.2.0 tarball, scripts at default and with `--dangerously-allow-all-scripts`:
     no `build/` directory is created, and the addon loads from `prebuilds/linux-x64.node`.
   - Four `npm rebuild` variants never ran node-gyp. On a dead `build/Release`, `npm rebuild better-sqlite3 --dangerously-allow-all-scripts`
     exits 0 ("rebuilt dependencies successfully") and leaves the dead file in place. That is the statement `512306e0` deleted
     as "falsified"; I reproduced it on npm 11.19.0.
   - No prebuild: `Cannot find module '…/build/Release/better_sqlite3.node'` with `MODULE_NOT_FOUND`, which
     `isNativeBindingError` still classifies as true. The heal chain is unchanged there (set-aside returns `[]`).
   - `smoke-tarball.mjs`, `doctor` and the sandbox `loadedBindingPath()` agree with 13.2.0's order.
2. **The new step.**
   - It can move a working addon only through F1, which is constructed.
   - It never leaves "no addon": the prebuild must load first, and the put-back is tested.
   - Concurrency: 4 concurrent `binding-probe-cli` runs × 3 rounds → exactly one heals, three defer on `install.lock`, and
     the tree always opens from the prebuild. Before the rename the tree was already dead, so a concurrent loader is never
     made worse.
   - `.unusable` files are left behind only if the put-back rename fails.
   - Symlinked `node_modules`: it acts on the link target, which is the same tree under the same data-dir lock.
   - Every caller holds the lock: install (`main` → `takeLock` → `install()`), `rebuild-binding`, `launch.mjs`, and
     `binding-probe-cli`. The CLI heal goes through `rebuild-binding`.
   - Windows: the dead file is never loaded by anyone, and the prebuild is loaded only in child processes. Not run on Windows.
   - Budget: see F5.
3. **Mixed trees.** The range adds no import or export in shipped files (checked with `git diff … | grep import/export`).
   The new callers read `result.setAside || []`. Old `binding-probe-cli` with the new lib heals shape A and exits 0, silently.
   The v6.35.4 lib on shape A returns `ok:false` (`file too short`), as expected, since it has no set-aside step.
4. **Tests.** See F7. The six tests discriminate for every behaviour they name, and none is vacuous on CI.
5. **Other.** The repository's own `node_modules/better-sqlite3/build/` holds a node-gyp configure output (Makefile,
   `config.gypi` with `npm/11.19.0`, two `.stamp` files, no `.node`), dated 05:19:55, the same second as the package was
   installed. It is harmless under 13.2.0 because there is no `.node`, but this `node_modules` is not a pristine `npm ci` tree.
