### A1 — coverage 分母读未截断 prompt，而查询是截断的 · **P1**

| 项 | 内容 |
|---|---|
| **位置** | `hook-memory.mjs:512`（`extractQueryTerms(userPrompt)`）对 `hook-memory.mjs:344`（`upsFtsQuery(userPrompt)`）；`extractQueryTerms` 定义在 `hook-memory.mjs:172-182`，阈值在 `:151-156`（默认 0.4），过滤在 `:509-522` |

**机制。** `:344` 用 `upsFtsQuery()` 建 MATCH 表达式，该函数带 `UPS_QUERY_CAPS = { maxChars: 2000,
maxTokens: 64 }`。`:512` 的 `extractQueryTerms(userPrompt)` 拿的是**原始 prompt**（path B 的 stdin 上限
是 `MAX_HOOK_STDIN_BYTES` 256KB，`:339-343` 自己的注释这么写的）。于是 `candidateCoverage` 的分母包含了
**从未被搜索过的词**，命中行按构造无法覆盖它们。

**影响（确定性复现，非语料相关）。**
复现脚本 `scratchpad/r6.mjs`，`:memory:` DB，1 条完美匹配行 + 30 条 filler：

前提断言（先于结论）：`upsFtsQuery(A) === upsFtsQuery(B)` → **true**（A=1983 字符，B=2703 字符 = A + 60 个
prompt 尾部 token）。即两次调用的 MATCH 表达式**逐字节相同**，候选池、BM25 分数、阈值全部相同，唯一变量是分母。

```
MEM_COVERAGE_THRESHOLD 未设（默认 0.4）
  A (1983 字符)                 -> 1 injected (#1)
  B (A + 尾部, 同一 FTS 查询)    -> 0 injected
对照：只关掉 coverage 过滤器
  B with MEM_COVERAGE_THRESHOLD=0 -> 1 injected (#1)
```
→ coverage 过滤器是 B 丢失注入的**唯一**原因。

分母发散的规模（`scratchpad/r4.mjs`，同一 prompt 生成器，逐档）：

| prompt 长度 | MATCH 里的词数 | coverage 分母 | 「行覆盖了全部被搜词」时的覆盖率 | ≥0.4？ |
|---|---|---|---|---|
| 500 | 31 | 20 | 1.0000 | 是 |
| 2000 | 34 | 53 | 0.6415 | 是 |
| 4000 | 34 | 96 | **0.3542** | **否** |
| 12000 | 34 | 418 | **0.0813** | **否** |
| 64000 | 34 | 2560 | **0.0133** | **否** |

注意 2000 字符档已经是 0.64 而不是 1.0——**字符上限只是致命的那一半**，两个分词器（`sanitizeFtsQuery`
vs `tokenizeHandoff`+`extractCjkKeywords`）本身就不一致，所以「切 2000 字符」这种最小修法只能把结构性归零
变成 0.64 天花板，修不干净。

**第二半：成本。** `lib/ups-query.mjs:9-15` 的 docblock 明写 cap 存在的理由是
「`extractCjkKeywords` 是 O(len × dict)，64KB CJK 要 31.8ms，全在模型看到这一轮之前」，并称 path B
是「the worse half」。`extractQueryTerms` 恰好调用的就是 `extractCjkKeywords`，且不带 cap。
同机 best-of-3（2026-09-08，纯 CJK prompt，`scratchpad/r4.mjs`）：

| prompt | `upsFtsQuery`（有 cap） | `extractQueryTerms`（无 cap） | 比值 |
|---|---|---|---|
| 8KB | 4.2 ms | 5.2 ms | 1.3× |
| 64KB | 3.6 ms | 41.7 ms | 11.4× |
| **256KB**（path B stdin 天花板） | 3.8 ms | **166.8 ms** | **43.9×** |

绝对毫秒随机器负载变化，**只引比值和量级**；有 cap 那一列在三档基本持平，这本身就是 cap 生效的对照。
其后 `candidateCoverage`（`:191-208`）还会为每个 (term, row) 新建一个 `RegExp`：64KB 档是
2560 词 × 至多 45 行 ≈ 1.15×10⁵ 次构造，这部分未单独计时。

**修法。** 一个词来源，不是两个。在 `lib/ups-query.mjs` 里加一个导出（例如
`upsQueryTerms(text)` 或至少 `upsCappedText(text)`），`upsFtsQuery` 和 coverage 分母都从它取；
`hook-memory.mjs` 改成消费它。**不要**在 `hook-memory.mjs` 里写 `userPrompt.slice(0, 2000)`——那会
把 cap 复制成第二份，正是 `ups-query.mjs` 头部注释说自己存在的理由（"guard-on-one-path shape"）。

**验收测试（RED-first）。**
1. 前提断言先写：`expect(upsFtsQuery(A)).toBe(upsFtsQuery(B))`——没有这一条，后面的断言可能只是在测两个不同查询。
2. `expect(searchRelevantMemories(db, A, 'p')).toHaveLength(1)`
3. `expect(searchRelevantMemories(db, B, 'p')).toHaveLength(1)` ← 修复前 RED（当前为 0）
4. 对照臂：`MEM_COVERAGE_THRESHOLD=0` 时 B 也是 1（证明损失归因于该过滤器，而非池/阈值）
5. 成本臂：`extractQueryTerms` 路径在 256KB CJK 输入下的耗时不超过 `upsFtsQuery` 的 N 倍（阈值宽松即可，
   它要挡的是「cap 又被绕过」的回归，不是抖动）。

**变异验证。** 把修复后的 `upsQueryTerms(text)` 改回 `extractQueryTerms(text)`（即去掉 cap），第 3 条必须变红；
把 `getCoverageThreshold()` 的默认值从 0.4 改成 0，第 3 条会**假绿**——所以第 4 条对照臂必须存在且断言
threshold=0 时两臂都注入，否则整组测试可以被一个默认值改动走过去。

**优先级 P1。** 打击面是 `<memory-context>` 整个注入面，触发条件是「prompt 超过 2000 字符」——贴报错、贴
diff、贴日志都够；且失败是**静默的空注入**，与「没匹配到」不可区分（这正是 `:394-401` 那个 `debugCatch`
注释说要避免的形态）。

**既有守卫为何没覆盖。** `tests/memory-inject.test.mjs:709-850` 的 6 个 v27 coverage 用例全部用
3 词短 prompt（`'dispatch race fixture'`，21 字符），从未越过 2000 字符 cap；`MEM_COVERAGE_THRESHOLD`
在全仓只有这一处测试引用（另两处是 README/CHANGELOG）。没有任何用例断言 cap 与分母同源。

### A3 — `keyObs` 是唯一没有 `notLowSignalTitleClause` 的面向模型检索 · **P2**

| 项 | 内容 |
|---|---|
| **位置** | `hook-context.mjs:503-512`（`keyObs`，喂 `### File Lessons` / `### Key Context` 两个 section） |

  （该文件主控在并行编辑，行号可能已移动）。

### P2-3 | `install.mjs:1708-1710` `const log = (msg) => { if (!json) console.log(...) }` | `--json` 丢掉全部 12 条修复命令

**机制**：doctor 的 `log()` 在 JSON 模式下是 no-op，而**所有** remedy / 细节行都走 `log()`，
不进 `checks[]`。JSON 消费者拿到 `{level:'fail', message:'Database: file is not a database'}`
就没了，人类面同一次运行拿到的是完整的 `rm -f …-wal …-shm && mv … .corrupt`。

**实测**（沙箱，DB 文件填 4096 字节随机数据）：
```
--json : fail | Database: file is not a database          ← 到此为止
人类面 : ✗ Database: file is not a database
         No backup snapshot exists beside the database. Set the broken file aside …:
         rm -f "…db-wal" "…db-shm" && mv "…db" "…db.corrupt" — memories … not recoverable
```
**丢失的名字集合**（doctor 体内 14 个 `log(` 站点，12 条带修复信息）：
`:1772` per-root binding repair · `:1830/1831` schema-skew 的 remedy 命令与 note ·
`:1975` hook-manifest repair hint · `:1996-1998` orphan hook 路径 + uninstall 修复 ·
`:2027` `claude mcp remove <name>` · `:2048/2051/2054` marketplace clone 说明 +
`git -C … status` · `:2086` FTS 完整性明细 · `:2110` `dbCheckRemedy` 的整条修复。

**影响**：`--json` 的存在理由（:1684-1690 注释）是"CI / wrapper 想对单条检查动作"。
一个 agent 或脚本按 `--json` 读 doctor，会拿到"你的库坏了"而拿不到"怎么修"——**同一份
诊断，两个面，一个面是哑的**。这与 v6.5.0 那条 release 说的是同一个形状。

**修法**：`checks.push({ level, message, details: [...] })`——`log()` 在 JSON 模式把行追加到

**验收测试（RED-first）**：`tests/doctor-json-carries-remedies.test.mjs`——沙箱塞一个坏 DB，
断言人类面 stdout 里出现的 `mv "…db" "…db.corrupt"` 子串，**同样出现在** `--json` 的
`JSON.stringify(checks)` 里。用同一 fixture 跑两次、比对两个面，而不是硬编码文案。

**变异验证**：把 `details` 的 push 删掉 → 变红；把 `dbCheckRemedy` 返回 null → 两个面同时
没有该子串，用例应写成"人类面有 ⇒ JSON 面也要有"的蕴含式，这样这个变异是**绿**的（正确，
它测的是两面一致，不是 remedy 存在）。

### P2-4 | `install.mjs:2253 / 2290 / 2318 / 2336`（`warn(...)` + `issues++`）| `issues` 计数与 `checks[].level==='fail'` 的条数对不上

**机制**：doctor 有两个报告器：`fail()` 打 ✗ 并推 `level:'fail'`，`warn()` 打 ⚠ 并推
`level:'warn'`。有 4 个站点调 `warn()` **却** `issues++`（Dev drift、Managed files、
Hook scripts 的两条）。于是 `issues` 数了一条 `level:'warn'` 的记录。
`buildDoctorSummary` 的文档头（:262-264）明确写着 *"`issues` are ✗-level; `warnings` are
⚠-level (informational)"* —— **这句话在出厂代码里是假的**。

**实测两组数**（沙箱，同一次运行的 `--json`）：
```
fixture A（无安装）:  issues=3, fail 级 checks=2 ; warnings=5, warn 级 checks=6
                      摘要 "3 issue(s) found. (+5 warnings)"，屏幕上 ✗ 只有 2 个
fixture B（skew 库）: 摘要 "5 issue(s) found. (+4 warnings)"，屏幕上 ✗ 只有 3 个

**修法**（二选一，倾向前者）：给这 4 处一个 `issueWarn()`，推 `level:'issue'`（或
`level:'fail', glyph:'warn'`），让 level 与计数同源；或者接受 ⚠ 计入 issues，但把

### P3-6 | `tests/doctor-summary.test.mjs:60-77` | 报告器纪律守卫是单向的：它看不见一个不计数的 `fail()`

**机制**：该守卫扫 doctor 源码，要求每个 `warn(` 附近有 `warnings++` 或 `issues++`。

**验收测试**：给该 describe 加 `it('the scan rejects a bare fail() with no issues++')`，
