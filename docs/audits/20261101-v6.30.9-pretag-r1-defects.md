## 发现

### F1 [P2] 加行 diff 中，代码 BEGIN 下面一行是装着第二个私钥 BEGIN 的 armor 头行时，候选版存下 v6.30.8 擦掉的私钥行

**严重度理由**：安全方向上比上一版差（v6.30.8 存 0 行密钥，候选版存 2 行）。输入是构造出来的：要求一个私钥 BEGIN 写在 RFC 1421 头行里（`+Comment: -----BEGIN RSA PRIVATE KEY-----`），正常会话里几乎只在本仓库扫描器测试夹具里出现。定 P2 而非 P3，是因为本次发布周期已把同族的构造形状当作发布前必修处理（D#607 F5 `X-----BEGIN : v`；tests/secret-scrub-cutoff-shapes.test.mjs 里有多条"代码 BEGIN 下的头行 BEGIN"用例）。若按 D#131"只有攻击者才写的形状不收"的口径，可降为 P3，由发布人决定。

**位置**（rc/secret-scrub.mjs，单文件 sed -n 读取）：
- :752 `if (run < 16 && (found === -1 || found <= i)) {` —— D#168 语法重读的入口
- :940 `if (kind === ARMOR && ++armors <= MAX_ARMOR_HEADERS) continue;` —— longs===0 时，重读把装着 BEGIN2 的头行当 armor 头跳过
- :823 `if (again.longs > 0 && again.end > found && keyEvidence(again, label, false)) return again.end;` —— 返回的 end 越过了 BEGIN2
- :1064 `KEY_BEGIN_RE.lastIndex = end;` —— BEGIN2 位于 end 之前，本轮再也不读它

**触发链**：BEGIN1 行首有代码（`+KEY = '''`）→ 首读形状 `\+KEY = '''` 不匹配下一行，什么也没读到 → 语法重读取 diff 标记 `+`，形状 `/^[ \t]*[-+ ]/` → `+Comment: -----BEGIN…` 去掉 `+` 后是 armor 头，计数后继续 → `+<64 位>` 算一行 LONG → 下一行在重读形状下不是 key 行（`+QWERTYUIOPasdfg` 去掉 `+` 后剩 15 位，按 SHORT 收尾；或 `+Comment: ` 去掉 `+` 后是 armor 头，直接停）→ 重读只擦到第一行 key。v6.30.8 走的路径是 BEGIN2 自己的读取：形状 `\+Comment[:-] ` 不匹配 `+<b64>` 行，整行连 `+` 一起仍是 base64（LONG）；`+QWERTYUIOPasdfg` 整行 16 位，也是 LONG；`+Comment: ` 恰好是它的前缀，算空行。所以 v6.30.8 擦到最后一行。

**复现**：`node /home/ai/.cache/cml-6309c/defects/work/q1_repro.mjs`
```
IN   "+KEY = '''-----BEGIN RSA PRIVATE KEY-----\n+Comment: -----BEGIN RSA PRIVATE KEY-----\n+MIIEowIBAAKCAQEAu1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gun\n+QWERTYUIOPasdfg\n+VfLLGRHmAKOLzbCZpNqdM0MGSFhnfRSbxnrDTHjHqNHnL2dsc8RIG1rN7nsUiaHP\n+hgsZH+ZH+Nj3KhnWTuotrsusbcuKGV8QotwGpDNSePvXW3QS8FPBrUpgD5lxBrD2"
BASE "+KEY = '''-----BEGIN RSA PRIVATE KEY-----\n+Comment: ***PEM_KEY***"
RC   "+KEY = '''***PEM_KEY***\n+VfLLGRHmAKOLzbCZpNqdM0MGSFhnfRSbxnrDTHjHqNHnL2dsc8RIG1rN7nsUiaHP\n+hgsZH+ZH+Nj3KhnWTuotrsusbcuKGV8QotwGpDNSePvXW3QS8FPBrUpgD5lxBrD2"
```
- `+Comment: `（只有前缀的一行）代替 16 位短行：BASE 同上（存 0 行），RC 存 `VfLLGR…`、`hgsZH+…` 两行。
- 同一输入包成 JSON 字符串、JSON 套 JSON、CRLF：base 存 0 行，rc 存 `VfLLGR…`（脚本末尾三行打印）。
- fuzz 最小化形状（seed 33）：`+Comment: -----BEGIN EC…` / `+Comment: -----BEGIN DSA…` / `+<64>` / `+Comment: <64>` → BASE `+Comment: -----BEGIN EC PRIVATE KEY-----\n+Comment: ***PEM_KEY***`，RC `+Comment: ***PEM_KEY***\n+Comment: KNfs…`（存下第二行）。

**范围**：只有加行 diff（`+` 是 base64 字符，v6.30.8 才读得到这些行）。`-` diff、`> ` 引用、Read 列号、grep 路径这几种形状下，v6.30.8 自己在第一行 key 就停了，候选版不比它差（例：Read 列号变体，base 存 3 行，rc 存 2 行）。
**fuzz 证据**（`MODE=swallow node fuzz.mjs <seed> 10000`，seed 31–34）：40,000 个用例中命中 8 个，全部是这一机制（`q1_fuzz_hits.json`；`node minimize.mjs q1_fuzz_hits.json` 可重新最小化）。mix 模式 48,000 个用例、memo 模式 16,000 个用例命中 0。
**修复方向**（未验证）：语法重读的区间里还有私钥 BEGIN 时（`ctx.nextBegin(next) < again.end`），返回值取这些 BEGIN 各自读取终点的最大值，而不是 again.end。
