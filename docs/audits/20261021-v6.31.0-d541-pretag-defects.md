## F1 — P1 — readable rows between two unreadable regions are dropped and reported as unreadable

lib/db-repair.mjs:243-272 (copyTable). The forward scan stops at the first failure; the backward
scan stops at the first failure from the end; every row between the two is dropped. When a table
has two damaged regions, all the readable rows between them are lost, and the warn line says they
"could not be read".

Repro (scripts/e2-twogaps.mjs): 600 observations, 67 leaf pages; plant 8 bytes at offset 0 of
leaf[16] (page 81) and leaf[50] (page 125); run repairDb.
```
repaired 0
[warn] observations: 294 rows copied; the rows after id 162 and before id 469 could not be read (database disk image is malformed).
obs before 600 after 294
lost ids: count 306 range 163 .. 468
lost rows readable by rowid from the kept file: 288
```
288 of the 306 dropped rows read back with `SELECT * FROM observations WHERE rowid = ?` on the kept
file; only the 18 rows on the two damaged leaves are unreadable. The same happens with two damaged
overflow chains, or a damaged leaf plus a damaged overflow chain.
Correct: after the backward scan stops, the rows between are probed (rowid seek past the failure,
or rowid lookups driven by an intact index on the table) so every row SQLite can still read is
copied; a gap line names only rows that really failed to read.

## F2 — P1 — tables initSchema does not create are dropped with exit 0 and no line

lib/db-repair.mjs:503-506 iterates the FRESH file's tables only (`for (const t of built.tables)`);
a table that exists only in the old file is never read, never counted, never named. Product tables
created lazily outside initSchema:
- `search_runs`, `search_results` (lib/search-telemetry.mjs:15-46, created on first recorded MCP
  search when CLAUDE_MEM_SEARCH_TELEMETRY=1 — includes the user's relevance ratings);
- `migration_cursors` (schema.mjs:1343-1345, the CJK index-term walk's cursor/window rows).
Any table a newer or older build left behind goes the same way.

Repro (scripts/e1-telemetry.mjs, scripts/e19-cursors.mjs): store with 50 search_runs + 50
search_results rows (or one migration_cursors row), index leaf planted.
```
repaired 0
[ok] Copied 306 rows into a fresh file; it passes SQLite's integrity check and its search indexes were rebuilt.
DIFF {"search_runs":{"tableMissing":true,"rows":50},"search_results":{"tableMissing":true,"rows":50}}
...
DIFF {"migration_cursors":{"tableMissing":true,"rows":1}}
```
The output then tells the user to delete the kept file "once you no longer need it" — the only
remaining copy of those rows.
Correct: enumerate the OLD file's ordinary tables too; copy a table the fresh file lacks (create it
from the old CREATE statement) or refuse / name it in a warn line; never drop it silently.

## F3 — P1 — a connection open across the swap is not detected; the repaired store is corrupted or a committed save is lost

lib/db-repair.mjs:120-138 (probeExclusive) and 550-555 (swap). Two gaps:
(a) A connection holds no lock until its first statement. better-sqlite3's constructor opens the
    file (fd on the old inode) without reading, so an opened-but-unused handle passes the probe.
    After the swap its first write reads the OLD inode through its fd but derives `<db>-wal` /
    `<db>-shm` from the path, i.e. the NEW store's log.
(b) The probe closes, releasing the exclusive lock, before link/rename. A process that opens and
    commits in that window writes into the old inode, which becomes the kept file.

Repro (a), deterministic (scripts/e4-idle-holder.mjs + holder.mjs): child does `new Database(db)`
and waits; `node install.mjs repair-db` runs; child then INSERTs and stays open 4 s; then a fresh
connection opens and closes.
```
repair-db exit 0
  ✓ Copied 305 rows into a fresh file; it passes SQLite's integrity check and its search indexes were rebuilt.
  ✓ Replaced .../claude-mem-lite.db. ...
holder: inserted 301
while holder open: new store integrity: {"ok":false,"problems":["Multiple uses for byte 1029 of page 96 Tree 5 page 75 cell 3: Rowid 301 out of order Tree 5 page 73 cell 7: Rowid 824633720833 out of order ...
after an RW open+close: claude-mem-lite.db:446464 (the -wal is now checkpointed into it)
{"ok":false,"problems":["Multiple uses for byte 1029 of page 96 Tree 5 page 75 cell 3: Rowid 301 out of order ... invalid page number 108 ...
```
The store repair-db had just declared sound is permanently corrupt once any connection checkpoints.
Repro (b), window widened by fault injection only (scripts/slowlink.mjs delays the swap's
`linkSync(db, aside)` by 1.5 s; scripts/e5-window.mjs runs `node cli.mjs save` during it):
```
cli save exit 0 [mem] Saved #301 [decision] "SAVED-DURING-SWAP" ...
repair-db exit 0  ✓ Replaced ...
new store has SAVED-DURING-SWAP: 0
kept damaged file has it: 1
```
Unwidened, (b) is a window of a few syscalls; hooks are skipped by the swap marker only if they
checked it before it was written, and the MCP server and CLI do not check it at all. Severity is P1
by likelihood (product openers run a pragma right after opening, and the user is told to close
every session); by consequence it is corruption.
Correct: the probe's exclusive lock is held across link/rename (not released before them), and the
header comment, README ("refuses, changing nothing, while another process has the database open")
and mem-cli help stop claiming a guarantee the mechanism cannot give for a not-yet-locked handle.

## F4 — P2 — rows SQLite silently skips are lost with no gap line

lib/db-repair.mjs:243-272. A leaf whose cell count is damaged makes the scan skip cells without
an error, so copyTable records no gap. Integrity_check names the symptom ("wrong # of entries in
index ..."), but repair-db prints no line for the lost rows.

Repro (scripts/e3-cellcount.mjs): 600 observations; leaf page 102 cell count 9 → 1.
```
integrity false [ 'Fragmentation of 3368 bytes reported as 0 on page 102', 'wrong # of entries in index idx_obs_epoch_project' ]
repaired 0
[ok] Copied 597 rows into a fresh file; it passes SQLite's integrity check and its search indexes were rebuilt.
obs before 600 after 592
```
The 8 lost rowids are still in every index on observations.
Correct: compare the rows read with an index's rowid set (or row count) and report the missing
rowids as a gap.

## F5 — P2 — symlinked database path: a write during the copy is not detected; the symlink is replaced

lib/db-repair.mjs:324 (storeState) and 331-358 (swapIntoPlace). SQLite names the log after the
symlink's TARGET; storeState stats `<link>-wal`, which never exists, so a commit that only grows
`<target>-wal` leaves storeState unchanged. linkSync(link, aside) hard-links the symlink itself, and
rename(fresh, link) replaces the symlink with a regular file.

Repro (scripts/e20-symlink-write.mjs): 40 000-row store at real/store.db, symlinked as the DB path;
during the copy another connection inserts an sdk_sessions row (a table already copied).
```
plain path:  repair-db exit 1 ✗ ... changed while it was being copied ...   (control)
symlink:     repair-db exit 0 ✓ Copied 40005 rows ... ✓ Replaced ...
             kept file has it: 1
             store at db path has the row: 0
```
And (scripts/e13-symlink.mjs): after the repair `data/claude-mem-lite.db` is a regular file,
`data/claude-mem-lite.db.damaged-…` is a symlink to real/store.db, and real/store.db (still damaged)
stays; "delete it once you no longer need it" deletes only the link.
Correct: resolve the path first (realpathSync) and work on the target and its real -wal, or refuse
a symlinked database path.

## F6 — P2 — re-running a printed set-aside or restore line overwrites the kept damaged file

lib/db-unusable.mjs:240-245. The aside name is fixed when the line is printed; `mv` overwrites an
existing target. Running the same line again (shell history, or after "did it work?") after the
next session has created a fresh store moves that store over the kept damaged file, and the
`touch`ed empty log over the kept log.

Repro (scripts/e23-rerun.mjs), sh:
```
1st run exit 0 | claude-mem-lite.db.damaged-STAMP=ORIGINAL-DAMAGED  claude-mem-lite.db.damaged-STAMP-wal=ORIGINAL-WAL
2nd run exit 0 | claude-mem-lite.db.damaged-STAMP=NEW-FRESH-STORE-WITH-NEW-MEMORIES  claude-mem-lite.db.damaged-STAMP-wal=
```
Both the original damaged file and its log are gone, exit 0. The restore line has the same shape
(`... && cp <snapshot> <db>`). damagedAsidePath's docblock says the new name fixes "a second
set-aside overwrite[s] the first"; it does only for separately printed lines.
Correct: a no-clobber move (`mv -n` is in GNU, BSD and busybox mv; or `ln <db> <aside> && rm <db>`,
which fails on an existing name) so a second run fails instead of overwriting.
