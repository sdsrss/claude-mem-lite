## 6b. "install/repair (exit 1, the dir and its fix)": install TRUE, repair UNSUPPORTED
`repair()` (install.mjs) never takes or checks install.lock. It downloads the latest signed release
and runs `execFileSync(node, [<tarball>/install.mjs, 'install'])`, so the outcome is decided by the
DOWNLOADED release's installer, not by this tree. The latest tag is v6.25.2 = 0cd60a25. Its installer,
run with the runtime at 0555:
```
[install] Another install/repair is in progress — skipping to avoid a torn write.
v6.25.2 install exit=0       -> execFileSync does not throw -> repair prints "Repair complete — resynced…"
```
The claim becomes true only once a release containing 6d5cac5d is the latest. Until then, repair also
downloads a whole release before it learns that the lock cannot be taken.

## 7. "Blocked is not held: no installer of this user can be running": FALSE
lockDirBlocked asks only whether the dir can be written. It does not check whether a live holder's
lock file is already in it, and doctor computes `lockHeldNow = !installLockBlocked && lockHeld(…)`
(install.mjs:3068). Demo (`$S/tools/heldblocked.sh`): a live node process takes install.lock, the
runtime dir is then chmod 0555, and a running update's `.update-staging-<now>-<holderpid>` is present:
```
t3: lockDirBlocked: {"dir":"…/runtime","code":"EACCES"}  lockHeld: true
    ✗ Install lock: install.lock cannot be taken — …/runtime cannot be written (EACCES) …
    ⚠ Stale temp files: 1 found (run: … cleanup once install.lock can be taken (see Install lock))
t1: ⚠ Stale temp files: update residue not checked — install.lock is held (by a running install, …)
```
The commit's own scenario reads the same: a root-run (`sudo`) installer is still running and holds the
lock in the root-owned runtime dir it created. pidAlive() counts EPERM as alive (lib/proc-lock.mjs), so
lockHeld is true for a root pid as well. HEAD's doctor then reports the in-flight swap as stale, or as
"Unfinished update … an update was interrupted", where v6.25.2 said it was held. cleanup stays safe
because it skips residue when the lock is blocked. Only doctor's report regresses. The same premise
is repeated in tests/update-residue-faces.test.mjs ("no installer of this user can be running") and
scripts/binding-probe-cli.mjs:119 ("is not an install in flight").
