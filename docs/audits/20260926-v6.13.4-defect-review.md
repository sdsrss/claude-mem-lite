## P2-1: upgrading the highest-id fast row changes which content the COALESCE floor keeps. On the live data shape, "Last Session" loses the structural Done / Not-done lines.

`hook-llm.mjs:1486-1493` (existingFast now `ORDER BY id DESC`) combined with the COALESCE UPDATE at `hook-llm.mjs:1520-1545`.

The UPDATE's `COALESCE(NULLIF(?, ''), <col>)` falls back to the content of the row it upgrades. The comment at hook-llm.mjs:1497-1501 says that floor exists to keep the **Stop row's** structural content (`completed` / `remaining_items` from the §10 markers) when Haiku returns empty fields: "the exact regression that made 72% of prod session_summaries ship with empty remaining_items".

When a session has two fast rows:
- the lower id is the Stop row: `writeFastSummaryBaseline`, `FAST_SUMMARY_LIMITS.stop` 600/600, with a structural tail extract.
- the higher id is the SessionStart /clear row: `saveHandoffAndFastSummary`, `sessionStart` limits 300/200. Its `completed` is observation titles only and its `remaining` comes from the handoff's unfinished list.

The commit now upgrades the SessionStart row. The Stop row's content is left in an orphan `notes='fast'` row with an older epoch, and the "Last Session" read (`hook-context.mjs:613-622`, newest epoch) never selects it.

Live population, read-only, 2026-09-26:
- 75 sessions have exactly two `notes='fast'` rows.
- 71 of the 75 pairs have identical `completed`, so the change makes no difference for them.
- In all 5 pairs whose content differs, the **higher** id is the emptier row. Examples:
  - id 182 has remaining_items of 201 chars; id 185 has 0.
  - ids 254/255, 315/320, 342/348 and 169/172 each have completed of 82/22/210/130 chars on the lower id and 0 on the higher.
- No pair goes the other way (higherHasRem 0, lowerHasRem 1).

Repro (probe test `tests/zz-probe-d75.test.mjs` in the scratch tree, same mocks as tests/hook-llm.test.mjs):
1. Insert fast row 1 with completed `STRUCT-DONE item` and remaining `STRUCT-NOTDONE item` at t0.

Net effect: whenever Haiku returns a degraded shape, the new code swaps a richer injected Last Session for a poorer one. The gain it buys is removing an id/epoch inversion that only matters on a same-millisecond tie (0 live tie groups). The cost does not need a tie. Its trigger (two fast rows where the later is emptier, plus a degraded LLM field) exists in 5 of 75 live pairs.

Possible remedies, not tested: take the COALESCE floor from the session's fast rows, preferring non-empty, and upgrade the highest id; or retire/merge the other fast row in the same transaction; or keep the lowest-id upgrade and accept the tie-only inversion. The new D#75 test asserts only which id gets `notes='llm'`. It cannot see this, because both of its fast rows carry the same `'fast completed'` and Haiku returns full content.

## P3-1: the "one shape" the commit removes has a cross-session instance that still produces the inversion without a tie. The same inversion can also recur within a session.

Commit message / findings.md D#75: "upgrading the older one stamped the newest created_at_epoch below a higher id, the one shape that makes the summaries' id DESC tiebreakers pick the older write".

(a) Cross-session, pre-existing and unchanged by this commit.
1. `/clear` inserts row B (fast) for the previous session and spawns llm-summary.
2. The next session's first Stop inserts row C (id > B).
3. The worker later re-stamps B with `created_at_epoch = now`.
4. B now has the newest epoch and the lower id, so "Last Session" shows the previous session instead of the latest one. No tie is needed.

Probe `tests/zz-probe-d75b.test.mjs`:
- S1 fast at t0, S2 fast at t0+1s, then `handleLLMSummary()` for S1.
- Output: `LAST "### Last Session\nRequest: S1 LLM summary\nCompleted: x ..."`
- The S2 row, the most recent session, is not shown.

(b) Within a session. Two llm-summary workers can run for the same session: Stop spawns one every turn, and /clear spawns one for prevSessionId. If both run after row B exists:
- worker 1 upgrades B (highest);
- worker 2 then finds A as the only remaining fast row and upgrades it with a later `now`.

That recreates exactly "newest epoch below a higher id". It follows from the code; I did not build it. The new test's title ("so id order stays write order") holds only for a single upgrade.
