# Pre-release defect review: 26dcd49..2e5e266 (e59daed, c112ef3, 2e5e266)

Reviewed 2026-09-28. Every claim below was measured on `git archive` copies of 26dcd49 ("old"),
e59daed and 2e5e266 ("new"), plus 41b9659 (v6.19.2, which D#160 names), under this directory.
Nothing in /home/ai/dev/claude-mem-lite was written. Key material in this report is limited to
12-character windows of synthetic keys.

Side note, outside the range: while I worked, the repo working tree picked up uncommitted edits
to secret-scrub.mjs and four other files (mtimes 22:01-22:09 UTC). I did not make them. A copy
taken at 22:12 UTC (sha256 9eb973ac...) no longer reproduces F2. It still reproduces F1 and F3.

### F1 (P1): partial new erasure blocks a pass-2 block match that 26dcd49 made
- Where: secret-scrub.mjs:692-715 (the reread) together with :769-771 (PEM_MARK written) and the
  block regex at :213, which does not cross `***PEM_KEY***`.
- Mechanism:
  1. On pass 1, the block regex BEGIN..END is blocked by a partial marker `-----BEGIN RSA PRIVATE KEY`
     (no trailing dashes).
  2. New code: the reread erases the cut key's first lines up to a prose line and writes PEM_MARK
     over the BEGIN. 26dcd49 erased nothing there.
  3. A later pattern removes the blocker: Authorization Bearer in pass 1, the pass-2 label
     lookbehind of a chain, or a DSN.
  4. On pass 2, 26dcd49's block regex matches BEGIN..END and erases every key line. New code has
     no BEGIN left, so the key lines after the prose line stay.
- Repro: `node probe-unblock.mjs` (synthetic key, 4 lines of 64 chars):
  ```
  == authorization: key lines stored by new but erased by old: 2
  OLD: "-KEY = '''***PEM_KEY***\nthe end"
  NEW: "-KEY = '''***PEM_KEY***\nSome prose line here.\n-8B4P+P71<64>\n-A/Pb7PI8<64>\nAuthorization: Bearer *** RSA PRIVATE KEY\n-----END RSA PRIVATE KEY-----\nthe end"
  == controlNoCode: 0   (26dcd49 itself stores the same two lines on "------BEGIN", no code)
  ```
- Rate: `node probe-unblock2.mjs`, 4,000 constructed cases. Leaks for authBearer 338/593,
  labelChain 209/369, dsn 212/369. Zero for passwordLabel, quotedSecret, plainPartial and
  hexAssign: those blockers either go on pass 1 before the block regex or never go. The result is
  the same against 41b9659.
- Realism: this needs a key split by a non-key line plus a partial BEGIN marker that a later
  pattern scrubs. It is the cut-off scanner's existing behaviour (see the control), now reached
  through code-prefixed BEGIN lines. It contradicts the commit's "key windows stored that 26dcd49
  erased: 0 in every arm" and the comment at :691.

### F2 (P1, not a regression): D#160 is still open in escaped text
- Where: at depth u>=1, the BEGIN-line walk stops at an unescaped `'` (:678, isStringEnd(0,1)
  is true). The left context comes out empty, `prefixShape('')` returns null (:504), and
  `reread = shape !== null && ...` (:692) never runs. OPENER_RE (:516) does not accept an escaped
  quote, so a JSON `\"-` or Python-repr `\'+` opener gets no second try.
- The D#160 tests build text with `'\n'` only (tests/secret-scrub-cutoff-shapes.test.mjs:584).
  The one JSON case (:646) uses `"""`, which JSON escapes, so it takes the path that works.
- Repro: `node probe-matrix.mjs` runs the commit's LEFT x KEYS matrix, head and cutMidLine, 80 cases
  per wrapper. "New stores" is the number of cases where 2e5e266 keeps key lines:

  jsonCrlf  32          60          0

  ```
  `node probe-edge.mjs`: a JSON-wrapped `-KEY = '''`, `"-`, grep -A `KEY = '''`, Read-tool
  `KEY = '''` and the real gpg export shape (BEGIN, blank line, body) under `+x = b'` each store 3
  of 3 lines on both old and new.
- Fuzz, lines arm, 100k cases, cases with code or an opener, excluding my artificial code-first
  shapes. Each count is the number of cases where new stores key windows but old erases the

### F3 (P2): new prose-loss class, a shared prefix that ends inside an escape
- Where: sharedPrefixLength (:525-543). The word rule only protects the `\t` unit when the match
  runs past it. When left and line differ on an escape's letter (`\"` over `\t`), the match stops
  after the backslash. The prefix is then a lone `\`, and the `t` is kept as content.
- Repro: `node probe-halfescape.mjs`, JSON-escaped, no key at all:
  ```
  "\tconst k = `-----BEGIN PRIVATE KEY-----\n\tSessionManager1\n\tTokenRefresher2\nthe end
  old keeps names: true   new keeps names: false
  new: {"content":"$ cat k.js\n\"\tconst k = `***PEM_KEY***\nthe end"}
  same without the opener: new keeps names: true; without opener and code: true
  ```
  `tSessionManager1` is 16 characters, so it is a LONG line, and two of them make a key. This is
  the failure the escaped-tab test (:640-649) describes, reached from the opposite side. One
  differential-fuzz case (lines arm, seed 31) found it independently.

### F5 (P3): linearity budget
`perf-probe.test.mjs` runs the same method as secret-scrub-linear: CHAIN prefix, crafted/benign,
200k characters, `npx vitest run <file> --coverage.enabled`, two runs per tree, back to back on
this machine:
```

pemCodeBeforeBegin (suite)    4.42 / 4.59   5.55 / 5.66
pemOpenerBeforeBegin (suite)  4.45 / 4.35   7.26 / 7.55
altDigitDash240               8.98 / 9.08   18.05 / 17.87
altEscaped                    11.69 / 11.91 20.14 / 19.97   (26dcd49 already over 10x)
altDash250                    8.39 / 8.60   12.03 / 11.81

- The alt* shapes are `(P + 'x' + BEGIN + '\n' + P + 'y' + BEGIN + '\n')` repeated, with P equal
  to `'1-'x120`, `'-'x250` or `'a:'x120`. Every BEGIN line is the first line of the BEGIN above it
  and shares P with it. altEscaped uses `\\n` breaks.
- Growth per doubling, 200k to 400k without coverage: 1.96-2.07x for every shape, so nothing is
  superlinear.
- Without coverage at 400k: altDigitDash240 takes 532 ms on 26dcd49 and 1,004 ms on 2e5e266.
- The suite's own new shape keeps a 25% margin to its 10x budget. None of the alt shapes are in
  the suite.

### F6 (P3): short first line under a `+` opener
With the `+` inside the first line (`+MIGB...`), the reread is skipped because that line is
already LONG, and `first` fails KEY_MAGIC_RE (:756). A 32-char MIG line plus a 12-char line under
`rb'+`, `'+` or `+KEY = '''` is stored 2/2 on both trees. The no-opener `+` form is erased.
Repro: `node probe-short.mjs`. Only keys cut inside their first 40 base64 characters are affected.

### F7 (P3): left context over 256 chars
`-` + 290 chars + ` = '''` + BEGIN stores 3/3 on both trees; at 250 chars new erases it
(`node probe-edge.mjs`). This is prefixShape's cap at :504.

### F8 (P3): comments and claims
- :691 "Read the first way, such a key was never taken, so none goes less" holds for one call only.
  F1 is a counter-example across passes, and so is the commit message's "0 in every arm".
- :689-690 says a first line that "is not key material" is read again. The code rereads SHORT
  (1-15 base64 characters, which can be a key's last line) and OTHER only. A BLANK or ARMOR first
  line uses up the reread with no effect.
- tests/secret-scrub-linear.test.mjs:86-87 "each one looks two lines ahead". For
  pemCodeBeforeBegin the scanner reads one line twice. Two lines are read only in the opener
  shape.
- The commit says every unmutated prose loss is "also lost by 26dcd49 on the same text without the
  code or opener". F3 is a counter-example. See Q2 for the 9 other cases.
- 2e5e266 is comments only: every changed line in its three files is a comment. The browse-core
  rule numbers (rule 2 is the same session, rules 3-4 are the 2 h working window) match
  tier.mjs:29-45, and Stop marks the row completed on every turn (hook.mjs:1229).

## Answers

**Q1, security.** Yes. F1 is an input class where the new scrubber stores key lines that 26dcd49
erased. It is crafted: a partial BEGIN blocker that a later pattern scrubs. Differential fuzz
found no other case:
- 0 leak cases in 400k cases against 26dcd49: lines arm, seeds 2/4/31, 100k each; edits arm,
  seed 3, 100k.
- 0 in 200k cases against 41b9659.
- 0 differences on the 2,550-input tracked-file corpus: raw, JSON and double-JSON.

Fuzz inputs:
- Keys: 12 real ones (openssl RSA 1024/2048 traditional, PKCS#8 and encrypted, EC, Ed25519;
  ssh-keygen ed25519, rsa and encrypted ecdsa; gpg ed25519 export) and synthetic ones.
- Line prefixes: 16 kinds, including diff +/-/space, `> `, `> > `, Read `     N\t` and `N→`, grep
  `f:N:`/`f-N-`, log, tab, `# ` and `// `.
- Code and opener left contexts: 29 codes and 13 openers.
- Breaks: LF, CRLF and CR.
- Wrappers: raw, json, json2, jsonTool, fence, pybytes, jsConcat, jsonFence.
- Decoded forms: xxd, C array and `\x` escapes.
- Edits: line-level random edits.

Decoded forms (hex dumps, C arrays, `\x` escapes) show no difference either way. Neither tree
erases them; that is pre-existing and outside this range.

**Q2, prose.** One new loss class: F3, a half-escape prefix. On my differential arms, 10 of 400k
cases lose tokens that 26dcd49 keeps even on the text with the code or opener removed:
- 1 is F3.
- 9 are cases where 26dcd49 does not see the key in the variant either. The first line's prefix
  differs without any code: a `>` or `> >` blank quote line with its trailing space trimmed, or an
  edited `#b3Bl...`. The new reread (which also runs with no code at all) takes the key, and the
  existing LONG/SHORT/ARMOR line rules then take b64-shaped content in the key's line run, such as
  a 40-hex line, a 33-char path, a 15-char last line or `Comment:` plus a 40-char line.
- The same class appears 3 times in 200k cases against 41b9659.

In the same shape, 26dcd49 stores the whole key: `> -----BEGIN PGP...\n>\n> lQ...` gives old 3/3
stored and new 0/3 (probe-edge.mjs).

**Q3, e59daed.** No output change found:
- 0 differences on 450k backslash- and break-heavy strings (`fuzz-nextline.mjs`, depth 0, 1 and 2,
  JSON and double JSON). An instrumented copy confirmed the fuzz reaches every branch. In 50k
  inputs: backslash then real break 63, run at end of text 70, CONCAT_AFTER 168, escaped CRLF
  9,832, depth-2 breaks 12,800.
- 120k structured cases were all identical.

By inspection the two paths are equivalent: at u=0 only CR/LF stop, and a run's next character
is skipped exactly as before. The tests do not pin two of its branches (M31, M34 in F4).

**Q4, performance.** No superlinear shape (1.96-2.07x per doubling). There are shapes above 10x
benign under coverage; see F5.

**Q5, tests.**
- On 26dcd49's secret-scrub.mjs, 10 of the 17 D#160 tests fail: all 8 kind/cut matrix tests,
  "a name in a diff" and "escaped tab".
- The 7 that pass are the prose and guard cases, which pass on old because old erased nothing
  there.
- Mutation results: F4.

**Q6, other.** F6, F7, F8.
- An empty left context is F2's mechanism.
- A BEGIN at the start or end of the text is fine: shape null, or -1 before any read.
- No crash in any fuzz arm (the crash counter read 0 in every run).
