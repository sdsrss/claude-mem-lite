## P1

### F1 [P1, REGRESSION] CONCAT_AFTER_RE backtracks quadratically: 16-19 s for 200k chars, 8 s for 26k chars when a 32-pass chain comes first
- Where: `secret-scrub.mjs:371` `CONCAT_AFTER_RE = /["'][ \t]*\+?[ \t]*(?:\r\n|\n|\r)[ \t]*["']/y`, called from
  `nextLine` at :412-413 for every escaped break at depth 1. When no `+` follows the quote, the two
  `[ \t]*` split one whitespace run in every possible way before the line-break alternative fails:
  O(k^2) per call for a quote followed by k spaces or tabs.
- Reached from any BEGIN whose line ends in an escaped `\n` (JSON, JS strings), because
  `cutOffKeyEnd` calls `nextLine(text, i, u, '"')` at once. Body lines reach it the same way.
- Repro (input = `-----BEGIN RSA PRIVATE KEY-----` + backslash-n + `"` + N spaces + `x`). Two runs:
  ```
  N=25000   new 259 / 262 ms      old 1 ms
  N=50000   new 1001 / 1292 ms    old 1 ms
  N=100000  new 3996 / 4443 ms    old 1 ms
  N=200000  new 15992 / 19484 ms  old 2 ms     (x4.0 per doubling)
  tabs, 200k: new 21809 ms
  40-label CHAIN prefix (the linear test's 32-pass driver) + N=25000 (25,695 chars): new 8020 ms, old 11 ms
  ```
  Benign 200k prose on the same build takes 2 ms. Every hook timeout is 2-5 s, so this input kills the hook.
- Not covered by the test: `tests/secret-scrub-linear.test.mjs` `pemConcatLines` puts `" +` right
  after each quote, which never takes the backtracking branch.
- Fix direction: `["'](?:[ \t]*\+)?[ \t]*(?:\r\n|\n|\r)…` (one whitespace quantifier before the
  break), or check it by hand like lineCore does.

- Where: `secret-scrub.mjs:545` `longest = Math.max(...rest.split(/[ \t]+/).map((t) => t.length));`

### F4 [P2, REGRESSION, trade-off chosen by the design] A last key line that is not WHOLE base64 is stored whole, which was erased before
- Where: `lineCore`/`classify` (:468-510) and the rule "a body line is WHOLE base64" (comment at
  :337-353). `lineCore` only strips a trailing `"`/`'` plus `[ \t+,;)\]}]`. Whatever else follows the
  last line keeps the whole line: a backtick, `</key>`, `"#`, a word, `[truncated]`, a space before
  `…`/`...`. When the key has a single body line, the whole body is stored. An Ed25519 PKCS#8 key is
  always a single `MC4C…` line.
- Repro:
  ```
  IN : `-----BEGIN PRIVATE KEY-----\nMC4CAQAwBQYDK2VwBCIEIHh6d3Jjb3ZqZ2xpbmtlcnM0NTY3ODkwYWJjZGVm`   (real newline)
  OLD: `***PEM_KEY***`
  NEW: (unchanged: the entire Ed25519 private key is stored)
  IN : <key>-----BEGIN RSA PRIVATE KEY-----\n<L64>\n<L64></key>              NEW keeps the second <L64>
  IN : -----BEGIN RSA PRIVATE KEY-----\n<L64> see above                      NEW unchanged; OLD "***PEM_KEY*** see above"
  IN : -----BEGIN RSA PRIVATE KEY-----\n<L64>\n<first 30 of L64>[truncated]  NEW keeps the 30-char cut line
  IN : -----BEGIN RSA PRIVATE KEY-----\n<first 30 of L64> ...                NEW unchanged
  ```
- Matrix, run this session: 6 key kinds (rsa, pkcs8, ed25519, ec, openssh, encrypted pkcs8) x 91 line
  shapes x 6 cuts x 6 followers = 19,656 inputs. 7,208 leak fewer key windows than on old. 656 leak
  more: 416 have text after the last base64 on its line, 48 each are backtick-inline, JS template,
  Rust raw string and XML (192 in all), and 48 are shellEcho (F3). 2,502 leak the same on both.
- The prose arm makes this trade on purpose (round-3 P3-B). The regressions listed here are the price
  of that choice, and the delimiter cases (backtick, `</…>`) carry no prose. Stripping a closing
  backtick and a `<…>` tag in `lineCore`, the way quotes are stripped now, would recover them.

### F5 [P2, REGRESSION by exposure; the root cause predates this range] A later pass chains the whole-block PEM pattern across prose, and the tail scanner now leaves the END it needs
- Mechanism: the whole-block PEM pattern (:205) cannot cross another BEGIN. Pass 1 replaces a
  complete key B. In a later pass of the fixed-point loop (:773), an earlier BEGIN A that B used to
  block can reach a later END C with no BEGIN in between, and everything from A to C is erased. On
  old, the tail regex usually consumed C's END in pass 1. The new tail scanner correctly declines
  "two short words above an END" (round-3 P3-D) and leaves C in place, so the chain completes.
- Real corpus: a differential over every text containing `PRIVATE KEY` in the repo's tracked files
  plus 231 local transcripts (639.6 MB) found 679 unique inputs; old and new differ on 70. In one of
  them, a round-3 review report quoted in this session's transcript, NEW erases about 1,510 chars of
  prose that OLD keeps. Traced by pattern: NEW pass 1 applies pattern 19 (6316 to 5101 chars), then
  pass 2 applies pattern 19 again (5101 to 3591, prose gone). OLD's pass 1 applies pattern 21, the old
  tail regex, and pass 2 finds nothing to do. The other 69 diffs are key fixtures that new now
  scrubs, or spans that old erased and new keeps.
- Minimal repro (L = a 65-char base64 line):
  ```
  IN : Keys start with -----BEGIN RSA PRIVATE KEY----- on their own line.\nIMPORTANT PROSE ONE.\n$ cat k\n
       -----BEGIN RSA PRIVATE KEY-----\nL\n-----END RSA PRIVATE KEY-----\nIMPORTANT PROSE TWO.\nintro\nL\nOK\nyes\n
       -----END RSA PRIVATE KEY-----\nafter
  OLD: Keys start with -----BEGIN RSA PRIVATE KEY----- on their own line.\nIMPORTANT PROSE ONE.\n$ cat k\n***PEM_KEY***\nIMPORTANT PROSE TWO.\nintro\n***PEM_KEY***\nafter
  NEW: Keys start with ***PEM_KEY***\nafter
  ```
  If the second END sits mid-sentence (`They end with -----END RSA PRIVATE KEY----- too.`), old and
  new both erase "on their own line … They end with ". That variant predates this range and is not a
  regression.
- Fix direction: stop the block pattern from crossing a `***PEM_KEY***` it wrote itself (treat the
  mark as a BEGIN in its negative lookahead), or run the block pattern once, outside the fixed-point loop.

## Questions checked with no defect found
- Idempotence: 100,000 fuzzed compositions (headers, ENDs, base64, armor, prefixes, quotes, escapes
  at depth 0-2, JSON once and twice, existing `***PEM_KEY***` marks): scrub(scrub(x)) !== scrub(x) in
  0 cases. This holds by construction below the cap: the loop exits on a pass that changes nothing,
  and the new scanners keep no state between calls (the /g regex lastIndex is reset, and the sticky
  regex lastIndex is set before each exec).
- Linearity of the other scanners: 22 crafted shapes stay linear at 25k/50k/100k/200k. None exceeds
  12 ms at 200k, against a 2 ms benign baseline. The shapes include alternating escape depths across
  BEGINs, blank-line and armor floods, quote runs before ENDs, long END prefixes, digit prefix shapes,
  backslash runs in lineCore, trailing punctuation runs and concatenation before ENDs. F1 and F2 are
  the only exceptions.
- writerSessionId matches the trigger exactly (length in code points plus the LIKE layout; 0/1,792
  mismatches). No reader rebuilds `manual-<project>` or pattern-matches these ids except
  `isAutoWritten` (prefix `manual-`), which `~` does not change. No existing row changes id: before
  this range, a uuid-shaped writer id could not be inserted.
- The narrow re-enrich move to `enrich-` is guarded by the same live and `optimized_at IS NULL` WHERE
  clause, and wide keeps `cand.title` and `cand.narrative`. save-enrich writes only lesson, aliases and
  scope. hook-llm's upgrade (:1366) targets its own pre-saved hook row. verify-apply's replacement save
  is user-approved.
- hook-launcher (b7d6f75): both converted stubs publish by rename. The remaining plain-writeFileSync
  stubs are only ever read with existsSync. Negative controls can pass vacuously but cannot go red by
  timing.
