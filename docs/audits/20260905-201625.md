### P1 — 关键功能错误 / 重大可靠性问题

**A20260905-R5-P1-1 · SessionStart 的锁清扫会删掉活进程持有的 `install.lock`，打开安装/自更新的互斥（已证实）**

> **状态：✅ 已修复（第一批，2026-09-05 20:29–20:34 UTC）。** 采用方案 (a)。变更、验证与变异证据见 §10。

- 代码位置与证据：
  - `hook.mjs:2081-2108 cleanStaleLockFiles()`：对 `RUNTIME_DIR` 下所有 `*.lock`，`stale = age > STALE_LOCK_MS`（`hook-shared.mjs:55` = 30 s）；**只有在不 stale 时才检查 pid**，即写入超过 30 s 的锁无条件 unlink。调用点 `hook.mjs:2399`（`handleSessionStart`，每次会话启动）。
  - `lib/proc-lock.mjs:25` 的 `DEFAULT_STALE_MS` = 5 min，且以 pid 存活为主要判据——它假定别人不会替它清锁。
  - 用这把锁的四个写路径都叫 `install.lock`：`install.mjs:3070`（`rebuild-binding`）、`install.mjs:3118`（`repair`）、`hook-update.mjs:895`（`installExtractedRelease`）、`scripts/launch.mjs:82`（MCP 启动时的原生绑定重建）。默认配置下它们与 `RUNTIME_DIR` 是同一目录（`hook-update.mjs:51 STATE_DIR = DB_DIR`；`hook-shared.mjs:47 RUNTIME_DIR = resolveRuntimeDir(DB_DIR)`）。
  - 代码库自己已经知道这个清扫器的行为：`hook.mjs:1948-1958` 解释 auto-maintain 的互斥体**故意不以 `.lock` 结尾**就是为了躲开它，`tests/auto-maintain-proc-lock.test.mjs:198` 用真实 SessionStart 验证了这一点——但 `install.lock` 没有得到同样的处理。
  - **沙箱复现（本轮，`mkdtemp` 数据目录，`CLAUDE_MEM_DIR` 指向沙箱）**：写入 `runtime/install.lock = {pid:<本 shell 存活 pid>, ts: now−31 s}` → `echo '{"session_id":"…"}' | node hook.mjs session-start` → 文件**消失**；对照组 `ts: now−5 s` 同样存活 pid → 文件**保留**。沙箱已删除。
- 影响：`repair` / 自更新 / 绑定重建的临界区通常 30 s–2 min（staging 内 `npm install` 超时 60 s，smoke 内 `npm rebuild` 超时 120 s）。任何一个并行 Claude Code 窗口在这期间启动，就会把锁删掉，第二个安装者随即拿到锁并开始往同一目录 rename——这正是 `lib/proc-lock.mjs` 头注释里描述的"撕裂的混合版本安装（server vN + hook vN+1）"。触发概率不高（需要两个会话且其中一个正在修复/更新），但后果是安装损坏，而且 `swap-in-progress` 标记（`hook-launcher.mjs:130`）只挡读者、不挡第二个写者。
- 最小修复方案（二选一，推荐 a）：
  - (a) `cleanStaleLockFiles()` 改为"pid 存活则不删"：先解析 pid，`process.kill(pid,0)` 成功（或 EPERM）→ 跳过；只有 pid 已死、或文件不可解析且 mtime > 30 s 才 unlink。episode 锁的获取方（`hook-episode.mjs:179-233`）自己按 30 s 年龄抢占，不依赖清扫器，所以行为不变。约 6 LOC，一个文件。
  - (b) 四处 `install.lock` 改名为不以 `.lock` 结尾（如 `install.proclock`），照 auto-maintain 的先例。缺点：升级过渡期新旧版本用不同锁名，恰恰在最需要互斥的那次更新里失去互斥。**不推荐**。
- 验收标准：① 把上面的沙箱步骤写成 `tests/auto-maintain-proc-lock.test.mjs` 同形状的用例（活 pid + 31 s 旧 `install.lock` 经真实 `hook.mjs session-start` 后仍存在；同目录一个死 pid 的 `decoy.lock` 仍被清掉，证明清扫器确实跑了）；② 该用例在改动前红、改动后绿；③ `tests/auto-maintain-proc-lock.test.mjs`、`tests/native-binding-selfheal.test.mjs`、`tests/hook-update.test.mjs` 与全量套件绿。
- 改动风险：低（只收紧删除条件）。前置依赖：无。

**A20260905-R5-P1-2 · `scripts/pre-commit.sh` 的版本同步检查在 HEAD 上就是坏的，整个提交门禁从第一步起从未执行过（第二批提交时发现，已证实并修复）**

- 发现方式：本批提交前跑 `bash scripts/pre-commit.sh`，它以 `❌ Version mismatch: package.json=3.96.1 vs CLAUDE.md=3.96.1` 退出 1——**打印出来的两个值一模一样**。
- 根因：`scripts/pre-commit.sh:14` 的 `CLAUDE_VER=$(grep -oP '(?<=\*\*Version\*\*: )\S+' CLAUDE.md)` 既没锚定行首也没有 `-m1`。CLAUDE.md 里这个字面量出现**两次**：真正的值 `- **Version**: 3.96.1`，以及描述发版守卫那句话里的 `` `**Version**: <v>` ``。于是变量拿到两行（`3.96.1` 和 `` <v>` ``），字符串比较必然不等，而错误消息只显示第一行，所以看起来像"两个相同的值不相等"。
- **不是本批引入的**：`git show main:CLAUDE.md` 跑同一条 grep 同样返回两行，即 HEAD 上就成立。
- 影响：该脚本**每一次调用都在第 1 步失败**，所以它下面的 `npx eslint .`、`npm run format:check`、`npx vitest run` 三道门禁从来没有运行过。没人发现是因为它既没装成 `.git/hooks/pre-commit`（本机确认不存在），CI 也只对它做 `shellcheck`（`ci.yml:67`）、从不执行。任何人把它接成真实 git hook 都会被永久挡住；手动跑的人会照提示去"同步 5 个文件"，而那 5 个文件本来就是同步的。
