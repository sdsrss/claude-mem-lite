## FALSE

### F1. a5af889 提交信息：cut-off key 的 whole-line 覆盖声明，对 `\n` 转义文本不成立

原文：
> "Ending an unterminated key at the next key header is dropped: the whole-line pattern covers the cut-off key"

同一问题也出现在两处代码注释：
- secret-scrub.mjs 注释 "A block whose END is missing is left to the next pattern"
- cut-off 注释 "Whole lines only, so prose naming a header mid-sentence keeps its text"

**问题：** 新的 cut-off pattern 只认真实换行 `\r?\n`。当文本里的换行是字面的 `\n`（JSON 转义）时，情况如下：
- 如果后面还有一个 key header，v6.18.0 和 v6.19.0 都会把 cut-off body 抹掉，tip 却会原样存下。这是相对两个已发布版本的回退。
- 如果后面没有 key header，三个版本都会泄漏（下面的 readResp 用例）。所以提交信息里 "now scrubbed" 这句也只对真实换行成立。

**证据：** `node probes/escaped.mjs probes`，输入为 `JSON.stringify` 过的 cut-off key：

```
v6.18.0/secret-scrub.mjs   readResp leak= true  cutoff+laterKey leak= false
v6.19.0/secret-scrub.mjs   readResp leak= true  cutoff+laterKey leak= false
../tree/secret-scrub.mjs   readResp leak= true  cutoff+laterKey leak= true
```

tracked 文件里就有这种形态的实例（见 M1）：`docs/audits/20260927-v6.19.0-pretag-defect.md` 的 JSON 转义用例在 tip 下输出

```
$ head -c 120 id_rsa\n-----BEGIN RSA PRIVATE KEY-----\nMIIEowIBAAKCAQEAu1SU1Lf...
```

而 HEAD 输出 `***PEM_KEY***`。

**触达面（据此判断严重度）：**
- 活库全部 39,904 个非空 text 字段中，新旧 scrubber 输出不同的有 0 个（`node probes/scrub-diff.mjs probes`）。
- hook.mjs 的 `normalizeToolResponse` 对非 Bash 工具会做 `JSON.stringify(toolResponse)`（hook.mjs:3498）。但 desc 走 `scrubTruncate`，它在 BEGIN 处截断，这条路径被挡住了。
- Read 在 `SKIP_TOOLS` 中。
- 仍然能整段到达 scrubSecrets 的，是 mem_save、import-jsonl 等写入的整段 JSON 文本。
