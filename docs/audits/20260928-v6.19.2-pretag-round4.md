## F1 — P1：空行之后只有一行正文、被引号截断的 cut-off key 整个存储

- 位置：`secret-scrub.mjs:632`（`if (pendingBlank) break;`），它排在 `:638` 的 CUT 分支前面；触发它的是 `:373`（`CUT_MARK_RE` 加了 `["'`]`）和 `:417-445`（`nextLine` 不再在引号处结束行）。
- 机制：7e77ae8 在转义文本中把行结束在字符串结束引号处，所以 `…\n\nlQdGBF…","stderr"` 最后一行的 core 是纯 base64 → `LONG`，而 `LONG` 在 `pendingBlank` 检查之前就被接受了（`:625-631`）。本提交之后这一行变成 `lQdGBF…","stderr":""}` → `CUT`，而 `CUT` 走到 `:632` 时 `pendingBlank` 为 true → `break`，此时 `longs === 0` → `return -1`，整个 key（BEGIN、头部、正文行）都不擦。
- 触发形状（都是真实形状）：PGP 私钥导出时 BEGIN 下面有一个空行（没有 `Version:` 时是 `BEGIN\n\nlQ…`，带 `Comment:` 时是 `BEGIN\nComment:…\n\nlQ…`）；加密 PEM 的 `Proc-Type`/`DEK-Info` 后面也有空行。`head -n 3 key.asc` / `head -n 5 id_rsa` 的输出存成 JSON（tool_response、导入的 transcript）或 Python repr，看到的正文只有一行时触发。第二种变体：正文行之间有空行（双倍行距输出，或者 `\r\r\n`），最后一行被引号截断 → 最后一行（64 字符）存储。
- 实际输出（dabca7d）：
  ```
  F1a PGP head -n 3, JSON
    "{\"stdout\":\"-----BEGIN PGP PRIVATE KEY BLOCK-----\\n\\nlQdGBFXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVy\",\"stderr\":\"\"}"
  F1b encrypted PEM head -n 5, JSON
    "{\"stdout\":\"-----BEGIN RSA PRIVATE KEY-----\\nProc-Type: 4,ENCRYPTED\\nDEK-Info: AES-128-CBC,0123456789ABCDEF\\n\\nMIIEpAIBAAKCAQEAu1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gun\",\"stderr\":\"\"}"
  F1c PGP head -n 3, Python repr
    "{'stdout': '-----BEGIN PGP PRIVATE KEY BLOCK-----\\n\\nlQdGBFXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU3eQo5iKx0wBzNtVy', 'rc': 0}"
  F1d double-spaced body, JSON
    "{\"stdout\":\"***PEM_KEY***\\n\\nKq8xLmN3vB7cZ2dF9gH1jK4lP6oI8uY0tR5eW3qA2sD7fG9hJ1kL3zX5cV8bN0mQ\",\"rc\":0}"
  ```
  7e77ae8 和 0959181 对这四个输入的输出都是 `***PEM_KEY***`（F1a–c 整个 key 被擦，F1d 两行正文都被擦）。
- 因果验证：在副本里把 `:632` 改成 `if (pendingBlank && kind !== CUT) break;`（只用来诊断，不是建议的修法）之后，F1a 输出 `{"stdout":"***PEM_KEY***","stderr":""}`，F1d 输出 `{"stdout":"***PEM_KEY***","rc":0}`。
- 同一根因但不是本提交引入的：真实换行（u=0）或截断标记后跟的 `BEGIN\n\n<64 字符正文> [truncated]` / `…` / CSV `",x`，7e77ae8 和 dabca7d 都整个存储，0959181 会擦（例如 `-----BEGIN PGP PRIVATE KEY BLOCK-----\n\nlQdGBF…Vy [truncated]\n` → 0959181 输出 `***PEM_KEY*** [truncated]\n`，另外两个版本原样保留）。这个问题从 7e77ae8 之前就在（相对 0959181 是回归），修 F1 时应该一起覆盖。
- CHANGELOG 覆盖情况：Known limits 里没有一条说「空行之后的 cut line」会被保留。「A fragment of 15 characters or fewer」说的是短片段，这里被保留的是 64 字符的正文加 header。
- 回归：vs 7e77ae8 **是**（JSON / repr 形状）；vs 0959181 **是**（所有形状）。

## F2 — P2：双重转义字符串里，16–39 字符的末行后跟 `\"` 时存储

- 位置：`secret-scrub.mjs:373`（`CUT_MARK_RE = /^(?: ?…| ?\.\.\.| ?\[| ?<|[`"'])/`）加上 `:417-445`。
- 机制：在 depth 2（`\\n` 换行，JSON 里的 JSON）中，内层字符串的结束引号写成 `\"`，所以紧跟 base64 run 的字符是 `\`，不是引号。于是 16–39 字符的 run 不算 CUT（40+ 仍然算 CUT，因为 CUT 对 40+ 不看后面跟什么）→ `OTHER` → `break`，末行保留。7e77ae8 的 `nextLine` 用 `isStringEnd(r, u)` 识别 depth-u 的转义引号，在那里就结束了行。
- 实际输出（dabca7d）：
  ```
  F2 JSON-in-JSON, last line 30
    "{\"content\":\"{\\\"stdout\\\":\\\"***PEM_KEY***\\\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\\\",\\\"rc\\\":0}\"}"
  ```
  7e77ae8：`{"content":"{\"stdout\":\"***PEM_KEY***\",\"rc\":0}"}`。0959181：整个 key 都保留（它不处理 depth 2）。CRLF 变体（`\\r\\n`）结果相同。末行是 64 字符时（`A2`）三个版本里 dabca7d 和 7e77ae8 都会擦。
- 触发条件：cut-off key 所在的字符串在 16–39 字符的末行后面就结束了，并且这个字符串是 JSON 里的 JSON（MCP 工具结果存成 transcript 等）。泄露量不超过 39 字符的 key 材料；前面的正文会被擦。
- CHANGELOG 覆盖情况：「a fragment of 15 characters or fewer is kept, which includes a short last line followed by more fields」只覆盖 ≤15 字符。16–39 字符的情况比段落写的更差。
- 回归：vs 7e77ae8 **是**；vs 0959181 否（0959181 更差，整个 key 都存）。

## F3 — P2：END 后跟闭合标签时，只有标签后面紧接换行或文本末尾才算「独占一行」

- 位置：`secret-scrub.mjs:394`（`CLEAN_AFTER_END_RE`：标签后面只允许 `[ \t]*`，然后必须是换行或文本末尾），用在 `:749`、`:760`。
- 机制：本提交修 round-3 F6（`<key>\n<tail>\nEND</key>`）时只接受「END + 一个标签 + 换行/结尾」。XML 放在 JSON 字符串里时是 `END</key>"}`，放在代码里时是 `END</key>",`，嵌套标签时是 `END</code></pre>`，这些都不是 clean → 16–39 字符的 tail 行（带数字，满足 `b64ish`）保留。
- 实际输出（dabca7d）：
  ```
  F3 tail, END</key> inside a JSON string
    "{\"x\":\"<key>\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\\n-----END RSA PRIVATE KEY-----</key>\"}"
  F3 tail, END</code></pre>
    "<pre><code>\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\n-----END RSA PRIVATE KEY-----</code></pre>\n"
  ```
  7e77ae8：与 dabca7d 相同。0959181：`{"x":"<key>\n***PEM_KEY***</key>"}` 和 `<pre><code>\n***PEM_KEY***</code></pre>\n`。`END</key>,\n` 以及 `k = "<key>\n…\nEND</key>"\n` 结果相同（dabca7d/7e77ae8 保留，0959181 擦）。
- CHANGELOG 覆盖情况：段落说 END 独占一行时，只有没有数字、`+` 或 `=` 的行才会保留；这里的 tail 行有数字，END 后面只有闭合标签和标点，却被保留了。比段落写的更差。
- 回归：vs 7e77ae8 否（本提交之前就是这样；本提交的修复只覆盖了一种写法）；vs 0959181 **是**。

## F4 — P3：armor 头部行跨过字符串结束引号，擦掉后续 JSON 字段

- 位置：`secret-scrub.mjs:417-445`（`nextLine` 在引号处不再结束）加上 `:622`（`ARMOR` 行不看后面的内容就 `continue`）。
- 机制：`…BEGIN PGP…\nComment: work","note":"the function\n…` 的 armor 行一直延伸到下一个 `\n`，所以后续字段 `"note":"the function` 都属于头部行。下一行只要是整行 base64（16+ 即可，因为 `armors > 0` 时 16–39 字符也算正文，见 `:648`），从 BEGIN 到这一行结尾都会被擦掉，包括其他字段的键名和文本。7e77ae8 在 `"` 处结束头部行，`next = -1`，于是什么都不擦。
- 实际输出（dabca7d）：
  ```
  F4 armor value runs into next JSON field
    "{\"stdout\":\"head -n 2 k.asc\\n***PEM_KEY***\\nis used\"}"
  ```
  输入里的 `","note":"the function\nreadPrivateKeyFromFile` 被擦掉了。7e77ae8 原样保留；0959181 的输出与 dabca7d 相同。第二个例子：`{"stdout":"BEGIN PGP…\nVersion: GnuPG v2","next":"commit\n3f2a…(40 hex)\nmore text"}` → dabca7d 和 0959181 都输出 `{"stdout":"***PEM_KEY***\nmore text"}`，7e77ae8 原样保留。
- 与本提交注释的关系：`:350-351` 写的是「A header value that runs on into the next JSON fields is still one header line, so it erases nothing without a base64 line under it」。这里的「base64 line」可以在另一个字段里，也可以是标识符或 git SHA。CHANGELOG 说 6.19.1 会擦「the JSON fields after a cut header value」，而这个形状下 dabca7d 的行为与 6.19.1 相同。
- 触发条件：cut-off 恰好停在 armor 头部行，并且后面某个字段的下一行整行是 16+ 字符的 base64 字符集。低。
- 回归：vs 7e77ae8 **是**；vs 0959181 否。

## F5 — P3：`END</code>` 现在算独占一行，HTML 行内代码里带数字的标识符被擦

- 位置：`secret-scrub.mjs:394`（标签分支）加上 `:759-760`。
- 机制：每行都包在 `<code>…</code>` 里时，`<code>` 被当作行前缀（上一行开头相同 → `prefixed`），END 后面的 `</code>` 现在满足 `CLEAN_AFTER_END_RE`，`lineCore` 又会剥掉上一行的 `</code>`，所以 `utf8ToBase64Encoder`（有数字 → `b64ish`）被当作 key 的最后一行。
- 实际输出（dabca7d）：
  ```
  F5 <code> lines, digit identifier over END
    "<code>***PEM_KEY***</code>\n"
  F5b <p> block, digit identifier over END</p>
    "<p>\n***PEM_KEY***</p>\n"
  ```
  7e77ae8：两个输入都原样保留。0959181：F5 保留，F5b 擦。
- CHANGELOG 覆盖情况：段落说 END 写在句子或行内代码里时，除非上一行以 key 编码开头或下面有 PGP 校验和，否则上一行会保留。`<code>…</code>` 就是行内代码，却被擦了。比段落写的更差。F5b（`</p>`）属于「END 独占一行时，有数字的行不保留」，在段落范围内。
- 回归：F5 vs 7e77ae8 **是**、vs 0959181 **是**；F5b vs 7e77ae8 **是**、vs 0959181 否。

## Q3 — 超线性 / 抛异常 / 不动点

- 两个套件在 dabca7d 上都是绿的（153 passed）。
- 自造的 20 多种 200k 输入，dabca7d 与 7e77ae8 在 50k / 100k / 200k 下的耗时（ms）：`quotesAfterBegin` 1.4→2.8、`armorQuoteRepeat` 3.8→7.0、`armorChainBegins`（转义换行，每个 armor 行里放一个 BEGIN）3.6→7.2、`blankThenBegins` 2.3→4.8、`escQuoteDepth2` 1.1→2.3、`tailTagSpaces`（`END</a>` + 200k 空格 + `x`）0.8→1.6、`tailLongTagName` 3.7→7.5、`concatNoBreak` 2.6→5.0、`backslashRunBegins` 4.3→9.1、`armorBeginsQuoteBlanks`（armor 行里放 BEGIN，中间夹 `"\n` 空行）4.1→6.4、`quoteBlanksAfterBegin` 2.3→4.4。输入长度翻倍，耗时约翻倍，200k 时没有一个超过 10 ms。每个输出 `scrub(out) === out`。
- 结构论证：`nextLine` 仍然每个字符最多访问一次。去掉引号结束之后，行可以跨过引号，但每个 BEGIN 最多走 16 行 armor，外加空行；一行正文就返回。空行和正文行里不可能有 BEGIN（BEGIN 行本身是 OTHER），所以每一行最多被约 17 个 BEGIN 走过。
- 随机组合 fuzz（从 40 个左右的 token 里取 3–12 个拼接，包括 BEGIN/END、各层转义换行、引号、`\"`、标签、行前缀、`…`），共约 160 万次，其中含 `PRIVATE KEY` 的输入都检查了 throw 和 `scrub(scrub(x)) === scrub(x)`：throws 0，非不动点 0。
- CONCAT 续行（`"…\n" +⏎ "…"`、Python 隐式拼接）与 7e77ae8 的行为相同（见 Q1）。
