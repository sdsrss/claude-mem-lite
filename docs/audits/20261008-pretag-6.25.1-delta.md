## P2-1: A journal that recovery leaves for a read error is replayed later over a newer committed swap and leaves a mix (contract 1)
The mechanism is CONFIRMED. EACCES from chmod 000 stands in for a transient read error. The trigger is PLAUSIBLE.

- Sites:
  - hook-update.mjs:977-985: `recoverInterruptedSwaps` hits a non-ENOENT read error, `continue`s, and leaves the dir
    unresolved. The delta added this branch (595318aa).
  - hook-update.mjs:1157: `installExtractedRelease` then goes ahead with a new swap over the half-swapped tree and
    commits it. Nothing retires the dir it left.
  - Later, when the journal can be read again, every replayer runs the old journal over the newer tree:
    recovery at the next update entry, `cleanup`, and `install`/`repair`.
- Repro, scripts/transient-read.mjs and transient-read2.mjs. Setup: swap S1 (vA->vB) was killed with hook.mjs moved
  out, and its journal cannot be read. Swap S2 installs vC and commits. The journal then becomes readable.
  ```
  tree:  S2 committed: true {"hook":"// vC hook","server":"// vC server","residue":[".update-backup-1000-1"]}
         after next recovery: 1 {"hook":"// vA hook","server":"// vC server","residue":[]}      <- MIXED
  doctor: ⚠ Unfinished update: 1 backup dir(s) ... still hold a swap journal ... (run: ... cleanup ...)
  cleanup: ✓ Finished an interrupted update: .update-backup-1000-1 (put back the files it had moved out)
           hook.mjs: // vA hook | server.mjs: // vC server                                      <- MIXED
  2f003bb6: recovery read the dir as "nothing moved" and deleted it; vC stays whole.
  ```
  The delta changed this case from "an obsolete copy of vA is lost" to "two releases are mixed later".
  doctor's own advice (cleanup) leads there.
- Triggers:
  - Windows: a process holding the journal with no read sharing gives EBUSY or EPERM. This is the same scanner class
    the delta's own retry rationale assumes.
  - Any OS: EMFILE or EIO.
  - Root-owned journal with mode 600: a `sudo` run with umask 077 is killed mid-swap, and a later chown makes the
    journal readable. That chown is the fix `dataDirAccessRemedy` names.
- Where the mix stays:
  - After `cleanup`.
  - After an update entry whose own new swap then fails its check, because that rollback restores the mixed tree.
  - An update entry whose new swap commits heals it.
- Fix direction, one of:
  - (b), preferred: once a swap commits, mark resolved every backup dir that was unresolved when it started. The
    committed swap replaced every switchable path, so this does in the updater what `retireLeftoverJournals` does in
    install. It also clears the obsolete unparseable dirs, so doctor stops asking for `repair` after a later
    successful update.
  - (a): on a read error, stop this update entry before staging and retry at the next entry. doctor and repair are the
    exit when the error persists.

## P3-1: The resolved marker is not guaranteed to outlive a journal that stays (contract 1)
PLAUSIBLE. This is reasoned; the ordering is measured on ext4 only.

- Site: hook-update.mjs:900-919.
  - When the journal rm fails and the marker was written (`resolved` true), `rmSync(backupDir, {recursive})` runs.
  - That recursive rm removes children in raw directory order and stops at the first error. It removes the marker
    too, so "inert" holds only if the journal comes before the marker in that order.
- Evidence, scripts/rmprobe.mjs on Node 26 / ext4. A recursive rm over a dir with a child that cannot be removed:
  ```
  readdir order [.swap-journal.json.f, .swap-resolved.f, a.f, lib.f, locked, m.f, node_modules.f, z.f]
  err EACCES  survivors [lib.f, locked, m.f, node_modules.f]   (both dot-files removed before the failure)
  ```
  On another ext4 dir, the raw `ls -U` order put `.swap-journal.json` before `.swap-resolved`. That order is a hash
  and varies per filesystem.
- On NTFS, enumeration is collated by name and `.swap-journal.json` sorts before `.swap-resolved`. A held journal
  therefore stops the rm before it reaches the marker, provided `remove_all` stops at the first error; that is NOT
  CHECKED on Windows. On ext4/APFS the trigger (journal unlink fails while a file can be created in the same dir) is
  very unlikely.
- If the order is wrong, or a kill lands in the rm after a failed journal rm, the result is: the journal stays,
  the marker is gone, and some backups are gone. A replay then gives a mix.
- The test "a committed swap whose journal cannot be removed" makes the fault throw before any child is removed. It
  therefore cannot say NO to the order. The kill sweep treats every rm as all-or-nothing.
- Fix: when the journal rm failed, remove the dir's other children explicitly, skipping SWAP_JOURNAL and
  SWAP_RESOLVED. Do not use rm -r on the dir.

## P3-5: The marker now discards the backup that a failed restore still needs, when the journal also cannot be removed (D#293 interplay)
CONFIRMED by reading: diff of discardBackupDir at 2f003bb6 against 9b8a92f6.

- 2f003bb6: when the journal rm failed, it returned early and kept the backups complete. The next recovery then
  retried the failed restore.
- Now: the marker is written, so the backups are removed even though the journal stays, and the marker stops any

- The case: a restore fails inside a rollback, and the journal rm fails too. On Windows both come from the same kind
  of file holder, so they tend to occur together.
- This is not a separate root cause; it narrows the accidental shelter around the known open item (D#293).
- Fix: as D#293 (rollbackInstall reports failed restores, and discard is skipped then). Nothing extra is needed if
  D#293 lands.

## Q1: Can a path in the delta break contracts 1–3? Ordering and kill points

- Commit path, order: marker → journal rm → backup rm -r → staging rm. Kill points:
  - Before the marker (microseconds after the smoke pass): replay → whole OLD. "committed" lives only in memory.
    Not a mix.
  - After the marker: discard, NEW.
  - After the journal rm: no journal, stale. NEW.
  - In the staging rm: residue only.
  - Reproduced by the killpoint sweep: every kill from the marker write on recovers to NEW.
- Rollback path: rollbackInstall → the same discard. Kill points are idempotent through the D#283 `restored` set.
  Reproduced by the sweep.
- Torn or failed journal write: temp + rename. The old journal stays whole. A persistent failure throws after about
  0.7 s → rollback with the in-memory arrays (pin test green).
- Failed journal removal: covered by the marker, with the order caveat in P3-1. Failed marker plus failed journal rm:
  backups stay complete, and a replay restores whole OLD. Reachable only when the dir cannot be written.
- Breaks found:
  - P2-1: a read-error journal is replayed over a later swap.
  - P3-1: the order is assumed.
  - P3-6: install's retire window.
- Contract 2: P3-7 (non-directory names). The read-error class agrees in the moment, but its later replay is P2-1.
- Contract 3:
  - Holds after `retireLeftoverJournals` succeeds.
  - It does not hold where the retire write fails (a warning names it), or in the P3-6 kill window.
  - Older code (6.25.0's install, cleanup or updater) ignores `.swap-resolved` and would replay a retired journal.
    Reasoned; this matters only on a downgrade or for an older copy that runs cleanup.
- Windows (all reasoned):
  - journalSwap: rename-over EPERM is retried.
  - Marker creation needs no handle on the journal.
  - A held journal plus NTFS collation: rm -r stops at the journal before the marker, assuming `remove_all` stops at
    the first error.
  - A loaded `.node` in the old node_modules inside the backup: rm -r removes the marker (it sorts early), then
    stops. The journal is already gone, so the dir is stale and is never replayed.
  - A delete-pending journal reads as EPERM: recovery leaves the dir until the name goes, then the dir is stale.

## Q2: Does the marker or the retry introduce a new failure?

- A marker is written on a dir that still needed replay only in these cases:
  - After a rollback whose restore failed (D#293). The delta widened this to the journal-rm-failed sub-case (P3-5).
  - install's retire before npm install (P3-6).
  - Otherwise the marker goes only on dirs whose swap committed or was rolled back, or which install retired after
    deploy.
- The retry:
  - It is bounded at 8 attempts, about 0.7 s of sleep (25·(1..7) ms). It then rethrows (killed by H8; pinned by
    "keeps failing").
  - It does not hide a persistent error: EACCES on Linux costs 0.7 s, then the swap stops and rolls back.
  - The sleep runs only on error. Worst case: every one of about 324 journal writes fails 7 times, about 3.8 min.
    That would outlast the swap marker's 2-minute staleness bound, but it is not realistic.
