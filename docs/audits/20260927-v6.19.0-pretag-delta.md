## Findings

### P2-A: the head cut can land inside a closed `<private>` span and store its content (a regression from 5203463)
utils.mjs:295-308 (unpairedPrivateMarks) + utils.mjs:310-315 (scrubTruncate).
The scanner tracks `<private>` and PEM marks independently and cuts at the smaller unpaired opener. A PEM BEGIN with no
END inside a PAIRED `<private>…</private>` is "unpaired", so the cut falls inside the span. The cut then removes the
`</private>`, so stripPrivate no longer redacts the span's first half. Before 5203463 the same input stored `[redacted]`.
```
node PR/desc-leak.mjs
1 HEAD desc   : "c → ok <private>TOTP 481-992"            (resp 'ok <private>TOTP 481-992 -----BEGIN RSA PRIVATE KEY-----</private> done')
1 pre-cut path: "ok [redacted] done"                          (= 08fb763's truncate(_scrubSecrets(win)))
1 Edit desc   : "notes.md: \"<private>vault pin 7731\" → \"x\""
```
This affects every scrubTruncate field (Edit old/new, Bash cmd, Grep, Agent, Web*, default). The mirror case, a `<private>` opener
inside a complete PEM block, cuts the block's END off and the new PEM regex then keeps the body (no END, no later BEGIN).
Fix: repeat the scan on the cut window until it finds no unpaired opener (each cut is shorter, so it terminates within 4096 chars).
Alternatively, ignore PEM marks that fall inside an open tag span.

### P2-B: a PEM key with no END that ends the text stays unscrubbed, and the new Bash tail shows it
secret-scrub.mjs:205-208; utils.mjs:330-333.
The new PEM regex ends a block at its END or at the next `-----BEGIN `. A cut-off key with NO later BEGIN (the plain
`head -c N key`, a truncated `gpg --export-secret-keys`) still does not match, so its body is kept in whole-text scrubs.
This gap already existed in v6.18.0. The v6.19 Bash tail (#37) adds a new surface: when the BEGIN lies more than 4096 characters before the
end, the tail window contains no mark, so the P3-1 check passes and the stored description shows the key's last ~49 characters:
```
node PR/desc-leak.mjs
2 len 5867 desc: "c → $ gpg --armor --export-secret-keys | head -c 6000…t6uE1oF2gH3jI5kL0mN9bV8cX7zA6s TAILKEYMATERIALxyz"
2 whole-text scrub keeps body: true
```
v6.18.0's description was the 60-character head only, so this exposure is new in v6.19.0. The same holds for an unclosed
`<private>` longer than the tail window (case 3: `"c → start…qqqq… SECRET-PIN-4412"`). stripPrivate leaves unclosed
openers by design, but the head cut treats the same opener as private, so the two ends disagree (P3 on its own).
Fix: add `|$` to the PEM END alternation. A header with no END then runs to the next BEGIN or the end; I did not time this
variant, but the regex shape suggests it stays linear. In scrubTruncateEnds, also scan `str` from DESC_SCRUB_WINDOW to the
tail start, or all of `str`, for an unpaired opener before showing a tail. That scan is linear and bounded by the hook stdin cap.

### P3
- P3-1 JWT regression vs v6.18.0 is only partly closed (secret-scrub.mjs:195). Still stored in plaintext; `\b` in v6.18.0 caught all of these:
  `cookie: my-sess-<jwt>`, `X-Auth-Token-<jwt>`, `sess--<jwt>`, and a 41+ character word before the hyphen (`node PR/jwt-pem.mjs`).
  The commit scopes its claim to "one word", so the claim is accurate. The regression is wider than the fix.
- P3-2 New PEM false positive (secret-scrub.mjs:205). A bare key header in prose followed by ANY later BEGIN, including CERTIFICATE or
  PUBLIC KEY, now erases all the text between them: `Keys start with -----BEGIN RSA PRIVATE KEY----- and certs … with -----BEGIN CERTIFICATE----- ok` →
  `Keys start with ***PEM_KEY***-----BEGIN CERTIFICATE----- ok`. v6.18.0 and 08fb763 left it intact. The distance is unbounded.
- P3-3 The scanner is case-insensitive but the scrubber is not (utils.mjs:295 `/gi` vs secret-scrub.mjs PEM `/g`). Lowercase
  `-----begin rsa private key-----` in docs cuts the head: `"docs: -----begin rsa private key----- is lowercase … VERDICT"` → `"docs:"`.
  A literal unclosed `<private>` (grep over this repo's sources) cuts every description field the same way, and in a ≤4096-character
  output it also drops the verdict. These cuts err on the safe side, so they cost false positives, not leaks (`node PR/desc-edge.mjs`).
- P3-4 Text is duplicated or an ellipsis appears when the windows overlap (4096 < len < 8192) and the content is short (utils.mjs:327-341):
  `' '*4000 + 'npm test: 12 passed' + ' '*80` → `"npm test: 12 passed…npm test: 12 passed"`; `' '*4090+'ABCDEFGH'` → `"ABCDEF…ABCDEFGH"`;
  5000 spaces → `"…"` (08fb763 returned `''`); `'hello world'+' '*4990` → `"hello world…"`. Budget held: 20,000 fuzz cases, 0 over
  100 characters, 0 with more than one ellipsis (`node PR/desc-fuzz.mjs`).
- P3-5 A lone HIGH surrogate at the head window's edge (existed before this delta; the delta keeps it). `' '*4095 + '😀' + 'x'*10` →
  snippet code units `d83d 2026 …` (`"\ud83d…😀xxxxxxxxxx"`). `str.slice(0, DESC_SCRUB_WINDOW)` is not guarded, and truncate only
  guards a cut it makes itself. The comment "truncate guards the head side" (utils.mjs:336) is therefore MISLEADING. The same slice feeds every scrubTruncate field.
- P3-6 Two new branches have no test that can fail. (a) Mutation M5, which deletes the "head gets an ellipsis before the tail" logic (utils.mjs:339-341): 279/279 pass.
  (b) Mutation M6, which drops the tail's `marks.openAt >= 0` arm (utils.mjs:333): 279/279 pass. That arm is what hides a cut-off key that starts inside the
  tail window, and no case covers it.
- P3-7 The test and the comment disagree on the incident's magnitude. tests/search-core.test.mjs:367-376 and lib/search-core.mjs:419-420 say
  "(0.18) scored 1.35e-4", but the test uses score -1.35e-5 and rawScore -6.8e-4, both 10x smaller. At the claimed 1.35e-4, the 1e-3→1e-4
  threshold change ALONE already stops the lift, so the test covers a different point than the one the comment describes.

- P3-9 A comment sits on the wrong test (tests/utils.test.mjs:1224-1227). The "P3-1 private block longer than the tail window" comment heads the F2
