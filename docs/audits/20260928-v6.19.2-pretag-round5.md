## Finding 1 (P2): F4 stops the key on armor values that contain a quote, a comma and a quote. Whole key stored

`secret-scrub.mjs:399` (`STRING_THEN_FIELD_RE`), used at `secret-scrub.mjs:629`:

```js
const STRING_THEN_FIELD_RE = /(?<!\\)["']\s*(?:,\s*\\?["']|[}\]])/;
...
if (kind === ARMOR && u > 0 && STRING_THEN_FIELD_RE.test(core)) break;   // longs === 0 → return -1
```

The test runs on the whole armor line and cannot tell a string's closing quote from a quote inside the
header value. Two kinds of quote pass the `(?<!\\)` lookbehind:
- any single quote in a JSON string at any depth, because JSON never escapes `'`;
- any double quote in a Python repr or bytes repr, because a single-quoted repr does not escape `"`.

So when `Comment: ['work', 'home']`, `Comment: say "hi", "bye"`, `X-Tags: 'a', 'b'` or a mid-line `"]`/`'}`
appears in escaped text, the scan stops at `longs === 0`, `cutOffKeyEnd` returns -1, and the key body under it
is stored. A trailing `"}`/`']` at the end of the value does not trigger it, because `lineCore` strips it
first. Only a match in the middle of the line does. gpg writes any `--comment` string into the armor, and the
X- headers written by tools are free-form.

Repro (harness in the appendix; `node zz_scratch/repro.mjs` in a worktree at 060fd6b):

```
R1a repr, Comment: keys ["work", "home"]
    NEW leaked 3/3 | OLD leaked 0/3 | REL leaked 0/3
R1b JSON, Comment: ['work', 'home']
    NEW leaked 3/3 | OLD leaked 0/3 | REL leaked 0/3
R1c JSON in JSON, Comment: 'a', 'b'
    NEW leaked 2/2 | OLD leaked 0/2 | REL leaked 2/2
R1d repr, Comment: say "hi", "bye"
    NEW leaked 3/3 | OLD leaked 0/3 | REL leaked 0/3
```

The input for R1b is `JSON.stringify({stdout: PGP_BEGIN + "\nComment: ['work', 'home']\n\n" + 3 body lines, rc: 0})`.
The output keeps all three 51–64-character body lines verbatim.

Attribution: a fuzz of 3 seeds × 30,000 inputs (generator in the appendix) found 30, 52 and 41 inputs where
NEW leaks a key window that OLD scrubbed. Every one of them stops being a leak when only the line at `:629`
is removed (mutant `mut4`), and none does when F1, F2 or F3 is reverted instead.

Regression vs b85920f: yes. vs 0959181: yes (R1a/b/d; for R1c, v6.19.1 leaked too).

## Finding 2 (P2): identical cut keys, one per pass. Past the cap they are stored and the result is not idempotent

This comes from how `cutOffKeyEnd` takes the BEGIN line's prefix (`secret-scrub.mjs:596-607`). When a cut key
is glued to the next BEGIN (`…<cut run>-----BEGIN …`), the next BEGIN's "line prefix" is the previous key's
cut line. `prefixShape` turns it into a regex (only digits are wildcarded). When the body line under that BEGIN
is the same text, `lineCore` strips it as a prefix and leaves `-----BEGIN…` behind, which is OTHER, so that
key is skipped in that pass. Each pass therefore scrubs only the first remaining key. With 33 or more copies,
`MAX_SCRUB_PASSES = 32` leaves the rest, and a second `scrubSecrets` call scrubs further. The content left is
the key's own first body run, 20–58 characters in these repros.

The commit extends this to shapes where OLD scrubbed nothing, now scrubs 32 and stores the rest:
- F1 lets a cut line after a blank line (PGP, encrypted PEM) end a key;
- F2 lets `\"` end a cut line.

The shapes without a blank line were already affected in b85920f. v6.19.1 clears all of them.

```
R3a same PGP key, head -c 90, glued x40 (JSON)
    NEW leaked 1/1 NOT-IDEMPOTENT | OLD leaked 1/1 | REL leaked 0/1
R3b same PGP key, head -c 90, glued x40 (raw)
    NEW leaked 1/1 NOT-IDEMPOTENT | OLD leaked 1/1 | REL leaked 0/1
R3c same RSA key, head -c 80, glued x40 (raw, no blank)
    NEW leaked 1/1 NOT-IDEMPOTENT | OLD leaked 1/1 NOT-IDEMPOTENT | REL leaked 0/1
R3d escaped, blank, 20-char run + \" x40
    NEW leaked 1/1 NOT-IDEMPOTENT | OLD leaked 1/1 | REL leaked 0/1
    R3b NEW: BEGIN left after 1/2/3 calls = 8/0/0
```

Counts of BEGINs left after one call, for 40 copies (`zz_scratch/q5b.mjs`):

| unit ×40 | NEW | OLD | REL |
|---|---|---|---|
| u0, no blank, `<20-run>"x ` | 8, not idempotent | 8, not idempotent | 0 |
| u0, blank, `<20-run>"x ` | 8, not idempotent | 40 | 0 |
| u1, no blank, `<20-run>\"x ` | 8, not idempotent | 40 | 0 |
| u1, blank, `<20-run>\"x ` | 8, not idempotent | 40 | 0 |
| u0, blank, `<50-run> x ` | 8, not idempotent | 40 | 0 |
| u0, no blank, `<50-run> x ` | 8, not idempotent | 8, not idempotent | 0 |
| u0, blank, `<20-run> [truncated] ` | 8, not idempotent | 40 | 0 |
| u2, blank, `<20-run>\\\"x ` | 8, not idempotent | 40 | 40 |

It needs the same key cut the same way 33 or more times, glued without a break. For example,
`for i in $(seq 40); do head -c 90 key.asc; done`, or a repeated log line. Different keys do not trigger it:
the glued output of `head -c 80`/`170` over 60 distinct keys scrubbed all of them in all three versions.

Regression vs b85920f: widened, as the table shows. vs 0959181: yes.

## Finding 3 (P2, not introduced): `tail -n 2` inside a tool-result object with later fields

`secret-scrub.mjs:397/760-761`. `CLEAN_AFTER_END_RE` requires a break or the end of the text after the
quote/punctuation/tag run. In a JSON or repr object, the string's closing quote is followed by the next
field (`","stderr":""`, `', 'rc': 0}`), so an END that is alone on its line in the decoded text is not
"clean". The single 16-39 line above it has digits and is still kept.

The Known limits paragraph says such a line is kept only "when it has no digit, `+` or `=` padding". Here it
has digits and is kept anyway, which is worse than the paragraph says.

The Bash tool-result object in a transcript usually carries stdout without its trailing newline, so this
shape is common. Round 4's F3 widened the characters after an END but not this case.

```
R5a Bash JSON {stdout,stderr,interrupted}
    NEW leaked 1/1 | OLD leaked 1/1 | REL leaked 0/1
R5b repr {'stdout':…, 'rc': 0}
    NEW leaked 1/1 | OLD leaked 1/1 | REL leaked 0/1
R5c same, stdout ends with a newline (control)
    NEW leaked 0/1 | OLD leaked 0/1 | REL leaked 0/1
```

R5a input: `JSON.stringify({stdout: "$ tail -n 2 k.pem\n" + L30 + "\n-----END RSA PRIVATE KEY-----", stderr: "", interrupted: false})`,
where L30 = `Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU`. NEW output:
`{"stdout":"$ tail -n 2 k.pem\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\n-----END RSA PRIVATE KEY-----","stderr":"","interrupted":false}`.
It also leaks at depth 2 (`JSON.stringify({c: JSON.stringify({stdout: L30+"\n"+END, rc: 0})})`) in all three versions.

Regression vs b85920f: no. vs 0959181: yes.

## Finding 4 (P3): F1 erases prose across any number of blank lines

`secret-scrub.mjs:643-650`. The CUT branch now comes before `if (pendingBlank) break`, so a cut line after
blank lines joins the key. The line that joins can be:
- after a key body;
- after a bare header, when the run is 40+, starts like a key encoding (`MIG…`), or armor headers came first;
- after 100 blank lines, as in R4b.

The erased span includes the blank lines, so the rest of the prose line is glued to `***PEM_KEY***`. The Known
limits sentence says "Right after a key header or body…", which does not tell a reader that blank lines in
between do not help.

```
R4a body, blank, ConcurrentHashMap<K,V>
    NEW lost 2/2 | OLD lost 0/2 | REL lost 2/2
    (NEW output: "$ head -3 id_rsa\n***PEM_KEY***<K,V> is thread-safe")
R4b body, 100 blank lines, git log --format="%H %s" line
    NEW lost 1/1 | OLD lost 0/1 | REL lost 1/1     (NEW: "***PEM_KEY*** docs: archive")
R4c header only in prose, blank, SHA line
    NEW lost 1/1 | OLD lost 0/1 | REL lost 1/1     ("The file begins with ***PEM_KEY*** docs: archive")
R4d PGP header + Version, blank, identifier[0]
    NEW lost 1/1 | OLD lost 0/1 | REL lost 1/1     ("***PEM_KEY***[0] = 1")
```

In the fuzz, reverting F1 alone (mutant `mut1`) removes 47, 49 and 56 of the extra prose-loss inputs per
30,000. v6.19.1 did the same, so the new code only restores that behaviour.

Regression vs b85920f: yes. vs 0959181: no.

## Finding 5 (P3): F4 is blind two escapes deep

`secret-scrub.mjs:399`. At depth 2 a string ends at `\"`. The lookbehind `(?<!\\)` rejects exactly that
quote, and the next field's opening quote is also `\"`. So the repair does nothing one level down, while
single quotes still trip it at any depth (Finding 1).

```
R2a depth 1 (the commit test)          NEW lost 0/2 | OLD lost 2/2 | REL lost 2/2
R2b same object one level deeper       NEW lost 2/2 | OLD lost 2/2 | REL lost 0/2
```

In R2b (`JSON.stringify({c: JSON.stringify({stdout: "head -n 2 k.asc\n"+PGP_BEGIN+"\nComment: work", note: "the function\nreadPrivateKeyFromFile\nis used"})})`),
NEW outputs `…head -n 2 k.asc\\n***PEM_KEY***\\nis used\"}"}`. The `note` key and its first two lines are gone.

Regression vs b85920f: no. vs 0959181: yes.

## Finding 6 (P3, not introduced): HTML-escaped and attribute shapes

`secret-scrub.mjs:374` (CUT_MARK_RE) and `:397` (CLEAN_AFTER_END_RE):
- CUT_MARK_RE has no `&quot;`, so a 16-39 last line before `&quot;` is not a cut line;
- CLEAN_AFTER_END_RE accepts neither `/>` nor whitespace inside a closing tag.

```
R6a &quot; after a 30-char last line      NEW leaked 1/1 | OLD leaked 1/1 | REL leaked 0/1
R6b END then "/> (XML attribute)           NEW leaked 1/1 | OLD leaked 1/1 | REL leaked 0/1
R6c END then </key > (space in close tag)  NEW leaked 1/1 | OLD leaked 1/1 | REL leaked 0/1
```

The Known limits paragraph covers an END "named in a sentence or in a backtick code span". An XML attribute
or HTML-escaped JSON is neither. Regression vs b85920f: no. vs 0959181: yes.

## Finding 7 (P3): the commit message's fuzz claim does not hold

The commit message says: "Differential fuzz, 3 seeds x 20,000 inputs: never leaks more or loses more prose
than b85920f".

My generator mixes BEGIN/END lines, armor lines (including quoted values), blank lines, 16–64 body lines,
cut lines with 10 marks, END trailers, JSON field breaks and prose, in 5 containers
(raw/JSON/JSON²/repr/Read-tool). Per 30,000 inputs (seeds 11/22/33):

| | seed 11 | seed 22 | seed 33 |
|---|---|---|---|
| NEW leaks a window OLD scrubbed | 30 (all F4) | 52 (all F4) | 41 (all F4) |
| NEW loses prose OLD kept | 188 (F3 82, F2 53, F1 47, F1+F2 6) | 183 (F3 80, F1 49, F2 45, F1+F2 9) | 174 (F1 56, F3 59, F2 49, F1+F2 10) |
| throws / not idempotent / >50 ms | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |

Attribution method: an input counts toward a change when reverting that change alone brings NEW back to no
worse than OLD. I checked samples of each group:
- the F2 prose losses are documented: a 16-39 run followed by a quote (JSON `\"`), or one under
  `Proc-Type`/`Version` headers;
- the F3 losses are documented: an identifier with a digit above an END that is clean after `\"`, `"}` or a
  closing tag;
- the F1 losses are Finding 4;
- the leaks are Finding 1.

A note on my own tooling: my first fuzz run used `seed * 1103515245` in doubles. That loses precision and
collapsed seeds 1/2 onto one sequence, so it reported 0 extra leaks. Only the `Math.imul` version above
counts.

## Per-question notes

**Q1 (F1, cut line after blank lines).**
- Leak side: a matrix of 7 key kinds × body lengths 1–3 × last line 16/20/39/40/41/64 × 5 marks
  × single/double spacing × 15 containers = 18,900 inputs (`zz_scratch/matrix.mjs`). Containers: raw, CRLF,
  JSON, JSON with stdout as the last field, JSON², JSON³, repr, repr list, bytes, Read-tool, JSON Read-tool,
  `<pre>`, JSON of `<pre>`, shell `echo "…"`.
- Results: NEW 150 leaks, OLD 9,300, REL 6,300. NEW never leaks where OLD did not. All 150 NEW leaks (and all
  100 that REL does not have) are a lone 16-character OpenSSH line with no key-encoding start, which the
  paragraph documents.
- Prose side: Finding 4.

**Q2 (F2, `\"` as a cut mark).**
- Leak side: depth 2 and depth 3 last lines, repr inside JSON, and JSON inside repr are all scrubbed now.
  The one leak left is `&quot;` (Finding 6).
- Prose side: in JSON, `word\"` is a decoded `word"`, which already counted in raw text, so the new losses
  (for example `configurationFileName\" is missing` under a key body) fall under the documented "a quote
  follows".
- In real-break text, `\"` is new (`configurationFileName\" is missing` after a body loses its first word,
  as v6.19.1 did). This is documented too.
- Interaction: F2 widens Finding 2.

**Q3 (F3, END followed by a mix).** These now count as alone and scrub in both depths:
- `\"`, `\"}`, `</key>\"}`, `</a></b></c>`, `\")`, `\'`, `\\"`, `</key>"`, `"\t]`;
- in raw text, `</a></b>` and `</key></data>"}`.

Not covered: Findings 3 and 6. The prose side (an identifier with a digit over a clean END) is documented.
Minor: an END followed by U+00A0 is not clean (found by accident; no finding).

**Q4 (F4).** Findings 1 and 5. Three cases keep prose loss in all three versions:
`const a = "…Comment: x"; const b = "\nreadPrivateKeyFromFile\n";`, `f("…Comment: x", "\nreadPrivate…")` and
`{"…Comment: x": "…"}`. The first two are not string-then-field shapes, and the last is a string used as a key.

**Q5 (performance, throws, idempotence).** Times are for one `scrubSecrets` call on 200k characters
(`zz_scratch/perf.mjs`), NEW / OLD / REL:
- BEGIN + 200k blank lines + cut: 12 / 5 / 5 ms.
- (BEGIN + 20 blanks) ×N: 7 / 7 / 6 ms.
- Escaped Comment with 200k quotes: 5 / 3 / 1 ms. With `" …, …` runs of 500 spaces: 2 / 2 / 1 ms.
  With `\"` runs: 3 / 3 / 1 ms.
- Cut run + 200k backslashes: 3 / 2 / 4 ms.
- END + 200k backslashes: 3 / 3 / 4 ms. END + `\"` runs: 4 / 4 / 8 ms. END + `</a>` runs: 2 / 2 / 5 ms.
- END + 40-character partial tags: 8 / 8 / 16 ms.
- (tail + END + tags) ×N: 5 / 6 / 3 ms.
- The one slow case is `(BEGIN\n\n + 20-run\" )` ×N: 256 / 8 / 4 ms. It is linear (25k: 50 ms, 100k: 130 ms,
  200k: 256 ms, 400k: 513 ms) and is Finding 2 running all 32 passes, not a superlinear pattern.
- Random 200k mixes in 5 containers (`zz_scratch/big.mjs`): NEW 11–21 ms against OLD 11–15 ms, idempotent.
- No throw in 90,000 fuzz inputs or in the crafted inputs.

`repro.mjs`: each case is `vs(name, input, secrets, prose)`. It runs NEW, OLD and REL and prints, for each:
- how many `secrets` substrings survive;
- how many `prose` substrings are missing;
- `NOT-IDEMPOTENT` when `f(f(x)) !== f(x)`.

The inputs are the ones quoted under each finding (R1a–R6c). For example:

```js
vs("R1b", JSON.stringify({ stdout: `${PH}\nComment: ['work', 'home']\n\n${[P1,B2,B].join('\n')}`, rc: 0 }), [P1,B2,B]);
vs('R3b', `${PH}\n\n${P1}${B2}`.slice(0, 90).repeat(40), [P1.slice(0, 40)]);
vs('R5a', JSON.stringify({ stdout: `$ tail -n 2 k.pem\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\n${E}`, stderr: '', interrupted: false }), ['Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU']);
```

Fuzz attribution: four mutants of NEW, each reverting exactly one change:
- F1: `if (pendingBlank) break;` put back before the CUT branch;
- F2: CUT_MARK_RE without `|\\+["']`;
- F3: the old CLEAN_AFTER_END_RE;
- F4: line 629 removed.

An input is attributed to a change when that mutant is no worse than OLD on it. The random generator uses
`Math.imul(seed, 1103515245) + 12345`.
