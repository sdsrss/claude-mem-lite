# Pre-release claims review: claude-mem-lite v6.35.1, candidate b12782c2

Reviewer: blind claims review, 2026-11-12 (21:16 to 21:30 UTC). `git cat-file -t b12782c2` printed `commit`.
I built the trees with `git archive` and copied `node_modules` in with `cp -a`: after = b12782c2,
before = b91b6384, and mid = 8042059d, used only to count reads. `git diff --stat v6.35.0..b91b6384 -- hook.mjs lib/ hook-*.mjs scripts/`
is empty, so "before" runs v6.35.0's hook code.
Every hook ran under `env -i`, with these variables set: a sandbox HOME, the brief's four variables, `CLAUDE_MEM_SKIP_{COMPRESS,OPTIMIZE,MAINTAIN}=1`,
and TMPDIR under this directory. No API key or proxy variable was set.
Machine: 12 cores, Node v26.8.1, V8 heap limit 4192 MiB. Load average was about 1 during the runs.
Scripts are in /home/ai/.cache/tmp/rv-6351-claims/scripts/. They have hard-coded tree and data paths. The trees and data
were deleted after the run. Rebuild them with the archive commands above, then run `node gen.mjs <dir>/data/big.jsonl 300`.

## Findings

### F1 (P2): the CHANGELOG blames the reporter's timeouts on a code path the reporter had turned off
- Sentence (CHANGELOG `## v6.35.1`, bullet 1): "Stop runs at the end of every assistant turn, and it parsed the session's
  whole transcript each time, once per question it asks when the transcript was too large to keep in memory. The
  issue's reporter saw it hit Claude Code's 5-second hook timeout on almost every turn of a 475 MB session."
- What is wrong: the "once per question" parse only happens when citation tracking is on. Issue #53 says:
  "`CLAUDE_MEM_NO_CITATION_TRACK=1` is set, so the citation scan is not involved." With the reporter's settings,
  v6.35.0's Stop parsed the transcript once per turn, or twice when the host sends no `last_assistant_message`.
  The parse was in the summary reply path. Bullet 2 fixes that path, but the entry attaches the reporter's symptom to bullet 1.
  The same bullet then quotes 4.9–5.1 s. That figure is for citation tracking on only, and the entry gives no number for the reporter's configuration.
- Evidence (300 MiB synthetic transcript, citation tracking off, ABBA, 6 Stops per arm, `scripts/exp-static.mjs`, 21:17Z):
  - The host sends `last_assistant_message`. Before: 546–566 ms, 1 whole read (314,577,252 B). After: 92–98 ms, 0 bytes.
  - No `last_assistant_message`. Before: 973–1024 ms, 2 whole reads (629,154,504 B). After: 99–111 ms, 2 opens, 131,072 B.
- Suggested fix: say that the reporter had citation tracking off, that their cost was the summary's whole-file parse
  (bullet 2), and that the per-question parse is what citation-tracking users paid above the in-memory limit.

### F2 (P3): the 5-second limit is the plugin's own setting, not Claude Code's
- Sentences:
  - CHANGELOG: "hit Claude Code's 5-second hook timeout"
  - 28472b3b: "took 4919-5052 ms against the host's 5 s timeout"
  - lib/transcript-digest.mjs:7: "against the host's 5 s timeout"
- What is wrong: `hooks/hooks.json` gives the Stop entry `"timeout": 5`, and install.mjs writes `timeout: 5` into the
  settings.json entries at lines 1237–1378. Claude Code enforces the 5 s, but claude-mem-lite chose it.
  (Not traced: a `var vu=600000` constant sits about 5 MB before the Stop-hook builder in the 2.1.322 binary. I did not confirm it is the default.)

### F3 (P3): "almost every turn" states a rate the issue says is unknown
- Sentences: CHANGELOG "on almost every turn of a 475 MB session"; 8042059d "Stop hit its 5 s timeout on nearly every turn".
- What is wrong: the issue's own data say "Successful silent runs are not persisted, so the true failure *rate* is
  unknown." What was actually observed: 600 of the 613 logged `timedOut` runs came from that one session.

### F4 (P3): the 4.9–5.1 s and "under 0.1 s" figures hold only for a narrow test case the entry does not describe
- Sentence (CHANGELOG): "On a 300 MB test transcript with citation tracking on, a turn's Stop took 4.9–5.1 s before
  and under 0.1 s after."
- Reproduced (`scripts/exp-steady.mjs`, 21:18Z; one ~50 KB turn appended before each pair of Stops; order alternated over 6 passes):
  - Before: 4941–5140 ms, 11 whole reads, 3,460,880,731 B (3300.5 MiB).
  - After: 100–113 ms, 64,653 B (0.06 MiB), 1 open.
- What the entry leaves out:
  - (a) The test transcript sits just above a step. transcript-scan.mjs keeps one parse in memory up to
    min(256 MiB, heap/4/3.45), which is 256 MiB on this 4192 MiB heap. At 240 MiB the same before tree took 597–653 ms with 1 read
    (`scripts/exp-240.mjs`, 21:29Z; after: 97–101 ms). So 4.9 s is the cost just above the step, not a measure of how Stop
    cost grows with size.
  - (b) The 11 reads happen only because the appended turn's assistant text contains a citation (`#12`). On the
    unmodified synthetic transcript the before tree did 9 reads (2,831,195,268 B) in 4051 ms (single run).
  - (c) "After" is the steady state once the digest has caught up. The first 5 Stops took 165–193 ms here
    (154–183 ms in 28472b3b).
  - (d) "Under 0.1 s" did not reproduce: 100–113 ms. The floor is node start-up plus imports. With citation tracking
    off and 0 transcript bytes read, Stop took 92–98 ms.
  - (e) "300 MB" is 300.0 MiB (314.6 MB), while the next line uses MiB.

### F5 (P3): the catch-up note covers only one of the cases that trigger it
- Sentence (CHANGELOG): "A transcript first seen above 64 MiB, such as a long session already running when you update,
  is read over several turns. Citation tracking writes nothing for it until it has been read to the end."
- Left out:
  - (a) The 64 MiB budget covers the transcript and its subagent files together (transcript-digest.mjs:43-45,
    123-134). A smaller transcript with large subagent files also catches up over several Stops, and so does any turn that appends more than 64 MiB.
  - (b) The digest also starts again from byte 0 in two more cases:
    - after every later version change: the state is keyed by `1:<package version>` (transcript-digest.mjs:157-167);
    - after garbage collection: any SessionStart deletes `transcript-digest-*` files idle for more than 24 h
      (hook.mjs:1983, 1997-2002). A long session resumed the next day therefore goes through catch-up again and records no citations meanwhile.
  - (c) If the session ends during catch-up, its citations are never recorded.
  - (d) If the runtime directory cannot be written, a transcript over 64 MiB never finishes.
    Probe (`scripts/unwritable.mjs`): with the parent dir replaced by a file, `complete` was false on all 7 calls. With a writable dir it became true from the 5th call.
    Before this release such a session was still tracked, just slowly.
  - (e) During catch-up the early return at hook.mjs:1495-1501 also skips the inputs for the bugfix-shape nudge and the
    unpersisted-decision reminder. That is more than "citation tracking".

### F6 (P3): "at most 64 MiB" is not true of bytes read
- Sentences: 28472b3b "A Stop reads at most 64 MiB of new bytes"; transcript-digest.mjs:13 "It reads at most
  `maxBytes` new bytes over all files".
- Measured (count-io preload):
  - Each full catch-up Stop read 71,311,360 B (68.0 MiB) of the transcript. The 4 MiB chunk read past the budget is thrown away and read again on the next Stop.
  - Each Stop also makes four probe reads of up to 4 KiB per file, and these are not counted against the budget. With 3000 subagent files the
    first Stop read 86.6 MB and each steady Stop read 49.2 MB (`scripts/exp-sub.mjs`).
  - What does hold: the bytes actually consumed are at most 64 MiB plus one line.

### F7 (P3): "no longer slows down" ignores the number of subagent files
- Sentences: b12782c2 subject "Stop no longer slows down as a session's transcript grows"; CHANGELOG "Stop reads only
  what the transcript gained since its previous run".
- What is wrong: every Stop opens each subagent file and reads and hashes up to 16 KiB of it, even when the file has not changed.
  The state file also stores about 260 B per subagent file. So the steady-state cost grows with the number of subagent files.
- Evidence (`scripts/exp-sub.mjs`, 21:19Z): after tree, citation tracking on, 20 KB subagent files, 4 steady Stops per arm,
  order alternated.

  | Subagent files | After | Before | Bytes read per Stop (after) | State file |
  |---|---|---|---|---|
  | 0 | 100–114 ms | 102–105 ms | 16.5 KB | 3.6 KB |
  | 200 | 105–114 ms | 106–111 ms | 3.29 MB | 55 KB |
  | 1000 | 133–138 ms | 132–139 ms | 16.4 MB | 261 KB |
  | 3000 | 212–225 ms | 175–188 ms | 49.2 MB | 779 KB |

  At 3000 small files, 6.35.1 is slower than v6.35.0.
- Scale on this machine: at most 25 subagent files per session, so the effect here is negligible. "Only what it gained" also leaves out the
  8 KiB of probe reads per file.

### F8 (P3): the shipped comment and the commit message give different read counts for the same 300 MB transcript
- Sentences: lib/transcript-digest.mjs:7 "on a 300 MB transcript Stop read the file 8 times and took 4.5-5.5 s";
  28472b3b "Stop read 3300 MiB in 11 whole-file reads and took 4919-5052 ms".
- Both numbers reproduce, but they describe different trees and inputs:
  - 8 is the 8042059d tree (never released) on a transcript with no citation: 2,516,618,016 B, 3612 ms, single run.
  - 11 is b91b6384 (v6.35.0 code) with a citation in the text.
- Neither says which. The released comment's "before" is a tree that users never ran.

### F9 (P3): the equivalence result holds, but the commit does not say how narrow its test population was
- Sentence (28472b3b): "On this machine's 196 transcripts (921.8 MB, 634 subagent files), each grown in 3 random cuts
  plus the whole file: 784 of 784 digests equal the path scanners, 784 of 784 tail replies equal the forward parse".
- Reproduced with a stricter check (`scripts/equiv2.mjs`): the reference answers came from the b91b6384 path scanners,
  not the same tree's refactored ones, and the subagent files grew with the same cuts.
  - Seeds 7 and 53: 0/784 mismatches, 0 incomplete digests.
  - Tail replies: 0/784 mismatches against b91b6384's `extractTailAssistantText`.
  - The check can fail: a mutant that drops the largest cited id gives 195/784. A tail mutant gives 183/196.
  - Today's corpus: 196 transcripts, 922.4 MB, 636 subagent files (the live corpus has grown).
- Not stated in the commit:
  - The largest transcript is 21.0 MB and none reaches 64 MiB, so the catch-up path never ran in those 784 checks.
  - `citeBack` and the subagent answer were empty in all 784 checks, so the comparison says nothing about those two.
    Per-answer non-empty counts: injected 686, citeRecall 679, mainText 574, bugfixShape 344, persistence 337, cited 195,
    userTyped 183, citeBack 0, subagent 0.
  - The repo's equiv.mjs copies the subagent files whole, so it never tests resuming a partly read subagent file.
  - Its reference answers come from the same tree's scanners, which share the per-record rule with the digest.
- I closed the catch-up gap separately (`scripts/catchup-equiv.mjs`). I joined 15 real transcripts into one 208.9 MB file with 44 subagent files.
  The digest finished in 5 calls and matched the b91b6384 scanners on all 12 answers. The state file was 21,446 B.
- The "337 mismatches" mutation could not be recomputed because the commit does not say what was mutated.

### F10 (P3): the entry leaves out facts about the new file on disk and about going back
- Mentioned: one file per transcript under `runtime/`.
- Left out:
  - It is written only when citation tracking is on. I checked: none existed in the citation-off sandbox.
  - It has mode 0600, holds the transcript's full path and observation ids, and is rewritten on every Stop.
  - It is deleted 24 h after its last write, at the next SessionStart.
  - Sizes seen: 836 B (synthetic), 21 KB (208.9 MB of real content), 779 KB (3000 subagent files).
- "Going back is pinning claude-mem-lite@6.35.0" leaves these files behind for good: v6.35.0's two garbage collectors
  (`gcStalePreRecallCooldowns` and `GC_PROJECT_MARKER_PREFIXES` in before/hook-shared.mjs:247-259) do not know the `transcript-digest-` prefix.

## Verified claims, not findings
- 8042059d "transcript reads per Stop 1 -> 0" (citation tracking off): verified with the host sending the reply (F1 numbers).
- 8042059d "8 times (9 before)": verified, 8 on the 8042059d tree and 9 on b91b6384, on the citation-free transcript.
- 8042059d and stopFinalReply "Claude Code 2.1.322 omits it when the last assistant message has no text": verified in the 2.1.322 binary.
  It uses `Jh(e){return e.findLast((n)=>n.type==="assistant")}` and
  `Ee=ne?Ts(ne.message.content,"\n").trim()||void 0:void 0`, so the field is also omitted when the text is whitespace only or there is no assistant message.
  Side note on code outside the diff: readStopHookInput's comment about `''` describes a value 2.1.322 never sends.
- 28472b3b "heap budget (256 MB at most)": verified (transcript-scan.mjs:46-71; 256 MiB here).
- 28472b3b "~11 scanners": 11 whole reads with a citation present, 9 without.
- 28472b3b "0.06 MiB read per Stop": verified (64,653 B). "Five Stops" of catch-up: verified (4 × 68.0 MiB, then 44.0 MiB).
- The saved-state conditions (inode, head and tail 4 KiB, version), "otherwise from byte 0", and "until it is the Stop
  writes no citation result" match the code. The `continues` check and the early return at hook.mjs:1495 do what the sentences say.
- "extractTailAssistantText ... now reads backwards" is true, as is the CHANGELOG's "read from the end of the transcript". Without
  the host's reply, Stop reads twice, 64 KiB each time.
- "as the per-turn reply record already did" is true; the v6.35.0 recordStopTurnReply preferred `lastAssistantMessage`.
- "the schema version stays 49": `CURRENT_SCHEMA_VERSION = 49` and schema.mjs is unchanged since v6.35.0.
- The runtime path `~/.claude-mem-lite/runtime/` "by default" is right. With `CLAUDE_MEM_DIR` set the file goes to
  `$CLAUDE_MEM_DIR/runtime`, and with `CLAUDE_MEM_RUNTIME_DIR` set it goes there (lib/resolve-data-dir.mjs:143-152).
- The Stop path reads the transcript nowhere outside `digestTranscript` and `stopFinalReply`: grep of trackCitationsAtStop
  and handleStop, plus 0 whole reads in every after-tree run.
- "Guard tests ... restated ... mutation-checked": I re-checked the D#152 restatement only. Forcing `continues()` to return false
  failed the e2e test ("expected 213586 to be less than 32768"). The file was restored and `cmp` confirmed it matched b12782c2.
  The 6 changed test files pass on the after tree: 302/302.
- 8042059d timings "876-1290 ms before, 101-178 ms after": the direction reproduces, but the ranges do not (546–566 and 92–98 ms here).
  "4483-5465 ms" (citation tracking on): single runs here gave 3612 ms (8042059d) and 4051 ms (b91b6384). These are not ABBA
  runs and are not used as evidence.
- Other comment claims match the code:
  - "UTF-8 never uses 0x0A inside a character";
  - "No matcher reads the prompt" (citation-tracker SURFACE_MATCHERS read only `command` and `text`);
  - `extractAllInjected` equals `unionSurfaces(extractInjectedBySurface)`, so the relevance set is unchanged;
  - the SOURCE_FILES ordering comment;
  - "~0.2 s of parsing there": 64 MiB / 475 MB × 1.6 s = 0.23 s.

## NOT CHECKED

- Whether 6.35.1 actually clears the reporter's timeouts: their 5 s was not reproduced. On 300 MiB with their settings, v6.35.0's Stop took 0.55–1.0 s here.
- Claude Code's default hook timeout. Only the hooks.json value is cited.
- Hosts other than Claude Code 2.1.322 sending or omitting `last_assistant_message`; Windows (inode semantics); live Claude Code sessions
  (the hooks were driven through stdin).

- The two concurrent-Stop / two-code-home cases for one transcript.
