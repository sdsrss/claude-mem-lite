# v6.35.2 pre-tag review, round 2 (delta `fcede32a..075a2afd`)

Candidate: `git rev-parse HEAD` = `075a2afd0705cdc07b332a7e32015d248d8445e1`, which matches the brief. Trees were built
with `git archive` (075a2afd, fcede32a, v6.35.1, v6.35.0) under `~/.cache/tmp/rv-6352-r2/`, each with a copied
`node_modules`. Every run used a sandbox HOME, had LLM keys and proxies unset, and had TMPDIR set inside that directory.
The repository was not written. Each mutated file was restored from a copy, and the tree was confirmed pristine
afterwards (md5 of the four touched files equals `git archive 075a2afd`).

**Verdict: no P0, P1 or P2 in the delta.** 567005ad restores v6.35.1's per-Stop bound, and I reproduced that. Four
P3 findings follow: one is about test strength and three are about prose.

## Findings

### R2-F1 — P3 — The restated tests bound a call's read at about 14x the budget, not at the budget

- Where: `tests/transcript-digest.test.mjs:253-271`. Each of the two tests asserts only that `complete` is false, on a
  4262-byte file with `maxBytes: 300`.
- Reproduce: `python3 -I mut-m2.py lib/transcript-digest.mjs <k>`. This puts back a second pass with
  `{ left: k * maxBytes }` when the save fails. Then run `npx vitest run tests/transcript-digest.test.mjs`.
  - k=12: 32/32 tests pass, so the mutation slips through.
  - k=13 and k=14: both restated tests fail.
  - Full fallback (`{ left: Infinity }`, M1): both restated tests fail, which confirms what the commit says.
- Why the slipping mutation matters: with k=12 applied, I timed the whole Stop hook on a 1 GiB transcript of the
  round-1 shape, with a directory planted at the state path. It took 4.68 s and 4.57 s and logged "still catching up;
  nothing written". Unmutated, the same input takes 0.45 s. That is 0.3-0.4 s under the 5 s Stop timeout on this host.
- Expected: a test of "each call still stops at its budget" fails for any read past the budget. Saw: up to 13x the
  budget per call passes.
- Fix shape (not applied): assert what a single call takes, for example `main.cited.size === 3` for 300 bytes of
  ~106-byte lines, or count the bytes `readSync` returns.
- Shape: the mutation is CONSTRUCTED by definition. The property it leaves unguarded is the one 567005ad exists for.

### R2-F2 — P3 — "Stays incomplete while saving fails" and "reads from the first byte again" are false when an earlier state is still on disk

- Where:
  - `lib/transcript-digest.mjs:16-18`: "such a transcript stays incomplete while saving fails".
  - `lib/transcript-digest.mjs:165`: `/* the next Stop reads from the first byte again */`, re-added by 567005ad.
  - The same claim appears in 567005ad's body: "the transcript stays incomplete and gets no citation writes while
    saving fails, as in 6.35.1".
- Reproduce: `node probes/resume-after-fail.mjs <tree> <dir>`. It runs six lines with `maxBytes: 300`: call 1 with a
  writable dir, then `chmod 0500` on the runtime dir, then calls 2 and 3.
  - At 075a2afd: call 1 gives `{"complete":false,"cited":[1,2,3]}`. Calls 2 and 3, whose saves fail, each give
    `{"complete":true,"cited":[1,2,3,4,5,6]}`.
  - v6.35.1 gives identical output.
- What happens: `atomicWriteFileSync` writes a temp file and renames it. A failed save therefore leaves the previous
  state in place, and the next call resumes from that state, not from byte 0. If the rest fits in one budget, the call
  completes and Stop writes results while saving still fails. This behaviour is correct, because it reads from a
  state that still describes the file. Only the statements are wrong.
- Shape: REAL in kind. It is the case 567005ad itself names: a state write failing on its own (disk or quota nearly
  full) after earlier Stops had saved. Here I simulated it with mode bits on a direct `digestTranscript` call. Not a
  regression.

### R2-F3 — P3 — 567005ad's "a dir Stop really cannot write makes it throw earlier" holds only when the session file must be written

- Where: the body of commit 567005ad. The code involved:
  - `hook-shared.mjs:480-486`: `getSessionId` writes nothing when a fresh session file can be read.
  - `hook-episode.mjs:133-140`: `acquireLock` spins for 1000 ms and then falls back.
- Reproduce: `probes/stop-ro.sh` with the LD_PRELOAD shim `shim/ro_shim.so`. The shim makes every open-for-write,
  rename, unlink and mkdir under the runtime dir fail with EACCES, and chmod fail with EPERM. That is a directory this
  user can read but not write.
  - Control, no session file: both 075a2afd and fcede32a stop with `[ERROR] stop: EACCES ... open '.../runtime/session-...'`
    before the digest, as the commit says.
  - Fresh session file left by SessionStart: Stop reaches the digest.
    - fcede32a: 4.48 s wall, `citations: 5000 ids scanned`. It read all 1 GiB through the withdrawn branch, plus the
      1 s lock spin.
    - 075a2afd: 1.33 s, `still catching up; nothing written`.
  - The shim log shows that the denied operations include `transcript-digest-ac915551b53290fa.json.tmp-<pid>`.
- Effect: none on the code at 075a2afd, because the branch is gone. The sentence understated how far the withdrawn
  branch reached.
- Shape: CONSTRUCTED, as a shim-simulated read-only directory. Reaching it for real needs a runtime dir that becomes
  unwritable after SessionStart while the session file stays readable and the DB writable. I know of no setup that
  does this.

### R2-F4 — P3 — 075a2afd's body describes D#852's trigger as a development checkout or a planted file

- Where: commit 075a2afd: "The CHANGELOG entry leaves out D#852/D#854: their triggers are a development checkout, a
  hand-edited or planted file, or a record shape seen only in constructed input."
- Evidence: the trigger for D#852's naming half is described differently in two places:
  - 3e85e098's own body names it as "two code homes of different versions running Stop on one transcript".
  - `lib/transcript-digest.mjs:24-25` names it as "a plugin registered twice during an update".
- The omission is still right. 6.35.1 is the only earlier release that has a digest, and its state name is
  `sha256(path)` while 6.35.2's is `sha256(code\npath)` (computed: `f5a1badc…` against `ac915551…` for the same file).
  So no user upgrading from 6.35.1 could have hit the reset. Only the stated reason is imprecise.
- Shape: prose only.

## Answers to the brief's questions

**1. Budget, completion and header after 567005ad**

- Bytes read per call, 1 GiB transcript (`probes/bytes-per-call.mjs`, readSync byte count):
  - 075a2afd, save failing: 68.01 MiB per call, the same on calls 1-3. That is 64 MiB of lines plus at most one 4 MiB

  - fcede32a, save failing: 1028.03 MiB and `complete: true` in one call.

  | input | 075a2afd | fcede32a | v6.35.1 |

  residue was left in the runtime dir.
- Two installed versions: v6.35.1 and 075a2afd alternating Stops on one 512 MiB transcript in one runtime dir. Each
  completed on its own 8th Stop (512/64), and the two left two state files with no reset. The unit test "another

- Inputs that never complete, all identical at v6.35.1 and none new in the delta:

    citation tracking stops for that session.
