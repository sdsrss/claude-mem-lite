## P2-1: A committed swap is rolled back at a later entry when its journal cannot be unlinked (contract 1)
CONFIRMED by fault injection. The Windows trigger is PLAUSIBLE (reasoned).

- Sites:
  - hook-update.mjs:876-882: `discardBackupDir` returns early when the journal rm throws, and keeps
    the full backups AND the journal.
  - hook-update.mjs:939: `recoverInterruptedSwaps` replays any journal it finds.
  - lib/doctor-stale-temp.mjs:66: classifies that dir as `unfinished-swap`.
  - install.mjs:2965: doctor says "an update was interrupted … run cleanup — it finishes an interrupted one".
- On disk, a committed swap whose journal unlink failed looks the same as a killed swap. The code
  comment says so on purpose ("so a replay restores one whole release"). That replay is a rollback
  of a release that passed its smoke check.
- Repro (`tree/tests/zz-review-probe.test.mjs`, case B): smoke passes and `rmSync(.swap-journal.json)`
  throws EBUSY once.
  ```
  B ret true fired true after commit NEW left [ '.update-backup-…' ] [ 'unfinished-swap' ]
  B after next-entry recovery: OLD
  ```
- Kill window (case B2). After the smoke passed, `discardSwapDirs` removes the STAGING dir before the
  journal (hook-update.mjs:890-896), so a kill in that rm also rolls the release back:
  ```
  B2 smoke at op 46 of 50
  46 rm …/.update-staging-… => OLD
  47 rm …/.update-backup-… (journal) => OLD
  48 rm …/.update-backup-… => NEW
  ```
  `tests/hook-update-swap-killpoints.test.mjs` accepts OLD or NEW at every kill point, so it cannot
  catch this.
- Effect:
  - `cleanup`, which doctor recommends, downgrades the install to the previous release.
  - If the new release already migrated the DB schema, the old code is locked out (the schema-skew
    invariant). This consequence is reasoned.
  - The next update entry rolls back, then re-swaps; if that swap's smoke fails, the install is left
    on the old release.
- It contradicts the CHANGELOG: "nothing rolls a release back once its check has passed" and "a journal
  a failed cleanup left behind was replayed at the next update" (listed as fixed).
- Fix direction:
  - Make the commit durable before any discard: write a commit record outside the backup dir, e.g.
    `runtime/swap-committed-<ts>` naming the backup dir. Recovery and classifyUpdateResidue should
    treat a committed backup dir as discard-only.
  - Remove the journal before the staging dir.
  - For the journal, use `rmSync(p, {recursive: true, force: true, maxRetries: N})`; Node ignores
    maxRetries unless recursive is set.

## P2-2: Recovery treats an empty or unparseable journal as "nothing moved" and deletes the only copy; cleanup then claims it restored the files (contract 2)
CONFIRMED (CLI, sandbox HOME).

- Site: hook-update.mjs:931-940. `journal = null` gives empty arrays, `rollbackInstall` is a no-op,
  and `discardBackupDir` deletes the dir.
- Repro: probes/homeA-*. The seed is a code dir whose server.mjs is NEW, a backup dir holding the only
  OLD server.mjs, and an empty `.swap-journal.json`. A v≤6.25.0 in-place write torn by a kill or
  ENOSPC leaves exactly this; the author measured 8/47 and 8/63 kill points.
  ```
  doctor:  warn Unfinished update: 1 backup dir(s) … (run: node install.mjs cleanup — it finishes an interrupted one …)
  cleanup: ✓ Finished an interrupted update: .update-backup-1700000000000-4242 (put back the files it had moved out)
  after:   server.mjs = "// NEW server from interrupted swap"; grep for the OLD content in $HOME → NONE
  ```
- `atomicWriteFileSync` (lib/atomic-write.mjs) does not fsync. After a power loss, some file systems
  can expose a zero-length renamed journal (reasoned, not reproduced). That journal takes the same path.
- Fix direction:
  - A journal that exists but does not parse to `{backedUp[], installed[]}` must not lead to a discard.
    Leave the dir and report it as needing `repair`, in both doctor and cleanup.
  - Or write numbered journals (`journal-<n>.json`, new names, never rename-over). Recovery would read
    the highest one that parses, which also removes the rename-over in P3-5.

## P2-3: install writes the tree although the interrupted swap was not finished, and the old journal is then replayed over the new install (contract 3)
CONFIRMED (CLI, hook-update cannot be imported). CONFIRMED by fault injection (journal unlink fails).
The Windows trigger is PLAUSIBLE.

- Sites:
  - install.mjs:1323-1333: if the import fails, it warns and leaves the dir.
  - install.mjs:1346-1358: `finishInterruptedSwaps` only warns ("Could not remove …").
  - install.mjs:1372: `install()` goes on to `deployCodeTree`.
- CLI repro (probes/homeD-*, `install --dev` from tree-noimport):
  ```
  ⚠ Could not finish an interrupted update here (simulated: hook-update cannot load) — it is left in place
  ⚠ Could not remove .update-backup-1700000000000-4242 from …/.claude-mem-lite
  Done! Restart Claude Code to activate.          (exit 0; cli.mjs and hook.mjs are fresh symlinks)
  --- next update entry: recoverInterruptedSwaps(codeDir) → recovered 1
  cli.mjs: No such file or directory; hook.mjs = "// before the interrupted swap"
  ```
- Fault-injected repro (case D): recovery runs with the journal unlink failing once (EBUSY), then NEW
  is deployed, then the next entry runs. Result:
  `MIXED:{"hook.mjs":"// new hook","package.json":"{\"version\":\"1.1.0\"}","server.mjs":"// new server"}`.
  The installed cli.mjs was deleted. The D#283 idempotence skips the backed-up paths but still deletes
  the journal's installed-only paths, which now belong to the newer tree.
- The same class occurs inside hook-update alone. If a journal unlink fails persistently across two
  update entries, the second entry stacks a new swap, commits it, and a later entry deletes that
  release's added files.
- Fix direction:
  - After `deployCodeTree` has written a complete tree, retire every pre-install journal: unlink it,
    or rename the backup dir to a name recovery ignores.
  - Or have install exit 1 when an unfinished swap remains.

## P2-4: A restore that fails inside rollbackInstall is followed by deleting the backup, which held the only copy
CONFIRMED by fault injection. The Windows trigger is PLAUSIBLE.

- Sites: hook-update.mjs:971-982 (the restore failure is only logged), followed by `discardSwapDirs`
  at :1145 and :1241 and by `discardBackupDir` at :940.
- Repro (case C): smoke fails, and `rename(backup/server.mjs → server.mjs)` throws EPERM once.
  ```
  C ret false fired true tree MIXED:{"hook.mjs":"// old hook","package.json":"{\"version\":\"1.0.0\"}"} residue []
  ```
  server.mjs is gone from both releases and nothing on disk records it. doctor and cleanup see nothing.
- Pre-existing. b472b7a3 reverted keep-on-failed-restore and deferred it to D#286; I read that commit
  after forming this finding. It still contradicts Q1 and the release title "a rolled-back or
  interrupted update keeps the old files".
- Windows triggers: AV or an indexer holding the backup file, or a delete-pending target name. Linux
  needs an unwritable target subtree.
- Fix direction: `rollbackInstall` returns the paths it failed to restore; discard only when none
  failed. A kept dir needs the D#286 retirement so it is not replayed over a later tree; that interacts
  with P2-1 and P2-3.

## P3-2: cleanup, install and other entries steal install.lock from a live updater after 5 min and replay its journal mid-flight
The lock steal is CONFIRMED. A hold longer than 5 min is reasoned.

- Site: lib/proc-lock.mjs:43. `ts` older than 5 min counts as stale even when the pid is alive.
- Repro (probes/homeL-*): install.lock names a live `sleep` pid with ts = now−6min.
  `cleanup` printed "✓ Finished an interrupted update" and "✓ Removed: .update-staging-…", and
  server.mjs went back to OLD.
- installExtractedRelease holds the lock through npm install (≤60s) and smoke. Smoke can include
  `npm rebuild` (≤120s, twice) and the source build (≤300s), so more than 5 min is reachable on a
  platform with no prebuild.
- The new doctor text "leaves a running one alone" (install.mjs:2965) is false in that window.
- Fix direction: do not steal on age while the holder pid is alive on this host, or refresh `ts`
  during long steps.

## P3-4: On a read-only mount (EROFS), a closed WAL store still double-counts and relays SQLite's message (the D#287 shape)
PLAUSIBLE, reasoned from the SQLite source.

- Cause: sqlite3.c:46883 returns `SQLITE_READONLY_DIRECTORY` only when `errno==EACCES`. On EROFS the
  -wal create falls through to a read-only open, which fails ENOENT and gives `SQLITE_CANTOPEN`
  ("unable to open database file").
- Then `walBlocked()` (install.mjs:2087, status :1845) is false. doctor prints
  `✗ Database: unable to open database file` and counts an issue beside `✗ Data directory … read-only`.
  DB schema and DB stats show the raw message too.
- Not run: no read-only mount here, and `unshare -rm` is denied.
- Fix: treat (dataDirDenied ∈ {EACCES, EROFS}) and (code ∈ {READONLY_DIRECTORY, CANTOPEN}) with no
  -wal present as walBlocked.

## P3-5: The journal is now rename-overwritten up to 2×162 times per update; on Windows each one can fail EPERM
PLAUSIBLE (Windows, reasoned).

- Site: hook-update.mjs:866-868, via `atomicWriteFileSync`, which does tmp + `renameSync` onto the
  existing journal.
- MoveFileEx REPLACE_EXISTING fails if AV or an indexer holds the just-written journal without
  FILE_SHARE_DELETE. Each failure aborts the update and rolls it back: safe, but under aggressive AV an
  update may never land.
- The count is 160 SOURCE_FILES + scripts + node_modules, two writes each.
- Fix: retry EPERM/EBUSY, or use numbered journal files (see P2-2).
