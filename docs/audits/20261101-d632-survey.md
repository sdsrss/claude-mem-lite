## 结论摘要

1. **`PRAGMA integrity_check` 和 `quick_check` 在 3.53.4 上不能单独充当闸门**，在本项目这种 schema 上会漏报。
   - 机制：schema 哈希里排第一的表如果是虚表（`tnum=0`），整库检查就会退化成"部分检查"，跳过空闲页表的遍历和"never used"扫描。
   - 实测：VACUUM 过的产品 schema 上，把空闲页表的叶子项改成一页正在用的表页，两个 pragma 都返回 `ok`；没 VACUUM 的同一种损坏会报 `2nd reference to page 65`。
   - 产品里有 `VACUUM`（`lib/maintain-core.mjs:972`）。
   - SQLite trunk 的代码今天仍是同样写法。没有找到上游报告。
2. **`sqlite_dbpage` 和恢复扩展都用不了**：better-sqlite3 13.0.3 的 prebuild 没编进 `SQLITE_ENABLE_DBPAGE_VTAB`，而 `sqlite_dbpage` 按文档不能在运行时加载。Node 26.8.1 自带的 `node:sqlite` 也没有。`dbstat` 有，但它按文档不列空闲页。
3. **better-sqlite3 不解析 URI 文件名**，`immutable=1` 和 `mode=ro` 走不通，只有 `readonly: true`（等于 `SQLITE_OPEN_READONLY`）可用。`immutable=1` 本来也不适合活库：我在 node:sqlite 上测到它直接忽略 WAL。
4. **close() 的问题，sqlite.org 写得很直接**："close() … will cancel all POSIX advisory locks on the same file for all threads and all file descriptors in the process"。同一个进程里用**同一份** SQLite 库再开一个连接是安全的。另链一份 SQLite（比如 `node:sqlite`）进同一进程，文档点名会造成损坏。
5. **成熟项目里没有一个在 REINDEX 或 FTS rebuild 之前加页级闸门**。
   - Firefox：先 `integrity_check`，失败了再 `REINDEX`，然后复查，还坏就下次启动替换。
   - Chromium：在新文件里 `sqlite3_recover`，再用 backup API 写回原库。
   - Android：检测到损坏就删库。
   - 共同做法是"在库外抢救、再替换"，不是"原地重建"。
6. **我的建议是自建，但范围很小**：把第二次尝试已经测过的读取器原样搬进子进程（下面称 A′），父进程永远不碰 store 的三个文件；子进程先 `ROLLBACK`，再 `db.close()`，最后才关 fd。备选是 C：用 backup API 把库拷到私有文件，再查副本，代价是磁盘和时间。只用 `quick_check` 的方案 B 要等上游修复。

## 1　写入前检测页级损坏

### 1.1　integrity_check 和 quick_check 管什么

**文档（https://sqlite.org/pragma.html#pragma_integrity_check）**列出的检查项：
- "Table or index entries that are out of sequence"
- "Misformatted records"
- "Missing pages"
- "Missing or surplus index entries"
- "UNIQUE, CHECK, and NOT NULL constraint errors"
- "Integrity of the freelist"
- "Sections of the database that are used more than once, or not at all"

另外：
- 默认最多报 100 条。
- 不查外键。
- 带 TABLENAME 时是"partial integrity check"，此时 "errors such as unused sections of the file or duplication use of the same section of the file by two or more tables cannot be detected"。只有 TABLENAME 是 sqlite_schema 时才查空闲页表。

**quick_check（同页 #pragma_quick_check）**："does not verify UNIQUE constraints and does not verify that index content matches table content"。它是 O(N)，integrity_check 是 O(NlogN)，"Otherwise the two pragmas are the same"。所以"索引和表内容是否一致"只有 integrity_check 查；页结构、空闲页表、重复引用两者都查。

**源码里的实现**：
- `sqlite3BtreeIntegrityCheck`（`sqlite3.c:84370`）。
- 先用 `checkList` 走空闲页表（`:84434-84439`）。
- 再用 `checkTreePage` 走每棵树（`:84465-84478`）。同一页被引用两次时报 "2nd reference to page N"。
- 最后扫一遍没被引用的页，报 "Page %u: never used"（`:84483-84500`）。
- 空闲页表里列了一页正在用的表页，靠的就是这套"引用位图"抓出来。

**虚表**：
- 从 3.44.0 起，integrity_check 会调虚表的 xIntegrity："now verifies the consistency of the content in various built-in virtual tables using the new xIntegrity method … FTS3, FTS4, FTS5, RTREE"（https://sqlite.org/releaselog/3_44_0.html；代码生成在 `sqlite3.c:146984`）。
- FTS5 的 xIntegrity 不看 isQuick（`sqlite3.c:264173` `UNUSED_PARAM(isQuick)`），所以 quick_check 也会跑完整的 FTS5 自检。在 FTS 已经坏了的库上，结果里会混着 FTS 的错误行，要分开判。

**查不出的东西**（推断）：格式正确但值错了的记录。R3 里 "10 rows changed" 那一类，结构检查原理上看不见。

### 1.2　新确认的盲区：虚表排第一，整库检查就变成部分检查

**源码链（3.53.4）**：
1. `PRAGMA integrity_check` 按 schema 哈希的迭代顺序收集根页：`if( HasRowid(pTab) ) aRoot[++cnt] = pTab->tnum;`（`sqlite3.c:146568`）。
2. 只跳过 imposter 表（`tableSkipIntegrityCheck`，调用处在 `:146554`）。
3. 虚表在这里也会被收进去，它的 tnum 是 0。
4. `OP_IntegrityCk` 把 `&aRoot[1]` 交给 btree（`:103891`）。
5. btree 那边，`aRoot[0]==0` 正好是"部分检查"的哨兵：`if( aRoot[0]==0 ){ … bPartial = 1; if( aRoot[1]!=1 ) bCkFreelist = 0; }`（`:84392-84396`）。
6. 结果是不走空闲页表，也不做 never-used 扫描。树内检查和树之间的重复引用照常做。

**哈希顺序为什么会让虚表排第一**：
- `insertElement` 把新元素插到迭代链表最前面，除非它所在的桶里已经有元素（`sqlite3.c:38726-38751`）。
- schema 按 `ORDER BY rowid` 装入（`:148273`）。
- VACUUM 先复制有存储的表，最后才把 `type='table' AND rootpage=0`（虚表）的行追加到 sqlite_schema 末尾（`:161776-161798`）。
- 所以 VACUUM 之后，虚表常常是最后装入、最先迭代的那个。是否真的排第一取决于表名的哈希。

**探针一（合成 schema）**：表 `a`，加一个 fts5 虚表；删行留出 100 个空闲页，再把页头的空闲页指针和计数（偏移 32/36）清零。
- 不 VACUUM：8 个虚表名全部报 100 条 never used。
- VACUUM 之后：8 个名字里有 4 个（`obs_fts`、`zz`、`x1`、`search`），integrity_check 和 quick_check 都返回 `ok`。
- 不建虚表：8/8 都报。

**探针二（产品 schema）**：`initSchema()`，4 个 FTS5 虚表，加一张垫表，50 个空闲页，做同样的清零。
- 不 VACUUM：两个 pragma 都报 50 条 never used。
- VACUUM 之后：都返回 `ok`。

**探针三（产品 schema，危险形状）**：把空闲页 trunk 的最后一个叶子项改成垫表的一页叶子页，也就是 D#593 说的"空闲页表列了一页活页"。
- 不 VACUUM：`Tree 64 page 64 cell 0: 2nd reference to page 65 | Page 90: never used`。
- VACUUM 之后：integrity_check 和 quick_check 都是 `ok`。
- 这个探针里我顺带跑了一次 FTS rebuild 加 REINDEX，行数 300→300，说明那一页没被分配到。这不能当作"不会丢行"的证据。

**能事先看出来**：`EXPLAIN PRAGMA quick_check` 的 `IntegrityCk` 行 p4 列出根页列表（显示逻辑在 `sqlite3.c:89862-89871`）。
- 产品 schema 不 VACUUM 时是 `[63,58,59,…`。
- VACUUM 之后是 `[0,0,0,41,…`。
- 首项为 0 就是部分检查，至少可以判成 unchecked，不会误判 ok。

**上游现状**：
- `https://sqlite.org/src/raw/src/pragma.c?ci=trunk` 的第 1774 行仍是同一句，`tableSkipIntegrityCheck` 也没变（402-408 行）。
- `btree.c?ci=trunk` 的 11239-11243 行仍是同一个哨兵。
- 网上搜索没找到这个问题的报告（论坛、工单）。是否已知，**未确认**。

### 1.3　为什么重建会写坏活页：SQLite 分配页时自己的防线很窄

- `allocateBtreePage`（`sqlite3.c:79740`）只拒绝越界的页号（`:79819`、`:79947`）。
- `btreeGetUnusedPage` 只在"这页此刻在内存里还被引用"时报损坏（`:75679-75693`，`sqlite3PagerPageRefcount(...)>1`）。
- 一页在磁盘上属于某张表、此刻不在缓存里，但空闲页表也列了它，它就会被交给新的索引。这和 R3 的丢行机制一致（推断）。

### 1.4　PRAGMA cell_size_check

- 文档：开启后 "additional sanity checking on database b-tree pages as they are initially read from disk … corruption is detected earlier and is less likely to spread"，默认关（https://sqlite.org/pragma.html#pragma_cell_size_check）。
- 实现：页初始化时调 `btreeCellSizeCheck`（`sqlite3.c:75487`），只查页内的 cell 边界。
- integrity_check 运行期间会把它关掉（`:84463-84464`）。
- 它不跨页，也不看空闲页表，对"空闲页表列了活页"没有作用。这一点是推断。

### 1.5　dbstat

- 编进了 prebuild（`compile_options` 里有 `ENABLE_DBSTAT_VTAB`；`deps/defines.gypi:19`）。
- 文档："only reports on the content of btrees … Freelist pages, pointer-map pages, and the lock page are omitted"（https://sqlite.org/dbstat.html）。
- 它和其他查询在同一个读事务里，能列出每棵树的每一页（含溢出页），所以能发现树与树之间的重复。
- 要发现空闲页表和树的重叠，还得另外拿到空闲页表的内容。第二次尝试就是为此去读文件的。

### 1.6　sqlite_dbpage

- 文档："direct access to the underlying database file by interacting with the pager … all changes are transactional"。
- 需要 `SQLITE_ENABLE_DBPAGE_VTAB`，并且 "is not run-time loadable. The only way … is to compile it in"（https://sqlite.org/dbpage.html）。
- 实测：prebuild 的 `compile_options` 里没有这一项，`deps/defines.gypi` 里也没有。`SELECT … FROM sqlite_dbpage` 报 `no such table: sqlite_dbpage`。
- Node 26.8.1 的 `node:sqlite`（SQLite 3.53.4）同样没有。
- 能用它就不必读文件：它经过 pager，WAL 和锁都由 SQLite 处理。但要用就得换掉或自编 SQLite。这属于依赖变更，需要单独授权。

### 1.7　校验和 VFS（cksumvfs）

据 https://sqlite.org/cksumvfs.html：
- 用途："intended to help detect database corruption caused by random bit-flips in the mass storage device"。
- 不在 amalgamation 里，是可加载扩展（ext/misc/cksumvfs.c）。
- 要求 reserve-bytes 恰好是 8，已有库要 VACUUM 重写才能启用。
- 只有在 `sqlite_dbpage` 存在时才能用 `verify_checksum()` 核对。

推断：页是经由 SQLite 写的，校验和就是对的。所以它抓介质位翻转，抓不到"逻辑上错但 SQLite 自己写出来"的损坏，比如丢锁导致的并发写。它还要给每个平台加一个原生扩展。

### 1.8　恢复扩展（sqlite3_recover / `.recover`）

据 https://sqlite.org/recovery.html：
- 需要 `sqlite3recover.c`、`dbdata.c`，并且 "must be compiled with … -DSQLITE_ENABLE_DBPAGE_VTAB"。所以 better-sqlite3 prebuild 用不了。
- 结果 "will always be suspect"：可能丢内容、复活已删除的内容、改值。
- 默认会扫空闲页表，可以用 `--ignore-freelist` 关掉。
- 本机有 `/usr/bin/sqlite3` 3.46.1，可以 `.recover`，但这不是产品能依赖的东西。

### 1.9　better-sqlite3 13.0.3 prebuild 里有什么（实测）

`PRAGMA compile_options` 里与本题相关的：
- 有：`ENABLE_DBSTAT_VTAB`、`ENABLE_FTS5`、`USE_URI`（定义为 0，见下）、`THREADSAFE=2`、`DEFAULT_WAL_SYNCHRONOUS=1`。
- 没有：`ENABLE_DBPAGE_VTAB`、恢复扩展、cksumvfs。

`pragma_module_list` 是：dbstat、fts3、fts3tokenize、fts4、fts4aux、fts5、fts5vocab、geopoly、pragma_module_list、rtree、rtree_i32。`USE_URI` 出现在列表里，只是因为这个宏被定义了（`sqlite3.c:23828-23830`），值是 0（`deps/defines.gypi:40`）。

## 2　读原始文件而不弄坏别的连接

### 2.1　sqlite.org《How To Corrupt An SQLite Database File》（https://sqlite.org/howtocorrupt.html）

**§2.2 Posix advisory locks canceled by a separate thread doing close()**：
- "the close() system call will cancel all POSIX advisory locks on the same file for all threads and all file descriptors in the process"。
- 例子就是"读前 16 字节判断文件类型"或"做备份"的 open/read/close。
- "This problem only arises when a thread tries to bypass the SQLite library and read the database file directly"。
- 从 3.51.0 起有额外防御，"help when the database is in WAL mode and is being accessed from multiple processes. But they are not a cure-all … never use close() on an SQLite database file while one or more database connections are open, even in other threads"。

**§2.3 Multiple copies of SQLite linked into the same application**：
- 每一份库各有一张全局打开文件表，"A close() operation on one connection might unknowingly clear the locks on a different database connection"。
- 所以在已经载入 better-sqlite3 的进程里再用 `node:sqlite` 开同一个库，就是这一节说的情形。这是推断，依据是 node:sqlite 自带一份 SQLite。

**§1.2 Backup or restore while a transaction is active**：
- 安全的拷贝方式是 `sqlite3_rsync`、`VACUUM INTO`、backup API。
- 直接拷文件只有在 "no transactions in progress" 时才安全，并且要连同 `-wal`/`-journal` 一起拷。

**§1.4 和 §2.6**：
- 日志必须和库文件在一起。
- 从 3.10.0 起，unix VFS 会解析符号链接，用规范名打开。这就是 D#632 条件 (3) 的根源："日志在链接目标旁边"。

### 2.2　SQLite 在进程内怎么绕开这个问题，以及 3.51.0 的防御为什么没救住第二次尝试

**进程内的绕法**：
- `sqlite3.c:41389-41450`：每个 inode 一个 `unixInodeInfo`。同一进程里别的 unixFile 还持锁时，"the call to close() the file descriptor is deferred until all of the locks clear"。
- 所以同一份库开的第二个连接在同一进程里是安全的，§2.2 原文也说 "perfectly safe … using the SQLite library"。
- 用户代码自己 `fs.openSync`/`closeSync` 不在这张表里，这正是第二次尝试 P0-1 的成因。

**3.51.0 的防御**：
- 发布说明："Improved resistance to database corruption caused by an application breaking Posix advisory locks using close()"（https://sqlite.org/releaselog/3_51_0.html）。
- 代码是 `unixIsSharingShmNode`（`sqlite3.c:44856-44893`）：最后一个连接要删 `-wal`/`-shm` 之前，用 `F_GETLK` 看 `-shm` 的 DMS 字节有没有别人持锁，有就不删（`:42232-42239`）。

**推断（未验证）**：
- 第二次尝试关掉的是 `-shm` 的描述符，受害进程连 DMS 锁都丢了。评审抓到的锁列表也是 `after:[]`。所以 hook 关闭时看不到"还有别人"，照删日志。
- 如果只关了主文件的描述符，DMS 锁还在，这个防御很可能会拦住删日志。
- 但主文件上的 SHARED 锁照样会丢，所以这不能作为放宽条件 (1) 的理由。

**`-wal` 文件**：unix VFS 只对主文件（xLock）和 `-shm`（xShmLock）加锁。WAL 文件以 `SQLITE_OPEN_WAL` 打开，`noLock = eType!=SQLITE_OPEN_MAIN_DB`（`sqlite3.c:46973-46974`）。所以关一个 `-wal` 的原始描述符不会丢任何 SQLite 锁（推断）。Litestream 的做法与此一致，见 2.3。D#632 把 `-wal` 也列进禁止清单，是更保守的写法，不需要放宽。

### 2.3　几种"读活库"的途径对照

| 途径 | 一手依据 | 用在本项目的情况 |
|---|---|---|
| 单独的进程 | §2.2：问题只在"同一进程"内。Litestream 本身就是独立进程，自己开 SQLite 连接，用长事务挡住检查点（`db.go:1272-1294`："Start long running read-transaction to prevent checkpoints"） | 父进程完全不受影响。子进程自己既有连接又开原始文件时，仍要注意关闭顺序 |
| 长期持有描述符、绝不中途关闭 | Litestream `db.go:1147-1149`："Open long-running database file descriptor. Required for non-OFD locks."。关闭顺序是先 `sqlDB.Close()`，再 `f.Close()`（`db.go:950-960`）。`litestream.go:160-161`："Do not use this with database files as it causes problems with non-OFD locks."（读 WAL 的函数允许 open/close）。`replica.go:45` 也是同样做法 | 可以放在服务器进程里，但 store 文件被替换或重建 inode 后，描述符会指向旧文件，比较脆弱 |
| 同一份库的第二个连接 | `sqlite3.c:41444-41450`；§2.2 | 在服务器进程内开只读连接跑 dbstat、quick_check 是安全的。危险的只是 fs 层的原始读 |
| `readonly: true` | better-sqlite3 `src/objects/database.cpp:154-158`（`SQLITE_OPEN_READONLY`）。只读 WAL 连接从不做检查点（`sqlite3WalCheckpoint`：`if( pWal->readOnly ) return SQLITE_READONLY;`，`sqlite3.c:71845`），关闭时的检查点就不会发生（`sqlite3WalClose`，`:70026-70060`） | 正好对应条件 (4)：打开器应先用只读句柄检查。评审实测"只读句柄跑检查，什么都不变"。只读打开在没有 `-wal` 时会新建空 `-wal`（评审观察，v6.30.8 也一样） |
| URI `mode=ro` / `immutable=1` / `nolock=1` | 文档：URI 默认关闭，要 `SQLITE_USE_URI=1` 或 `SQLITE_OPEN_URI`（https://sqlite.org/uri.html §2）。immutable "skips all file locking and change detection … might return incorrect query results and/or SQLITE_CORRUPT errors"；nolock 和正常连接混用 "database corruption can result" | better-sqlite3 13.0.3 用不了：`USE_URI=0`，`sqlite3_open_v2` 不带 `SQLITE_OPEN_URI`（`database.cpp:154-158`，`sqlite3ParseUri` 在 `sqlite3.c:190512-190514` 判断）。实测两种 URI 都是 `SQLITE_CANTOPEN`。在 node:sqlite 上实测 immutable 打开后看不到只提交在 WAL 里的表（`no such table: t`），所以它不适合活库 |
| `node:sqlite` | v22.5.0 加入，v22.13.0 起不需要 flag，v25.7.0 起 "release candidate"（https://nodejs.org/api/sqlite.html）。有 `readOnly` 选项，字符串 URI 可用（实测） | 不能和 better-sqlite3 同进程（§2.3）。Node 22.0–22.12 要 flag。没有 sqlite_dbpage |
| `sqlite_dbpage` | 经过 pager，有事务性（dbpage.html） | 没编进来（1.6） |

## 3　成熟项目会不会在 REINDEX 或 FTS rebuild 之前做完整性闸门

| 来源 | 实际做法 | 依据 |
|---|---|---|
| SQLite 文档 | FTS5 的 `'integrity-check'` 和 `'rebuild'` 各自独立。rebuild "first deletes the entire full-text index, then rebuilds it"，没有提先查页。REINDEX 文档讲的用途是 collation 或函数定义变了。pragma 文档只在 `case_sensitive_like` 改变 LIKE 定义导致索引"看起来坏了"时建议 REINDEX。对真正的损坏，文档给的是 recovery（在库外抢救） | https://sqlite.org/fts5.html §6.7、§6.12；https://sqlite.org/lang_reindex.html；pragma.html（case_sensitive_like 一节）；recovery.html |
| Firefox Places | 每周空闲维护，第一步是 `checkIntegrity`。另开一个连接（"Create a new connection for this check, so we can operate independently from a broken Places service"）跑 `PRAGMA integrity_check`；**不是 ok 才** `REINDEX`（"First, try to reindex, this often fixes simple indices problems."），然后复查；还坏就设 `places.database.replaceDatabaseOnStartup`，下次启动替换。启动时发现损坏：新建 `.recover` 文件，`ATTACH` 坏库，逐表 `INSERT INTO main.x SELECT * FROM corrupt.x`，再改名覆盖 | `toolkit/components/places/PlacesDBUtils.sys.mjs:99-126, 1446-1491`；`Database.cpp:837, 950, 990, 1027, 1060`（github.com/mozilla-firefox/firefox main，该文件最近提交 1100736 / 2026-10-29） |
| Android | `isDatabaseIntegrityOk()` 对主库和附加库跑 `PRAGMA x.integrity_check(1)`，由应用自己调用。默认的 `DefaultDatabaseErrorHandler.onCorruption` 直接删除数据库文件。没有自动 REINDEX | `core/java/android/database/sqlite/SQLiteDatabase.java:2888-2924`；`core/java/android/database/DefaultDatabaseErrorHandler.java:53-106`（android.googlesource.com frameworks/base main） |
| Chromium `sql::Recovery` | 出错回调里 `RecoverIfPossible`：用 `sqlite3_recover_init` 恢复到 `<db>.recovery`，再用 `sqlite3_backup_init(db, …, recover_db, …)` 一步写回原库，失败就 `RazeAndPoison`。`FullIntegrityCheck` 只是诊断，不是重建前的闸门 | `sql/recovery.h:95-150`；`sql/recovery.cc:94, 123, 196-262, 268-310`；`sql/database.h:557-568`（github.com/chromium/chromium main，recovery.cc 最近提交 ff4805d / 2026-05-28） |
| Litestream | `restore -integrity-check none\|quick\|full`，只在还原出来的新文件上跑。见 2.3 的锁处理 | `cmd/litestream/restore.go:40, 80-88`；`replica.go:1382-1416`（benbjohnson/litestream main @ 1068145，2026-10-31） |
| Apple Core Data | 没找到公开文档提到 integrity_check 或 REINDEX，Core Data 也不开源。**未确认**。QA1809 只说备份和恢复要用 `migratePersistentStore:…`，"rather than file system APIs" | https://developer.apple.com/library/archive/qa/qa1809/_index.html |

小结：
- 没有任何一个项目在"自动重建索引"之前加页级检查。
- Firefox 是反过来的：确认坏了才 REINDEX，然后靠复查加下次启动替换兜底。
- 处理坏库的通行做法是在库外抢救：新文件里 recover 或逐表复制，再用 backup API 写回或改名替换。
- 这些项目的 integrity check 都通过 SQLite 自己的连接完成。Firefox 在同一进程里另开一个连接，同一份库，符合 §2.2。

## 4　建议

### 4.1　采用现成的，还是自建

**不能直接采用的**：
- `quick_check`/`integrity_check`：1.2 的盲区，而且产品会 VACUUM。
- `sqlite_dbpage`/recover：没编进来，换 SQLite 构建等于引入新依赖。
- immutable 或 URI：better-sqlite3 不支持，而且对活库不正确。
- cksumvfs：目标不对，还要改库格式。

**结论**：自建一个小东西，并且尽量复用第二次尝试已经测过的部分。
- 第二次尝试的 P0 出在"在哪个进程里读"，不在读取器本身。
- R1：2,710 个样本逐页比对 0 页不同，判定 5,524/5,524 与第一次尝试相同。
- 评审把 close 挪到 ROLLBACK 之后的对照副本，在跨进程写者加 PASSIVE/RESTART/TRUNCATE 检查点下跑了 36,226 次检查，0 次 damaged、0 次 unchecked。

### 4.2　满足 D#632 条件的最小设计（A′：读取器搬进子进程）

1. **一个只做检查的叶子入口**。父进程用 `spawnSync(process.execPath, [entry, realpath(dbPath)], { timeout })` 调它，从 stdout 读 `{state, lines}`，只解析 JSON。
2. **子进程里**：
   - `new Database(p, { readonly: true, fileMustExist: true })`。
   - 跑 b6628ea7 的 `checkStorePages`：钉住快照、读文件、dbstat、每表 quick_check。
   - 然后严格按这个顺序收尾：`ROLLBACK` → `db.close()` → 关闭所有原始描述符（或者直接退出）。
   - 这样子进程关描述符时已经不持有连接，条件 (1) 对子进程也字面成立。只读连接不会做关闭检查点（`sqlite3.c:71845`）。
3. **父进程的接入点**：
   - 服务器的 `mem_fts_check rebuild`、`fts-check rebuild`、doctor、打开器的 VTAB 分支，都在任何读写打开或重建之前调用子进程。
   - doctor 把检查放在 `claude mcp list` 之前（条件 2）。测试要用一个"会启动服务器"的 `claude` 桩。
   - 打开器在开 raw 读写句柄之前调用（条件 4）。
   - `unchecked` 一律拒绝，fail closed。
4. **父进程永远不 open/read/close store 的 `.db`、`-wal`、`-shm`**。`statSync`、`realpathSync`、`existsSync` 不产生描述符（推断）。
   - 守卫要能说"不"：用 `git show b6628ea7` 的真实调用点做变异，确认守卫会红。
   - 按项目已有的教训，守卫要按行为写，不能只靠文本扫描。
5. **竞态尺子**：写者必须在另一个进程（条件 1 的原文）。可以沿用评审 `race-writer`/`race-checker` 的形状，三种检查点轮换，报重叠计数。
6. **复制命令**（条件 3）：
   - 用 `realpath(db)` 所在目录里的同名 `-wal`/`-shm`（依据 §1.4、§2.6）。
   - 也可以考虑由产品用 backup API 生成副本。好处：一致快照，自动解析链接和 WAL，不会把代码目录里的 node_modules 一起拷。代价：坏库上 backup 可能失败，而 `cp` 不会。

**代价（实测，Node 26.8.1，470 MB 合成库，负载约 6.7）**：起一个加载 better-sqlite3 并只读打开的子进程，用了 215–323 ms（5 次）。读取器本身的代价沿用评审的数：2.2 GiB 上 doctor 从 0.27 s 涨到 1.25–1.29 s。

**残留风险**：
- 子进程的快照和父进程随后的重建之间有一个时间窗。父进程可以在检查前 `BEGIN IMMEDIATE`，一直持有到重建结束来关掉它，代价是 hook 在检查期间拿不到写锁。默认建议不持有，写进说明。
- WAL 和 `-shm` 的解析仍在，它曾出过 d1cb8753 的问题。
- 第二次尝试 P3 里的内存、"一直在变"、热日志拒绝等问题还要逐条处理。

### 4.3　备选 C：backup 到私有文件，在副本上查

**做法**：
1. 只读连接 → `db.backup(tmp, { progress: () => 0x7fffffff })`，一步完成，得到一个快照。
2. 关闭这个连接。
3. 在没有任何连接的私有副本上：读第 1 页，走空闲页 trunk 链，用 dbstat 拿到树页集合，求交集、查越界、查计数。

**好处**：
- 活库只经过 SQLite 自己的 pager 访问，完全没有原始描述符。
- 不需要解析 WAL 和 `-shm`。
- 如果放在 doctor、fts-check 这类异步面上，甚至可以不起子进程。better-sqlite3 的 backup 只有异步 API，同步面仍需子进程。

**代价**：
- 实测 470 MB 拷贝用了 758–862 ms（3 次，热缓存，负载约 6.7）。
- 按比例推到 2.2 GiB 约 3.5–4 s，**未实测**。
- 临时磁盘等于库的大小。`/tmp` 可能是 tmpfs（本机是 12G 的 tmpfs），要放在同一文件系统并先查剩余空间。
- 坏库上 backup 可能失败，会得到更多的 unchecked。数量没测。

**适用**：只适合少见的重建路径。doctor 每次都跑的话太贵。

### 4.4　备选 B：只用 quick_check（目前不可行）

- 在同一进程、同一份库的第二个只读连接上，先跑 `EXPLAIN PRAGMA quick_check` 确认根页列表首项不为 0，再跑 `PRAGMA quick_check`。
- 这是最省代码的"采用现成"方案，同进程也是锁安全的（§2.2）。
- 但在 VACUUM 过的库上，它会一直判 unchecked。

**建议**：把 1.2 的复现（探针二、三）报到 SQLite 论坛。上游修好、better-sqlite3 跟进之后，B 可以替换掉自建的读取器。注意它也会跑完整的 FTS5 自检（`sqlite3.c:264173`），代价可能接近 R4 量到的 FTS5 自检（577 MB 上 2.2–2.3 s）。这一点**未实测**。

### 4.5　长期方向（只记一笔）

三个成熟项目都选择"坏了就在库外抢救再替换"。和这些做法对齐，判为 damaged 时就不该原地重建。可以考虑一个"所有会话关闭后，逐表复制到新文件、重建 FTS、改名替换"的命令（Firefox 的路线，用纯 SQL 就能做）。注意 better-sqlite3 的 ATTACH 不能用 `mode=ro`。
