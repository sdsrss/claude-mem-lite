**P2-1 install.mjs:1761-1790 + tests/install-flag-guard.test.mjs:363-367：status 的"可读不可写"修复对生产格式的 DB 不成立**
- 场景：schema.mjs:1326 把 DB 设成 `journal_mode = WAL`。最后一个连接关闭后 -wal/-shm 会被删除，这是 sudo 跑完后的常态。
  这种 DB 放在 500（或 root 拥有的 755）目录里，readonly 打开会失败，因为 SQLite 需要创建 -shm。
  结果 status 输出 `✗ Database: exists but check failed — attempt to write a readonly database — <dir> can be read but not written (EACCES)`，
  没有计数；JSON 里是 `exists:true, error:"attempt to write a readonly database"`，EACCES 不见了。
  只有当别的进程正开着这个 DB（-wal/-shm 已存在）时，才能拿到计数。
  新测试的 fixture 是 rollback-journal 格式的 DB，所以测的是生产环境里从不出现的形状。
- 证据（`REVIEW_SCRATCH=$S node $S/scripts/status-probe.mjs <tree> <case>`）：
  - head 500（非 WAL）：`✗ Database: 2 observations, 1 sessions — … can be read but not written (EACCES)`
  - head 500-wal（已关闭）：`✗ Database: exists but check failed — attempt to write a readonly database — … can be read but not written (EACCES)`
  - head 500-wal-open（有连接持有）：`✗ Database: 2 observations, 1 sessions — …`
- doctor 也有同样的盲区，修复前就存在。`$S/scripts/doctor-wal500.mjs <tree> wal` 输出：
  `⚠ DB schema: could not determine compatibility … (attempt to write a readonly database)` 和 `✗ Database: attempt to write a readonly database`。

  方向：给 fixture 加 `pragma journal_mode=WAL` 再 close；读取路径需要一种不依赖 -shm 的方式，比如 SQLite 的 `immutable=1`。better-sqlite3 是否接受 URI 我没有验证。

**P3-1 hook-update.mjs:873-879 + 935-936：删不掉的 journal 在之后的 swap 后被再次重放，会删掉新 release 的文件**
- 场景：R1 提交，`rm(journal)` 失败，备份按设计完整保留。下一次入口时 recovery 把 R1 回滚到旧版（这是连贯的）。
  如果此时 journal 仍然删不掉，接着安装 R2 会成功。再下一次入口（例如 R3 在 `npm install` 时离线失败）时 recovery 第三次重放 R1 的 journal：
  所有 backedUp 项的备份都已不存在，被 skip；但 installed-only 项（R1 新增、旧版没有的路径）被 rmSync，删掉的是 R2 的同名文件。
- 证据：`review-killpoints.test.mjs` 里的 F2，`F2 after failed R3 {…}` 中 R2 的 `cli.mjs` 消失了（`expected undefined to be '// new cli v2'`），并且 `.update-backup-*` 永久残留。
- 前提是 journal 删除要在连续两个入口都失败，现实概率低。修复前的代码是 `rm -r` 整个目录，如果持续失败，情况更坏（每次都删全部 installed）。
- 方向：删 journal 失败时，改为把 journal 覆写成空列表，或把备份目录改名成 tombstone，让 recovery 只删除、不重放。

- 场景：`rollbackInstall` 的第一轮删除 target，删到一半遇到 busy 文件抛 EBUSY 并被吞掉（target 目录还在、内容不全）。
  接着 `renameSync(backup → target)` 失败：目录是 ENOTEMPTY/EPERM；win32 上文件被无 share-delete 打开时 MoveFileEx 失败。错误被吞掉。
  随后 `discardSwapDirs` / `discardBackupDir` 先删 journal 再删备份目录，旧副本就没了，return false，只有 debugCatch 留下记录。
- 证据：
  - F1a：在 smoke 失败的路径上，删除新 node_modules 时先删掉一部分再抛 EBUSY；Linux 上 rename 原生就报 ENOTEMPTY。
    结果是 `{"hook.mjs":"// old hook","node_modules/dep.js":"new-dep","package.json":"…1.0.0","server.mjs":"// old server"}`：
    旧 node_modules 丢失，新 node_modules 残缺，residue `[]`。03e9ef8c 上结果完全一样。
  - F1b：swap 中途抛错，恢复 server.mjs 时 rename 抛一次 EPERM。结果树里没有 server.mjs。
- 为什么在 win32 上现实：1132 行在 smoke 之前就清除了 swap marker，而 smoke 最长可以跑几分钟（rebuild 120s×2 + source build 300s）。
  这段窗口里启动的 hook/MCP 会加载新树里的 better_sqlite3.node。如果之后 smoke 失败，回滚删 node_modules 时就会碰到已加载、无法删除的 DLL。
  另一个来源是 Defender 扫描刚写出的 .node。这正是 D#283 提到的同一类 EBUSY。
- 方向：
  - 让 `rollbackInstall` 返回是否全部恢复成功。不完整时保留 journal 和备份目录，交给下次入口的 recovery 重试；现在重放是幂等的，这样做是安全的。
  - win32 上 rmSync 加 `maxRetries`/`retryDelay`：Node 会对 EBUSY/EPERM/ENOTEMPTY/EMFILE/ENFILE 退避重试，默认是 0 次。

**P3-7 hook-update.mjs:1144-1145 + 873-879：已提交的 swap 会被"延迟回滚"**
