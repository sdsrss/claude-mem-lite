# Pre-release review: `uninstall --purge` (c79bd41e, edf93f3f, e375b8ab, 8202410a)

Reviewer tree: `git archive 9da56038` + copied node_modules, Node 26.8.1 (the only Node on this host). install.mjs is identical at e375b8ab and 9da56038, so the line numbers below hold for both. Every run used a sandbox HOME (and CLAUDE_MEM_DIR when set) under the work dir, with LLM keys and proxies unset. Baseline: `npx vitest run tests/install-lifecycle.test.mjs` passed 58/58.

## Verdict
- **Data loss / following a link (P0):** none found. The purge never deleted through a link in any shape I ran. On Node 26, rmSync removes a top-level link or an inner directory link without following it. I ran a real `install --dev` into a sandbox HOME, which made 47 top-level links (node_modules and scripts are directory links into the checkout), then `uninstall --purge`. Result: `✓ Data purged`, `Done!`, exit 0, and the checkout was untouched (15142 files before and after, same md5 of the file list).
- **Contract points 1–4:** each holds on Linux for every shape I ran.
- **Contract point 5:** false in one constructed shape (F2). The dev-link exemption is narrower than the contract says (F1, P2).
- **Highest severity:** P2 (F1). Everything else is P3.

## Findings

### F1 — P2, REAL (anyone who used `install --dev` on an earlier release): code links from an earlier dev install block the whole purge
- **Where:** install.mjs:609, where `DEV_LINK_NAMES` is the *running* release's SOURCE_FILES first segments plus `scripts` and `node_modules`.
- **What breaks:** a dev install from an earlier release left top-level links that nothing ever removes:
  - The dev branch (install.mjs:613-642) re-links only current names and clears only `registry`.
  - `pruneStaleInstallFiles` skips symlinks (install.mjs:4204) and runs only in the non-dev branch.
  - Each leftover link is "a link other than a dev code link", so the purge removes nothing, skips CLAUDE_MEM_DIR and exits 1 on every rerun.
- **Leftover links that exist in history:**
  - `commands` (dev branch of v2.50.0, `git show v2.50.0:install.mjs` lines 248-251; nothing removes it today).
  - SOURCE_FILES names since removed: `.mcp.json` (until 09aafaa9, v3.63.0), `registry.mjs` / `registry-retriever.mjs` / `registry-github.mjs` (until 944f2162, 2026-09-06), `launch-preflight.mjs`, `binding-probe-cli.mjs`.
  - The reverse case too: a dev install from a newer checkout, uninstalled by an older `npx` release that lacks a new top-level name.
- **Repro:** dev links `cli.mjs`, `scripts` and `node_modules`, plus a stale `registry.mjs` link (dangling) and a `.mcp.json` link, plus CLAUDE_MEM_DIR=`$H/reloc` holding a store. Output:
  ```
    ⚠ ~/.claude-mem-lite/.mcp.json is a link to …/repo/.mcp.json, ~/.claude-mem-lite/registry.mjs is a link to …/repo/registry.mjs. --purge does not delete through a link, so it removed nothing (CLAUDE_MEM_DIR …/reloc included).
    ✗ Uninstalled, but the purge is incomplete: see the lines above.
  exit=1
  ```
  Everything stayed, `reloc/claude-mem-lite.db` included. The same layout on 79374f2d's install.mjs gave `✓ Data purged`, `Done!`, exit 0, with the directory gone. So this is a regression for these users.
- **Effect:** it fails safe (nothing deleted), but a code link is reported as if it guarded data, and the user has to delete links by hand that they never made.
- **Falsifies** claim 1's "does not block". The claim holds only for names in the running release's SOURCE_FILES.

### F2 — P3, CONSTRUCTED: "Done!" and exit 0 with `~/.claude-mem-lite` still there when it cannot be looked at
- **Where:** install.mjs:1997-1998 swallows the lstat error (EACCES included). Then `existsSync(DATA_DIR)` at :2015 is false on EACCES, so no branch prints anything.
- **Repro:** HOME set to mode 0600, CLAUDE_CONFIG_DIR outside HOME, a store inside. Output: `✓ MCP server removed`, `✓ Hooks and plugin settings cleaned`, `Done!`, exit=0. `claude-mem-lite.db` is still there and no line mentions the purge.
- **History:** this predates the change (79374f2d used the same existsSync gate). Contract point 5 as worded ("Done! … only when ~/.claude-mem-lite is gone") is false for this shape.
- The same existsSync-means-absent defect was fixed for the relocated store (statSync + `err.code`, install.mjs:2041-2047) but not for the home directory. The new lstat already holds the error code.

### F3 — P3, REAL-narrow: a dangling link blocks the purge on every rerun, and the refusal names no remedy
- **Shapes:**
  - `~/.claude-mem-lite/runtime -> …/gone` (dangling, inside a real directory) gives `⚠ ~/.claude-mem-lite/runtime is a link to …/gone. --purge does not delete through a link, so it removed nothing.` and exit 1, although nothing is behind it.
  - A dangling top-level link behaves the same way; the test at tests/install-lifecycle.test.mjs:514 pins that.
- **Why it matters:** the line never says what to do (remove the link by hand, or the target too if intended, then rerun). That also applies to F1 and to an unrelated CLAUDE_MEM_DIR skipped because of a link.
- This matches the contract's wording; it is a usability defect, not a wrong outcome.

### F4 — P3, REAL (`claude` not on PATH, or `claude mcp remove` failing while registered): exit 3, not 1, and the final line hides the incomplete purge
- **Where:** install.mjs:2133-2139 returns `EXIT_MCP_UNREGISTERED` (3) before the `purgeIncomplete` check at :2140.
- **Repro:** `~/.claude-mem-lite` a link, plus `~/.claude.json` still listing `mem-lite`. Result: exit=3. The `⚠ … is a link … removed nothing.` line prints, but the closing `✗` line mentions only the MCP server.
- This precedence existed before; contract point 1 says "exits 1".

### F5 — P3, CONSTRUCTED: the rule against deleting through links is not applied to CLAUDE_MEM_DIR (all predates the change)
- **(a) The relocated store is itself a link:** `reloc/claude-mem-lite.db -> ext/store.db` gives `✓ Relocated data purged (…/reloc)`, `Done!`, exit 0, and `ext/store.db` stays. Code: `purgeOwnedDataEntries` rmSyncs the link (install.mjs:2207-2213).
- **(b) CLAUDE_MEM_DIR nested inside `~/.claude-mem-lite`:**
  - The whole-directory rmSync takes a user file in it (`data/my-notes.txt` was deleted), against the 6.33.0 rule that keeps the user's files in a relocated directory.
  - A store link one level down is unlinked and the target kept.
  - Result: `✓ Data purged`, `Done!`, exit 0, `ext/store.db` left.
  - The links check looks at the top level only (install.mjs:1993-1996).
- Neither shape is in the contract's wording, but the release text "nothing was linked out of it" invites the reading that they are covered.

### F6 — P3, REAL in containers that mount a volume at `~/.claude-mem-lite`; NOT RUN, reasoned from the code: exit 1 while everything was removed
- **Mechanism:** with `~/.claude-mem-lite` a mount point, rmSync empties it, and the final rmdir fails with EBUSY.
- **Result:** the catch at install.mjs:2026-2028 prints `Could not remove ~/.claude-mem-lite (EBUSY).` and exits 1, with no data left.
- **Why not run:** this host denies user namespaces (`unshare -rm` failed writing uid_map) and has no fuse3 headers, so I could not build a mount point.

### F7 — P3, CONSTRUCTED: CLAUDE_MEM_DIR spelled as the default with a trailing slash gives contradictory lines
- **Repro:** CLAUDE_MEM_DIR=`$H/.claude-mem-lite/` with a 0555 subdirectory. Output:
  ```
    ⚠ Could not remove ~/.claude-mem-lite (EACCES).
    ✓ Relocated data purged from …/.claude-mem-lite/
    ⚠ Kept 1 entry there that it does not recognise as claude-mem-lite's: locked. …
  exit=1
  ```
- **Cause:** the `MEM_DATA_DIR !== homeDir` string comparison (install.mjs:2038, from 6.33.0) runs the relocated purge on the same directory. The exit code is right; the ✓ line contradicts the line above it.

### F8 — P3: test gaps (mutations that survive)
- **Method:** 16 per-site mutations of install.mjs. For each, the runner asserted that exactly one site was replaced and the file changed, then ran `npx vitest run tests/install-lifecycle.test.mjs`. install.mjs was restored byte-equal afterwards.
- **Score:** 12 of 16 killed.
- **Survivors:**

| Mutant | Change | What it shows |
|---|---|---|
| M11 | `&& existsSync(join(DATA_DIR, e.name))` added to the inner-link filter, so dangling inner links are ignored | Inner dangling links are not pinned (the top-level dangling case is). |
| M13 | Inner-link check limited to `['claude-mem-lite.db', 'runtime']` | Only those two names are tested. A `claude-mem-lite.db-wal`, `metrics` or backup link would go unchecked with all 58 tests green. |
| M14 | `'metrics'` added to `DEV_LINK_NAMES` | Nothing stops a data name from entering the exemption. |
| M16 | Relocated purge skipped in the "still there when the removal returned" branch | The race test does not assert the relocated purge. Contract 3 arguably covers that case ("removal fails"). |

- **Killed:** M1 (no dev exemption), M2 (inner links never found), M3 (top-level link not detected), M4 (relocated purge despite links), M5 (no post-removal check), M6 (failure not marked incomplete), M7 (errno hard-coded to EACCES), M8 (relocated purge skipped on failure), M9 (CLAUDE_MEM_DIR always named), M10 (link branch not marked incomplete), M12 (race branch also prints "Data purged"), M15 (link target not named).

## Contract points 1–5 (Linux, Node 26.8.1)
1. **Holds.** Shapes run: absolute link; relative link with relative HOME; link to a link; HOME with a trailing slash; dangling link; CLAUDE_MEM_DIR = target, `<link>/`, `<link>/.`, inside the target, or unrelated (the last four via the tests). In each, the link and target were intact, no "Done!", exit 1. Before (79374f2d): `✓ Data purged`, `Done!`, exit 0, store left (re-run).
2. **Holds**, with F1 as the exception. Shapes run: inner `claude-mem-lite.db-wal` link with relative HOME; dangling `runtime` link; store and runtime links via the tests.
3. **Holds.** EACCES (0555 subdirectory): `⚠ Could not remove ~/.claude-mem-lite (EACCES).`, the relocated store was purged, exit 1. Before: a stack trace (`Error: EACCES … at rmSync … at uninstall (install-base.mjs:1978)`) and the relocated store left (re-run).
4. **Holds** in a real race: a churn process doing writeFileSync + unlinkSync in `runtime/`, 10 runs plain and 10 runs re-creating the directory. 0 of 20 printed "Done!" with the directory left. Plain: 4 clean Done, 6 incomplete with the directory left. Re-creating: 10 incomplete.
5. **False** for F2 (constructed). Outside the contract's wording: F5.

## The three claims
- **"A dev-install code link at the top level does not block the purge, and is not followed."**
  - "Not followed": holds. Node 26 direct check, plus the real `install --dev` → purge run with the checkout intact.
  - "Does not block": false for code links from an earlier release (F1).
- **"The relocated CLAUDE_MEM_DIR purge still runs when ~/.claude-mem-lite fails to be removed, but not when ~/.claude-mem-lite is a link."** True (install.mjs:2038, the EACCES run, mutants M4/M8 killed). It is also skipped when the directory merely holds a non-dev link, which the claim leaves out. It does run in the "still there" branch, and no test pins that (M16).
- **"tests/install-lifecycle.test.mjs covers each of contract points 1–5."** Each point has at least one test that fails when it breaks (12 of 16 mutants killed). The four survivors in F8 are the gaps.
