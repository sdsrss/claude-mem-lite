## Non-TRUE claims

### P1

**P1-1 — CLAUDE_MEM_SKIP_UPDATE also disables the manual update, which then says "Already up to date"**
- Location: README.md:1195; CHANGELOG.md (working tree) v6.23.2 Docs bullet.
- Claims: README "Skip the 24h update check against GitHub Releases and its session-start notice." CHANGELOG "`CLAUDE_MEM_SKIP_UPDATE` turns off the check and the notice."
- Verdict: OVERSTATED by omission. The list of things the variable turns off leaves out the update command that the same paragraph tells users to run.
- Evidence: hook-update.mjs:75 `if (isDevMode() || process.env.CLAUDE_MEM_SKIP_UPDATE) return null;` sits inside `checkForUpdate`. `manualUpdate` (install.mjs:3221) calls `checkForUpdate({ force: true, allowInstall: true })`; on `null` it prints `Already up to date (v${ver})`. M6 reproduces this with an install at v1.0.0.
- Effect: a user who sets the variable to silence the notice later runs `node install.mjs update`, is told they are current, and stays on the old release, which may lack security fixes.
- Suggested correction: in the README and CHANGELOG, say "Turns off every release check: the 24h background check, its session-start notice, and `node install.mjs update` (unset it to update)". Better: make `manualUpdate` report "update checks are disabled by CLAUDE_MEM_SKIP_UPDATE" instead of "Already up to date". That is a code change and is not in this release.

**P2-4 — NO_PROXY does not "match the way curl, Python and Go match it"**
- Location: CHANGELOG fix 2 heading; commit 1e39452 subject; lib/proxy-fetch.mjs:55-60 doc comment.
- Claims: "`NO_PROXY` matches the way curl, Python and Go match it." The comment says the matcher "follows what curl, Python and Go share", then lists: written with or without a leading '.' or '*.'; an IP entry matches exactly; :port narrows; IPv6 with or without brackets.
- Verdict: FALSE as stated. The matcher is a union of dialects, not their shared part. In M2 it disagrees with curl on 4 of 9 single-variable probes and with Python on 5 of 9, and with both on which variable wins when NO_PROXY and no_proxy are both set.
- Where it departs from each:
  - **curl** does not honour `*.x`, `host:port`, or `*` inside a list (M2). curl 8.18 does honour CIDR (M2), which the matcher does not.
  - **Python** does not honour `*.x`, unbracketed `::1`, or `*` inside a list. It does suffix-match an IP host (`0.0.5` exempts 10.0.0.5), which the matcher does not.
  - **Go**, per the survey table ("Strips leading . ?" = No; "Supports CIDR blocks?" = Yes; "Detects loopback IPs?" = Yes): `.x` does not cover the apex `x` (it does here), and Go has CIDR and the loopback bypass, which the matcher lacks.
  - **Precedence**: the survey's "Case precedence" row is lowercase for curl and Python and Uppercase for Go. proxy-fetch.mjs:46 reads `NO_PROXY || no_proxy`, so uppercase wins: Go's rule (M2, last row).
  - The survey says nothing about ports, `*.`, IPv6 brackets or IP-suffix matching, so citing it for those rules is unsupported. Its curl CIDR "No" is stale for curl 8.18.
- Suggested correction:
  - CHANGELOG: "`NO_PROXY` understands the forms common clients accept", keeping the sub-bullets, plus one more: "When `NO_PROXY` and `no_proxy` differ, `NO_PROXY` wins (as in Go; curl and Python prefer the lowercase one)."
  - Doc comment: "a union of curl's and Python's leading-dot rule with Go's `*.` and `:port`; it differs from each client somewhere (see above)."

**P2-5 — "a connect to it never leaves the host" is weaker as a safety premise than it reads**
- Location: lib/anthropic-base-url.mjs:19-24; CHANGELOG fix 3; commit 8001bd0.
- Claims: "Plain http:// is allowed only to this machine ... a connect to it never leaves the host". CHANGELOG: "A connection to either address stays on the machine."
- Verdict: TRUE for a direct connect (M4, Linux). OVERSTATED as the reason the key stays on the machine.
- Evidence: with Node's opt-in `NODE_USE_ENV_PROXY=1` and HTTP_PROXY set, native fetch hands the plain-http request to the proxy, `x-api-key` included and unencrypted (M5). That happens even under this machine's own NO_PROXY (`localhost,127.0.0.1,::1`), which exempts 127.0.0.1 but not 0.0.0.0. Loopback is exposed the same way when NO_PROXY does not list it, so this is a pre-existing gap, but `0.0.0.0` is the address typical NO_PROXY lists leave out.
- Rated P2 rather than P1 only because NODE_USE_ENV_PROXY is opt-in. Tested on Node 26 only.
- Suggested correction: "a direct connect to it never leaves the host. Node's NODE_USE_ENV_PROXY=1 sends http requests to HTTP_PROXY unless NO_PROXY lists the host; that applies to loopback too." Alternatively, refuse plain http when NODE_USE_ENV_PROXY is set.
