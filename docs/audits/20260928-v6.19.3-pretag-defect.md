## Findings

### F1 — P2 — D#155's keep rule stores complete private keys that are not base64 (secret-scrub.mjs:214-219)

**Q1 answer: yes.** e377959 keeps a complete BEGIN…END block whose body has no 16-char base64 run
and has a space between two non-space characters. The comment at secret-scrub.mjs:209-211 states
the premise: "every line of every key format is a run of 16+ base64 characters … so a body with no
such run holds none". That is true of PEM *encodings* and false of key *material*: a decoded key
between the markers has no base64 run. 41b9659 erased every complete block, so it redacted these
shapes. e377959 stores them whole.

Measured with real keys generated in this sandbox (openssl 3.5.5). "stores" means the private
scalar/exponent's first hex line survives scrubSecrets:

| shape (all between a private-key BEGIN and END) | 41b9659 | e377959 |
|---|---|---|
| `head -1 k.pem; openssl pkey -in k.pem -noout -text; tail -1 k.pem`, Ed25519 (`priv:` hex) raw / JSON-escaped | redacted / redacted | **stored / stored** |
| same, EC P-256 raw / JSON-escaped | redacted / redacted | **stored / stored** |
| same, RSA-1024 raw (privateExponent, prime1, prime2, …) | redacted | **stored** (whole 2145-char text kept) |
| same, RSA JSON-escaped | redacted | redacted (only because `\nprivateExponent` is a 16-char run) |
| C array `// <BEGIN>` / `static const uint8_t key[] = { 0x30, 0x77, … };` / `// <END>` | redacted | **stored** |
| Python `# <BEGIN>` / `KEY = b"\x30\x77…"` / `# <END>` | redacted | **stored** |

Repro (files under this dir; keys are throwaway, generated here):
```
R=<this dir>; R=$R node $R/fuzz/dump-probe.mjs   # RSA composed + `openssl pkey -text` (PEM then dump)
R=$R node $R/fuzz/dump-probe2.mjs                # EC and Ed25519, raw + JSON
R=$R node $R/fuzz/carray-probe.mjs               # C array, Python bytes
```
Output:
```
composed.txt ... old keeps privateExponent: false ... new keeps privateExponent: true  new len 2145
composed_ec.txt priv line b3:15:ff:… | raw: old false new true | json: old false new true
composed_ed.txt priv line 1d:3d:d8:… | raw: old false new true | json: old false new true
c-array bytes 121 | old stores key bytes: false | new stores key bytes: true
py-bytes bytes 121 | old stores key bytes: false | new stores key bytes: true
```
Differential fuzz (fuzz/diff-fuzz.mjs; 12-char windows of every key line / dump line / array row;
a "regression" is a window in the e377959 output that is absent from the 41b9659 output):
- 30,000 inputs, seed 202, all segment kinds: 8,638 regressions. 8,637 regress only windows of an
  openssl dump or a byte array; 1 regresses a base64 key line (F2).
- 30,000 inputs, seed 101, without the dump-between-markers and byte-array generators: 29
  regressions, all dump windows (a standalone dump the composition put between a BEGIN-only and an
  END-only segment); 0 regress a base64 key line.

Scope of the exposure, so the grade can be checked: the dump or array has to sit INSIDE a BEGIN/END
pair. `openssl pkey -text` prints the PEM first and the dump after it, so the dump leaks in BOTH
trees there (pkeytext.txt: old keeps privateExponent: true, new: true). The PostToolUse description
path is not affected: utils.mjs:295 scrubTruncate cuts its window before the first BEGIN. The
whole-text writers are: user_prompts (hook.mjs:3038 `scrubSecrets(promptText)`), import-jsonl
tool_result content (lib/import-jsonl.mjs:166), mem_save content, and restore's re-scrub. Graded P2
because it needs that composition; it is a full private key written to the database, and the rule's
own doctrine ("a leak costs more than the prose") argues for fixing before tag if the fix is cheap.
Candidate fix: also erase when the body holds a byte dump — e.g. 16 consecutive hex bytes with
separators `(?:\b[0-9a-f]{2}[:, ]\s*){16}`, `(?:0x[0-9a-f]{2}\s*,\s*){8}`, `(?:\\x[0-9a-f]{2}){8}`
(case-insensitive) — or keep only short bodies (every D#155 test case body is under 200 chars).
Measure both arms on fuzz/diff-fuzz.mjs before shipping.

### F2 — P3 — a kept marker block changes what the key scanners reach (secret-scrub.mjs:214-219 with 715-820)

A block the new rule keeps leaves its BEGIN, its lines and its END in the text, where 41b9659 had
one `***PEM_KEY***` token. In 60,000 fuzz inputs this stored a base64 key line 41b9659 erased
twice, and an unlabelled password once:
```
R=<this dir>; R=$R node $R/fuzz/f2-replay.mjs
full-b64 "ZtS3/XebBS7K" | old stores: false | new stores: true | input chars 1096
smoke-b64 "AQdAjQoUi3/A" | old stores: false | new stores: true | input chars 446
full-password "Hunter2Correct!!" | old stores: false | new stores: true | input chars 485
```
smoke-b64 is a CR-separated, `+`-prefixed PGP key with no END of its own, followed on its last
line by a placeholder block and then a stray END (`…zw9 <BEGIN>\r+<your key here>\r+<END> <END OPENSSH>`).
In 41b9659, erasing the placeholder joined the key's last line to the stray END's line, so the
tail scan from that END reached four key lines (an old tree with scrubKeyTails removed stores them:
fuzz/f2-mech2.mjs, `old without tail scanner stores: true`). In e377959 the placeholder's own
lines sit between, and the scan stops at `+<your key here>`. Not the `floor`: a copy with
`floor` forced to `last` still stores all three (fuzz/f2-mech.mjs). 41b9659's catch was incidental.
full-password: `Hunter2Correct!!` alone on a line between a BEGIN and an END in a JS string
concatenation; 41b9659 erased it with the block, e377959 keeps it (no other pattern covers an
unlabelled password, in either tree). All three inputs are generator compositions (a placeholder
block glued between a key's lines and its END; a random character mutation), not shapes seen in
tool output. The simple placements do not regress: fuzz/barrier-probe.mjs (key tail, placeholder
block on the same line / next line / own lines, then the END) stores the same in both trees.

### F5 — P3 (observation) — browse's "current session" is empty from the first Stop of every session (lib/browse-core.mjs:23-30)

Stop marks the hook row `completed` on every turn (hook.mjs:1223-1232, `status IN ('active',
'completed')`), and nothing sets it back to `active` (UserPromptSubmit is `INSERT OR IGNORE`,
hook.mjs:3002-3007; grep for `status = 'active'` finds only WHERE clauses). So from the first Stop
getActiveMemorySessionId returns '' (or another project hook row still active), and computeTier
rule 2 (tier.mjs:34) never fires for the session in progress. tests/browse.test.mjs pins this ("is
no session once Stop has marked the hook row completed"), so it is intended; it means D#153 removed
the wrong answer rather than restoring a right one. Rules 3-4 (same project, last 2h) still put the
session's own rows in the working tier. Display only.

### Pre-existing (not introduced by the range) — P3 — a quote before a diff `+` on the BEGIN line defeats the cut-off scanner

Found while explaining F2. A cut key (no END) whose lines carry a `+` prefix, when the BEGIN line
has a quote before its `+` (`'+-----BEGIN …` / `b'+-----BEGIN …`), is stored whole in BOTH trees:
the BEGIN line's prefix shape is `'+`, the body lines' prefix is `+`, so the first body line reads
as the SHORT line `+` and cutOffKeyEnd returns -1 (secret-scrub.mjs:659).
```
R=$R node $R/fuzz/preexist-probe.mjs
b'+ CR, cut | old stores: true | new stores: true
b'+ LF, cut | old stores: true | new stores: true
+ LF, cut (no b') | old stores: false | new stores: false
'+ LF, cut | old stores: true | new stores: true
```

## Answers to the questions

**Q1 (security).** Yes — F1: complete private keys in a non-base64 encoding between a BEGIN and an
END (openssl `-text` dumps, C byte arrays, Python `\x` bytes) are stored by e377959 and were
redacted by 41b9659. For base64 key material: 0 regressions in 30,000 fuzz inputs without the
dump/array generators (seed 101), 1 in 30,000 with them (seed 202) and 1 in a 3,000-input smoke
run (seed 11); both are F2. Generator: real RSA-1024/2048 (PKCS#8, PKCS#1, PKCS#1 encrypted with
Proc-Type/DEK-Info), EC (PKCS#8, SEC1, encrypted PKCS#8), Ed25519, OpenSSH ed25519 and RSA, a GnuPG
armored secret key, and synthetic keys (7 labels, widths 64/70/76, armor headers incl. `C:\`
paths and PGP CRC); segments: full key, head/tail by lines, head by chars, flattened on one line,
middle elided, BEGIN-only, END-only, marker-naming prose (the D#155 cases), plain prose, other
secrets; 13 separators (LF, CRLF, CR, `\n`, `\\n`, `\\\\n`, `\r\n` escaped, `<br>`, space, tab,
` | `, blank line), 17 line prefixes (Read's `     N\t`, `N→`, grep `f:`/`f-N-`, `> `, `> > `,
diff `+`/`-`/space, `| `, `// `, `# `, `web-1  | `, indent, tab), 11 wrappers (JSON once/twice,
JSON object, Python bytes repr, JS concatenation, fence, `<pre><code>`, backticks, XML), and up to
three random character edits. Windows are 12-char substrings; the leak test is window-in-output
(fuzz/lib.mjs, fuzz/diff-fuzz.mjs; runs: out-full.json, out-b64only.json).

**Q1, perf commit 853e28e.** Output identical to 41b9659 on every input tried: perfDiff 0 of
63,000 (3,000 + 30,000 + 30,000; three-arm runs above). Code read agrees: `isB64Code` accepts the
same 65 code units as `[A-Za-z0-9+/=]`, every call site checks `i < length` first, `' \t+,;)]}'`
is the old class, and a line that starts with `-----BEGIN ` classifies OTHER with or without the
new early break (no strip applies when `shape` is null, the core starts with `-`), which breaks
the loop in both arms.

**Q2 (text 41b9659 kept that e377959 erases).** None found. Every tracked text file of the
e377959 tree, raw and JSON-wrapped (1,694 inputs; fuzz/corpus.mjs): 18 differ, and in all 18 the
new output is longer (keeps more). Fuzz: 48 inputs where a token of 41b9659's output is missing
from e377959's, after dropping 16+ base64 runs; all 48 token sets are key structure (END/BEGIN
markers, armor headers, a key's last line, a PGP CRC, a line prefix) in a composition where
41b9659 stored a key and e377959 erases it (e.g. fuzz/out-full.json lostProse, `…Proc-Type: 4,…
DEK-Info…` and a full encrypted RSA body that 41b9659 stored). The one prose-looking token
(`KEY-----Run`) is a tokenisation artefact: the sentence is still in the new output.

**Q3 (readers of the hook id, browse current session, restored ids).** Nothing in the shipped files
(package.json#files, bash hooks included) parses the hook id's tail or its shape: the readers of
`memory_session_id` patterns are lib/provenance.mjs:40 (prefix `manual-`), hook-optimize.mjs:595
and :1348 (prefix `manual-`), lib/browse-core.mjs:26 (`LIKE 'hook-%'`), search-engine.mjs:407 (via
isAutoWritten), schema.mjs:911/920/1016/1026 (uuid shape; `~` ids are 37 chars). No bash hook reads
a session id. The session id is not sanitised into a file name or matched by a regex anywhere. The
browse current session has two callers (server.mjs:1878, mem-cli.mjs:1865), both feeding only the
tier classifier; stats-core.mjs:164 and search-core.mjs:505 pass ''. A restored row's `restore-`
id is read by isAutoWritten (auto-written: intended) and keeps it out of the manual-only narrow
re-enrich pool (hook-optimize.mjs:595), which is also right. See F5 for the reach of the current
session.

**Q4 (parallel paths).** sdk_sessions writers: hook.mjs:1854 and :3004, hook-llm.mjs:295 (hook id
from getSessionId/createSessionId -> hookSessionId; every SessionStart mints a fresh one at
hook.mjs:2772, so a pre-upgrade uuid-shaped session file lives at most until the next
SessionStart), lib/save-observation.mjs:210, lib/compress-core.mjs:101, hook-optimize.mjs:599/1352/1609
(all writerSessionId), lib/import-jsonl.mjs:93 (`import-<cc uuid>`, 43 chars, and content id !=

re-save). PEM marker pairing: only the block pattern (secret-scrub.mjs:215); the two line scanners
do not pair, and utils.mjs:295 only cuts at the first marker.

**Q5 (performance).** F3. Nothing superlinear: every kept-block shape's ratio is flat from 200k to
400k. Under coverage two shapes exceed the suite's 10x budget; the existing suite passes.

**Q6.** F4 (tests), F5 (observation). Versions agree at 6.19.3 in package.json, package-lock.json
