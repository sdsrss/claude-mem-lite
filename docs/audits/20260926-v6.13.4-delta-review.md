### P3-2 (pre-existing, same in ASC and DESC): the common healthy timeline never reaches the protected path
Every Stop spawns llm-summary (hook.mjs:1605). If the Stop-spawned worker succeeds before /clear, the Stop row is already
`llm` when SessionStart writes the second row; the /clear worker then finds ONE fast row and upgrades it with its own
(emptier) floor, and that row wins Last Session (newest epoch). Probe S1 (Stop row upgraded by a full reply, then /clear row,
then a degraded reply), identical output on NEW and on the DESC mutation:
  ROWS [{"id":1,"notes":"llm",...,"completed":"FULL-DONE","remaining_items":"FULL-REM"},{"id":2,"notes":"llm","request":"llm request","completed":"","remaining_items":""}]
  LAST "Last Session\nRequest: llm request\n\n### Recent ..."
So the ASC choice only matters when every earlier Stop-spawned run failed or returned early. Not a regression; scope note
for the comment's implied guarantee.

### P3-3 (pre-existing; ASC is the WORSE order here): two successful runs while both fast rows exist
A Stop-spawned worker whose Haiku call straddles a quick /clear SELECTs existingFast after row 2 exists (the SELECT runs
after `callLLM` returns, hook-llm.mjs:1490 vs 1440). Then two runs each upgrade one fast row, and the LATER upgrade wins
Last Session. Probe S3 (two fast rows, two degraded runs back to back):
  NEW (ASC):   LAST "Last Session\nRequest: llm request\n\n### Recent ..."   (id 2, the /clear row, upgraded last)
  DESC mutant: LAST "Last Session\nRequest: llm request\nCompleted: STRUCT-DONE\nRemaining: STRUCT-NOTDONE\n..."
Neither ordering is right for both this and the single-run population the case pins (where DESC loses them). D#79 already
records "two llm-summary workers ... can each upgrade a different fast row" as reasoned-not-built; this is now built.
A content-aware floor (e.g. COALESCE across all of the session's fast rows, or retiring sibling fast rows on upgrade)
would be order-independent.

### P3-4 (pre-existing, same in ASC and DESC): a Stop row with Failed/Uncertain markers is not `notes='fast'`
writeFastSummaryBaseline sets `notes = structuredNotes || 'fast'` (hook.mjs:1128), so a Stop tail carrying Failed: /
Uncertain: writes notes "Failed: ..." and is invisible to existingFast. The only fast row is then the SessionStart row,
which is upgraded; the Stop row's Done / Not done (and Failed/Uncertain) never reach Last Session. Probe S2 (notes
'Failed: x' Stop row + empty fast /clear row + degraded reply), identical on NEW and DESC:
  ROWS [{"id":1,"notes":"Failed: x","completed":"STRUCT-DONE","remaining_items":"STRUCT-NOTDONE"},{"id":2,"notes":"llm","request":"llm request","completed":"","remaining_items":""}]
  LAST "Last Session\nRequest: llm request\n\n### Recent ..."
Live 09:07Z: 9 structured rows; 3 sessions pair one with a fast row (144/145, 304/307, 446/448, fast row completed 0 /
remaining 0 in all 3). The commit comment "the LOWEST id is the Stop row, which carries the structural Done / Not done
extract" therefore covers only Stop rows whose tail had no Failed/Uncertain lines — the richest Stop rows are excluded.

### Population / reachability note (affects the "5 of 75" evidence, see B4)
Live 09:07Z: 0 of the 75 two-fast sessions (and 0 of 217 single-fast sessions) have any observation passing
`notLowSignalTitleClause`; indeed 0 fast-row sessions have any observation at all (164 obs live, 14 sessions).
handleLLMSummary returns at `recentObs.length < 1` (hook-llm.mjs:1399) before existingFast, so none of the 75 pairs can
reach the UPDATE today. The pairs are a survivor population (sessions the upgrade never touched), usable as a picture of
what the two writers produce, not as a rate at which the regression fires.
