## Findings

### C1 — P1 — `.claude/settings*.json` is still read without bound on every hook event

- Where: CHANGELOG.md:21-28 ("no longer read without bound … every hook event read the project's
  `.claude/settings*.json` the same way … now counts as unreadable when the plugin reads … `.claude/settings*.json`");
  release commit 005fb981 ("project files are read only when they are regular files, up to 4 MiB"); 4e040a82 body.
  The reads that remain: `scripts/hook-launcher.mjs:199-215` (`pluginDisabled()`, plain
  `JSON.parse(readFileSync(path, 'utf8'))` of `<project>/.claude/settings.json` and `settings.local.json`, at module top
  level, before the entry is imported) and `scripts/post-tool-use.sh:49-55` (`[[ -r "$_f" ]]` then `_settings=$(<"$_f")`
  for the same two files). Both files are unchanged since v6.35.2. Every node hook in `hooks/hooks.json` runs through
  hook-launcher.mjs (SessionStart, PreCompact, PreToolUse Edit/Write/Read, PostToolUse recall, PostToolUseFailure, Stop,
  UserPromptSubmit; pre-tool-recall-bash.sh, pre-agent-inject.sh and post-tool-use.sh hand off to it too), so the
  bounded read in hook.mjs runs only after the launcher's unbounded one.
- Reproduce (project `P` = git repo with `.claude/settings.json -> /dev/zero` committed):
  - `CLAUDE_PROJECT_DIR=$P node probes/run-cap.mjs 1048576 $P 15000 '{"session_id":"x","source":"startup"}' -- node
    $RV/cand/scripts/hook-launcher.mjs hook.mjs session-start` → peak RSS 521,152 KB, 273 ms (read stopped only by the
    1 GiB cap: ERR_MEMORY_ALLOCATION_FAILED, caught, fail open).
  - Same input, `node $RV/cand/hook.mjs session-start` directly (the path the new test exercises) → peak 87,584 KB, 116 ms.
  - Launcher, `scripts/user-prompt-search.js`, 4 GiB cap → cand peak 3,667,116 KB in 1,234 ms; v6.35.2 3,666,920 KB in
    1,467 ms. `hook.mjs stop` and `scripts/pre-tool-recall.js` via the launcher, 1 GiB cap: 521,084 / 521,104 KB.
    With no memory cap (a real hook) the read continues until allocation fails or the hook timeout (2-15 s) kills it.
  - `bash $RV/cand/scripts/post-tool-use.sh` with a Read tool payload → SIGKILL at the 10 s probe deadline, peak 3.9 MB
    (bash discards the NUL bytes and loops); the same project without the link exits 0 in 6 ms. hooks.json gives this
    hook 5 s, so every Read tool call would wait out the timeout. v6.35.2: identical.
- Expected: after this release no hook reads a project settings scope that is a device without a bound.
  Saw: hook.mjs, plugin-key, install.mjs and adopt-cli are bounded; the launcher and the bash prefilter, which run first,
  are not. `tests/project-files-not-regular.test.mjs` ("every hook event reads the project settings scopes") imports
  hook.mjs directly, so it cannot see the launcher. A regular settings file over 4 MiB is also still honoured by the
  launcher and the bash prefilter while hook.mjs and `status` now ignore it (constructed; no one has a 4 MiB settings file).
- Shape: REAL. A cloned repository can commit `.claude/settings.json` or `.claude/settings.local.json` as a symlink to
  `/dev/zero` (git stores symlinks; this is the shape the CHANGELOG itself names). Not a regression: v6.35.2 behaves the
  same. The P1 is the release note: it tells a user that this committed-file hazard is closed for settings files, which
  bears on whether opening an untrusted repository with the plugin enabled is safe. Unchecked premise: whether Claude
  Code 2.1.x itself starts in such a repository (NOT CHECKED below); if it hangs first, neither the old hazard nor this one
  is reachable in a real session, and the settings half of the bullet should not be claimed either way.

### C2 — P2 — "as `unadopt --all` already did" is false: v6.35.2's `--all` removed the block from a file over 4 MiB

- Where: CHANGELOG.md:29-30; 4e040a82 body ("unadopt of one reports `absent`, as unadopt --all and readBlockAt already did").
- Reproduce: `probes/mk-big-adopted.sh <tree> <proj>` (writeManaged, then pad CLAUDE.md to 4,344,929 bytes), register the
  project in the sandbox `~/.claude.json`, run `node <tree>/cli.mjs unadopt --all` and, in a fresh copy, `unadopt`.
  - v6.35.2 `--all`: `[unadopt --all] <proj> → removed`, "removed 1 CLAUDE.md block(s)"; block gone, `.claude/` gone.
    v6.35.2 single `unadopt`: `→ removed`, block gone. (Path: `hasResidue` is true from the detail doc and state, then
    `removeManaged` → `removeBlockAt`, a plain read in v6.35.2.)
  - v6.35.2 `--all` on the same file with no doc/state: skipped silently ("removed 0"), no `absent` line either.
  - Candidate `unadopt`: `→ absent`; candidate `--all`: "cleaned partial residue (detail doc/state, no block)". In both,
    the detail doc, the state file and `.claude/` are deleted and the whole block (begin sentinel to end sentinel,
    18 lines) stays in CLAUDE.md, still pointing at the deleted doc.
- Expected: v6.35.2's `--all` reported such a block as absent. Saw: it removed it, in the shape adopt leaves (block + doc +
  state); in the only shape it did not touch it printed nothing. The statement also hides that the new `unadopt` deletes
  the doc and state while leaving the block.
- Shape: REAL but uncommon: an adopted CLAUDE.md (adopted by <= 6.35.2) that grew past 4 MiB, or a repository whose
  committed CLAUDE.md is over 4 MiB.

### C3 — P3 — "at most one byte past the limit is read" / "at most limit+1 bytes" is false; the overshoot is up to one 64 KiB chunk

- Where: `lib/regular-file.mjs:18-19` (docstring), 4e040a82 body ("unchanged: … at most limit+1 bytes").
- Reproduce: `node probes/overread.mjs $RV/cand/lib/regular-file.mjs` (counts the bytes `fs.readSync` returns).
  `/proc/kallsyms` (fstat size 0, regular): 4,200,622 bytes read for the 4,194,304 limit (6,318 over); `/proc/self/maps`
  with `maxBytes` 10: 4,093 bytes read. The loop reads 65,536-byte chunks and checks `total > maxBytes` after each.
- Expected: at most maxBytes + 1. Saw: up to maxBytes + 65,536. Still bounded; the wording is wrong.
- Shape: CONSTRUCTED only (needs a size-0 or growing regular file, e.g. a link to /proc).

### C4 — P3 — "a cap killed `npm`": the 240 s cap killed `/bin/sh`, and npm kept running too

- Where: `lib/binding-probe.mjs:296` and `tests/binding-source-build-uncapped.test.mjs:3` ("a cap killed `npm` and left
  node-gyp compiling"); 5d762ae9 body ("So a compile past the cap killed npm").
- Reproduce: package.json script `"s": "sleep 7.31 && echo done"`; `spawnSync('/bin/sh', ['-c', 'npm run s'],
  {timeout: 2000})` → ETIMEDOUT at 2,004 ms, direct child pid = the `/bin/sh` wrapper; afterwards `ps` shows
  `npm run s` (reparented to 1), `sh -c sleep 7.31 && echo done` and `sleep 7.31` all alive. execSync: ETIMEDOUT at 2,003 ms,
  same survivors.
- Expected: npm killed. Saw: on dash the shell is the direct child and is the only process signalled. The conclusion the
  text draws (the compile outlives the cap) holds, more so.
- Shape: REAL (Ubuntu /bin/sh is dash).
