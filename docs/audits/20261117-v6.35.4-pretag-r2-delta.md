## Findings

### R2-1 (P2): `unadopt --all` says it cleaned residue it left, counts it, and never converges

- **Where:** `adopt-cli.mjs:1084-1087`, the else branch of `unadoptProject`.
- **Setup:** `.claude` is a link out of the project that is refused (committed, or outside git). The doc and state sit in the linked directory. CLAUDE.md has no block, because a first `unadopt` removed it.
- **What happens:** `removeManaged` returns `action: 'absent'` with `left: [.claude]` and deletes nothing. `unadoptProject` then takes the else branch and prints:
  ```
  [unadopt --all] ~/work/app → cleaned partial residue (detail doc/state, no block)
    ⚠ left ~/work/app/.claude alone: a link this repository commits, to ~/outside, outside this project
  [unadopt --all] removed 0 CLAUDE.md block(s) (+1 partial-residue cleanup(s)) ... exit=0
  ```
  The output is identical on every run, and both files stay.
- **The loop:** `adopt --status` keeps printing "1 with a CLAUDE.md managed block or partial residue … run `unadopt --all` to remove every CLAUDE.md block", which sends the user back into the same no-op.
- **Repro:** `T=cand bin/q3.sh` (Seq B: unadopt, unadopt, unadopt --all ×2, status, adopt).
- **Expected:** not "cleaned", and not counted as a cleanup. It should be counted as not removed, the way `skipped-symlink` is, or at least worded as "left".
- **Shape:** REAL. A cloned repository that commits `.claude` as a link out of it, or the user's own committed `.claude` link into dotfiles (a layout the CHANGELOG lists).
- **v6.35.3:** deleted the two files in the linked directory (the D#880 defect). Its "cleaned" was therefore true; it now is not.
- **Note:** the single `unadopt` prints "→ absent" plus the ⚠ line, exit 0. That is correct.

### R2-2 (P2): the "git lists it as untracked" shortcut skips the `.git` check

- **Where:** `lib/project-link.mjs:50-51`. `userMade` is asked first, and `if (made) continue` returns before `place()`, so a user-made link is never checked against `.git`.
- **Effect:** an archive unpacked inside a git work tree (or one unpacked and then `git init`ed) has its links listed as untracked, so they are written through wherever they point, including into `.git`.
- **Repro, `.git/config`:** a tar holding `pkg/CLAUDE.md -> ../../.git/config`, unpacked into `vendor/` of an existing repository, then `adopt` in `vendor/pkg`.
  - cand: `[adopt] …/vendor/pkg → created`, exit 0.
  - Afterwards `git status` in the enclosing repository fails: `fatal: bad config line 7 in file .git/config`.
  - v6.35.3 does the same.
- **Repro, the plugin's two files** (`bin/q1a.sh`): an archive carrying CLAUDE.md with the block and `.claude -> <outside>`.
  - Unpacked inside a work tree, ignored or not, or followed by `git init`: on cand, SessionStart and adopt overwrite `plugin_claude_mem_lite.md` and `.plugin_claude_mem_lite_state.json` in the named directory, and `unadopt` deletes them there.
  - Unpacked outside git, or after `git add`: refused (cand). v6.35.3 writes in all five placements.
  - A bash rc directory that sources every file (Fedora's `~/.bashrc.d/*`) would source the doc. I checked that this stops at a syntax error on line 1 and runs nothing.
- **Expected:** the CHANGELOG says links are written through "only when it resolves inside the project and outside .git (in any letter case), or when git lists it as untracked", and "An archive unpacked into a git work tree is not covered".
  - The `.git` exclusion could run before the untracked shortcut. No layout a user builds links CLAUDE.md or `.claude` into a `.git` directory.
  - The disclosure names "unpacked into a git work tree" but not "unpacked, then `git init`".
- **Shape:** REAL. A downloaded zip or tarball unpacked into `vendor/` or `third_party/` of a repository, or into a home directory that is a git work tree. The `.git/config` write needs an explicit `adopt` there. SessionStart only rewrites a CLAUDE.md target that already holds the block, and the legacy cleanup only one holding `<claude-mem-context>`.
- **v6.35.3:** same, and also outside work trees. This is not a regression; it is a residual risk that is only partly disclosed.

### R2-3 (P2): when git does not answer, SessionStart runs past its 15 s hook timeout

- **Where:** `lib/project-link.mjs:103-119` (`timeout: 5000` per call, uncached), reached from `claudemd.mjs:431` on a refresh. `hooks/hooks.json:16` gives SessionStart 15 s.
- **Repro 1** (`bin/q-hang.sh`, a fake `git` first on PATH that sleeps 30 s; adopted project with an older doc). SessionStart wall time:

  | Layout | v6.35.3 | cand | Extra git calls on cand |
  |---|---|---|---|
  | dotfiles-linked CLAUDE.md, untracked | 11.2 s | 21.2 s | one `ls-files`, one extra `rev-parse` |
  | `.claude` also linked | 11.2 s | 21.2 s | same |
  | committed `CLAUDE.md -> AGENTS.md` | 11.2 s | 16.2 s | — |

- **Repro 2** (`bin/q-fsmon.sh`, real git with `core.fsmonitor` set to a hook that sleeps): 11.7 s on v6.35.3 against 16.7 s on cand, for both layouts.
  - `git ls-files` runs the fsmonitor hook; `rev-parse` does not.
  - In the dotfiles layout the refusal also leaves the doc stale. The refresh is therefore retried, and the extra time paid, on every SessionStart while git hangs.
- **Expected:** stay inside the hook's budget, as v6.35.3 did in the same state.
- **Shape:** REAL but uncommon: a stuck fsmonitor daemon, or a project on a stalled network mount. It is not driven by repository content.
- **Not verified:** what the host does at 15 s. I measured wall time only.

### R2-4 (P2): for a link git lists as tracked, the refusal says "a link this repository commits" and the remedy deletes the user's setup

- **Where:** `lib/project-link.mjs:64-72` and `78-84`. `kind: 'committed'` is returned for any tracked entry: a staged symlink, or a regular file the user replaced with a link.
- **Repro** (sandbox `overtracked-remedy`): the repository tracks CLAUDE.md (`team line`), and the user replaces it with a link to `~/dotfiles/CLAUDE.md`.
  - cand adopt prints `CLAUDE.md: a link this repository commits, to ~/dotfiles/CLAUDE.md, outside this project. Not written through; delete the link, then run adopt again.`, exit 1. The repository commits a file there, not a link.
  - Following the remedy (delete the link, adopt) gives `→ created`. `git diff` then shows `-team line` and the 18 block lines added.
  - The team's tracked text is gone from the working tree, and the user's notes no longer load.
- **Same remedy elsewhere:** for the user's own committed link (`dotmd-committed`), or a repository's committed `.claude` link to a shared settings directory, "delete the link" drops what that link supplied, and git shows the deletion of a tracked file.
- **Expected:** text that matches what git reported, and a remedy that does not lose tracked content. For example, `git checkout CLAUDE.md` before adopt, or saying the layout cannot be adopted.
- **Shape:** REAL but uncommon. The CHANGELOG lists both layouts. The F3 case-insensitive checkout gets the same text.
- **v6.35.3:** wrote through; no remedy was needed.

### R2-10 (P3): statements in the delta that are imprecise or wrong

- **CHANGELOG bullet 1 and the `project-link.mjs:9-11` header:** "The detail doc and the state file are never written through a link, as in 6.35.3."
  - Both are written through an untracked `.claude` link (dotfiles layout, archive gap) on cand; see the `dotdir-git` row in `q2.log` and R2-2.
  - In 6.35.3 they were written through committed `.claude` links too: that was D#880.
  - The statement holds only for a link at the file's own path.
- **`project-link.mjs:121-123`:** "false: … on a case-insensitive file system a committed file whose name differs only in case".
  - `git ls-files -s -o -- …/CLAUDE.md` prints nothing for an index entry `claude.md`, with `core.ignorecase` false or true (`sbx/icase`).
  - Such a path answers `null` ('unknown'), not `false`. `false` comes from an entry of exactly that name (the F3 shape).
- **`project-link.mjs:25-26`:**
  - 'committed' is described as "git lists a staged symlink there", but it is also returned for a tracked regular file (R2-4).
  - "a path in a submodule" cannot happen for the two relative paths checked: the doc and the state are refused as whole files before git is asked.
- **`hook-context.mjs:485`:** "A span at the end of the file". The condition is "no newline right after the end tag".
  - `…</claude-mem-context>trailing` still becomes `keep thistrailing`.
  - A CRLF file becomes `keep this\r\r\ntrailing`.
  - Both are the same as v6.35.3, so CHANGELOG bullet 4 is true only for the LF, own-line shape it shows.
- **`adopt-cli.mjs:1103`:** "with the detail doc and its state file beside it". They are in the project's `.claude/`, not beside the linked file.

## Answers to the questions

### Q1: repository content writing outside the project, into `.git`, or over the user's files

The candidate refuses every committed-link shape I built. Each was written through on v6.35.3:

- committed `.claude` or CLAUDE.md link out;
- the same in a git submodule;
- the same seen from a linked worktree;
- committed into `.git` or `.GIT`;
- an archive unpacked outside git, or unpacked and then staged.

Remaining:

- An archive unpacked inside a work tree, ignored or not, or unpacked and then `git init`ed: writes outside, and adopt writes into the enclosing repository's `.git/config` (R2-2).
- A committed CLAUDE.md link to the user's own untracked file inside the project: adopt appends to it (R2-9).
- A session started inside a committed directory link (R2-11).
- An archive carrying its own `.git` (R2-12).
- Case-insensitive file systems: not checked (see NOT CHECKED).

### Q2: layouts users build with links

Run with `bin/q2.sh`; full rows are in `q2.log`.

Behaves the same on both trees:
- untracked dotfiles CLAUDE.md or `.claude` in git;
- worktree links to the main checkout;
- monorepo subdirectory with committed links inside the repository;
- committed `CLAUDE.md -> AGENTS.md`;
- a project reached through a symlinked path, with committed or user links.

Refused on the candidate where v6.35.3 wrote:
- dotfiles links outside git;
- the user's own committed link;
- a link over a tracked file;
- a git that does not answer.

What the user sees on the candidate in those refused layouts:
- adopt exits 1 and names the link (but see R2-4 and R2-8);
- SessionStart changes nothing and prints nothing, leaving a stale doc;
- `adopt --status` prints "✓ adopted";
- unadopt exits 1 with the by-hand note, or exits 0 with "left .claude alone".

Stow-linked doc or state files: refused on both trees. `unadopt` unlinks the user's link on both trees.

### Q3: unadopt and unadopt --all outcomes and sequences

Correct:
- block left behind a refused CLAUDE.md link → exit 1;
- the user removes the block, then unadopt again → exit 0, doc and state removed;
- adopt afterwards stays refused.

Wrong:
- R2-1: `--all` with a refused `.claude` link never converges;
- R2-5: dry runs;
- R2-6: target over 4 MiB;
- R2-7: orphan sentinel.

I found no data loss beyond R2-4's remedy path and R2-9's blank-line collapse, which is pre-existing.

### Q4: mixed trees during an update

The changed files sit in `SOURCE_FILES` at these positions: `lib/project-link.mjs` 39, `claudemd.mjs` 56, `adopt-cli.mjs` 62, `hook-context.mjs` 162. I built a tree at each split point (S2 to S5) and ran SessionStart, adopt, unadopt and `install.mjs status` (PATH without `claude`) on three layouts (plain, committed CLAUDE.md out, committed `.claude` out). That is 48 runs: all exited 0 or with the intended refusal, and none wrote an Error or a stack trace to stderr.

Only text differs during the S3 window (new `claudemd.mjs`, old `adopt-cli.mjs`): unadopt prints a bare `→ skipped-symlink` with exit 0, or `→ removed` with no "left" line, while the files are still protected.
