Reviewer: independent release lens (did not prepare the release). Date 2026-09-29 (UTC).
Trees: `git archive 0b9c50b` / `git archive 26dcd49` copies and two `git clone` copies under

## Findings

### P2-1: the CHANGELOG says an install shape is locked when it is not, and says the fix reaches a shape it does not reach

`CHANGELOG.md:11-13` (0b9c50b): "The published package locks its dependency tree, so 6.19.3
installs that version everywhere. 6.19.4 requires `ip-address` 10.6.0 or later and locks 10.7.2."
0b9c50b's message makes the same claim: "so 6.19.3 installs 10.5.0 everywhere".

(a) **The direct install is unlocked.** README:72 and :726 document `npx claude-mem-lite`. It
runs `install()`, which copies `SOURCE_FILES` from the npm package into `~/.claude-mem-lite`
(install.mjs:1216-1218) and runs `npm install --omit=dev` there (install.mjs:552).
`SOURCE_FILES` lists `package-lock.json` (source-files.mjs:34), and npm never packs that file. It
does not list `npm-shrinkwrap.json`, the only lockfile the tarball carries. The code that
actually runs therefore resolves unlocked. Reproduction:
```
npm pack claude-mem-lite@6.19.3 && tar -xzf ...        # published tarball
node copysrc.mjs pub6193/package direct6193b           # copies SOURCE_FILES as install.mjs does -> "missing: package-lock.json"
cd direct6193b && npm install --omit=dev --ignore-scripts && npm ls ip-address
  -> @modelcontextprotocol/sdk@1.31.0 > express-rate-limit@8.7.0 > ip-address@10.7.2
control: same dir + the tarball's npm-shrinkwrap.json copied in -> ip-address@10.5.0
```
So 6.19.3 did not install 10.5.0 everywhere. This shape has taken the newest version its
override allows since 10.7.2 was published on 2026-09-15. It also means "6.19.4 locks 10.7.2" is
false for this shape: it gets the newest version `>=10.6.0` at install time.

(b) **A plugin install with a linked node_modules keeps the old tree.** On a new plugin
version dir, `scripts/setup.sh:193-198` symlinks `$ROOT/node_modules` to
`~/.claude-mem-lite/node_modules` whenever that directory holds better-sqlite3.
`syncDataDirFromCache` copies source only (`skipNpmInstall: true`, hook-update.mjs:1217), and
plugin mode disables the GitHub-tarball install (hook-update.mjs:72, :109). Nothing ever runs
`npm install` on that tree again. Reproduction in a sandboxed HOME: a data-dir node_modules
with ip-address 10.5.0, plus `CLAUDE_PLUGIN_ROOT=<fresh 0b9c50b archive> bash scripts/setup.sh`:
```
✓ Dependencies linked from .../plugsim/home/.claude-mem-lite
ip-address resolved from plugin ROOT (6.19.4): 10.5.0
```

(c) **Mitigation the entry does not state.** claude-mem-lite never loads the vulnerable code.
I started server.mjs in a sandboxed HOME with a `registerHooks` resolve probe. It made 305
resolutions under @modelcontextprotocol/zod and none to `ip-address`, `express-rate-limit` or
`express`. A positive control with the pattern widened caught all 305. Only the SDK's
`server/auth/*` router imports express-rate-limit. The security effect of (a) and (b) is
therefore nil. The problem is the claim, and the missing sentence that would let users judge
urgency.

Suggested wording: "npm global/npx installs (via the published shrinkwrap), the plugin's own
install and self-update lock 10.7.2; a direct install resolves the newest `>=10.6.0`; a
plugin whose node_modules links to ~/.claude-mem-lite/node_modules keeps its existing tree.
claude-mem-lite never loads ip-address (only the MCP SDK's unused HTTP auth router does)."

### P2-2 (pre-existing since v3.58.0, not a regression, does not block): the published shrinkwrap installs the dev tree for registry users

`npm shrinkwrap` (publish.yml:88, :148) copies all 204 `dev: true` entries into the published
`npm-shrinkwrap.json`, and npm installs them for a dependent:
```
cd reginstall6193 && npm init -y && npm install claude-mem-lite@6.19.3 --ignore-scripts
  npm 11.19.0: 300 packages, 533M; vitest, @vitest, eslint, knip, prettier present under
               node_modules/claude-mem-lite/node_modules, all 19 @oxc-parser platform bindings
  npm 10.9.2 : 237 packages, 172M; same 4 dev tools present
  unlocked tarball install (control): 97 packages, 57M
```
Consequence: publish.yml:78 gates on `npm audit --omit=dev`, but registry users get the dev
tree as well, so a dev-only advisory would reach them without failing the gate. A full
`npm audit` on 0b9c50b reports 0 today, so there is no current exposure. A related effect:
npm 10.9.2's `npm shrinkwrap` drops the 18 `libc` fields (dev-optional @oxc-parser, @rolldown
and lightningcss bindings; reproduced in a copy), so an npm-10 registry install fetches both
the gnu and musl bindings. Neither issue changes in this release.

### P3

- **P3-1: 46ec110's message inverts the fe80 defect.** It says "misclassifies fe80::/64 as
  link-local". GHSA-rpw4-54j3-4h4q says `isLinkLocal()` "recognizes fe80::/64 rather than
  fe80::/10", so the defect is missing the rest of the /10. Reproduced: 10.5.0
  `new Address6('fe81::1').isLinkLocal()` returns false; 10.7.2 returns true. The commit is
  pushed, and the CHANGELOG words it correctly.
- **P3-2: one of the two advisory IDs is never named.** Only GHSA-2vr4-cq9g-pvrc (NAT64) is
  named, in 46ec110's title and CHANGELOG:10. GHSA-rpw4-54j3-4h4q (fe80) appears nowhere. In
  CHANGELOG:10 the 2vr4 ID sits directly before the fe80 description, which reads as if 2vr4
  were the fe80 advisory. Name both IDs.
- **P3-3: the override has no upper bound.** `package.json:233` `"ip-address": ">=10.6.0"`.
  `fast-uri` (:232) carries `<4`; this override does not. The unlocked direct-install shape
  (P2-1a) would force a future ip-address 11 onto express-rate-limit's `^10.2.0`. This predates
  the release (`>=10.1.1` was also uncapped), and the module is not loaded at runtime. The
  advisories list 10.5.1 as the first patched version; 10.6.0 is stricter and harmless.
- **P3-4: smoke-tarball does not exercise the locked shape.** publish.yml:97-98 says it runs
  "so the smoked tarball is the locked shape that publish ships". `npm install <local tgz>`
  (scripts/smoke-tarball.mjs:104) ignores the tarball's shrinkwrap under both npm majors.
  Installing my packed 6.19.4 tgz gave @modelcontextprotocol/sdk 1.31.0 and express-rate-limit
  8.7.0, where the shrinkwrap in that same tgz locks 1.30.0 and 8.5.2. A registry install
  (`_hasShrinkwrap = true`) does honour it: 6.19.3 gave ip-address 10.5.0, nested. This
  predates the release.
- **P3-5: the new linearity shapes run closest to their budget.** tests/secret-scrub-linear.test.mjs:86-91
  adds three shapes, and they are now the three highest ratios in the file. Under coverage on
  0b9c50b, 3 runs: pemCodeBeforeBegin 4.47-4.62x, pemOpenerBeforeBegin 4.30-4.47x,
  pemEscapedQuotesBeforeBegin 3.75-3.90x, against a 10x budget. The next highest is
  pemLongLabels at 2.94-2.97x. For CI run 36499181278 I estimated 2.85-5.77x: the three
  shapes' reported ms divided by a benign time inferred from the other shapes' local ratios.
  The single-shot design (one crafted run against the min of 3 benign runs) has flaked on CI
  before: run 36456237182, `pemHeadersNoEnd ... expected 10.219525191009756 to be less than 10`.
  publish.yml:75 runs test:coverage, so a flake fails the Release validate job. The job is
  re-runnable. Not blocking.
