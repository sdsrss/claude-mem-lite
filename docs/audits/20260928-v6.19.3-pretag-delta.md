### F4 — P3 — the break count does not match its documentation for escaped CRLF and `<br>`+newline (secret-scrub.mjs:427-428 JSDoc, :442 regex)

The JSDoc says "one break: real, escaped at any depth, or `<br>`". `\r\n` escaped (4 characters, any
depth) matches `\\+[nr]` twice, and `<br>` followed by a real newline counts twice, so a two-line
body in those encodings goes while its raw form stays (probe/breaks.mjs):
```
LF 2-line kept: true   CRLF: true   CR: true   esc \n: true   esc \r\n: FALSE   esc2 \\r\\n: FALSE
<br>: true   <br>+LF: FALSE   <BR/>: true   U+2028/VT/FF/NEL: 2-line true, 3-line true (not counted)
raw CRLF kept: true | JSON.stringify(raw CRLF) kept: false
```
Direction: over-erasure only (41b9659 erased all of these), so no regression vs 41b9659; the ssh.py
shape from a CRLF file inside a JSON tool result keeps losing its middle line. U+2028, VT, FF and
NEL are not breaks for the line scanners either, and the count clause still binds, so a 3-line body
in them is not a leak path; it is a gap in "at most two lines" as documented.

### Q3 answer (isMarkerProse)

Clause by clause (secret-scrub.mjs:440-445):
- length `> 256`: correct as documented; pinned from both sides (M01-M03 fail).
- breaks `> 1` over `/\r\n|\r|\n|\\+[nr]|<br\s*\/?>/gi`: real LF, CRLF (as one) and CR count;
  escaped `\n`/`\r` at any depth count (a run of backslashes then n/r; so `\nabla`-style text and a
  literal `\n` in quoted code count too, over-erasure only); `<br>`, `<br/>`, `<br />`, `<BR>`
  count. Not as documented: escaped CRLF counts two, `<br>`+newline counts two (F4); U+2028/2029,
  VT, FF, NEL, `%0A`, `&#10;` do not count (harmless for leaks: the line scanners do not treat them
  as breaks and the count clause still binds). Pinned: the threshold and the LF, escaped-`\n` and
  `<br>` arms. Unpinned: the CRLF, CR, escaped-`\r`, `<br/>` and case arms (F3), and the CR arm is
  what closes two of round-1's F2 inputs.
- count `>= 40` over `[A-Za-z0-9+/=]`: correct; pinned. It is taken after the patterns that run
  before the block pattern in the same pass (KV labels, AWS, JWT, …), so a body those patterns
  shorten is judged on what will be stored (the `xxd` row above).
  The JSDoc's "Without this clause a decoded key, or a key re-wrapped to lines under 16 characters,
  was kept" is history (6575aba had neither clause). With only this clause removed (M15) the
  re-wrapped-key test stays green; the line clause alone erases that shape. M15 fails the
  decoded-key test and the 39/40 threshold test.
- run `{16}`: correct; pinned (M19-M21). The class includes `+/=`; narrowing it to alphanumerics
  (M24) survives the suite.
- words `\S[ \t]+\S`: correct; pinned (M22). Widening `[ \t]` to `\s` (M23) survives; it would keep
  a two-line body of two 15-character key fragments.
- body slice (`indexOf('-----', 11) + 5` .. `lastIndexOf('-----END ')`): correct for every label
  the pattern accepts; M25/M26 (END or BEGIN text counted into the body) are caught.
Interaction with the scanners that run after it on every pass: a kept BEGIN never anchors a
cut-off key (its rest-of-line reaches `-` or a line holding the END, and cutOffKeyEnd returns -1;
d2 and the tracked corpus agree). A kept END does anchor the tail scanner: F2 (one-line block,
lines above go) and F1 (two-line block, a stray END after it cannot reach a key tail above).
Passes are monotone: replacements only remove counted characters, so a kept body stays kept and
an erased one is gone; idempotence failures 0 in 60,000 d2 inputs for both trees.
