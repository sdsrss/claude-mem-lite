## Findings

### F1 [P1, CONFIRMED] The swap gate treats leftovers of a finished swap as an unfinished one, which blocks updates permanently
hook-update.mjs:912-920 (`unfinishedSwapLeft`), :1128 (gate), :874-886 (`discardBackupDir`)

`unfinishedSwapLeft` matches any `.update-backup-*` directory. `discardBackupDir` deletes the journal FIRST, so
that a dir without a journal means "the swap is over" (comment at :868-873). If the recursive rm after that fails,
the dir stays without a journal. On every later entry, recovery replays an empty journal (`rollbackInstall([],[])`
returns true), `discardBackupDir` fails again, the gate sees the dir, and the call returns false. Nothing ever
clears it.

Trigger: a committed swap whose OLD tree contains a subtree the user cannot delete. For example, a `sudo` rebuild
left a root-owned `node_modules/better-sqlite3/build/` (the repo already treats sudo runs as a real population, D#284).
The swap renames node_modules (user-owned) into the backup, the commit runs, and the discard fails with EACCES.

Evidence (P-block probe, real fs, the build/Release dir chmod 0555 as a non-root user):
- HEAD e4cacbdf: `{"r1":true,"journalLeft":[false],"r2":false,"r3":false,"cli":"// cli v1.1"}`
- parent d712f69c: `{"r1":true,"journalLeft":[false],"r2":true,"r3":true,"cli":"// cli v1.3"}`

No user ever sees this. The only trace is debugLog (CLAUDE_MEM_DEBUG). doctor says "Stale temp files: 1 found (run:
node install.mjs cleanup)", and cleanup run as the user hits the same EACCES. Under CLAUDE_MEM_DIR relocation,
doctor and cleanup scan MEM_DATA_DIR (install.mjs:2871, :3301), but the backups live in CODE_DIR
(hook-update.mjs:56), so doctor does not even count the dir.

PLAUSIBLE extension (not run): syncDataDirFromCache (:1380) goes through the same gate. A plugin-mode data-dir code
copy then stops tracking the cache, which is the schema-skew lockout that function exists to prevent.

Fix direction: block only while the backup dir still holds a journal (or a backup listed in it). Report a blocked
swap in doctor.

### F2 [P2, CONFIRMED] A restore that keeps failing now blocks updates forever and leaves a mixed tree
hook-update.mjs:961-968, :904-908, :1128

R1 holds: the backup survives. But nothing limits the retries and nothing lets the next forward swap through. The
parent tree lost the old node_modules (the R1 bug), but its next update replaced the half-deleted tree. HEAD keeps
the old node_modules safe in the backup and stays on old code over the NEW release's node_modules. No update can
start, and no user-visible signal says so.

P-persist probe (the new node_modules carries a 0555 dir, so the rm during rollback fails and the rename back hits
ENOTEMPTY):
- HEAD: `{"r1":false,"oldDepSafe":true,"r2":false,"r3":false,"dep":"new-dep","nm":["dep.js","stuck"],"hook":"// old hook"}`
- parent: `{"r1":false,"oldDepSafe":false,"r2":true,"r3":true,"dep":"new-dep","hook":"// new hook v1.3"}`

On Windows (EBUSY or EPERM from AV or open handles) the failure is transient and the retry design fits. On a
persistent EACCES it does not.

### F3 [P2, CONFIRMED] doctor tells the user to delete the backup R1 kept, and cleanup deletes it
install.mjs:2871-2875 (scan), :3294-3301 (cleanup), lib/doctor-stale-temp.mjs:29,99

A kept backup dir (journal plus the only copy of a file) is counted as stale temp, and `cleanup` removes it while
holding install.lock. So R1 ("a later install entry must be able to finish the restore") fails whenever the user
follows doctor's advice before the next entry. This behaviour predates the commit, but a2cf96a1 makes kept dirs a
designed state.

Repro: sandbox HOME, `$HOME/.claude-mem-lite/.update-backup-1791400000000-4242/{server.mjs,.swap-journal.json}`
(journal `{"backedUp":["server.mjs"],"installed":["server.mjs"]}`), then `runcli.sh tree-e4cacbdf kept -- doctor`
and `-- cleanup`:
```
  ⚠ Stale temp files: 1 found (run: node install.mjs cleanup)
  ✓ Removed: .update-backup-1791400000000-4242
```
After that, `ls -a $HOME/.claude-mem-lite` lists only hook.mjs and runtime: server.mjs is gone for good.
Fix direction: doctor/cleanup should skip a backup dir that holds a journal, or replay it under the lock.

### F4 [P2, CONFIRMED with a simulated direct install] R2 does not hold for writers outside installExtractedRelease
install.mjs:1318 (`deployCodeTree` in install()), :526; repair spawns `install.mjs install`; scripts/hook-launcher.mjs:364,424 auto-run repair

`install` and `repair` write INSTALL_DIR without calling recoverInterruptedSwaps and without the gate. A kept
journal survives them. The next installExtractedRelease entry replays it over the newer tree:
- it deletes paths the failed release added (cli.mjs);
- it renames the old node_modules over the newer one.

If that same entry then fails (npm install offline/timeout, or smoke), the damage stays. The kept-dir state (a
half-deleted node_modules, or a missing server.mjs) is exactly what triggers the hook-launcher's automatic repair.

P-replay-full probe (kept dir from a failed v1.1; then v1.2 files and node_modules written directly, as
deployCodeTree plus npm install would; then an entry for v1.3):
- HEAD, npm offline: `{"r2":false,"cli":null,"hook":"// hook.mjs v1.2 direct","dep":"old-dep"}`. Same result when smoke fails.
- parent, npm offline: `{"r2":false,"cli":"// cli.mjs v1.2 direct","dep":"v1.2-dep"}`
- both, when v1.3 passes: v1.3 installed whole.

Fix direction: install()/repair run recoverInterruptedSwaps first, under the same lock, or retire a journal once a
full deploy has replaced the tree.

### F10 [P3, CONFIRMED by the new test's own assertion] R3 does not hold across entries when the journal unlink throws
hook-update.mjs:876-880; tests/hook-update-rollback-barrier.test.mjs:340-349

A committed swap whose journal cannot be removed keeps the journal and the backups. The next entry's recovery then
rolls the committed release back to the old one. The new test asserts exactly this
(`expect(read(dataDir, 'cli.mjs')).toBe(null); // one whole release: the old one`). This is the design from
49832565, not a regression. Still, "nothing that throws afterwards may roll it back" is true only within the call.

### F11 [P3, PLAUSIBLE] The completion check reads existence through existsSync
hook-update.mjs:992, :1013

existsSync follows symlinks and returns false on EACCES or ELOOP. A backup that is a dangling symlink, or one
under an unreadable path, reads as "already restored". `rollbackInstall` then returns complete and the dir is
discarded. An lstat-based check would be exact. Reach is low: the trees are copies, and sync skips dev mode.

## Answers to the questions

1. **Every path.**
   - R1 holds on the smoke-fail path (:1179), the thrown-mid-loop path (:1273) and recovery (:961). Shown by the
     suite and by P-persist (`oldDepSafe:true`).
   - R3 holds in-process on the commit path (:1183, :1272).
   - Updates CAN now be blocked permanently: F1 (journal-less leftovers) and F2 (a restore that keeps failing).
   - A kept backup IS deleted by a later step: `cleanup`, which doctor recommends (F3).
   - A kept journal can also be replayed over a newer direct install (F4).
2. **Return value.** It is correct for whole-dir entries. A dir is renamed as one, so `backup/<dir>` still exists
   after the loop if and only if its rename back failed (ENOTEMPTY/EPERM); P-persist shows this. It is also
   correct for journaled-but-never-moved intents: no backup, so the target still holds the old file, so true.
   Installed-only paths whose rm failed are not counted. That leaves extra new files behind but loses nothing.
   Caveat: F11.
3. **install.mjs messages and shapes.**
   - Untrue: F8a (names an -shm that exists).
   - Contradiction inside one doctor run: F5 ("not checked — not accessible" next to "no install owns a binding").
   - Missing detail: F6.
   - `--json` changes a consumer would notice: F7 (`database.error` = EACCES for a corrupt store). doctor's
     better-sqlite3 entry also goes from fail to warn in the locked case, which is intended; exit code 1 is kept
     by the Data directory / Entry points ✗ lines.
   - Cross-face disagreement: F9.
4. **Tests.**
   - On the parent sources the new tests are red: on d712f69c, 4 failed and 6 passed (all 4 new cases); on
     a2cf96a1, 3 failed and 42 passed (the 3 new/changed cases).
   - Per-site mutations on HEAD, each applied exactly once (checked) and each turning red:

   - Not covered: gate over-blocking (F1), doctor/cleanup on a kept dir (F3), the relocated shape for R6/R7
