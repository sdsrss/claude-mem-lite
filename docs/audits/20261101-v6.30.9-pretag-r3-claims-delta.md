### F1 [P2] D#615 这句里的对比和实际不符：6.30.8 在"BEGIN 前面有文字"的多数形状下本来就擦这些行

句子（CHANGELOG.md:17-19）：
> Lines below a BEGIN with text before it that look like key lines (a hex hash, a long path or identifier) can be erased even when they are not a key (D#615), as 6.30.8 already erased them below a BEGIN with nothing before it.

两个分句单独读都对：6.30.9 确实会擦，6.30.8 在空 BEGIN 下确实也擦。问题在对比本身。这句话让读者以为"BEGIN 前面有文字"是 6.30.9 新加的误擦范围，可 6.30.8 在 19 种"前面有文字"的形状里已经擦了 9 种。

输入（t615tab.mjs）：`<left>-----BEGIN RSA PRIVATE KEY-----` / `<pre>da39a3ee5e6b4b0d3255bfef95601890afd80709`（40 位十六进制）/ `the end`。另用 64 位 sha256 行再跑一遍，原文和 JSON 两种包装都跑。

| BEGIN 前的文字（下面行的前缀） | 6.30.8 | 6.30.9 |
|---|---|---|
| 无（无） | 擦 | 擦 |
| `+`、`-`、`> `、`     5\t`、`5→`、`keys/conf.py:5:`（同类前缀） | 擦（6 种全擦） | 擦 |
| `KEY = '''`（下面行无前缀） | 擦 | 擦 |
| `+const k = \``（`+`） | 擦 | 擦 |
| `'+`（`+`） | 擦 | 擦 |
| `-KEY = '''`、`> key = "`、`     5\tKEY = """`、`5→KEY = """`、`keys/conf.py:5:KEY = '''`、`"-`（同类前缀） | 留 | **擦**（新） |
| `b'-`（`-`） | 原文留、JSON 擦 | **擦** |
| `# K = "`（`# `）、`// KEY = '''`（`// `）、` KEY = '''`（`-`） | 留 | 留 |

逐字输出举例：
- `+-----BEGIN RSA PRIVATE KEY-----\n+da39…0709\nthe end`：两棵树都输出 `+***PEM_KEY***\nthe end`
- `KEY = '''-----BEGIN RSA PRIVATE KEY-----\nda39…0709\nthe end`：两棵树都输出 `KEY = '''***PEM_KEY***\nthe end`
- `'+-----BEGIN RSA PRIVATE KEY-----\n+da39…0709\nthe end`：两棵树都输出 `'+***PEM_KEY***\nthe end`
- `-KEY = '''-----BEGIN RSA PRIVATE KEY-----\n-da39…0709\nthe end`：6.30.8 原样不动，6.30.9 输出 `-KEY = '''***PEM_KEY***\nthe end`

真正变了的只有一类：命名前缀（diff 的 `-`、Read 列号、grep 列、`> `）和 BEGIN 之间夹着代码或字符串开引号。旧版那句 "on a diff, Read, grep, quoted or list line" 比现在的 "with text before it" 更接近这个范围。
严重度理由：这句把升级的误擦代价说大了，会让一部分用户为了少丢文字留在 6.30.8，而 6.30.8 在 236/360 个矩阵用例里会存下密钥行。代价本身小（只丢误擦的非密钥文字），所以定 P2。
建议改法：把 "with text before it" 换成 "with code or a string opener before it"，把 "with nothing before it" 换成 "with only a line prefix before it"。改完还有一处不精确：`+` 行下 6.30.8 本来就擦（`+` 是 base64 字符），但范围已经和实测基本对上了。

## 核对为真的句子

- **标题**（CHANGELOG.md:5）"more cut-off private keys are erased before they are stored"：成立。矩阵复现（matrix.mjs，15 种上下文 × 4 种 × 2 种截断 × 3 种包装 = 360 例）：6.30.8 存 236 例，6.30.9 存 0 例，两边丢文字都是 0，与第 15-16 行一致。差分 fuzz（fz.mjs 用 mulberry32 随机数，22 种 BEGIN 行形状，1-7 行随机混合）：不加偏置的 20,000 例里，6.30.9 比 6.30.8 多存密钥的 0 例，6.30.8 比 6.30.9 多存的 1,169 + 1,174 例。"more" 是净值，不是超集，下面 Known limit 写了这一点，所以标题和正文不矛盾。
- **Known limit**（CHANGELOG.md:24-25）"a crafted added-diff shape, with a second BEGIN inside a header line, can keep key lines that 6.30.8 erased"：存在，方向也对（t633b.mjs，原文 / JSON / JSON 套 JSON 三种结果相同）：
  - `+KEY = '''-----BEGIN RSA…` / `+Comment: -----BEGIN RSA…` / `+MIIE<60>` / `+<15 位>` / `+<64>` / `+<64>`：6.30.8 输出 `+KEY = '''-----BEGIN RSA PRIVATE KEY-----\n+Comment: ***PEM_KEY***\nthe end`，一行不留；6.30.9 输出 `+KEY = '''***PEM_KEY***\n+JBck…\n+bRVg…\nthe end`，留 2 行。把 15 位行换成 `+Comment: `，结果同样是 6.30.8 留 0、6.30.9 留 2。BEGIN1 本身也在头行里（`+Comment: -----BEGIN EC…` / `+Comment: -----BEGIN DSA…` / `+MIIE…` / `+Comment: <64>`）：6.30.8 留 0，6.30.9 留 1。
  - "crafted" 和 "added-diff" 这两个限定都成立。密钥体自然时（64/64/64/20 位）两棵树都是 0；换成 `-` 行，6.30.9 留 2、6.30.8 留 4，候选更好；去掉头行里的 BEGIN，候选更好（2 对 4）；BEGIN1 只有 `+` 前缀时两边相同（2 对 2）。
