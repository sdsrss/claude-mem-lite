# Pre-release delta review, round 2: `uninstall --purge` link rule (commit 1cf1ceae, claude-mem-lite 6.35.0)

Scope: `git diff 9da56038 1cf1ceae -- install.mjs tests/install-lifecycle.test.mjs`. All runs were in my own trees: 1cf1ceae, the parent 9da56038 (which contains D#835, e375b8ab), and v6.34.0, each with node_modules copied in. Every run had HOME and CLAUDE_MEM_DIR inside the work dir, `env -i`, PATH=/usr/bin:/bin plus a dir holding only `node` and a fake `claude`, on Node v26.8.1. Line numbers below are for the 1cf1ceae tree.

## Verdict

The commit does what it says. A dev install's code links (from this release or an earlier one) and a user's own links are now removed, and their targets are never followed. Every name claude-mem-lite writes data under by default still blocks the purge. The blocking set only shrank: no name blocks now that did not block before.

There is one gap. When CLAUDE_MEM_DIR is a path under `~/.claude-mem-lite` reached through a link whose name is not one of the owned data names, that name is where the store lives, but `isOwnedDataName` does not know it. The purge then prints `Done!` with the store left behind (F1). This is a regression against the parent tree; v6.34.0 behaves the same way. No data is lost in any shape I tried.

## Findings

### F1 — P2, REAL but narrow: CLAUDE_MEM_DIR under ~/.claude-mem-lite through a non-owned link ends in "Data purged" and "Done!" with the store left
- Code: install.mjs:1994 (the filter only knows the fixed owned names). Then install.mjs:2018 `rmSync(DATA_DIR…)` unlinks the link. At install.mjs:2037–2051 the relocated purge runs, `statSync(<link>/claude-mem-lite.db)` gets ENOENT because the link is already gone, and the purge does nothing and says nothing.
- Shape: `~/.claude-mem-lite/mem -> /ssd/mem` with `CLAUDE_MEM_DIR=~/.claude-mem-lite/mem`. A deeper path behaves the same (`~/.claude-mem-lite/vol -> /ssd`, `CLAUDE_MEM_DIR=~/.claude-mem-lite/vol/mem`). With this setting, claude-mem-lite writes its store, its WAL and `runtime/` under `mem`, so `mem` is "a name claude-mem-lite writes data under", which is what the contract says must block.
- Evidence, from `reloc-through-link.sh <tree> mem <tag>` in the work dir:
  - 1cf1ceae: `✓ Data purged (~/.claude-mem-lite/)`, `Done!`, `EXIT=0`. The target still holds `mem/claude-mem-lite.db`, `mem/claude-mem-lite.db-wal` and `mem/runtime/s.json`.
  - parent 9da56038: `⚠ ~/.claude-mem-lite/mem is a link to …/ssd/mem. --purge does not delete through a link, so it removed nothing (CLAUDE_MEM_DIR …/.claude-mem-lite/mem included).`, `EXIT=1`.
  - v6.34.0: `Done!`, `EXIT=0`, store left. So this is not a regression against the last release, but this commit reopens a shape D#835 had closed.
  - Control: the same link with CLAUDE_MEM_DIR spelled as the target (`/ssd/mem`) gives `✓ Relocated data purged`, `Done!`, and the target is empty. That run is correct.
- Why P2 and not P3: no product step creates this shape, but a user can reach it with ordinary disk management. For example, they set CLAUDE_MEM_DIR to a subdirectory of `~/.claude-mem-lite`, later move that subdirectory to another disk and link it back. The result is the exact D#829 symptom: a purge claim with the memories still on disk. Nothing is deleted.
- Suggested direction (not prescribed): when MEM_DATA_DIR, as spelled, lies under DATA_DIR, also treat the first path segment of `relative(DATA_DIR, MEM_DATA_DIR)` as an owned name in the filter. That uses only spelled paths, so it avoids the resolved-path failure modes D#811 rejected. A regression case for the INNER table would be `{ links: { mem: <ext dir> }, mem: join(dir, 'mem') }`.

### F2 — P3, CONSTRUCTED: a mixed-case link on a case-insensitive filesystem (macOS APFS default, Windows) no longer blocks
- install.mjs:2192–2193 compares names exactly. On a case-insensitive filesystem, claude-mem-lite's writes to `runtime/…` (or `claude-mem-lite.db`) go through a link named `Runtime` (or `Claude-Mem-Lite.db`). `readdir` returns `Runtime`, `isOwnedDataName('Runtime')` is false, the link is unlinked, the data stays at the target, and the purge says `Done!`. Before 1cf1ceae every non-dev link blocked, so this shape did block then.
- Evidence: on Linux, links named `Runtime`, `METRICS` and `Claude-Mem-Lite.db` were each unlinked with `Done!`, exit 0 and the target intact (shapes run). That outcome is correct on a case-sensitive filesystem. I could not reproduce the case-insensitive half on this host because it needs root to mount casefold; it is reasoned from the code. Mutation M17 (lower-casing the name before matching) leaves 13/13 tests passing, so no test pins this.
- CONSTRUCTED: the user has to give the link a different case from the name the product uses.

### F3 — P3, test gap: no test has an `errors/` link
- The code is right: an `errors` link blocks (shapes run: `exit 1, blocked, linkLeft, targetIntact`). But mutation M10 (`name !== 'errors' && Object.hasOwn(OWNED_DIR_FILES, name)`) passes all 13 purge tests. The new INNER cases (tests/install-lifecycle.test.mjs:628–643) cover the WAL, a snapshot, `metrics/`, `backups/` and `managed/`, not `errors/` (lib/err-sampler.mjs writes there when CLAUDE_MEM_CATCH_SAMPLE is set). The comment at :628 says "Every name it writes data under", which overstates the coverage by this one name.

### Out of scope (pre-existing, not in this diff): a subdirectory named `constructor` in CLAUDE_MEM_DIR crashes the relocated purge
- install.mjs:2236 `const inner = OWNED_DIR_FILES[name]` looks the name up through the prototype chain. For `constructor`, `toString`, `valueOf` and similar names, `inner` is a function, and install.mjs:2255 `inner.test(c)` throws `TypeError: inner.test is not a function` out of `uninstall`, with a stack trace and exit 1. The docblock says the function "Never throws". Nothing is removed and the store stays, so the failure is data-safe. It reproduces on v6.34.0 as well. The new `isOwnedDataName` correctly uses `Object.hasOwn`; this sibling lookup does not. CONSTRUCTED: the user needs a subdirectory with a prototype name in their CLAUDE_MEM_DIR.

## Answers to the brief's questions

**1. Does any data name escape `isOwnedDataName`?**
I enumerated the writers by grep over every shipped `.mjs`/`.js`/`.sh` file (the package.json `files` set): 391 write call sites, every `join(<data/code dir>, '<literal>')`, every path built by suffixing DB_PATH, scripts/setup.sh, and the git history of all names joined to a data or code dir. The top-level names written in `~/.claude-mem-lite` are:
- the store `claude-mem-lite.db` and its `-wal`/`-shm`/`-journal`, plus `claude-mem.db` (schema.mjs, setup.sh)
- snapshots `claude-mem-lite.db.<tag>-<ISO>-<pid>-<seq>.bak`, with tags pre-maintain, pre-delete and pre-edge-prune, all lower-case (lib/db-backup.mjs:148–149)
- legacy backups and their temp files (install.mjs:202–217, setup.sh:170–178)
- `.corrupt[-ISO[-N]][-wal]` (lib/db-unusable.mjs:421)
- `.snapshot-check-<pid>-XXXXXX` (lib/db-unusable.mjs:224)
- `plugin_claude_mem_lite.md` (lib/local-steering.mjs:66)
- `.update-staging-*` and `.update-backup-*` (hook-update.mjs:1287–1306)
- `runtime/` (every hook marker, plus install.lock, update-state.json and swap-in-progress, all under runtime/)
- `metrics/`, `errors/`, `backups/`
- from releases before 5.0: `managed/` and `resource-registry.db`

Each of these blocks when it is a link. I checked 24 owned names, and every one gave `exit 1`, the link kept, the target intact and no `Done!`. Names that do not match, and why that is right:
- `settings.json`: haiku-client.mjs:240 only reads it.
- `.npm-install-failed`: scripts/launch.mjs:98 writes it into ROOT; it is a failure marker, not memories.
- `package-lock.json`: code, replaced by rename.
- the code names.

The only real miss is the CLAUDE_MEM_DIR-chosen name in F1, plus the case variants in F2 (CONSTRUCTED).

On historic remedy names: `claude-mem-lite.db-wal.corrupt` (from d011af1f) never shipped; v6.30.3, v6.30.4 and v6.30.5 have 0 occurrences of it. `.unhidden-move-*` was reverted before any tag.

**2. Can a link removed under the new rule be followed?**
No, as far as I could test. Using `rmSync(recursive, force)` on Node 26.8.1 against a real directory that held an absolute directory link, a relative directory link, a directory link with a trailing slash, a file link, a dangling link, and file and directory links nested inside a real subdirectory: every link was removed and every target was left byte-for-byte; called directly on a directory link, it removes only the link.

End to end, I ran a real `install --dev` in a sandbox HOME. It created 47 top-level links, none of them an owned name, plus real `lib/`, `cli/`, `server/` and `runtime/` directories. The purge then gave `Done!`, exit 0, and the link targets (my review tree, node_modules included) had 15302 files before and after with an identical sorted file list.

Mutation M19 makes the purge follow links before `rmSync`. It fails both the dev-install test and the new test, so the tests' target-intact assertions can detect a purge that follows links.

**3. Shapes that changed outcome.**
- Blocked before and should still block, but now pass: F1, a real shape (and a regression against the parent), and F2, CONSTRUCTED.
- Block now but should not: none. The owned names and the parent's dev-name exemption (DEV_LINK_NAMES) have no names in common. I checked all 50 current names and all 144 historic top-level SOURCE_FILES names against the matcher and none match, so the new blocking set is a subset of the old one.
- Some names that still block are ones the product never writes through, because it replaces them by rename or creates them with `wx`: `plugin_claude_mem_lite.md`, the snapshot names, `.update-*`, `.snapshot-check-*`. A link there would be user-made. Blocking on it is a conservative over-block and is unchanged from before.
- The shape the commit targets is fixed. Links named `registry.mjs`, `.mcp.json`, `commands` and `registry` each gave `exit 1` on the parent and now give `Done!`, exit 0, with the target intact.

**4. Do the tests fail when the new code is broken?**
I ran 19 per-site mutations plus M19 in my tree. Each one was applied and checked to have landed, run against the `data left behind` describe block (13 tests), then restored.

Caught:
- M0, back to the DEV_LINK_NAMES rule: fails the new test.
- M1, never owned: 10 INNER fail.
- M2, always owned: both dev tests fail.
- M3, no OWNED_WHOLE_DIRS: runtime, two-links and managed fail.
- M4, no OWNED_TOP_RE: the 6 store, WAL and snapshot cases fail.
- M5, no OWNED_DIR_FILES: metrics and backups fail.
- M7, no `isSymbolicLink` check: 12 fail.
- M8, LIVE_STORE_RE only: the snapshot case fails.
- M9 and M13, managed dropped: managed fails.
- M11, metrics dropped: metrics fails.
- M12, backups dropped: backups fails.
- M14, the store's main file only: WAL and snapshot fail.
- M15, WAL/SHM dropped: WAL fails.
- M16, snapshots dropped: snapshot fails.
- M18, relocated purge gate removed: "CLAUDE_MEM_DIR = an unrelated directory" fails.

Survived:

- M6, `name in OWNED_DIR_FILES` instead of `Object.hasOwn`: this only changes prototype-named links (a `constructor` link would block). Negligible, CONSTRUCTED.
