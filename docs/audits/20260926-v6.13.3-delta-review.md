## (B) Claims

### FALSE
**F1 — hook-handoff.mjs:804-806 and docs/measurement/findings.md:591-592 (the "Correction" to C8):**
"`rowid DESC` picks the older write whenever a tie involves a row rewritten after the other was first inserted."
Counterexample (:memory:, same UPSERT shape as hook-handoff.mjs:583-598):
```
X insert (exit,  epoch T)  -> rowid 1
Y insert (clear, epoch T)  -> rowid 2
Y rewrite (UPSERT, epoch T): Y is "a row rewritten after the other was first inserted"
ORDER BY created_at_epoch DESC, rowid DESC -> picks Y-rewrite  (the NEWEST write)
```
The claims review's own C8 probe is the same counterexample ("There B happens to be the later write, so rowid
DESC is right in that ordering"). The accurate condition is the one the review wrote: it is wrong when the
LOWER-rowid row's latest write comes after the higher-rowid row's latest write. The commit body's hedge
("where it CAN be wrong, not where it always is") is right; the shipped text replaced "exactly the rewritten
rows" with another universal. Also: findings.md puts `"can be wrong", not "is"` in quotes, but the review's
words are "where it CAN be wrong, not where it always is" — a paraphrase in quotation marks, immediately followed
by "whenever". Severity: doc-only.

### TRUE-BUT-MISLEADING
**M1 — findings.md:599-601 / commit body: "0 of 16,158 same-project summary pairs vs 2 of 173 handoff pairs"; "What
separates the two decisions is measured, not structural".** Numbers reproduce EXACTLY, read-only at
2026-09-26T08:13:59Z: summaries 452 rows, 16,158 same-project pairs, 0 with `a.id<b.id AND a.epoch>b.epoch`,
0 tied; handoffs 53 rows, 173 pairs (rowid), 2 inverted (rowid 184/185 and 167/171, both an `exit` row
upserted past a later `clear` row), 0 tied. No growth to reconcile: no summary row has epoch ≥ 07:56Z (max id
452 at 07:45:07Z); two handoff rows were upserted after 07:56Z (rowid 195 at 08:01:22Z, rowid 193 at 08:13:34Z)
without changing either count. Misleading part = population (doctrine rule 3): only rows that went through the
UPDATE can invert, and those are the 14 `notes='llm'` rows (the INSERT path writes `notes=''`, 58 rows; 371 are
`'fast'`). Pairs whose lower-id row was upgraded: **281**, 0 inverted; the other 15,877 pairs cannot invert by
construction. The smallest margin between an upgrade and the next same-project summary is 6,772 ms. The
difference from handoffs is therefore also structural — how often the row is rewritten (14/452 summaries, once
each, seconds after insert, vs a handoff UPSERT per Stop) — and the measurement is a snapshot of that.
Suggested: "0 of 281 pairs whose lower-id row was upgraded (14 upgraded rows)".

**M2 — findings.md:597-598: "a tie between an upgraded row and a later insert picks the older write (built by the
review, not observed)".** Drops the ordering the review built (defect review P3-1 repro: fast id2 inserted at
ms t, THEN the upgrade of id1 at the same ms t). If the insert follows the upgrade within the ms, `id DESC` picks
the newer write. Needs "when the upgrade lands after the insert".

**M3 — commit body: "a finally kills the child if a premise fails"; test:369 "must not leave it running past the
fixture".** It kills the vitest main only; the pool worker running the fixture body survives orphaned (P3-1).
