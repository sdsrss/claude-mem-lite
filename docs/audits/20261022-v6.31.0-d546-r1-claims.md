## 0. Verdict

The new tree's headline numbers reproduce exactly. My rerun of the author's ruler gives 1,639 repaired, 3 refused, and
0 in every problem class, and the per-plant outcomes are identical to the author's archived run on all 2,769 plants.
The doctor figures also reproduce exactly. Five things are wrong or overstated:

- **P1: "plants where a row SQLite returns intact is not in the repaired store 0 (142)" is false as worded.** On 25
  plants, a row that the ruler's own reads return intact sits in the repaired store with damaged values. The reads are
  rowid lookups on the main file alone or on the main file with its log. The ruler's NOT-READ class only checks whether
  the rowid is present, so it cannot see these 25. The 0 holds only under "the rowid is absent".
- **P2: "A table whose definition the log garbled is read through the definition the main file holds" is false
  outside a narrow case.** It holds only for this version's own tables, and only when the set of column names changes.
  Probes found three failures. A garbled column name in a table this version does not create is carried silently into
  the repaired store. A garble that drops two columns from that table refuses the whole repair and offers the
  set-aside, although 240 observations read. Two column definitions swapped in `observations` swap the values of all
  240 rows, and no line says so.
- **P2: the set-aside and restore are offered when SQLite reads most of the store, and the refusal line misstates
  what SQLite can read.** On main21-741, `repair-db` prints "SQLite cannot read <db>: no observation could be read" and
  then the set-aside. On that plant, 2,691 rows in 11 other tables read with plain SQL. SQLite's own `.recover`
  returns all 1,195 observations byte-equal to the truth. The README says the set-aside is for when "SQLite cannot read
  the database at all".
- **P2: refusals with no usable next step exist, despite "0 (164)".** A sqlite_sequence leaf that reads one row twice
  stops the repair with "repair-db stopped: UNIQUE constraint failed: sqlite_sequence.rowid. Run doctor …". Doctor then
  sends the user back to `repair-db`. The version refusal tells the owner of an older store to run "the repair-db of the
  claude-mem-lite that wrote it". `repair-db` ships for the first time in this commit, so no older version has one. The
  `create` and `unsound` refusals print no next step at all. The ruler's detector also passed a refusal whose command
  line was missing.
- **P2: "a row is lost with no line naming it 0" counts a table as named if any line names it.** Under a mutation that
  withholds the damage line, the ruler stays at 0 on the 4 plants (908 rows) where that creates a silent loss. Two
  plants drop 941 rows each from 5 tables that no line names; only the generic "Part of its list of tables could not be
  read" covers them.

Several claims hold up under re-measurement: the doctor result (286/286 ✗, 0/583 ✗, 0 writes); the refusal byte
check, mutation-verified; the backup failing mid-way after 2,000 or 3,000 pages, which leaves the main file and log
byte-identical; the write lock held at the first backup step; and the need for about three copies of free space.

## 2. The ruler: what it executes, and whether it can say NO

What it executes:
- `run.mjs` imports `repairDb` from the tree under test and runs it in-process with default options. So `swapGuard`
  is `fn => fn()`, not `withSwapBarrier`, and the CLI wiring in `install.mjs` (data-dir check, import fallback,
  printing) never runs. Three tests in tests/db-repair.test.mjs cover that wiring.
- No plant has a holder, a concurrent writer, an older or newer schema, a full disk, or a backup error. The new arm's
  3 refusals come from 2 code paths: leave-for-hand, and the fallback after "no observation". The `changed`, `busy`,
  `version`, `columns`, `create`, `write`, `unsound`, SQLITE_FULL, backup-error and integrity-fails-after-write paths
  are never reached. The "0 refusals changed a byte" and "0 with no next step" figures therefore stand on 3 plants and
  2 paths.
- `doctor.mjs` runs the shipped `install.mjs doctor` per plant. That is the right path.

Mutations, each on a copy of the tree (Appendix B, `mutate.mjs`, which asserts that each replacement landed exactly
once), swept with the author's sweep.sh against the copy:

| Mutant | What it plants | Swept | Ruler result |
|---|---|---|---|
| silentDrop | observations with rowid % 97 == 3 are reported written and never inserted | all 4 populations | **NOT-READ on 1,638/1,638** repaired plants; SILENT on 1,110/1,638, because a line names observations on the other 528 |
| refuseByte | every refusal flips byte 27 of the main file | 869, main | **"REFUSED but main changed" 3/3** |

| maskedDamage | the "some of its pages are damaged" line withheld whenever the same table also has a from-main-file, transplanted or dropped-column line | all 4 | **0 flagged: blind.** In the unmutated output, the mask removes a damage line on 170 repaired plants. On 4 of them, the table loses rows and no other loss line names it: 908 rows (log23-206 zz_values 48, log23-308 zz_values 60, log23-291 zz_noindex 400, log23-773 zz_noindex 400) |
| doctorWrites | doctor opens, reads and closes read-write before its integrity check | 869, doctor arm | **changed on 240/286** failing plants; the other 46 fail doctor's read-only open first and never reach the block |

So the ruler can say NO to a row drop when the dropped rows are readable intact, to a byte changed on refusal, to a
refusal with no text, and to doctor writing. It cannot say NO to:
- a damaged copy kept in place of an intact readable row (rowid presence only);
- a loss whose table is named by a line that is not a loss line;
- a next step whose command is missing.

Its next-step regex would also flag two real refusal texts as having no next step: the version refusal and the
"Could not open … permissions" refusal. Neither occurs in the populations.

## 3. Hunting the promise

Instrument: `hunt.mjs` (Appendix B). For every plant of the four populations, on copies, it records three things.
- The ruler's own readable rows.
- SQLite's `.recover`: rows recovered into their own tables, and observation-width rows in `lost_and_found`, matched
  to the truth by id and values.
- The store with its log read through the main file's own table definitions, via writable_schema on a copy.

It then runs `repairDb` and compares the result with the truth. Two full runs. `zz_values` is left out of the
`.recover` counts because I did not validate its representation (int64 extremes, BLOBs, text with NUL).
