## Findings

### C1 (P2): the 6.35.1 entry's rollback `rm` names the default data dir only
- **Where:** `CHANGELOG.md:35-37` (v6.35.1 entry, added by acb65bad).
- **Claim:** "6.35.0 does not remove the `transcript-digest-*.json` files this release writes to its runtime directory; `rm ~/.claude-mem-lite/runtime/transcript-digest-*.json` does."
- **First half: true.** 6.35.0's SessionStart left a digest file it had aged by 3 days. The control run, with 6.35.1's own SessionStart, removed it, so the probe can tell the two apart.
- **Second half: false when `CLAUDE_MEM_DIR` or `CLAUDE_MEM_RUNTIME_DIR` is set.**
  - `README.md:1269` documents `CLAUDE_MEM_DIR` as "All databases, runtime files, and managed resources are stored here".
  - `lib/resolve-data-dir.mjs:143-150` resolves the runtime dir as `$CLAUDE_MEM_RUNTIME_DIR`, or else `<data dir>/runtime`.
- **Reproduce:**
  ```
  node probes/reloc.mjs t-v6.35.1 t-v6.35.0 data/reloc
  # 6.35.1 Stop with CLAUDE_MEM_DIR=data/reloc/reloc-data, file aged 3 days, then 6.35.0 SessionStart
  after t-v6.35.1 Stop: .../reloc/reloc-data/runtime [ 'transcript-digest-0d8e405fe40b9c31.json' ]
  after t-v6.35.0 SessionStart (file aged 3 days): [ 'transcript-digest-0d8e405fe40b9c31.json' ]
  HOME=data/reloc/home bash -c 'rm ~/.claude-mem-lite/runtime/transcript-digest-*.json'
  rm: cannot remove '.../reloc/home/.claude-mem-lite/runtime/transcript-digest-*.json': No such file or directory   (exit 1)
  ls reloc-data/runtime -> transcript-digest-0d8e405fe40b9c31.json   (still there)
  ```
- **Expected:** a command that removes the files wherever the runtime dir is. The repository's own 6.34.0 README note does this: "delete `runtime/turn-replies-*.json` from the data directory".
- **Seen:** the command works only for the default data dir.
- **Real or constructed:** REAL. Relocating the data dir with `CLAUDE_MEM_DIR` is a documented, supported setup.
- **Why P2 and not P1:** the wrong command deletes nothing and fails loudly. What remains is orphan files that 6.35.0 never reads. Measured state sizes: 829 B for a one-line transcript, about 796 KB for a transcript with 3000 subagent files.
- **Secondary (CONSTRUCTED):** a write killed between the temp file and the rename leaves `transcript-digest-<h>.json.tmp-<pid>` (the temp name in `lib/atomic-write.mjs`). The `*.json` glob does not match it. 6.35.1's GC does catch it, because it matches on the prefix.

### C3 (P3): "A transcript above 64 MiB" understates who was affected
- **Where:** `CHANGELOG.md:10`.
- **Claim:** "A transcript above 64 MiB is read to the end when Stop cannot keep its progress between turns."
- **What the code does:** the 64 MiB budget covers the main transcript plus its subagent files together. `lib/transcript-digest.mjs:12` says "over all files", and `digestPass` shares one `budget` object.
- **Reproduce:** a 40 MiB main transcript plus a 30 MiB `subagents/agent-a.jsonl`, run on 6.35.1 with a read-only runtime dir:
  ```
  {"tree":"t-v6.35.1","complete":false,...}   x3
  ```
- **Real or constructed:** REAL shape (Claude Code writes `<session>/subagents/*.jsonl`); the sizes are constructed. A user with a 40 MiB transcript would wrongly read themselves as unaffected.

### C4 (P3): the first stall cause cannot happen between released versions
- **Where:** `CHANGELOG.md:12-13`.
- **Claim:** "two installed copies of different versions running Stop on one transcript, each throwing away the other's progress".
- **True of 6.35.1's code, but no two released versions trigger it:**
  - Only 6.35.1 names its state by the transcript path alone.
  - Two 6.35.1 code homes share the identity `1:6.35.1` and resume from each other. Probe: complete on the 2nd call.
  - 6.35.1 with 6.35.2: the names differ. Probe: 6.35.1 completes on its 2nd call.
  - 6.35.0 writes no state at all.
  - During an update, `package.json` (`source-files.mjs:386`) is swapped after `lib/transcript-digest.mjs` (`:259`). So a half-swapped home's new lib already puts the code version in the file name.
- **How I reproduced it:** only with a version string no release carries (`9.9.9-alt`). Alternating with that copy left 12/12 Stops incomplete on 100 MiB, which matches 3e85e098's "12/12".
- **Real or constructed:** CONSTRUCTED for 6.35.1 users. Only the second cause (a runtime dir that cannot be written, e.g. read-only or ENOSPC) applies to real 6.35.1 installs. The renaming still matters going forward, because it keeps 6.35.2 and later pairs apart.

### C5 (P3): the headline omits the case 3e85e098 says is not covered
- **Where:** `CHANGELOG.md:5` (headline, which also becomes the Release title) and `:10`.
- **Claim:** "citation tracking no longer stalls on a transcript Stop cannot resume".
- **The commit's own caveat:** 3e85e098 says "Not covered: a filesystem whose inode numbers change between opens saves a state the next Stop rejects." The Release body does not say this.
- **Mechanism:** `saveState` succeeds, so the read-the-rest fallback does not run (`transcript-digest.mjs:122`). The next call's `continues()` then rejects the state on the inode check (`:258`).
- **Reproduce:** candidate, 100 MiB transcript, replaced with `cp` + `mv` (new inode) between calls, 4 calls: `complete:false` every time.
- **Real or constructed:** CONSTRUCTED (cp + mv). The real equivalent is a filesystem without stable inode numbers; I did not test one.

### C6 (P3): "another shape" is checked for containers only, not Set elements
- **Where:** `CHANGELOG.md:21`.
- **Claim:** "A saved progress file of another shape is read again from the start."
- **What the code checks:** `sameShape` (`transcript-digest.mjs:272`) accepts any Set where the model is a Set; it never looks at the elements.
- **Reproduce:** `node probes/f9.mjs t-57df7b5a <dir> <variant>`:
  ```
  setOfStrings  ({$set:["1"]})   -> resumed, cited ["1",2]   (id 1 no longer a number)
  setOfObjects  ({$set:[{x:1}]}) -> resumed, cited [{"x":1},2]
  array         ([1])            -> restarted, cited [1,2]   (correct)
  ```
- **Real or constructed:** CONSTRUCTED. It takes a hand edit, or a dev checkout that changes an element type; those are the two sources the bullet itself names.

### C7 (P3): "one to eleven whole parses" undercounts 6.35.0
- **Where:** commit 3e85e098 body.
- **Claim:** "That is one streaming pass, against 6.35.0's one to eleven whole parses per Stop on the same population."
- **Reproduce:** `node probes/count-stop.mjs t-v6.35.0-count <dir> 1`. This uses the instrumented v6.35.0 tree with its memo budget forced to 0, on a transcript with an injection, a citation, assistant text and a finalization prompt. Result: `mainParses: 15`.
  - 13 of them are in `trackCitationsAtStop`: `extractCitationsFromTranscript` ×3, `extractInjectedBySurface` ×3, `extractUserTypedIds`, `extractCiteBackSignals`, `hasMainThreadAssistantText` ×2, `computeCiteRecall`, `countUnsavedBugfixShape`, `countDeliberatePersistence`.
  - 2 are `extractTailAssistantText`.
  - Within the memo budget the count is 1.
- **Cross-check:** 6.35.0's own `lib/transcript-scan.mjs` comment says "twelve".
- **Context:** on this machine the 6.35.0 memo budget is 256 MiB (heap limit 4192 MB). So above 64 MiB, 6.35.0 parsed once up to 256 MiB and 13 to 15 times beyond that.
- The number is only in the commit message, not in the Release body.

### C8 (P3): the e2e comment overstates what the idempotency key prevents
- **Where:** `tests/e2e.test.mjs:3262-3264` (comment) and `:3336` (assertion message).
- **Claim:** "...uncited — and its idempotency key then keeps the complete Stop from deciding it again".
- **Reproduce:** in `t-mut`, apply M1b (the early return moved to the cite-recall payload block) and log the state after each Stop:
  ```
  AFTER-FIRST  {"uncited_streak":1,"decay_seen_count":1,"access_count":0,"citation_log":1,"citation_surface_log":1}
  AFTER-SECOND {"uncited_streak":0,"decay_seen_count":1,"access_count":1,"citation_log":1,"citation_surface_log":1}
  ```
- **What happens:** the complete Stop late-upgrades the row (`updatePromote`: `uncited_streak = 0`, `seenInc` 0). The key stops the decay count and the logs from being counted again; it does not stop the verdict from changing.
- **Consequence for the test:** with the first assertion removed, the test passes under M1b. Only `expect(state(), ...).toEqual(before)` holds the gate; the `:3336` assertion cannot fail under M1b.
- 97337c47's description of M1b reproduces exactly: the new case fails with "expected { uncited_streak: 1 … } to deeply equal { uncited_streak: +0 …}", and the payload-only case passes.
