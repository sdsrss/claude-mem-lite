### P2-4 "an entry written for any of them is now honoured"：实测 curl/Python 接受的若干写法插件不认
- 位置：CHANGELOG.md:15-17 标题 "`NO_PROXY` accepts the forms curl, Python and Go accept" + "An entry written for any of them
  is now honoured"；lib/proxy-fetch.mjs:57-59 doc comment "this accepts the UNION of the forms curl, Python and Go accept - an
  entry a user wrote for any of them is honoured"；dededbb 提交信息 "it disagrees with each on some forms (…) because it
  accepts the union"。
- 实测（同一张表喂给三方；插件走 `httpConnectProxyFor`，curl 看 `-v` 连的是 :9 代理还是目标，Python 调
  `urllib.request.proxy_bypass_environment`）：
  | entry → URL | plugin | curl 8.18 | Python 3.14 |
  |---|---|---|---|
  | `10.0.0.0/8` → https://10.1.2.3/ | PROXY | DIRECT (`Trying 10.1.2.3:443`) | PROXY |
  | `0:0:0:0:0:0:0:1` → https://[::1]/ | PROXY | DIRECT (`Trying [::1]:443`) | – |
  | `0.0.1` → https://10.0.0.1/ | PROXY | – | DIRECT |
  Go 的 httpproxy 也做 CIDR 和按 IP 值比较（源码印象，未运行）。
- CHANGELOG.md:28 和 doc comment 自己都写了 "No CIDR"，所以同一段里自相矛盾；非规范 IPv6 写法和 Python 的 IP 后缀匹配没被提到。
  dededbb 只列了插件"比别人宽"的那一侧分歧，"比别人窄"的这一侧（上表）不是 "because it accepts the union" 能解释的。
  后果：用户为 curl 写的 `NO_PROXY` 条目被插件忽略 → 走代理（CONNECT+TLS，无明文）→ 失败后回落到 CLI。功能性，非安全性。
- 建议：CHANGELOG 改成 "It now accepts every name and `host:port` form those three accept; IP entries must be spelled the
  way the URL normalises them, and CIDR ranges are not supported." doc comment 同理把 "an entry a user wrote for any of them
  is honoured" 改为 "for names and ports"。
