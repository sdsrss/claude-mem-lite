## P2-1: the claude CLI leg of every background LLM call re-creates a removed data dir

- **Where:** haiku-client.mjs:41-49 (`cliSpawnCwd`: `mkdirSync(join(resolveRuntimeDir(DB_DIR), 'cli-cwd'), { recursive: true })`),
  reached from haiku-client.mjs:810 (sync leg) and :891 (async leg). It is not guarded by
  `workerDirGone`, and lib/worker-data-dir.mjs is not imported in haiku-client.mjs.
- **Why it is reachable in a worker:** `callLLMWithModelAsync` (haiku-client.mjs:403-431) falls
  back to `callModelCLIAsync` whenever the API or OpenRouter leg fails, and goes straight to it in
  `cli` mode, the default when no key is set. The CLI cwd is created recursively just before
  each spawn. The semaphore (hook-semaphore.mjs `acquireLLMSlot`, O_CREAT in RUNTIME_DIR)
  blocks this by accident when the dir is gone BEFORE a slot is taken. It does not block it
  when the dir goes while a slot is already held: during the API attempt, during a
  compat retry, or in enrich-save (lib/save-enrich.mjs:103-117), which calls the model with
  no slot at all, just after `openDb()` at hook.mjs:3806.
- **Evidence, real worker entry, end to end:** I spawned `hook.mjs llm-episode` with the worker
  mark, HOME in a sandbox, `ANTHROPIC_API_KEY` set, and a `--require` preload whose `fetch`
  removes the data dir and then throws ("offline"). This simulates the dir being removed during
  the direct-API attempt. `CLAUDE_CODE_PATH` pointed at a stub:
  ```
  env -i PATH=/usr/bin:/bin HOME=$H MEM_NO_AUTO_ADOPT=1 CLAUDE_MEM_HOOK_RUNNING=1 CLAUDE_MEM_BG_WORKER=1 \
    CLAUDE_MEM_NO_DELAY=1 ANTHROPIC_API_KEY=sk-probe-not-real CLAUDE_CODE_PATH=$RV/stub-claude-obs.sh \
    PROBE_DATA_DIR=$H/.claude-mem-lite NODE_OPTIONS="--require $RV/rm-on-api.cjs" \
    node hook.mjs llm-episode $H/flush.json
  exit=0
  fetch https://api.anthropic.com/v1/messages -> removed data dir
  stub called cwd=.../home5/.claude-mem-lite/runtime/cli-cwd args=-p --model haiku ...
  .../home5/.claude-mem-lite
  .../home5/.claude-mem-lite/runtime
  .../home5/.claude-mem-lite/runtime/cli-cwd
  ```
  Unit-level, with the dir already gone (`CLAUDE_MEM_DIR` missing, mark set, cli mode):
  `mode cli dataDir exists before: false` / `result {"text":"{\"ok\":true}"} dataDir exists after: true`,
  with `data/runtime/cli-cwd` created.
- **Consequence:** once `cli-cwd` exists, `workerDirGone(DB_DIR)` reads false. Every guard
  added in 57581aab then switches off for the rest of that process: ensureDb, metrics,
  hook-errors and record-once. This is the "came back holding .claude-mem-lite/" shape the
  commit set out to remove.
- **Test gap:** tests/worker-data-dir.test.mjs:132 says "every handler opens the database after
  its LLM round-trip, which is when a sandbox or a data dir has had time to go". The round-trip
  itself is a writer, and no case covers it.
- **Fix shape:** in `cliSpawnCwd`, skip the mkdir when `workerDirGone(DB_DIR)` (or when
  `workerDirGone(resolveRuntimeDir(DB_DIR))`) and let the spawn fail. Then add a case beside the
  `sinks` table: run a marked `callHaiku` with the dir gone and with a stub `CLAUDE_CODE_PATH`.

## P2-2: the update-check worker re-creates a data dir removed during its release lookup

- **Where:** hook-update.mjs:1516-1524 (`saveState`: `mkdirSync(join(STATE_DIR, 'runtime'), { recursive: true })`,
  `STATE_DIR = DB_DIR` at :59). `update-check` is a BG event (hook.mjs:266) and is spawned from
  session start in every install shape, the plugin included, when `isUpdateCheckDue()`
  (hook-update.mjs:212). The dispatch exit at hook.mjs:291 runs only once, at process start.
  The network lookup comes after it, then `saveState`. That save happens on failure as well,
  because failed lookups are now recorded.
- **Evidence, real worker entry, end to end:** I spawned `hook.mjs update-check` with the worker
  mark, HOME in a sandbox and the data dir present. A preload `fetch` removes the dir, then throws:
  ```
  env -i PATH=/usr/bin:/bin HOME=$H MEM_NO_AUTO_ADOPT=1 CLAUDE_MEM_HOOK_RUNNING=1 CLAUDE_MEM_BG_WORKER=1 \
    PROBE_DATA_DIR=$H/.claude-mem-lite NODE_OPTIONS="--require $RV/rm-on-fetch.cjs" node hook.mjs update-check
  exit=0
  fetch https://api.github.com/repos/sdsrss/claude-mem-lite/releases/latest -> removed data dir
  fetch https://api.github.com/repos/sdsrss/claude-mem-lite/tags?per_page=1 -> removed data dir
  .../home3/.claude-mem-lite
  .../home3/.claude-mem-lite/runtime
  .../home3/.claude-mem-lite/runtime/update-state.json
  ```
  Unit-level: `checkForUpdate({force:true, allowInstall:false})` in a marked process with
  `CLAUDE_MEM_DIR` missing gives `dataDir exists before: false` / `result null ms 14 dataDir exists after: true`.
- **This is the contract's own example:** "would recreate ~/.claude-mem-lite after an uninstall
  mid-flight". `uninstall --purge` during a session-start update lookup leaves
  `~/.claude-mem-lite/runtime/update-state.json` behind.
- **Test gap:** the update-check case in tests/worker-data-dir.test.mjs removes the dir before
  the spawn, so it covers only the dispatch exit.
- **Fix shape:** guard `saveState` with `workerDirGone(STATE_DIR)` (hook-update.mjs may import
  the node:fs-only leaf without breaking tests/repair-path-no-native-dep). Then add a case that
  removes the dir from inside the stubbed fetch, as above.

Other unguarded recursive mkdirs that a worker can reach, each with only a millisecond window
after the dispatch check, so not filed separately: lib/proc-lock.mjs:123 (auto-maintain lock,
hook.mjs:2315) and lib/native-binding-hint.mjs:94/153.

## P3-2: write-shrinkwrap can exit 0 having written nothing, and the release would then ship unlocked

- scripts/write-shrinkwrap.mjs:147 runs `main` only when
  `fileURLToPath(import.meta.url) === process.argv[1]`. Called through a symlinked absolute
  path, the realpath'd URL differs, the script exits 0 and writes no file:
  ```
  ln -s /home/ai/dev/claude-mem-lite $RV/link; node $RV/link/scripts/write-shrinkwrap.mjs --out $RV/sw3.json
  exit=0   (sw3.json absent; the same call through the real path writes it)
  ```
  scripts/smoke-tarball.mjs:87 then self-skips every shrinkwrap check because the file is
  absent, and the `publish` job (publish.yml:150-153) runs no smoke at all. The result is an
  unlocked publish with every step green.
- Not reachable with the standard `actions/checkout` layout: no symlink, and the relative
  `node scripts/...` call resolves to the real path. Cheap hardening: `test -f
  npm-shrinkwrap.json` after each step, or `resolve(realpathSync(argv[1]))` in the guard.

## P3-3: a relative CLAUDE_CONFIG_DIR still sends setup and update to ~/.claude

- lib/data-paths.mjs:44 and scripts/setup.sh:42-51 ignore a non-absolute value and fall back to
  ~/.claude. The 7d4d9b5e commit message records that the claude CLI took `''` as a relative
  config dir and wrote `backups/.claude.json.backup.*` into the cwd. So the host honours
  relative values, while this code prunes and edits ~/.claude: the same D#176 failure, for
  relative values only. Pinned as intended by tests/post-tool-use-disabled.test.mjs "a relative
  CLAUDE_CONFIG_DIR is ignored: ~/.claude decides". This is a decision to confirm, not a slip.

## P3-4: setup.sh one-shot markers are per data dir, not per config home

- scripts/setup.sh:319 `MCP_MIGRATION="$CODE_DIR/runtime/.mcp-dedup-v2.78"` and :403
  `RESIDUE_MARKER="$CODE_DIR/runtime/.residue-warned-v2.55"`. A user whose marker was written
  under ~/.claude (every existing user) never gets the MCP dedup or the residue warning
  evaluated against `$CLAUDE_CONFIG_DIR`. With two profiles sharing one data dir, only the first
  profile to start is checked. Low impact: it is legacy v2.x residue.

## P3-5: the bash and Node absolute-path rules differ at two edges

- `path.isAbsolute('C:/cfg')` on POSIX is `false`, but the bash `case` (setup.sh:42,
  post-tool-use.sh:31) says `C:/cfg -> absolute`. On Windows, `path.win32.isAbsolute('\\srv\cfg')`
  is `true`, but bash says `relative`. The parity matrix in tests/post-tool-use-disabled.test.mjs
  covers neither case. Unlikely values.
