## Summary

128 claims checked: **75 TRUE, 16 FALSE, 33 MISLEADING, 2 UNSUPPORTED, 2 NOT CHECKED**.
Findings: **2 x P1, 2 x P2**, the rest P3.

- **P1-1** repair-db's lock probe opens the store read-write and its close checkpoints the damaged WAL into the
  main file before any refusal. On 21 of the 869 D#535 plants doctor names repair-db, repair-db then refuses, and
  the main file, which alone read 200 of 241 observations before the run, no longer opens (SQLITE_CORRUPT).
  repair-db then prints the set-aside, saying the memories "are not recoverable without" a backup. Starting a
  session instead keeps those 200 rows: the MCP server's own WAL recovery drops the log. The claims that hide
  this: "opens the old store read-only", "changes no row", "keeps the damaged file", README "repair-db prints the
  snapshot restore or the set-aside instead".
- **P1-2** "copies every row SQLite can still read" is false once a table has two unreadable leaves. The rows
  between them are readable but are not copied, and the output says "the rows after id 90 and before id 181 could
  not be read" (72 of those 90 rows read back by rowid). Then it says to delete the kept file "once you no longer
  need it".
- **P2-1** "Nothing was replaced; <db> is as it was" and README "It refuses, changing nothing" are false at the file
  level when the WAL holds committed rows. The main file's sha changes and the WAL ends at 0 bytes. The rows read
  the same. "The damaged file is kept" means the checkpointed file, not the pair as found.
- **P2-2** db-repair.mjs:55-56 says an FTS5 table that will not connect "is damage too". Since b337fe8a it is
  classified "not checked". repair-db prints "Could not open … this is not damage repair-db can fix" on plant
  p78-v8, a store the archive's copy (C3) repaired and the copy in c30495f8 would have repaired too.

## Findings

### P1-1 repair-db rewrites the damaged main file before it refuses, and then says the memories cannot be recovered
`lib/db-repair.mjs:120-138` (probeExclusive: a read-write open, `BEGIN EXCLUSIVE`, `COMMIT`, close), called at
`lib/db-repair.mjs:455` before openOld and before every refusal except "not open" and "busy".

Claims this contradicts or hides:
- c30495f8 commit: "opens the old store read-only (again with writable_schema …)". The first open is read-write.
- `lib/db-repair.mjs:115-116`: "Closing it, as the only connection, checkpoints the log into the main file, which
  changes no row." The rows as read through main+WAL do not change. What the main file alone holds does: 200
  readable observations become a file that throws SQLITE_CORRUPT.
- `lib/db-repair.mjs:116`: "A file SQLite cannot read (SQLITE_NOTADB) cannot be probed at all". The probe fails, but
  its close still checkpointed on p1-v0 and p1-v1 (main alone 200 -> SQLITE_NOTADB).
- `lib/db-unusable.mjs` dbUnusableRemedy doc: "keeps the damaged file". The doctor and SessionStart note: "keeps the
  damaged one beside it; if it cannot read the file, it prints what to run instead".
- README "Damaged database": "A file SQLite does not recognise as a database at all cannot be read, and `repair-db`
  prints the snapshot restore or the set-aside instead."
- The refusal's own remedy: "No backup snapshot exists beside the database, so memories in the damaged file are not
  recoverable without one." This became true because of repair-db's own write.

Evidence:
- E12 (p37-v0, step by step): checkIntegrity leaves main ff1ed6e9 and the 2.2 MB WAL alone, and the main file alone
  reads 200 obs. After probeExclusive (acquired=true) the main file is 99c1d824, the WAL is gone, and the main file
  alone throws SQLITE_CORRUPT.
- SWEEP: 23 of 26 refusals rewrote a main file that alone read 200 observations. In arm B, 21 of those 23 were
  plants where the shipped doctor's printed step is `Once every Claude Code session is closed, run: … repair-db`.
- E13: on the same plants, an MCP server start, i.e. doing nothing but opening a session, recovers the 200
  observations.
- v6.30.3 base on the 19 malformed ones: its doctor printed `rm -f <wal> <shm> && mv <db> <db>.corrupt`, which keeps
  the pristine 200-observation main file as `<db>.corrupt` (archive d533-d535 :290-291).

So a user who follows doctor's step ends with an empty store and a kept file SQLite cannot open. Before the step,
200 of 241 rows were recoverable from the main file, automatically on the next session start. This is the same
shape as D#525's P1-1 (following doctor's printed step loses rows a plain session keeps).

Reachability: only when repair-db runs before any MCP server start since the damage, e.g. doctor followed by
repair-db from a terminal after the damaging session closed. The README routes exactly the `✗ Database: … malformed`
case there. If a session starts first, the server's WAL drop keeps 200 and loses the WAL's 41.

Population: 21 of 869 single-page WAL plants (23 counting the two "not a database" ones, which reach repair-db only
via the README line).

### P1-2 "Copies every row SQLite can still read" drops readable rows between two damaged leaves and calls them unreadable
`lib/db-repair.mjs:243-272` (copyTable: forward until the first throw, then backward until the next. Rows between a
second and a first damaged leaf are never read).

False or misleading wording:
- Commit titles c30495f8 ("copies every readable row"); c30495f8 body ("backward past an unreadable leaf, the gap
  reported by id").
- `lib/db-repair.mjs:14-15` ("no remedy recovers it … the gap is reported by rowid") and `:205-206` ("the rows
  between are the gap").
- README command list and section ("It copies every row SQLite can still read …", "Rows on a page SQLite cannot read
  are lost either way").
- mem-cli help, install.mjs printUsage, INTEGRITY_REMEDY and its doc ("Every page SQLite still reads goes into a
  fresh file"), the dbUnusableRemedy note, tests/db-repair.test.mjs:1.
- The output line `observations: 210 rows copied; the rows after id 90 and before id 181 could not be read`, followed
  by `The damaged file is kept as … — delete it once you no longer need it.`

Evidence: E2. Two damaged observation leaves, 282/300 rows readable one by one. The repair kept 210, and 72 of the
90 ids inside the reported gap (100..171) read back by rowid from the old file.

A user who takes the line at its word and deletes the kept file, as the next line invites, loses 72 rows that were
readable. Population: any table with two or more unreadable leaves. The single-page sweep has none (0 of 869), and
the archive lists "A C3 that resumes past more than one damaged leaf" under NOT CHECKED, so the shipped text claims
what nobody measured.

### P2-1 "is as it was" / "changing nothing" / "the damaged file is kept" are false when the WAL holds committed rows
`lib/db-repair.mjs:521` and `:536` ("Nothing was replaced; ${dbPath} is as it was."), README ("It refuses, changing
nothing, while another process has the database open, when a row it read cannot be written to the fresh file, or
when the database is from another schema version"), c30495f8 ("keeps the old file as <db>.damaged-<time>"), README
("the damaged file stays beside it"), `:591` ("The damaged file is kept as …"), tests/db-repair.test.mjs:216 ("the
damaged file is kept byte for byte").

Evidence: E1.
- Refusal on one unwritable row: the main sha went d9149c04 -> 68945af7 and the WAL is 0 B, while the output says
  "is as it was". The rows are equal (41 prompts).
- Repair: the aside is a checkpointed main (sha 22b361d0, not c5a443fc), with no aside-wal.
- The test's "byte for byte" holds only because its fixture has no WAL (buildStore closes, which checkpoints). The
  WAL test case (db-repair.test.mjs:272) never compares the aside.

Rows read the same, so no loss here by itself. It is the mechanism of P1-1, and the statements are wrong.

### P2-2 An FTS5 table that will not connect is called "not damage", contrary to the comment, and repair-db refuses a store its copy repairs
`lib/db-repair.mjs:49` (isDamage) and `:72` (a throw before a row that is not damage -> notChecked). The comment at
`:55-56` says the opposite: "preparing it connects every FTS5 table, and one that will not connect is damage too".
`:416` says "Not a damaged file: SQLite could not open or check it at all (a permission, a path)."

Evidence: E3. `invalid fts5 file format (found 99…)` and `unrecognized option: "AAAAAAAAt"` are SQLITE_ERROR, so both
come out notChecked. repair-db prints "Could not open … Nothing was changed; this is not damage repair-db can fix."
It did open the store, and a copy rebuilds every FTS table.

SWEEP: plant p78-v8 (WAL damage on schema page 78, offset 1500) is in the Q2 population. The archive's C3 passed it
(only p10-v5 and p41-v6 failed there). The shipped repairDb refuses it with that line, and the new doctor prints
`✗ FTS5 rebuild errors` plus `⚠ Database integrity: not checked`, with no step. The c30495f8 version of readIntegrity
counted this throw as a failed check, so this is b337fe8a's narrowing. Its commit message describes the narrowing
correctly; the comment it left does not.

Related, P3: `:6-9` attributes "this copy 114" to the shipped code. That number is the archive's scratch C3. The
shipped code scores 113 of 117 on this run's Q2 population, with p78-v8 refused.

### P3 (wording, precision, test comments)
1. `lib/db-repair.mjs:113-114` says "every open WAL connection holds a shared one". This feeds the c30495f8 claim
   "refuses … while another process has the store open", README "while another process has the database open" and
   mem-cli "it refuses while another process has the database open". E4: a connection that has opened but not yet
   run a statement holds no lock, and the probe acquires. tests/db-repair.test.mjs:278 says the same thing the
   claim denies ("A connection takes its shared lock on its first read").
2. b337fe8a: "SQLITE_READONLY (a database file mode 0444)". tests/db-repair.test.mjs:466-467: "fails on the file's
   mode (SQLITE_READONLY)". E7: SQLITE_IOERR_LOCK, "disk I/O error". The test asserts only `acquired === false` and
   /Could not open/. The user sees "Could not open …: disk I/O error. … this is not damage repair-db can fix"
   directly under "SQLite's integrity check fails".
3. "deleting nothing" (set-aside note), "it deletes nothing" (restore note), tests/doctor-db-remedy.test.mjs "the
   command moves, never deletes". Every such command ends `&& rm -f <db>-shm`. The -shm holds no rows.
4. tests/doctor-json-face-parity.test.mjs: "a command printed earlier can never move a file onto an aside made
   since". E10: re-running the same printed set-aside after the next session created a store moves that store onto
   the kept damaged file (mv overwrites). damagedAsidePath's "never an existing name" holds only at generation time.
5. tests/db-unusable.test.mjs: "a stale log left beside a new store would be replayed into it". E5: SQLite deletes a
   WAL whose database has 0 pages. The danger is real only beside a restored snapshot.
6. tests/db-repair.test.mjs:539: "The first step that names the database or its log moves it aside". The test's own
   next assertion is that this step is `touch <db>-wal`.
7. tests/db-repair.test.mjs:6: "Each one fails integrity_check, which is the premise every case asserts first". Four
   repairDb cases do not assert it: "leaves the fresh file as the product builds it", "refuses when not one
   observation can be read", "copies the rows on both sides of an unreadable leaf", "prints the snapshot restore …".
8. UNSUPPORTED: tests/db-repair.test.mjs:410 "on a large store that is minutes saved" (no timing anywhere), and :414
   "nothing of ours touched the file", whose assertion is `expect(original).toBeTruthy()` and checks nothing.
9. SessionStart notice and doctor detail for kind 'repair' start the note with "It copies …" before the command is
   named (doctor: "run: <cmd> — It copies …"). "if it cannot read the file, it prints what to run instead": for the
   schema and unknown kinds after repair-db there is no command.
10. formatDbUnusableNotice prints "exists but SQLite does not recognise it as a database" for kind 'repair' with
    "database disk image is malformed" (E8). The wording predates this range; the edited condition keeps it.
11. install.mjs doctor comment: "Read-only: it writes nothing, and a page it cannot read is reported rather than
    checkpointed into the file". Doctor's own read-write FTS handle (install.mjs:3140), closed a few lines above,
    has already checkpointed. The archive has doctor changing the main file on 820 of 869 plants.
12. server.mjs FATAL "The database file itself is damaged". `walRecoveryAttempted` is set on any error from the open
    after the WAL delete (schema.mjs ensureDbWithWalRecovery), not only a corruption error.
13. dbUnusableRemedy doc: "the set-aside (which keeps 0 rows)". The old set-aside (`rm -f wal shm && mv db
    db.corrupt`) kept the pristine 200-observation main file in `<db>.corrupt` (archive :290-291). Only the live
    store was empty. The doc also says "doctor" for v6.30.2's doctor without naming the version.
14. "Run repair-db from the claude-mem-lite version that wrote it" cannot be followed for an older store: no
    released version has repair-db.
15. copySequence "an id must never be handed out twice" (`:277-278`). E16: with sqlite_sequence unreadable, the next
    id is 296 (deleted ids 296-300 are reused), and the line "the fresh file has none of its rows" is wrong for that
    table, which holds the AUTOINCREMENT maxima. Sweep: p4-v0/v1/v6.
16. README "the output names each such gap by table and id". A gap with neither bound prints "the other rows" with no
    id (15 lines in the sweep, e.g. "sdk_sessions: 0 rows copied; the other rows could not be read").
17. "The damaged file is kept as A (with A-shm) — delete it once you no longer need it": "it" covers two files, and
    the undo line leaves A-shm behind (E14).
