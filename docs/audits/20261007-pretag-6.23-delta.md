## P2

### P2-1 "or it updates itself within a day" is false (CHANGELOG.md:9-10, README.md:244-246, README.zh-CN.md:205-207)

No automatic path installs a release on a direct or npx install.

- **Code.** SessionStart's background worker calls `checkForUpdate({ allowInstall: false })` (hook.mjs:3990, since 2dba920 / v3.62.0). That call only records `updateAvailable` for the banner.
- **The repo's own notes.** CHANGELOG.md:9535 and :9560 (v3.62.0) say the release check "does **not** self-install ... on any install type".
- **Run.** `vitest -t "without entering the installer"` in tests/audit-findings-20260814.test.mjs passed. It models a DIRECT install (no CLAUDE_PLUGIN_ROOT). The check found v999.0.0 and wrote `updateAvailable:true`, and the fake curl log was empty, so the installer was never entered.
- **What does install a release.** Only `claude-mem-lite update` (install.mjs:3221, allowInstall:true) and a self-heal `repair`.

So with CLAUDE_MEM_SKIP_UPDATE unset, a 6.22.1 direct user gets a "v6.23.0 available" banner and stays on 6.22.1. The variable only removes the banner and the check (hook-update.mjs:75/163/196).

The claim probably came from stale prose that predates 2dba920. Fix all copies together:
- README.md:826: "Direct install / npx mode keeps auto-update enabled"
- README.md:835: the trust table's "auto-update from GitHub Releases"
- README.zh-CN.md:667: the same claim in Chinese

Suggested text: "a direct or npx install stays where it is: the daily check only shows a banner (CLAUDE_MEM_SKIP_UPDATE=1
silences it), and `claude-mem-lite update` is what moves it". zh to match.

### P2-2 "so the plugin sends the key neither to that URL nor to api.anthropic.com" (CHANGELOG.md:36-38)

For plain http to a non-loopback host, the key DOES reach that URL in plaintext, through the `claude -p` child that the plugin
starts with its own environment (`cliSpawnEnv` = `...process.env`, haiku-client.mjs:687-693).

Run:
- Setup: callHaiku with ANTHROPIC_API_KEY=<fake 40-char key> and ANTHROPIC_BASE_URL=http://172.17.0.1:<port> (a non-loopback local fake gateway), CLAUDE_CONFIG_DIR sandboxed.
- The resolver rejected the URL, and the direct leg logged "skipping direct API call".
- The fake gateway then received `POST /v1/messages?beta=true` with `x-api-key: sk-ant-a…(40)` and UA `claude-cli/2.1.292`.

The doctor text added by 8fe9bba says exactly this ("the claude CLI fallback reads the same variable and will"), so CHANGELOG and
doctor now disagree. The sentence holds only if "the plugin" excludes the process the plugin starts.

Suggested text: "...skips the direct leg, so that leg sends the key neither to that URL nor to api.anthropic.com. Calls fall back
to `claude -p`, which reads ANTHROPIC_BASE_URL itself, so plain http to a non-loopback host still carries the key there
unencrypted". README.md:253-257 and README.zh-CN.md:213-216 make no such claim.

Context, outside the delta:
- In 6.22.1 this configuration sent the direct leg to api.anthropic.com over TLS, and only failed calls reached the CLI.
- In 6.23.0 every background call goes through the CLI to the http gateway.
- The host Claude Code session already uses that URL, so the added exposure is limited, but the notes should not say the opposite.
