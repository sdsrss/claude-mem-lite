## P2-1 — PEM rewrite (D#130) stores the body of an unterminated private-key block that v6.18.0 scrubbed

`secret-scrub.mjs:199`
`/-----BEGIN [A-Z0-9 ]*PRIVATE KEY(?: BLOCK)?-----(?:(?!-----BEGIN )[\s\S])*?-----END …-----/g`

The tempered body stops at the next `-----BEGIN `. So when a private-key block has no END line and
a later block does (for example a key that was cut off, then pasted whole, or a key followed by a
cert and then another key), the first block's match fails and its **key body stays in the stored
text**. The old `[\s\S]*?` ran from the first BEGIN to the first END and scrubbed all of it. The
commit comment says "A stray header before a complete block now stays". That holds for a header on
its own. It also holds for a header followed by key material, and that key material is what the
contract forbids storing.

Repro: `node probes/pem.mjs`
```
truncated-then-full
 OLD: "$ head -c 120 id_rsa\n***PEM_KEY***"
 NEW: "$ head -c 120 id_rsa\n-----BEGIN RSA PRIVATE KEY-----\nMIIEowIBAAKCAQEAu1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gunVTLw7onLRnrq0\n$ cat id_rsa\n***PEM_KEY***"
 K1 leaked NEW: true OLD: false
key-then-cert-then-key
 NEW: "-----BEGIN OPENSSH PRIVATE KEY-----\nMIIEow…rq0\n-----BEGIN CERTIFICATE-----…***PEM_KEY***"   K1 leaked NEW: true OLD: false
```
The only test for this case (`tests/secret-scrub-linear.test.mjs`, "a later complete PEM block after a
stray header") uses a header with an EMPTY body, so it cannot see this.

A candidate fix that stays linear: end the block at END **or** just before the next BEGIN:
`-----BEGIN …-----(?:(?!-----BEGIN )[\s\S])*?(?:-----END …-----|(?=-----BEGIN ))`. `probes/pemfix.mjs`
shows it scrubs both bodies and runs 3 / 4 / 9 ms for 32 passes at 50k / 100k / 200k chars of
`pemHeadersNoEnd`, so it grows linearly. It over-scrubs a cert that sits between the two keys. That
errs in the safe direction.

## P3-1 — Bash head+tail: the tail's own scrub window can split a >4 KB `<private>` block or PEM block and leak its end

`utils.mjs:299-302` (`scrubTruncateEnds`). For output longer than 4096 chars, the tail is scrubbed
from `str.slice(-4096)`. If a `<private>` block or a PEM block starts before that window and ends in
the output's last ~49 chars, the window sees a closer with no opener. `stripPrivate` leaves a stray
closer alone by design, and the PEM pattern needs its BEGIN. The outer `scrubSecrets(desc)` at
`hook.mjs:746` rescues this only when the opener also lands in the 51-char head. v6.18.0 took only
the head, so these shapes did not leak there.

Repro: `node probes/desc2.mjs` (the old arm is `git show 1b54741:utils.mjs`, with the outer scrub applied as hook.mjs does)
```
privateTail OLD "c → log line ok log line ok log line ok log line ok log line ok…"
privateTail NEW "c → log line ok … lo…pppppppppppppp MY-PRIVATE-TOTP 481-992 </private>"
pemPrefixed8k OLD "c → $ cat key.pem xxxx…"
pemPrefixed8k NEW "c → $ cat key.pem xxxx…elsz6BIPWdkry5AHOVc -----END RSA PRIVATE KEY-----"
```
(`elsz6BIPWdkry5AHOVc` is the last 19 chars of the key's last base64 line.) This only happens when the
block is at least ~4 KB and ends at the output's end: a `<private>` block that long, an 8192-bit RSA key, or an
armored GPG secret key of about 6.7 KB. One way to fix it: drop the tail when its window holds an unpaired
`</private>` or `-----END … PRIVATE KEY`. Another: scrub the tail window starting at the last
opener before it.

## P3-2 — JWT start `(?<![\w-])` stops catching a JWT glued to a word by a hyphen

`secret-scrub.mjs:191`. v6.18.0 used `\b`, which matched between `-` and `e`. The new lookbehind
rejects any `-` before the token, so `<word>-eyJ…` is no longer scrubbed:
```
"cookie: sess-eyJhbGc…"  OLD ok  NEW LEAK
"file auth-eyJhbGciOi…"  OLD ok  NEW LEAK
```
(repro: the inline `node -e` in this review. The input strings are the 5 above, built from the test file's JWT.)
The quadratic case it fixes is a `-eyJ` run inside ONE dotless token. Excluding `-` only when a
base64url char comes right before it would keep the fix: `(?<![\w-])eyJ|(?<=[^\w-][\w]{1,40}-)eyJ`
bounds the look-back. I have NOT timed that alternative.

## P3-3 — `CLAMPED_IDF_SCALE = 1e-3` is reachable by an obs row whose IDF is informative, and ranks it #1

`lib/search-core.mjs:420,450`. The comment says "No row whose IDF is informative scores anywhere near
this scale". That is false for the obs leg. FULL_SCORE's multipliers can shrink a raw bm25 by up to
0.5 (type) × 0.5 (importance 0) × 0.2 (noise) × 0.4 (cite) = 0.02, and length normalisation on a long
row shrinks the raw score too. The session and event legs have multipliers >= 1, so the premise holds
there. Prompts use raw bm25 with no multipliers.

Repro (real pipeline through `handleSearchForTest`): `probes/clamp-reach.test.mjs`. It seeds 200 obs
rows, the term in 91 of them (idf = ln(109.5/91.5) = 0.18, **not** clamped), and one project-p row
that is `change`, importance 0, injection_count 8, uncited_streak 3, with a 20k-token body. It adds 14
events, 2 of which match. Run with
`CLAUDE_MEM_DIR=<tmp> npx vitest run --root tree --dir probes clamp-reach`, with the clamp branch
toggled by an env switch (applied, then reverted from a copy):
```
LONE RAW obs -0.00013506591182544457
clamp ON : [{"src":"obs","id":200,"title":"long build log","score":-1},{"src":"event","id":13,"title":"quillon crash fixed","score":-1},{"src":"event","id":14,…,"score":-0.88}]
clamp OFF: [{"src":"event","id":13,…,"score":-1},{"src":"event","id":14,…,"score":-0.88},{"src":"obs","id":200,"title":"long build log","score":-0.25}]
```
The heaviest-demoted, weakest-matching row moves from last to first. It ties at -1 and wins the tie
because obs rows are pushed first and the sort is stable. Reaching this needs a term in close to half
the obs rows plus heavy demotion, so it is an edge case, and the ranking change applies where it is
not meant to. A threshold on the **raw bm25** (before the multiplier chain) would separate the two
cases. Today it tests the final score.

## P3-4 — Provenance mark: two writers are misclassified

`lib/provenance.mjs:16` reads authorship from `memory_session_id` alone.
- `hook-optimize.mjs:1316` (cluster-merge, run daily and unattended) overwrites the keeper row's
  title, narrative, facts and lesson with an LLM merge of every member, some of which may be
  machine-written. It keeps the keeper's `memory_session_id`. The keeper is chosen importance-first,
  which often picks a `manual-` save. The merged row then renders **unmarked**, as an explicit save.
- `lib/activity.mjs:191` (`activity promote --execute`) turns events into observations through
  `saveObservation`, so every promoted row gets `manual-<project>`. The eligible events include
  Haiku-written episode events (`persistHaikuSummary`, `hook-llm.mjs:520`), so machine-written
  lessons render unmarked.
Both renderings use the search/get format, so the CLI and MCP faces agree with each other. Neither is
correct. Also for the record: recent, recall and timeline (`mem-cli.mjs:721,776,1138,1185`,
`server.mjs:750`) do not mark rows on either face. So "unmarked" means "explicit save" only on the
search and get pages.

## P3-5 — The lone-surrogate guard in `scrubTruncateEnds` has no test, and removing it breaks output

`utils.mjs:302` `.replace(/^[\uDC00-\uDFFF]/, '')`. With the guard removed (probes/mutate.sh
`noSurrogate`), `tests/utils.test.mjs` and `tests/episode-input-filter.test.mjs` still pass: 347/347.
The guard does matter, though. `probes/surr.mjs` runs 35,994 valid-UTF-16 outputs of 1–6000 chars:
with the guard, 0 have a lone surrogate and the longest snippet is 100. Without it, 21,429 of 35,994
start the tail on a lone `\udexx`, and that string is persisted. Needs one test.

## P3-6 — (PRE-EXISTING, not introduced) the early return drops the tail and can store a partial token

`utils.mjs:297` `if (flat.length <= max) return flat;`. `flat` is the scrubbed-then-trimmed 4096-char
head window. Take output made of 4070 spaces, then `ghp_`, then 36 chars. The window cuts the token
to 22 chars, which is below the pattern's 36. Trimming makes it short, so it is returned as is:
`OLD "c → ghp_A1b2C3d4E5A1b2C3d4E5A1"` and `NEW` gives the same string. The head+tail change keeps this
behaviour and adds the loss of the verdict on that path.
