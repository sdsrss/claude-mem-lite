# Blind defects review: repair-db at 8575ac48 (feat/d546-repair-db), round 3

## Verdict

Random damage did not break the read side or the accounting. I ran 2,725 random plants: bytes in the main file, log frames re-signed, stale page versions in the log and in the main file, one-character garbles of sqlite_master text, and 1 KB / 4 KB / 64 KB pages, on stores with and without a log, with tables this version does not create. They showed no unnamed row loss, no store or log bytes changed on a refusal, no kept copy that differed from the store as found, no printed undo line that failed, and no crash or hang. I checked that the harness can say NO by deleting and editing rows after a repair, and it flagged them. The defects come from targeted plants at the edges:

- **Error-code classification.** Damage that SQLite reports as `SQLITE_CANTOPEN` or `SQLITE_READONLY` is classed as "not damage". The user then gets "check permissions" refusals with no working next step. A rerun loops, and each run keeps another full copy of the store.
- **Case-sensitive definition matching.** Definitions are matched by exact case, but SQLite resolves names without regard to case. So a table SQLite reads in full is dropped, or the whole repair is refused.
- **Unverified single values steer decisions.** The `schema_version` value, the main file's page-size field and a garbage rowid each decide what happens to the whole store.
- **The README's `.recover` advice** destroys the kept copy that the undo line depends on.

I would not tag before F1–F3 are fixed. F7 depends on whether "cannot save new observations" counts as "worse than as found".

## Findings

Severity follows the brief's scale. Every finding below was reproduced unless it is marked SUSPECTED. Line numbers refer to the tree at 8575ac48. Case names refer to `repro.mjs` in the Appendix.

### P0

**F1 (P0): a definition that differs from this version's only in identifier case loses the table, or the whole repair is refused, though SQLite reads every row**

- **Where:**
  - lib/db-salvage.mjs:650-664 (`fits` / `usable` compare column names with exact `includes` / `===`)
  - :783-786 (`inLog.has(t)`)
  - :710-711 (`ensureTable`, `freshCols.has(t)`)
  - :630-635 (`candidates`)
  - The table-name comparisons throughout are case-sensitive.
- **Layout:** one character of a CREATE TABLE text in sqlite_master changes case (one bit, 0x20), plus any damage that fails the integrity check. The repro uses one never-used page appended to the file, which names no table. For the log case it uses one damaged events frame in the log.
  - SQLite resolves identifiers without regard to case. In the store as found every row reads, and the product's own queries work.
- **Observed** (case `case-table`, `CREATE TABLE Sdk_sessions`):
  ```
  as found: SELECT count(*) FROM sdk_sessions → 10
  warn: sdk_sessions: could not be read (its definition cannot be read); the repaired store has none of its rows.
  warn: Sdk_sessions: it could not be made in the fresh file (table "Sdk_sessions" already exists).
  after: SELECT count(*) FROM sdk_sessions → 0
  ```
- **Observed** (case `case-column`, `Source_prompt_id` in deferred_work): 20 rows as found, 0 after.
  ```
  warn: deferred_work: could not be read (its definition reads differently from this version's); the repaired store has none of its rows.
  ```
- **Observed** (case `case-obs-wal`, `Title TEXT` in observations, store with a log): as found, 400 observations read with the log and 200 from the main file alone.
  ```
  fail: repair-db cannot read …: no observation could be read (its definition reads differently from this version's). Nothing was written to the database.
  info: No backup snapshot exists beside the database. This command sets the damaged file aside so the next session creates a fresh store. …
  ```
  The user is told to set the whole store aside.
- **Random sweep:** in the 119-plant run of one-character definition garbles that printed named losses, the case-only flips (`unfiNished`, `sOurce_prompt_id`) dropped whole tables (session_handoffs 8 rows, deferred_work 30 rows).
- **README conflict:** the README's rule is "a definition that names a column this version does not have … is not read through". Under SQLite's rules `Source_prompt_id` is a column this version has. No README rule covers a table name that differs in case. The lines for these tables give a false cause ("its definition cannot be read").
- **Severity note:** this is P0 by the scale's wording: the repaired store holds fewer readable rows than the store as found (10 → 0, 20 → 0). Every such table is named in the output, so if named losses are rated under P2 instead, this becomes P2. The observations variant refuses and prints the set-aside.

### P1

**F2 (P1): a log whose header names an unknown WAL version gets "not damage repair-db can fix", while the main file alone reads in full**

- **Where:**
  - lib/db-repair.mjs:57 (`NOT_DAMAGE_RE` includes `CANTOPEN`)
  - :119-135 (`checkIntegrity`)
  - :378 (`if (integrity.notChecked) return refuseCannotOpen(...)`)
  - :336-343
- **Layout:** the `-wal` header's format-version field (bytes 4-7) is 3007001 instead of 3007000, with the header checksum and every frame checksum recomputed. SQLite then returns `SQLITE_CANTOPEN` for every open of the store with its log.
- **Observed** (case `wal-version`):
  ```
  as found: SQLITE_CANTOPEN: unable to open database file ; main file alone observations → 200
  checkIntegrity → {"ok":false,"problems":[],"notChecked":"unable to open database file"}
  fail: Could not open …/claude-mem-lite.db: unable to open database file. Nothing was written to the database; check the file's and its directory's permissions and free space — this is not damage repair-db can fix.
  ```
- **doctor**, same store, via `node cli.mjs doctor` in the sandbox: `✗ Database: unable to open database file`, with no remedy line, because `isDbUnusableError` deliberately does not match this text.
- **README conflict:** the README says that when "SQLite cannot read the database at all, it prints the snapshot restore or the set-aside instead". Neither is printed.
- **Result:** the user has no working next step. The permissions are fine, and the 200 checkpointed observations the main file holds are never offered. Store bytes are unchanged.

**F3 (P1): `SQLITE_READONLY` caused by damage at the write-back gets "check permissions … run repair-db again", a loop that discards the checked copy and keeps another full copy of the store on every run**

- **Where:**
  - lib/db-repair.mjs:57 (`READONLY` in `NOT_DAMAGE_RE`)
  - :572-600: `isDamage(failure)` is false, so the code takes either the generic refusal at :597-600 or `refuseCannotOpen` at :596
  - :648 (`removeFile(tmp)` deletes the checked copy)
  - lib/db-salvage.mjs:96-107 and :608: `headerPageSize` trusts the main file's raw header field
- **Three layouts, all reproduced:**
  - **a. One damaged log frame (case `wal-p1-pagesize`).** The newest page-1 frame in the log says page size 8192 (bytes 16-17), re-signed. repair-db reads the main file alone (200 observations), builds the fresh file, then the backup into the store returns `SQLITE_READONLY` (page sizes differ in WAL mode).
    ```
    fail: Could not write into …: attempt to write a readonly database; the database reads as it did. Check the file's and its directory's permissions and free space, then run repair-db again.
    info: The store as found is kept byte for byte as ….damaged-…Z and ….damaged-…Z-wal.
    ```
    The second run gives the same refusal and adds another `.damaged-*` pair. After two runs the directory holds two full copies of the store and log.
    - doctor on this store: `✗ Database: malformed database schema (…)`, followed by "Once every Claude Code session is closed, run: … repair-db". This closes the loop.
    - Store and log bytes are unchanged.
  - **b. Main file's page-size field (case `main-pagesize`).** The main file's page-size field says 8192, so the main file alone is unreadable; the store with its log reads, because page 1 is in the log. Add one damaged events frame in the log. `headerPageSize` builds the fresh file at 8192, the backup into the 4096-byte store fails `SQLITE_READONLY`, and the same refusal follows (400 observations readable as found).
  - **c. Read-only file format (case `wal-p1-readonly`).** The newest page-1 log frame has write version 3 (read-only format) plus a damaged fragmented-bytes count in the same frame. The lock probe fails `SQLITE_READONLY`:
    ```
    fail: Could not open …: attempt to write a readonly database. Nothing was written to the database; check the file's and its directory's permissions and free space — this is not damage repair-db can fix.
    ```
    400 observations are readable as found.
- **README conflict:** the README says "when SQLite cannot write into it, it leaves the checked copy and prints the command that puts it in place". In a and b the checked copy is deleted and no command is printed.

**F7 (P1): a garbage rowid is copied as read and raises sqlite_sequence to 2^63-1, after which every new observation fails `SQLITE_FULL`**

- **Where:** lib/db-salvage.mjs:308-440 copies the rowid as read; :909-935 raises each counter to the fresh file's own `sqlite_sequence` (the floor), which the copied rowid has pushed to the maximum.
- **Layout** (case `big-rowid`): one observations cell on a non-rightmost leaf is re-encoded with rowid 2^63-1 and its record left intact (row 179).
  - As found, SQLite's max-rowid seek uses the rightmost leaf, so inserts work.
- **Observed:**
  ```
  as found: an observation insert → ok
  warn: observations: some of its pages are damaged (Tree 5 page 80 cell 7: Rowid 9223372036854775807 out of order), …
  warn: observations: 1 row(s) an index lists could not be read (ids 179).
  after: sqlite_sequence for observations → 9223372036854775807 ; an observation insert → SQLITE_FULL: database or disk is full
  ```
  The table is named, but nothing says the repaired store can no longer save an observation. The store as found could.
- **Plausibility:** the cell was crafted by hand. A random-damage path to a constraint-passing record under a rowid of 2^53 or more is unlikely. Any garbage rowid of 2^53 or more would also break the product's use of JS numbers. If "cannot save" counts as "worse than as found", rate this P0.

### P2

**F4 (P2): one flipped bit in `schema_version` makes repair-db refuse the store as "another schema version" and print the set-aside**

- **Where:** lib/db-salvage.mjs:600-603; lib/db-repair.mjs:429-440.
- **Layout** (case `version-bit`): the version byte goes from 49 to 48, plus one damaged observations leaf.
- **Observed:**
  ```
  fail: The database is at schema v48 and this claude-mem-lite builds v49; a copy between them would drop columns or skip a migration. Nothing was written to the database.
  info: No backup snapshot exists … sets the damaged file aside so the next session creates a fresh store …
  ```
  The product's own `initSchema` takes the same store to v49 with no error (checked: 48 → 49, 200 observations, integrity ok).
- **Next step:** the set-aside keeps the file, but leaves an empty live store. No version can repair this store: there is no older repair-db.

**F5 (P2): a store in read-only file format passes as "nothing to repair" while every write fails**

- **Where:** lib/db-repair.mjs:373-377; install.mjs:3128-3135.
- **Layout** (case `readonly-format`): the newest page-1 log frame has write version 3 (byte 18). One bit flip from 2; page 1 is in the log after most commits that grow the file.
- **Observed:**
  ```
  repair-db → healthy: "passes SQLite's integrity check — nothing to repair"
  a write: SQLITE_READONLY attempt to write a readonly database
  ```
  - doctor, on the same layout in the main file: `✓ Database integrity: ok`, then `⚠ FTS5 integrity issues detected: … CORRUPT (attempt to write a readonly database)` and `✗ FTS5 rebuild errors: … attempt to write a readonly database`.
  - `cli.mjs save` → `[mem] save failed: attempt to write a readonly database`.
- **Result:** every line points at permissions. A fresh-file copy would fix it, but repair-db declines.

**F6 (P2): the README's `.recover` advice destroys the kept copy, and the printed undo line then replaces the store and fails half-way**

- **Where:**
  - README.md:1019-1020, "stay only in the kept file, where the sqlite3 command-line tool's `.recover` may find some of them"; README.zh-CN.md:787 says the same.
  - lib/db-repair.mjs:636-643, the undo line.
- **Observed** (case `recover-advice`, sqlite3 3.46.1):
  ```
  kept copy as found before .recover: true true
  after .recover: kept main as found: false ; kept -wal: absent
  undo: cp: cannot stat '….damaged-…Z-wal': No such file or directory
  store after undo equals the store as found: false false
  ```
- **Mechanism:** the sqlite3 CLI opens the kept file read-write. Its close checkpoints the kept, damaged log into the kept main file and deletes the kept `-wal`. The undo line then runs `rm` and `cp` over the live store before failing on the missing `-wal`. That leaves the store with the damaged log folded in, which is exactly the state the design avoids.

**F8 (P2): TEXT bytes that are not valid UTF-8 are changed in the copy, in a table no line names**

- **Where:** lib/db-salvage.mjs:310 and :755. Values travel as JS strings: `.raw(true).safeIntegers(true)` reads TEXT as a string.
- **Layout** (case `utf8`): observation 10's title holds `C3 28 FF`, as a bit flip inside a text payload leaves it; an events leaf is damaged elsewhere.
- **Observed:**
  ```
  as found: hex(title) of observation 10 → 7469746C6520C328FF
  after:    hex(title) of observation 10 → 7469746C6520EFBFBD28EFBFBD
  ```
  Only events is named. Embedded NUL bytes survive.
- **Why P2:** the product reads both versions as the same JS string, so it sees no change. The README says rows are "copied as read", and here they are not.

**F9 (P2): a table the log dropped comes back from the main file, under a line that says SQLite could not read it**

- **Where:** lib/db-salvage.mjs:824-830 adds the main file's tables, and `lost()` at :816 returns true for a table with no account; lib/db-repair.mjs:706-714 prints the line.
- **Layout** (case `dropped-table`): `observation_vectors` (300 rows) is checkpointed, then dropped in the log, the way v49's migration drops it. One events frame in the log is damaged.
- **Observed:**
  ```
  as found: observation_vectors → SQLITE_ERROR: no such table: observation_vectors
  warn: observation_vectors: 300 row(s) SQLite could not read with the log were taken from the database file without it, …
  after: observation_vectors → 300
  ```
- **Result:** the line's cause is false; SQLite read the log, and the log dropped the table. The repaired store keeps a table the migration already removed, and nothing will drop it again.

### P3

**F10 (P3, code reading, not reproduced): `AGREEMENT_RE` never matches SQLite 3.53.4's wording**

- **Where:** lib/db-salvage.mjs:48-49.
- **Detail:** the alternative `non-unique entry in UNIQUE index` does not match the bundled SQLite's message, which is "non-unique entry in index " (better-sqlite3 deps/sqlite3/sqlite3.c:146946, SQLITE_VERSION 3.53.4). The other index-agreement messages (`row N values differ from index X`, `index X stores an imprecise floating-point value for row N`, `rowid not at end-of-record for row N of index X`) are not in the regex either.
- **Effect:** these fall to the structural branch, which has no page number, so the table is named even when only the index is broken. Such a table is then treated as lost, which brings in rows the log deleted, under a line.

**F11 (P3): the kept-copies listing is inaccurate**

- **Where:** lib/db-repair.mjs:326-333.
- **Observed** (case `kept-listing`):
  ```
  info: Kept from an earlier repair: ….damaged-2026-01-01T00-00-00-000Z-shm — delete it once you no longer need it.
  ```
  A `-shm` appears beside a kept copy as soon as someone opens it, as F6's advice leads them to. The `.repaired-<stamp>` checked copy left by an earlier refusal is never listed.

## NOT CHECKED

- **The MCP server deletes the log before repair-db can read it** (pre-existing, outside the diff). `ensureDbWithWalRecovery` (schema.mjs:1892-1915) deletes `-wal` and `-shm` when a corruption error reaches `ensureDb` at session start. So a session started before repair-db can discard the log the feature reads first. Only read, not exercised.
- **Concurrency of my own:** sessions opening or writing during the read or the write-back, and a process killed mid-backup. The existing tests cover some of this; I ran them (79/79 passed) but added nothing.
- **Platforms and file systems:** Windows and macOS, network and read-only file systems, and reflink-capable file systems for `COPYFILE_FICLONE`.
- **Store size:** nothing above about 7 MB was tested. Timing reference: a 6.6 MB store with 220 of 440 observations leaves damaged repaired in 804 ms.
- **Log-header damage that SQLite treats as "no log":** bad magic, a salt change, a page size at a new stride, a frame whose page number is 0 or huge. SQLite silently reads the main file alone, and repair-db and doctor say healthy. This is outside the contract (SQLite cannot read those rows), so it is not filed.
- **`version === null` with a column-set difference** (the `columns` refusal, a sibling of F4): reasoned, not run.
- **Untested paths:** `sqlite_stat1` being dropped from the copy (planner statistics only); UTF-16 stores; fish or zsh quoting of the printed lines (bash only, with a path holding `'`, a space and `$`: the undo and set-aside lines worked); doctor's `--metrics`, `--benchmark` and `--session-audit` modes; the SessionStart notice rendering (read only).

### A2. `repro.mjs`

```js
// Standalone reproductions for the blind review of 8575ac48 (repair-db).
// Usage: TREE=<extracted tree> node repro.mjs <case> <workdir>
import Database from 'better-sqlite3';
import { createHash } from 'node:crypto';
import { copyFileSync, existsSync, mkdirSync, openSync, readFileSync, rmSync, writeFileSync, writeSync, closeSync } from 'node:fs';
import { execFileSync } from 'node:child_process';
import { join } from 'node:path';
const TREE = process.env.TREE;
const { initSchema } = await import(join(TREE, 'schema.mjs'));
const { repairDb, checkIntegrity } = await import(join(TREE, 'lib/db-repair.mjs'));
const [, , which, work] = process.argv;
const sha = (p) => (existsSync(p) ? createHash('sha1').update(readFileSync(p)).digest('hex').slice(0, 12) : 'absent');

/** A WAL store: 200 observations + other tables checkpointed; with log=true, more rows left in the log. */
function build(dir, { log, big = false }) {
  rmSync(dir, { recursive: true, force: true });
  mkdirSync(dir, { recursive: true });
  const p = join(dir, 'claude-mem-lite.db');
  const db = new Database(p);
  db.pragma('journal_mode = WAL');
  db.pragma('foreign_keys = OFF');
  initSchema(db);
  db.pragma('foreign_keys = OFF');
  db.pragma('wal_autocheckpoint = 0');
  const fill = (tag, n) => {
    const s = db.prepare(`INSERT INTO sdk_sessions (content_session_id, memory_session_id, project, started_at, started_at_epoch) VALUES (?, ?, 'p', '2026', 1)`);
    const o = db.prepare(`INSERT INTO observations (memory_session_id, project, type, title, narrative, created_at, created_at_epoch) VALUES (?, 'p', 'discovery', ?, ?, '2026', ?)`);
    const e = db.prepare(`INSERT INTO events (project, event_type, title, body, created_at_epoch) VALUES ('p', 'lesson', ?, ?, 1)`);
    const d = db.prepare(`INSERT INTO deferred_work (project, title, created_at_epoch) VALUES ('p', ?, 1)`);
    for (let i = 0; i < n / 20; i++) s.run(`c-${tag}-${i}`, `m-${tag}-${i}`);
    for (let i = 0; i < n; i++) o.run(`m-${tag}-${i % 10}`, `title ${tag} ${i}`, `narrative ${'n'.repeat(i % 300)}${big && i % 37 === 0 ? 'Z'.repeat(6000) : ''}`, i);
    for (let i = 0; i < n / 2; i++) e.run(`ev ${tag} ${i}`, 'b'.repeat(i % 200));
    for (let i = 0; i < n / 10; i++) d.run(`dw ${tag} ${i}`);
  };
  db.transaction(() => fill('a', 200))();
  db.pragma('wal_checkpoint(TRUNCATE)');
  if (log) {
    db.transaction(() => fill('b', 200))();
    // copy the pair while the connection is open: its close would checkpoint the log
    copyFileSync(p, `${p}.m`);
    copyFileSync(`${p}-wal`, `${p}.w`);
    db.close();
    copyFileSync(`${p}.m`, p);
    copyFileSync(`${p}.w`, `${p}-wal`);

function walCk(buf, s0, s1, be) {
  for (let i = 0; i + 7 < buf.length; i += 8) {
    const a = be ? buf.readUInt32BE(i) : buf.readUInt32LE(i);
    const b = be ? buf.readUInt32BE(i + 4) : buf.readUInt32LE(i + 4);

}

function editWal(p, fn) {

  const be = wal.readUInt32BE(0) === 0x377f0683;
  const ps = wal.readUInt32BE(8);
  const frames = [];
```
