### F1 · P3 · CONFIRMED · lockHeld and acquireLock disagree when the lock's DIRECTORY cannot be written or entered; doctor, `cleanup --dry-run` and `cleanup` then contradict each other
`lib/proc-lock.mjs:224-236` (lockHeld), `install.mjs:3508` (dry-run), `install.mjs:3032` (doctor)

acquireLock fails closed when it cannot create its temp file or rename a stale lock aside
(`createExclusive` returns 'error' and the function returns null; a rename failure returns null).
lockHeld only looks at the lock file, so it says "not held". Real cleanup then skips update residue
and says an install is running. Doctor and the dry run count that residue and send the user to cleanup.

Probe (`lockprobe.mjs`, real acquireLock and lockHeld, a sandbox dir per case):
```
AGREE     no lock                                  lockHeld=false acquireLock=acquired
AGREE     live holder                              lockHeld=true acquireLock=null
AGREE     dead holder                              lockHeld=false acquireLock=acquired
AGREE     unreadable lock file                     lockHeld=true acquireLock=null
AGREE     lock is dangling symlink                 lockHeld=true acquireLock=null
AGREE     lock is a directory                      lockHeld=true acquireLock=null
AGREE     empty lock file                          lockHeld=false acquireLock=acquired
DISAGREE  dir cannot be entered (000), no lock     lockHeld=false acquireLock=null
DISAGREE  dir cannot be entered (000), dead lock   lockHeld=false acquireLock=null
DISAGREE  dir read-only (0555), no lock            lockHeld=false acquireLock=null
DISAGREE  dir read-only (0555), dead lock          lockHeld=false acquireLock=null
AGREE     dir read-only (0555), live lock          lockHeld=true acquireLock=null
DISAGREE  parent read-only, runtime dir absent     lockHeld=false acquireLock=null
```
End to end, two realistic shapes:

(a) **This release's own D#295 scenario.** CLAUDE_MEM_DIR is on the real read-only FUSE mount,
the code dir `~/.claude-mem-lite` is writable and holds `.update-staging-1700000000000-1`:
```
--- doctor
  ⚠ Stale temp files: 1 found (run: node .../install.mjs cleanup)
--- cleanup --dry-run
  ✓ Would remove: .update-staging-1700000000000-1
  1 stale file(s) would be removed.
--- cleanup
  ⚠ Update residue skipped: install in progress (install.lock held)
  No stale files found.
```
(b) **The shape a `sudo` run leaves** (the code comments name it). data/runtime is not writable
(0555 here, equal to root-owned 0755 for a non-root user), and the data dir is fine. Output is the
same three lines. Doctor names nothing about runtime/.

The lockHeld docstring (new in this delta) justifies the unenterable case like this: "One whose
directory cannot be looked into is not known to be held by anyone; the caller names that directory
on its own". That is false three ways:
- a dir that can be entered but not written is not "cannot be looked into", and nothing names it;
- `cleanup --dry-run` is a caller, and it never names the directory (`Would finish an interrupted
  update: …` with a 000 runtime dir, then the crash in PRE-1);
- under CLAUDE_MEM_RUNTIME_DIR, doctor scans the override dir, not `data/runtime`, so with
  `data/runtime` at 000 it printed `⚠ Stale temp files: 1 found (run: … cleanup)` and named nothing.

This is the class of the P3-1 fix (unreadable lock file) one level up, and the fix did not cover it.
The lead's claim "lockHeld and acquireLock agree for … a runtime dir that cannot be entered" is
**FALSE**.

Fix direction: a read-only probe that predicts acquireLock's failure. Report held/blocked when the
lock dir exists and `accessSync(dir, W_OK|X_OK)` fails, or when the dir is absent and its nearest
existing ancestor is not writable. Better still, have doctor and the dry run print the real cause
("install.lock cannot be taken: <dir> is not writable (EACCES/EROFS)") instead of "install in
progress".

### F4 · P3 · CONFIRMED · an unreadable install.lock is reported as "held by a running install, update or repair"; nothing is running, and the state never clears
`install.mjs:3050-3052`, `lib/proc-lock.mjs:230-234`

P3-1 made lockHeld return true for an unreadable lock. The new doctor text then names a running
installer. Lock `{"pid":<dead>,…}` at mode 000:
```
--- unreadable lock (dead pid): doctor
  ⚠ Stale temp files: update residue in …/.claude-mem-lite not checked — install.lock is held by a running install, update or repair, and cleanup skips it too
--- cleanup
  ⚠ Update residue skipped: install in progress (install.lock held)
```
acquireLock can never steal an unreadable lock, so every update, install, repair, rebuild and
cleanup is blocked until a human fixes the mode. Doctor tells the user a process is running, which
sends them to wait. The new test (`update-residue-faces`, "a lock that cannot be read is held …")
encodes that wording for a dead pid (0x7ffffffe).

Two smaller wording gaps in the same text:
- it lists "install, update or repair", but the code comment above it, and the holders in the code
  (`scripts/launch.mjs:121`, `scripts/binding-probe-cli.mjs:110`, install.mjs rebuild-binding),
  include binding rebuilds;
- the legacy data-dir residue skipped under the lock is not mentioned.

### F5 · P3 · CONFIRMED (real read-only mount) · the CANTOPEN mapping misses a same-cause state and catches a different-cause one
`lib/wal-open-blocked.mjs:38-44`, `mem-cli.mjs:3884-3887`

Measured on the real FUSE ro mount:
- **V3, no database at all** (CLAUDE_MEM_DIR on a ro mount, DB absent). Every mem-cli command now
  says a WAL database exists:
  `[mem] Error: Cannot open database: SQLite cannot open a WAL database without creating its -wal/-shm files beside it, and …/data cannot be written (EROFS)`.
  At 73fb919d the same run printed `Cannot open database: unable to open database file`. The remount
  fix is still correct; the stated cause is not. doctor and status check existsSync first, so only
  mem-cli is affected.
- **V2, `-wal` present and `-shm` absent.** Opens on the real mount gave `SQLITE_CANTOPEN unable to
  open database file`, readonly and read-write alike: the same cause and the same remedy as the
  closed store. The `-wal` guard excludes it, so the pre-D#295 output comes back:
  `✗ Database: unable to open database file` counted beside `✗ Data directory` (6 issues, not 5),
  status says `exists but check failed — unable to open database file`, and mem-cli relays the raw
  message with no fix. For comparison, V1 (`-wal` and `-shm` both present) opens and reads on the ro
  mount (`{"c":3}`). So the state that tells "the mount blocks the open" apart from "it does not" is
  whether `-shm` exists, not whether `-wal` does.
These are outside the contract's "cleanly closed store", so P3. But the docstring's rationale
("CANTOPEN has other causes, so it counts only … with no -wal beside the DB") does not match what was
measured: the guard keeps V3 (a different cause) and drops V2 (the same cause).

### F6 · P3 · CONFIRMED · erofs-sim-preload.mjs: faithful for the closed store, but its header overclaims ("every write fails"), and it diverges for a store left open by a crash
`tests/fixtures/erofs-sim-preload.mjs:8-11`

Fidelity, closed store: shim arm (chmod 0500 + preload) against the real ro mount, paths
normalized, `diff` empty for all of `install.mjs doctor`, `install.mjs status`,
`cli.mjs doctor --metrics`, `cli.mjs search foo`, `cli.mjs recent 3`, `cli.mjs stats`. V2 and V3
also matched line for line. The only boundaries this code reads (accessSync on the data dir, and the
SQLite error code) are the two the shim swaps, and `accessSync` is the only access call on the data
dir in install.mjs, mem-cli.mjs, cli.mjs and lib/.

What a real ro mount does that the shim does not: it also makes the FILES under the dir read-only.
chmod on the dir does not, so writes to existing files go through. With a crash-left store (V1,
`-wal` and `-shm` present):
- real mount: `cli.mjs search foo` → `[mem] Error: Cannot open database: attempt to write a readonly database` (no fix);
- shim: SQLite opened the writable -shm, and the run WROTE the DB file. `cmp` against the source
  copy: `differ: byte 4101`, mode changed to 0600. mem-cli went on to a migration error
  (`no such column: created_at_epoch`, from my toy schema).
So "The test makes the directory unwritable for real, so every write fails" is false. The fixture
cannot stand in for a ro mount anywhere but a cleanly closed store. Nothing in the delta's assertions
depends on that, so the fidelity claim holds for the scenario actually tested.
