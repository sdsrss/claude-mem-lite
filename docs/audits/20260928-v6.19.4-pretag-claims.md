## P1

### #5 The D#160 fix does not reach JSON-escaped text with a single-quoted code context (secret-scrub.mjs cutOffKeyEnd)

The new 80-case matrix is run only with real line breaks. Run once and twice JSON-escaped (the same file's own
`json` / `jsonTwice` convention for the D#145 leak arm), HEAD still stores key lines in 32 of 80 cases:

```
node matrixd.mjs <tree> <depth>      (80 = 4 kinds x 2 cuts x 10 left contexts, the test's own fixtures)
26dcd49 depth 0: 68/80 store key lines    2e5e266 depth 0:  0/80
26dcd49 depth 1: 60/80                    2e5e266 depth 1: 32/80  leaking lefts: diffMinusCode, grepContextCode, diffIdentifierM, doubleQuoteThenMinus (8 each)
26dcd49 depth 2: 60/80                    2e5e266 depth 2: 32/80  (same four)
```

Mechanism (code read, confirmed by the leaking set): at depth u >= 1 the BEGIN line's left-context walk stops at an
unescaped quote (`isStringEnd`), and a single quote is never escaped by JSON. For `-KEY = '''` the left context
becomes '', `prefixShape('')` is null, and `let reread = shape !== null && longs === 0` disables the reread. For an
escaped double-quote opener (`\"-`), `OPENER_RE` does not match because the context starts with a backslash.
`"""` contexts survive because JSON escapes them (readToolCode passes at every depth).

A production path that produces exactly this: `lib/import-jsonl.mjs:167`,
`scrubSecrets(JSON.stringify(toolResult?.content ?? ''))`. Read-tool output of a Python file with a cut key:

```
node json160b.mjs
Read output, raw                           26dcd49: 6/6  2e5e266: 0/6   (key windows kept)
Read output, import-jsonl content array    26dcd49: 6/6  2e5e266: 6/6
Read output, KEY = """ in content array    26dcd49: 6/6  2e5e266: 0/6
```

Own differential fuzz (fuzz4.mjs, seed 21, 40,000 inputs; head cut, code/opener left, no random edit), inputs where
HEAD stores key windows: depth 0 0/2,218 (26dcd49 1,354); depth 1 853/2,226; depth 2 463/1,116; depth 3 476/1,116;
depth 4 425/1,068. By left context: every `'`-bearing context 342-393 of 726-829; `"`/backtick contexts 0.

The commit's headline example ("`-KEY = '''` in a diff") is one of the shapes still stored once escaped. Not a
regression (26dcd49 stores them too), but the commit title, the test header and the test matrix present D#160 as
closed. Suggested: add depth 1/2 arms to the D#160 matrix; either let the reread run on a null shape when the left
context was cut at a quote, or re-derive the context without the string-end stop.

## P2

### #6 "every key the old reading took is taken the same way" is false across BEGINs

Per BEGIN the argument is right: the reread fires only on a first line of kind SHORT/OTHER, where the old reading
returned -1. But a key taken at an earlier BEGIN advances `KEY_BEGIN_RE.lastIndex` past a later BEGIN that sits in
an armor line of the taken span, and that later BEGIN's own (old) reading can reach further.

```
node cross.mjs      (lines: -KEY = '''<BEGIN> / -Comment: <BEGIN> / MIIE<b64:60> / -Comment: <b64:64> x2 / -Comment: <b64:20> / prose)
26dcd49 windows kept: 0 / 6
c112ef3 windows kept: 4 / 6     output: -KEY = '''***PEM_KEY***  then the three `-Comment: <b64>` lines stored
```

Contrived input, but it is a leak-direction regression against 26dcd49 and it falsifies an absolute stated as
by-construction. The code comment's narrower "such a key was never taken, so none goes less" (same BEGIN) holds.

### #9 Removing `longs === 0` changes more than a prefix character; keeping it keeps a D#160-family leak

```

readToolKeyOnBeginLine   26dcd49 4/4                              c112ef3 4/4   longs===0 removed 0/4
```

The parenthetical "(it can only change which line prefix character is erased)" is false, and the rationale "kept

generator; it shows the generator never puts key base64 on a code BEGIN line.
