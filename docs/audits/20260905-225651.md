### A20260905-R7-P1-1 — 子代理注入提取器不区分「被注入」与「引用了这段注入文字」

- **位置**：`lib/citation-tracker.mjs:1071-1088` `extractInjectedFromSubagentPrompt`
- **证据**：函数遍历 `readTranscriptEntries` 的**每一条** entry，只用 `SUBAGENT_INJECT_MARKER`（正文含 `surfaced by your operator's claude-mem-lite`）和行锚 `SUBAGENT_INJECT_ID_RE` 过滤，**没有 `entry.type` 门**。同文件 `SURFACE_MATCHERS.task_imperative`（`:634-640`）为同一形状专门写了命令门，理由原文是「gating on the COMMAND too means a transcript that merely quotes the framing — a review of this code, say — is not counted as an injection」。该防御没有装到这个面。
- **沙箱复现**（`mkdtempSync`，一条 `type:'assistant'` 且正文引用了该块的 entry）：
  ```
  A.  assistant-quoted marker → injected = [9001]      ❌ 计为已注入
  A2. collectSubagentSurface  → {injected:[9001], cited:[9001], files:1}  ❌ 自我引用
  ```
  `collectSubagentSurface` 做的是**每文件 seen∩said 交集**，所以同一条引用文字同时进了分子和分母 → 该 id 的 cite-rate 恒为 100%。
- **影响**（三条，均已核对调用点，非推断）：
  1. **能凭空打开解码入口门**。`hook.mjs:1250` 的条件是 `injected.size > 0 || keyCtxIds.size > 0 || (subDecayOn && sub.injected.size > 0)`，而 `subDecayOn` 默认为真（`:1247-1249`，只有 `0/off/false/no` 关）。一个真实注入为零的会话会因为一句引用跑起 decay，写 `cited_count` / `uncited_streak` / `demoted_at`。
  2. **credit `access_count`**。`sub.injected` 经 `hook.mjs:1184` 进 `buildCitationRelevanceSet`，成为 `bumpCitationAccess` 的放行集；`access_count` 再经 `maintain` 的 `boost` op 抬 `importance`（该文件 `:1004-1006` 自己记录的 D#206 开放路径）。
  3. **污染 `subagent` 面的 cite-rate**。D#164/D#177 就是拿这个数（25.5%，14/55）决策是否把该面并入解码分母的。
- **加重情节**：**读取器无条件运行，写入器默认关闭**。`collectSubagentSurface` 在 `hook.mjs:1166` 无门调用，而注入面 `pre-agent-inject.js` 默认关（`CLAUDE_MEM_SUBAGENT_INJECT=on|1` 才开，`scripts/pre-agent-inject.js:16`）。**在默认安装上不存在真注入，因此该提取器找到的每一个 id 按构造都是假阳性。**
- **最小修复**：给循环加 entry 类型门，与同文件 `extractUserTypedIds:285` 一致（`if (entry.type !== 'user') continue;`）。
- **验收标准**：新增用例——同一条 marker 文本分别放进 `type:'assistant'` 与 `type:'user'` 两条 entry，前者 `injected` 为空、后者命中；并对修复做变异验证（把类型门删掉，用例必须转红）。
- **改动风险**：低—中。**前置依赖：必须先确认真实注入落在哪种 entry 上**——本机 40 个真实 subagent 转录中 marker 出现 0 次（该开关未开），所以「`user` 是对的类型」目前是推断而非实测。开 `CLAUDE_MEM_SUBAGENT_INJECT=on` 派一次子代理、抓一条真转录，再定门的取值。**在这条实测之前不要改**，否则可能把整个面从 100% 假阳性改成 100% 假阴性。

### A20260905-R7-P2-1 — 写进用户项目的详情文档里嵌了随机器和版本变化的绝对路径

- **位置**：`adopt-content.mjs:60-171` `getDetailDoc()`，经 `claudemd.mjs:215-220` 落到 `<cwd>/.claude/plugin_claude_mem_lite.md`
- **证据**：`CLI_INVOKE`（`cli-path.mjs:25`）在插件安装形态下解析为
  `node /home/<user>/.claude/plugins/cache/sdsrss/claude-mem-lite/<VERSION>/cli.mjs`。本机实测该文档内**出现 24 次**，且路径里钉着版本号 `3.95.0`。
  同文件 `buildClaudeMdBlock()`（`:32-36`）**特意不用** `CLI_INVOKE`，注释原文：「that resolves to an absolute path that differs per install — it would make this committed/refreshed block churn across machines」。同一条理由对详情文档同样成立，但那里的豁免依据写的是「(.claude/, gitignored)」。
- **影响**：那句豁免只是**本仓库**的选择（`.gitignore:42` 的 `/.claude/`），不是用户项目的属性——`.claude/` 是放项目级 settings/commands/agents 的标准位置，很多项目会提交它。对这类项目：
  1. 每次插件升版，`needsRefresh` 看到 doc 漂移 → 重写整份文件 → git 无谓变更；
  2. 队友拉到的是只在别人机器上存在的 `$HOME` 路径，24 条命令全不可用；
  3. 多机协作时该文件必然互相覆盖。
- **最小修复**：详情文档改用与托管块同样稳定的形式（裸 `claude-mem-lite` 命令 + 一行「如何解析绝对路径」说明），把 `CLI_INVOKE` 留给运行时生成、不落用户仓库的面（MCP `instructions`、hook 恢复提示）。
- **验收标准**：`getDetailDoc()` 的输出中不含 `homedir()` 前缀；新增用例断言两台不同 `$HOME`/不同版本下 `getDetailDoc()` 逐字节相等。
- **改动风险**：低。纯内容改动，但**属"已发布产物的用户可见默认行为变化"**（写进用户仓库的文件内容变了），按 §2 硬升级规则落地需 minor 升版并在 CHANGELOG 写明。
- **前置依赖**：无。

### A20260905-R7-P2-2 — `removeManaged` 会删掉符号链接本身，而 `writeManaged` 特意穿透它

- **位置**：`claudemd.mjs:262-267`
- **证据**：块被移除后若剩余内容 `raw.trim() === ''`，走 `unlinkSync(p)`。当项目 `CLAUDE.md` 是指向 dotfiles 仓库的符号链接时，删掉的是**链接**，不是目标。这与 `lib/atomic-write.mjs` 建立的不变量相反——该模块正是为此存在（`claudemd.mjs:80-86` 记的 audit 2026-09-02 **P0**-5：本地 temp+rename 会把链接替换成普通文件，所以改用先 lstat、写穿到真目标的共享写入器）。
- **沙箱复现**：
  ```
  B1. writeManaged 后 CLAUDE.md 仍是符号链接？  ✓ 是（写穿）
  B2. removeManaged 后符号链接还在？            ❌ 否 —— 链接被删
      dotfiles 目标仍存在？                      是（成为孤儿）
  ```
- **影响**：用户 chezmoi/stow/yadm 管理的 `CLAUDE.md` 链接被静默摘除，dotfiles 里的目标文件变孤儿。`unadopt` 承诺的是"不留痕迹"，实际是改变了用户的文件布局。
- **可达性（如实说明）**：**窄**。需同时满足「`CLAUDE.md` 是符号链接」且「移除我们的块后整份文件只剩空白」——后者通常意味着该文件是 adopt 自己创建的，而 adopt 创建的是普通文件。触发路径是用户事后把它换成了链接。**列为 P2 是因为它违反的是一条既有 P0 修复确立的不变量，不是因为它常见。**
- **最小修复**：unlink 前 `lstatSync(p).isSymbolicLink()`——是链接就写空内容（穿透）而不是删除；或干脆只在我们确实创建过该文件时才删（state sidecar 里记一个 `createdFile: true`）。
- **验收标准**：沿用上面的 B1/B2 沙箱作为用例；变异验证删掉 lstat 分支后必须转红。
- **改动风险**：低。
- **前置依赖**：无。
