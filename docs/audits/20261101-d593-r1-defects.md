## 发现

### P0-1　`checkStorePages` 关闭自己打开的描述符，进程持有的 SQLite POSIX 锁随之全部释放。`mem_fts_check rebuild` 之后，MCP 服务器整个会话不再持有任何锁，已提交的行会丢

**位置**
- lib/store-pages.mjs:102 打开 `-shm`。
- :120 `closeSync(shm)`，在 beginPinnedRead 的 finally 里，紧跟着 BEGIN；这时 quick_check、dbstat、读文件都还没开始。
- :131 和 :135 打开主文件和 `-wal`，:167 关闭（经由 :302 的 `pages?.close()`）。
- 受影响的调用方：
  - 服务器的长寿读写句柄（server/fts-check.mjs:29）
  - cli/fts-check.mjs:104
  - doctor 的 rwDb
  - 打开器的 raw 句柄（schema.mjs:1884）
  - 两个只读预检

**机制**
- POSIX 的 fcntl 锁按"进程 × 文件"记。进程关掉某个文件的任何一个描述符，它在这个文件上的所有锁都会释放。
- WAL 模式下，SQLite 在连接存活期间一直持有两把锁：主文件上的 SHARED 锁，和 `-shm` 第 128 字节上的 DMS 锁。读事务期间还持有 `-shm` 上的读锁。
- 锁被放掉以后，SQLite 的记账仍以为自己持着，所以 SHARED 和 DMS 不会再去申请。

**锁的单步证据**（`scripts/locks.mjs`，跑 2 次结果相同）：
```
node scripts/locks.mjs $B/race/l.db control
{"mode":"control","before":["shm:…:128-128","db:…:1073741826-1073742335"],"after":["shm:…:128-128","db:…:1073741826-1073742335"],"walAfterOtherClose":true,"shmAfterOtherClose":true}
node scripts/locks.mjs $B/race/l.db check
{"mode":"check","state":"ok","before":[…同上…],"after":[],"walAfterOtherClose":false,"shmAfterOtherClose":false}
```
检查之后，本进程在 `/proc/locks` 里一把锁都没有。另一个进程关闭时以为自己是最后一个连接，于是检查点并删掉了 `-wal` 和 `-shm`，而第一个连接还开着。

**数据丢失的复现**（`scripts/lockloss.mjs`，跑 2 次结果相同）。场景：一个长寿连接 A 调 `handleMemFtsCheck(a, {action:'rebuild'})`；然后 hook 形状的子进程 h1 打开、插入、关闭；A 插入；h2 插入、关闭；A 再插入；最后 A 关闭。
```
control:            "survived":["h1","a1","h2","a2"]
rebuild (新代码):   "A mem_fts_check rebuild: Successfully rebuilt: …","h1 inserted and closed: wal=0 shm=0",… "survived":["h1","a1","a2"]
rebuild (v6.30.8):  "survived":["h1","a1","h2","a2"]
```
每步写 300 行的版本（`scripts/lockloss300.mjs`，2 次相同）：新代码下 h2 的 300 行全部丢失，v6.30.8 下 1200 行全在。两种情况 integrity_check 都返回 `ok`，没有任何检查会把这次丢失报出来。

**谁会遇到**
- 任何调用了 `mem_fts_check rebuild` 的会话，结果是 ok、damaged 还是 unchecked 都一样：只要库是 WAL 模式，`-shm` 就会被打开再关闭。
- 从那以后，每个 hook 关闭时都会删掉日志。服务器之后的提交写进了已删除的 inode，别的进程看不到；服务器检查点或退出时，再用旧页覆盖主文件。
- 工具描述（tool-schemas.mjs:868）和 README.md:130 都推荐在搜索结果不对时用它。
- doctor 的 rwDb、`fts-check` 的 CLI 句柄、打开器的 raw 句柄也会丢锁。这几处我没有跑并发场景，只在服务器形状上演示了丢行。

### P2-1　存储文件是符号链接时，复制命令不复制日志

**位置**：lib/db-unusable.mjs:159 用的是 `realpathSync(dirname(dbPath))`，:163 是 `cp -aL`。

**问题**：SQLite 把 `-wal` 和 `-shm` 放在链接目标旁边，不在链接所在的目录里。所以副本里只有主文件，最近一次检查点之后提交的内容全部缺失。坏在日志帧里的那一类损坏，恰好也在被漏掉的文件里。

**复现**（2 个夹具，各 2 次）。把 `real/claude-mem-lite.db` 链接到 `data/` 下，运行 doctor，doctor 打印的是：
```
test ! -e $R/data.copy-2026-11-01 && cp -aL $R/data $R/data.copy-2026-11-01
```
照做之后：`real/` 里有 `.db`（409,600 字节）和 `-wal`（103,032 字节），副本里只有 `.db`。第二个夹具的日志有 1,174,232 字节，副本里同样没有 `-wal`。

数据目录本身是链接的情况没有问题。

### P2-2　同一根因让检查在读事务期间没有读锁：并发写者 + 检查点下，好库会被判 `damaged`

数据来自 `scripts/race-writer.mjs` 和 `race-checker.mjs`，每组跑 44–45 秒，库不增长：

| 写者检查点 | 检查者 | 提交数 | ok | damaged | unchecked |
|---|---|---|---|---|---|
| 每 5 次提交轮换 PASSIVE / RESTART / TRUNCATE | 只读，复用句柄 | 12,456 | 17,877 | 3 | 950 |
| 同上 | 读写，复用句柄 | 12,361 | 10,846 | 7 | 1,395 |

- **damaged 的样子**：有 "Tree 31 page 31 cell 179: Rowid … out of order"、"2nd reference to page 658"、"the freelist: 272 pages listed, the header says 264"，SQLite 自己也会抛 "database disk image is malformed"。
- **unchecked 的原因**：主要是 "the log does not match its index"（603–1,258 次），还有 "disk I/O error"、截短的日志等。
- **对照组**（`$B/patched`，只把关闭挪到 ROLLBACK 之后）：分别 21,626、13,956、644 次检查，全部 ok。对照组写者的提交数是 1,577、1,356、103,729，因为读锁这回真的挡住了日志重启。
- **频率**：在中等写速、只有自动检查点的条件下，我测到 0/18,536。真实 hook 负载下的频率没测。

### P2-3　打开器 VTAB 分支拒绝重建以后，raw 读写句柄关闭时仍然把日志检查点进主文件

**位置**：schema.mjs:1880 打开 raw，:1884 拒绝，:1892 `raw?.close()`。

**问题**：规格把打开器排除在"不写"之外，理由是"同一个 hook 接着就会写"。但如果 VTAB 错误是真的，重试会再抛一次，hook 就不写了，这时唯一的写就是这次关闭检查点。

**复现**：按测试套件的方法注入两次错误（`scripts/opener.mjs wt 2`），在 p5-v1 上跑，2 次结果相同：
```
before {"main":"5d91a85e9d7d","wal":"d85486297d2d","mainOnly":200}
… "FTS rebuild reported: not rebuilt: the database's pages are damaged" … "attempted":false
after  {"main":"1608001b48e5","wal":"da39a3ee5e6b","mainOnly":0}
```
单步隔离（`scripts/rwclose.mjs`）：读写句柄只开不读就关，什么都不变；读写句柄跑一次检查再关，主文件被改写，`-wal` 消失；只读句柄跑检查，什么都不变。

我没有找到一个打开时会自然抛 VTAB 的库，这里依赖注入。

## 核对过、与说法一致

- **只读检查不改字节**：869 个 plant 跑两轮，sha1 没有一个变。只读打开会新建 `-shm`；没有 `-wal` 时会建一个空的 `-wal`。v6.30.8 也是这样。
- **页坏场景（A4、A5、A9）**：doctor 只给一个 ✗，加复制命令，FTS 那一行是 ⚠ not checked；`--json` 里 pages 只有一条 fail。fts-check 在 inlog1、p5-v1、main2 上都拒绝且 sha1 不变。
- **数据目录本身是链接**：副本里是真文件，包括 `-wal`。
- **这些形状都判 ok**，并且都带未检查点的日志帧：
  - auto_vacuum=FULL、auto_vacuum=INCREMENTAL
  - 64 KiB 页、64 KiB 页 + FULL、512 字节页
  - 保留 40 字节
  - 跨过锁字节页的稀疏库（4 KiB 和 64 KiB 页）
  - 5 GiB 稀疏库（1,310,720 页，文件偏移超过 4 GiB）
  - 2.2 GiB 实库（578,984 页）
  - 没有热日志的回滚日志库
- **A3**：2.2 GiB 只坏 FTS 的库，doctor 重建成功，fts-check exit 0；同一个文件当快照判 `ok`（2,400 条）。
- **869 集和第一次尝试对照**：state 869/869 相同（214 damaged、655 ok）。lines 有 6 个不同，但每个重放 20 次，两棵树自己都在两种输出之间跳，比如新代码 p66-v1 是 15:5，旧代码是 17:3。这是 SQLite 在这些坏页上本身的不确定。
- **只读数据目录**（4 种组合）：新旧版本结果相同。
- **好库**：doctor 只多一行 ✓，其余输出和退出码不变；fts-check 和 MCP 的文字也不变。
- **换版顺序**：source-files.mjs:286–380 的顺序下，被杀的换版留下的组合都能加载。
- **测试**：store-pages、store-pages-gate、snapshot-check 三个文件 148/148 通过。没有任何测试覆盖锁或跨进程写者。
