## FALSE
F1. "upgrading the older one stamped the newest created_at_epoch below a higher id, **the one shape** that makes
the summaries' id DESC tiebreakers pick the older write. It now upgrades the highest." (commit body; same
wording in findings.md paragraph and in the tests/hook-llm.test.mjs case comment "which is the one shape that
breaks the id DESC tiebreakers on session_summaries"; test title "so id order stays write order").
The llm UPDATE restamps `created_at_epoch` on whichever fast row it picks; the id DESC tiebreakers that matter
(session pool, Last Session) are PROJECT-scoped, so an upgrade of the PREVIOUS session's highest-id fast row
still lands below the NEXT session's higher id. Built on the NEW tree (43571e3), probe test in my tree only:
  - no tie: A fast (id1, t0), B fast (id2, t0+1000), handleLLMSummary(A) ->
    `[{"id":1,"s":"sess-A","notes":"llm","e":1790413126447},{"id":2,"s":"sess-B","notes":"fast","e":1790413067445}]`
    -> lower id, newer epoch: the same inversion, post-fix. (Last Session then shows "A llm request" with no tie.)
  - tie: B inserted at X, then A upgraded at fake time X ->
    `[{"id":1,...,"notes":"llm","e":1790413121474},{"id":2,...,"notes":"fast","e":1790413121474}]`,
    `buildSessionContextLines` Last Session = "Request: B fast" — id DESC picked B, the write that happened
    BEFORE A's upgrade, i.e. the older write, on the fixed tree.
  So upgrading the lower-id row within one session is not "the one shape", and the change does not make
  "id order stay write order". (Production writers restamping session_summaries.created_at_epoch:
  `git grep "UPDATE\s+session_summaries"` -> only hook-llm.mjs:1521; that single UPDATE produces the shape
  whichever row it picks.) Live: 0 project-scoped id/epoch inversions today (read-only, 08:48Z), so latent.
