## P2-1 — "cannot be taken" comes from an access() precheck, not from acquireLock's own error, so the D#304/D#307 symptoms persist for any create failure access() does not predict
- lib/proc-lock.mjs:260-274 (`lockDirBlocked`), consumed at install.mjs:3550-3557 (cleanup), install.mjs:4124-4135
  (runLockedInstall), install.mjs:3056 (doctor), scripts/launch.mjs:124.
- acquireLock still returns a bare null for every `createExclusive` 'error'. The new answer is a separate
  `accessSync(dir, W_OK|X_OK)` walk. When the create fails and access() says the dir is fine, every face
  still reads the failure as "held".
- Reproduced on HEAD with a dangling runtime symlink. Setup: `~/.claude-mem-lite/runtime -> <gone>/runtime`
  plus one `.update-staging-*` dir:
  - `lockDirBlocked: null  lockHeld: false  acquire: null` (direct call)
  - `cleanup --dry-run` → `✓ Would remove: .update-staging-1600000000000-1`, `1 stale file(s) would be removed.`
  - `cleanup` → `⚠ Update residue skipped: install in progress (install.lock held)`, `No stale files found.`, exit 0
  - `install` → `[install] Another install/repair is in progress — skipping to avoid a torn write.`, exit 0
  - `doctor --json` → `warn Stale temp files: 1 found (run: … cleanup)` and no Install lock line.
  This is the full original symptom set: the dry run and the real run disagree, a lock is reported that
  does not exist, install exits 0 having done nothing, and doctor is silent about the lock.
- Same class, not run here:
  - ENOSPC or EDQUOT on the data dir (disk full or quota).
  - EMFILE.
  - Windows. The Node docs for fs.access say it "does not check the ACL and therefore may report that a
    path is accessible even if the ACL restricts the user". libuv also treats a directory as never
    read-only. So on Windows lockDirBlocked returns null for every blocked dir, and the whole fix does
    nothing there.
- D#307 asked for "one shared 'can the lock be taken' answer (held / free / cannot be taken: dir + errno)".
  Suggested fix: have acquireLock (or a variant returning `{release}|{held}|{error:{dir,code}}`) report
  the errno of the failed create, and keep lockDirBlocked only for the read-only faces (dry run, doctor).

## P3-7 — self-heal behaviour change: the CLI heal is now reachable on 13 and has no cooldown
- mem-cli.mjs:3816-3828 → healAndReexec → `cli.mjs rebuild-binding`.
- Measured, back to back. Setup: a tree with full better-sqlite3 13.0.3 minus prebuilds/ and build/, and
  a PATH with node/npm but no python3/make/g++:
  - base 0cd60a25 `cli.mjs recent`: 81 ms and 73 ms, exit 1, raw MODULE_NOT_FOUND.
  - HEAD: 20464 ms on the first call, 470 ms on the second, exit 1 both, and the rebuild was re-run on
    each call.
- The hook path has a 6 h cooldown (hook-launcher NB_HEAL_MARKER). The CLI path has none.
- Risk, not reproduced: on a slow unsupported platform that has a working toolchain (for example 32-bit
  ARM, which 13 ships no prebuild for), the timeouts do not fit:
  - the CLI's outer `timeout: 300_000` (mem-cli.mjs:3827);
  - rebuild-binding loops over up to 3 runtime roots;
  - each root gets a source build of up to 240 s (lib/binding-probe.mjs:291).

  A SIGTERM from the outer timeout kills only `node rebuild-binding`, and the npm/node-gyp grandchild
  keeps running. The next CLI call steals the dead pid's lock and starts again with `node-gyp clean`. On
  such a device the build may never converge and may tear. Consider a cooldown marker on the CLI heal, or
  an outer timeout that covers roots × 240 s.
