## P2-1 (CONFIRMED). Replay order ignores dirs whose journal cannot be read, so the newest-first stack loses the only copy of a file

Files: `hook-update.mjs:962-972` (`nextSwapSeq` skips unreadable journals),
`hook-update.mjs:1072-1094` (recovery `continue`s past a non-ENOENT read error or an unparseable
journal, so that dir never enters `replays`), `hook-update.mjs:1101` (sort by seq; a tie keeps
readdir order).

The D#293 contract requires that replay order among several unresolved backup dirs not depend on the
wall clock, and that a replay never lose the only copy of a file. Both rules break when a journal
cannot be read at a particular moment (EBUSY/EPERM from a scanner on Windows, EACCES). There are two
variants. Each was reproduced with the repo's own fault harness from
`tests/hook-update-restore-failure.test.mjs`, plus a `readFileSync` fault. The source is in the
appendix.

**Variant A: seq tie, so readdir order decides.**
1. U1 (smoke fails): restoring `server.mjs` fails (EPERM). K1 is kept with `seq:1`.
2. U2 starts while K1's journal cannot be read (EBUSY). Recovery skips K1. `nextSwapSeq` ignores
   K1 and returns 1. U2's smoke fails and restoring `hook.mjs` fails. K2 is kept, also with
   `seq:1`.
3. Faults clear. `recoverInterruptedSwaps` sorts on a tie, and the stable sort keeps readdir order.
   - With ascending order (NTFS lists names sorted, i.e. by the `<ms>` in the name, which is the
     wall clock): K1 is replayed first and puts back old `server.mjs`. K2 is replayed next, and
     because K2 installed `server.mjs` it deletes it.
   - Final tree has no `server.mjs` and no residue to restore it from.

Output:
```
PROBE seqs asc K1 1 K2 1
PROBE after recovery asc {"hook.mjs":"// old hook","node_modules/dep.js":"old-dep","node_modules/sub/x.js":"old-x","package.json":"{\"version\":\"1.0.0\"}"} residue []
PROBE after recovery desc {"server.mjs":"// old server", ... } residue []      <- same state, only readdir order differs
× K1 journal unreadable while U2 starts -> both seq 1; readdir asc
✓ K1 journal unreadable while U2 starts -> both seq 1; readdir desc
```

**Variant B: newer dir unreadable during a recovery, so an older dir is replayed under it.** This
variant does not depend on order.
1. K1 (`seq 1`, holds old `server.mjs`) and K2 (`seq 2`, holds old `hook.mjs`) are kept, as in the
   repo's own two-dir test.
2. A recovery runs (cleanup, install, or the next update entry) while K2's journal cannot be read.
   K2 is skipped by `continue`, so the "none older while a newer one is unfinished" rule is never
   applied. K1 is replayed: `server.mjs` comes back and K1 is discarded.
3. A later recovery can read K2. Its replay deletes `server.mjs` (K2 installed it, and it is not in
   K2's restored set) and puts back `hook.mjs`.

Output:
```
PROBE2 seqs first 1 second 2
PROBE2 after R3 backups [ '.update-backup-…' ] first still there false
PROBE2 after R3 tree {…,"server.mjs":"// old server"}
PROBE2 after R4 tree {"hook.mjs":"// old hook","node_modules/dep.js":"old-dep",…,"package.json":…} residue []
× older kept dir is replayed while the newer one is skipped as unreadable; newer replay later deletes what it restored
```

Preconditions are narrow: two failed restores plus a journal read failure at a particular moment.
The outcome is the exact one D#293 exists to prevent: a file whose only copy was in a backup dir is
deleted, and nothing is left for doctor or cleanup to point at.

Fix direction (not implemented):
- Put `seq` in the backup dir NAME (for example `.update-backup-<seq>-<ts>-<pid>`), so ordering and
  `nextSwapSeq` never depend on reading a journal.
- Have recovery stop (replay nothing older) when any unresolved dir's journal cannot be read.

The repo's own ordering tests stay green because none of them makes a journal unreadable.

## P3-1 (CONFIRMED). `lockHeld()` and `acquireLock()` disagree on an unreadable install.lock, which reproduces D#297a verbatim

Files: `lib/proc-lock.mjs:58-60` (`isStale` treats an unreadable lock as stale, so `lockHeld`
answers false) vs `lib/proc-lock.mjs:157-166` (`acquireLock` cannot read it, retries the create,
and returns null). Also `install.mjs:3030` and `install.mjs:3505`.

The `lockHeld` docstring says "by the same rule acquireLock steals by". It is not the same rule for
a lock this user cannot read. Example causes: a root run with umask 077, or an ACL.

Repro: sandbox HOME with `.update-staging-1700000000000-1` in the code dir and
`runtime/install.lock` at mode 000 (dead pid, old ts).
```
== doctor
  ⚠ Stale temp files: 1 found (run: node …/install.mjs cleanup)
== cleanup --dry-run
  ✓ Would remove: .update-staging-1700000000000-1
  1 stale file(s) would be removed.
== cleanup
  ⚠ Update residue skipped: install in progress (install.lock held)
  No stale files found.
```
In this shape, doctor and the dry run contradict the real cleanup, which is the contradiction D#297a
fixed for a live holder. (The lock itself blocks install, update and cleanup until the SessionStart
sweeper unlinks it by mtime. That part predates this range.)

## P3-2 (CONFIRMED). Doctor hides a genuinely interrupted swap whenever any process holds install.lock, and says "An update holds install.lock"

File: `install.mjs:3030`, `install.mjs:3071-3075`.

`lockHeld` is true for every install.lock holder, not only an update:
- `scripts/launch.mjs:123`: every MCP launch's binding check.
- `scripts/binding-probe-cli.mjs`.
- `rebuild-binding` and `install`.
- Since D#294, for up to 1 h, a crashed holder whose pid was recycled.

While it is true, doctor drops the "⚠ Unfinished update" warning for a swap killed long ago, prints
a green "✓ Stale temp files: none", and attributes it to an update.

Repro: a backup dir with a journal (`ts` 1700000000000), plus install.lock held by a `sleep 300`
pid. Output with the lock held:
```
  ✓ Stale temp files: none
    An update holds install.lock right now; its staging and backup dirs in …/.claude-mem-lite are not counted — cleanup skips them too.
```
After killing the holder:
```
  ⚠ Unfinished update: 1 backup dir(s) in … still hold a swap journal — …
```
Cleanup skips in the same window, so the two faces agree. The cost is a green line on a check that
was not run, and wording that names the wrong holder.

## P3-3 (CONFIRMED in part). D#294's 1-hour live-holder bound turns a recycled pid into a 1-hour wedge, and `install`/`repair` report success while skipping

Files: `lib/proc-lock.mjs:35,56-57`, `install.mjs:4028` (skip returns exit 0),
`install.mjs:3763-3764` (repair's child `install` exits 0, then repair prints "Repair complete"),
`scripts/launch.mjs:123` (waits 20 × 500 ms per launch).

A holder that crashed (SIGKILL, closed terminal, Ctrl-C mid-`install`) leaves its lock behind. If
its pid is reused within the hour, `pidAlive` answers true (EPERM counts as alive), and the lock
holds for up to 60 min. Before this range the limit was 5 min. PID reuse is reasoned rather than
observed: common on Windows, plausible with pid_max 32768 or under containers / shared homedirs.
During that window:
- `install` prints "Another install/repair is in progress — skipping" and exits 0.
- `repair` then prints "✓ Repair complete — resynced from verified release" with nothing written.
  The false success predates this range; this range widens the window.
- Updates skip silently, and cleanup skips residue.
- Every MCP launch waits 10 s before falling back to probe-only.

Confirmed: a lock `{pid:1, ts: now-40min}` gives `install exit=0` and `rebuild-binding exit=1`,
both skipping. `acquireLock` on `{pid:1, ts: now-30min}` returns null.

Also by design: a live direct `install` whose npm has stalled for more than 1 h is still stolen
from (no heartbeat). The `LIVE_HOLDER_MAX_MS` comment acknowledges this.

## P3-5 (REASONED, partly visible in the repo's own test). A failed restore leaves a mixed tree live, with the swap marker cleared, until an entry nothing schedules

Files: `hook-update.mjs:1136-1164` (`rollbackInstall`: rm failure swallowed; `finally`
clears the swap marker), `hook-update.mjs:62` (24 h update interval).

When the rollback can neither delete the new path nor rename the old one back, the tree holds files
from two releases:
- Windows: the target is held without FILE_SHARE_DELETE, so both `rmSync` and MoveFileEx
  REPLACE_EXISTING fail.
- Linux: a directory that can only be partly emptied, followed by ENOTEMPTY.

The repo's test "smoke fails, removing the new node_modules stops halfway" builds exactly this
intermediate state: new `node_modules/dep.js` beside old `server.mjs`. The kept dir fixes it at the
next update, install or cleanup. On a direct install the next automatic entry is the 24 h update
check, unless a hook happens to hit ERR_MODULE_NOT_FOUND and triggers repair. Before this range the
state was permanent, so this is a residual risk, not a regression.

## P3-6 (REASONED). Install-side retirement edges for kept dirs

`install.mjs:1436-1439`:
- `retireLeftoverJournals()` runs before `installDependencies`. If npm then fails (`process.exit(1)`),
  a kept dir whose only copy was the old `node_modules` is already resolved, and the next
  recovery or cleanup deletes it. The comment at `install.mjs:1394-1399` acknowledges this.
- If `deployCodeTree` throws mid-copy (EACCES/ENOSPC), retirement never runs. A later recovery
  replays the kept dir over the half-written install tree: it deletes that release's new-only paths
  and puts the old file back.

Both predate this range for killed-swap journals. D#293 adds kept dirs to the population of dirs
that reach them.

## Appendix: probe source (added to a copy of the restore-failure harness)

Harness change: the `node:fs` mock gained

```js
readFileSync(p, o) {
  const f = take(c().readFaults || [], String(p));
  if (f) throw Object.assign(new Error(`${f.code}: simulated read failure`), { code: f.code });
  return real.readFileSync(p, o);
},
```

plus `readFaults: []` in `ctl` and in its `afterEach` reset. Probe cases:
```js
describe('PROBE seq tie', () => {
  for (const order of ['asc', 'desc']) {
    it(`K1 journal unreadable while U2 starts -> both seq 1; readdir ${order}`, async () => {
      const dataDir = makeDataDir();
      mockedExecSync.mockImplementation(smoke(false));
      const mod = await loadModule(dataDir);
      ctl.renameFaults.push({ name: 'restore-server', code: 'EPERM', sticky: true, match: restoreOf(dataDir, 'server.mjs') });
      expect(await runInstall(mod, dataDir, makeReleaseDir())).toBe(false);
      const [first] = backups(dataDir);
      expect(first).toBeDefined();
      const j1 = JSON.parse(fs.readFileSync(join(dataDir, first, '.swap-journal.json'), 'utf8'));
      // U2: K1's journal cannot be read for the duration (EBUSY: a scanner holds it)
      ctl.readFaults.push({ name: 'read-k1', code: 'EBUSY', sticky: true, match: (p) => p === join(dataDir, first, '.swap-journal.json') });
      ctl.renameFaults.push({ name: 'restore-hook', code: 'EPERM', match: restoreOf(dataDir, 'hook.mjs') });
      await new Promise((r) => setTimeout(r, 5));
      expect(await runInstall(mod, dataDir, makeReleaseDir())).toBe(false);
      expect(ctl.fired).toContain('read-k1');
      expect(ctl.fired).toContain('restore-hook');

      expect(second).toBeDefined();
      ctl.readFaults = [];
      ctl.renameFaults = [];
      const j2 = JSON.parse(fs.readFileSync(join(dataDir, second, '.swap-journal.json'), 'utf8'));
      console.log('PROBE seqs', order, 'K1', j1.seq, 'K2', j2.seq);
      ctl.readdirOrder = order;
      mod.recoverInterruptedSwaps(dataDir);
      const snap = snapshot(dataDir);
```
