## F1 — P2 — A real opening quote after a letter (`b'`, `r'`, `$'`) is rejected, so the walk defaults to `"`

`secret-scrub.mjs:623` — `(k - 1 === 0 || /[\s:,[{(=]/.test(text[k - 2]))`.

Python bytes/raw reprs and bash ANSI-C strings open with a letter or `$` before the quote. The new position rule rejects that quote; when no earlier quote on the line sits in an allowed position, `quote` stays at the default `"`. Two consequences:

- The string's real closing `'` is not a terminator, so when text follows it on the same line, the last key line reads `Xq9…GaU', b''` and is classified OTHER: a 16-39 character last line is stored.
- A `"` inside the string (for example in a PGP `Comment:` header) now ends the string, so the walk stops at the header and the whole key body is stored.

`proc.communicate()` printed as a tuple is the everyday shape: `(b'…', b'')`. A dict or `CompletedProcess` repr is rescued because an earlier `'stdout'`/`['head'` quote is in an allowed position (shown below).

```
=== communicate() tuple, RSA cut mid-line
IN : "(b'-----BEGIN RSA PRIVATE KEY-----\\nMIIEpAIBAAKCAQEAu1SU1LfVLPHCozMxH2Mo4lgOEePzNm0tRgeLezV6ffAt0gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', b'')"
cur: "(b'***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', b'')"
old: "(b'***PEM_KEY***', b'')"
rel: "(b'***PEM_KEY***', b'')"
=== communicate() tuple, PGP header with quote
IN : "(b'-----BEGIN PGP PRIVATE KEY BLOCK-----\\nComment: \"work key\"\\n\\nlQdGBFXq9Zb…NtVy\\nXq9Zb…NtVy', b'')"
cur: (input unchanged: whole key body stored)
old: "(b'***PEM_KEY***', b'')"
rel: "(b'***PEM_KEY***', b'')"
=== py r-string
IN : "r'-----BEGIN RSA PRIVATE KEY-----\\nMIIEpA…gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', 'x'"
cur: "r'***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', 'x'"
old: "r'***PEM_KEY***', 'x'"
rel: "r'***PEM_KEY***', 'x'"
=== shell ANSI-C
IN : "echo $'-----BEGIN RSA PRIVATE KEY-----\\nMIIEpA…gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU' > k"
cur: "echo $'***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU' > k"
old: "echo $'***PEM_KEY***' > k"
rel: "echo $'***PEM_KEY***' > k"
=== dict repr (earlier allowed quote rescues)
IN : "{'stdout': b'-----BEGIN RSA PRIVATE KEY-----\\nMIIEpA…gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', 'rc': 0}"
cur: "{'stdout': b'***PEM_KEY***', 'rc': 0}"   (old, rel identical)
```

The differential fuzzer (`.d3/diff.mjs`, seeds 3 and 11, 951 + 1285 distinct inputs over 10 leads x 5 key bodies x 5 prefixes x 7 followers) found exactly this shape and nothing else as cases where `cur` keeps more key material than `old` (2 inputs per seed, both `b'`/`r'` leads with `', 'rc': 0}` after).

Regression vs da9120a: yes (old takes the first quote and gets `'`). Vs 0959181: yes.
Severity P2: a cut-off key (no END), escaped text, an opener after a letter with no earlier allowed-position quote, and either text after the closing quote (one 16-39 line) or a `"` in an armor header (whole body).

## F2 — P2 — A prose quote in an allowed position is still taken as the opening quote (F1 of the previous round, repaired only for apostrophes inside words)

`secret-scrub.mjs:623`, same condition. The rule rejects `Here's`, but a quoted word in prose (`Run 'head id_rsa':`, `cat('k')`, `Run "head id_rsa":` in a Python repr) has its opening quote after a space or `(`, so the walk takes it. The consequences are the ones the previous round's F1 described: the real closing quote is not a terminator, the last 16-39 line is stored, and with an apostrophe in a PGP header the whole key is stored.

```
=== JSON with quoted word before BEGIN
IN : "{\"stdout\":\"Run 'head id_rsa':\\n-----BEGIN RSA PRIVATE KEY-----\\nMIIEpA…gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\",\"stderr\":\"\",\"interrupted\":false}"
cur: "{\"stdout\":\"Run 'head id_rsa':\\n***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\",\"stderr\":\"\",\"interrupted\":false}"
old: (same as cur)
rel: "{\"stdout\":\"Run 'head id_rsa':\\n***PEM_KEY***\",\"stderr\":\"\",\"interrupted\":false}"
=== JSON with quoted word, PGP Alices
IN : "{\"stdout\":\"File 'k.asc':\\n-----BEGIN PGP PRIVATE KEY BLOCK-----\\nComment: Alice's key\\n\\nlQdGBFXq9Zb…NtVy\\nXq9Zb…NtVy\",\"stderr\":\"\"}"
cur: (input unchanged: whole key body stored)
old: (input unchanged)
rel: "{\"stdout\":\"File 'k.asc':\\n***PEM_KEY***\",\"stderr\":\"\"}"
=== py repr with "quoted" word before BEGIN
IN : "{'stdout': 'Run \"head id_rsa\":\\n-----BEGIN RSA PRIVATE KEY-----\\nMIIEpA…gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', 'rc': 0}"
cur: "{'stdout': 'Run \"head id_rsa\":\\n***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU', 'rc': 0}"
old: (same as cur)
rel: "{'stdout': 'Run \"head id_rsa\":\\n***PEM_KEY***', 'rc': 0}"
=== JSON with cat(k) before
IN : "{\"stdout\":\"cat('k') gives:\\n-----BEGIN RSA PRIVATE KEY-----\\nMIIEpA…gun\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\",\"stderr\":\"\"}"
cur: "{\"stdout\":\"cat('k') gives:\\n***PEM_KEY***\\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\",\"stderr\":\"\"}"
old: (same as cur)
rel: "{\"stdout\":\"cat('k') gives:\\n***PEM_KEY***\",\"stderr\":\"\"}"
=== JSON with Heres before BEGIN (the case this commit fixed)
cur: "{\"stdout\":\"Here's the head:\\n***PEM_KEY***\",\"stderr\":\"\"}"   (old kept the last line; rel erased it)
```

Quoting a file or command name in single quotes before pasting its output is common prose in an agent transcript, so the repaired shape (`Here's`) is one member of a larger class the position rule does not reach. F1 and F2 together say the quote character cannot be recovered from the character before a quote in either direction.

Regression vs da9120a: no (old leaks the same). Vs 0959181: yes.
Severity P2: needs escaped text, a quoted word earlier in the same string, and a cut-off key; the PGP variant stores the full body.

## F3 — P2 — The clean-END rule erases one identifier or path line (16+ base64-alphabet characters) over an END alone on its line

`secret-scrub.mjs:777` (`clean`) and `:787` (`|| clean`). Any single line of 16-39 characters from `[A-Za-z0-9+/=]` over a lone END is now a key tail, and the span takes the END line too. da9120a's F7 repair had stopped exactly this for bare lines ("an identifier of 16-39 characters over an END in prose is not"); the clean rule brings it back, and the F2 prefix repair extends it to prefixed text the release did not touch.

```
=== identifier over lone END
IN : "const name = 'x';\nreadPrivateKeyFromFileSync\n-----END RSA PRIVATE KEY-----\n"
cur: "const name = 'x';\n***PEM_KEY***\n"
old: (unchanged)
rel: "const name = 'x';\n***PEM_KEY***\n"
=== path w/o leading slash
IN : "src/components/SignInButton\n-----END RSA PRIVATE KEY-----\n"
cur: "***PEM_KEY***\n"          old: (unchanged)          rel: "***PEM_KEY***\n"
=== camel over END doc
IN : "The helper is\nparsePrivateKeyPemString\n-----END RSA PRIVATE KEY-----\nis what it looks for."
cur: "The helper is\n***PEM_KEY***\nis what it looks for."   old: (unchanged)   rel: same as cur
=== Read tool numbered
IN : "     1\treadPrivateKeyFromFile\n     2\t-----END RSA PRIVATE KEY-----\n"
cur: "     1\t***PEM_KEY***\n"          old: (unchanged)          rel: (unchanged)
=== grep -n
IN : "a.js:10:loadPemFileFromDiskNow\na.js:11:-----END RSA PRIVATE KEY-----"
cur: "a.js:10:***PEM_KEY***"          old: (unchanged)          rel: (unchanged)
=== JSON escaped
IN : "{\"s\":\"loadPemFileFromDiskNow\\n-----END RSA PRIVATE KEY-----\\n\"}"
cur: "{\"s\":\"***PEM_KEY***\\n\"}"   old: (unchanged)   rel: same as cur
=== JSON Read-tool identifier
IN : "{\"c\":\"     1\\timport x\\n     2\\treadPrivateKeyFromFile\\n     3\\t-----END RSA PRIVATE KEY-----\\n\"}"
cur: "{\"c\":\"     1\\timport x\\n     2\\t***PEM_KEY***\\n\"}"   old, rel: (unchanged)
=== docker logs identifier
IN : "web-1  | loading parsePrivateKeyPemString\nweb-1  | loadPemFileFromDiskNow\nweb-1  | -----END RSA PRIVATE KEY-----\n"
cur: "web-1  | loading parsePrivateKeyPemString\nweb-1  | ***PEM_KEY***\n"   old, rel: (unchanged)
=== docker 2 identifier lines   (longs >= 2, reached through the F2 prefix repair, not the clean rule)
IN : "web-1  | fooBarBazQuxQuuxCorge\nweb-1  | anotherLongIdentifierX\nweb-1  | -----END RSA PRIVATE KEY-----\n"
cur: "web-1  | ***PEM_KEY***\n"   old, rel: (unchanged)
=== tail JSON array   (an array of strings: the `"` prefix of the line above matches, so the END counts as clean)
IN : "[\n  \"Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\",\n  \"-----END RSA PRIVATE KEY-----\"\n]"
cur: "[\n  \"***PEM_KEY***\"\n]"   old, rel: (unchanged)
```

Not erased: a line with `.`, `_` or `-` (`/etc/ssl/private/server.key`, `PRIVATE_KEY_PATH_VARIABLE`), a markdown bullet (`- decodeBase64PrivateKeys`, the `-` prefix does not match), a line under 16 characters.

The trade-off is structural: a 16-39 character last key line and a camelCase identifier are the same string class, and the only evidence the rule adds is where the END sits. The commit's own tests keep text only for END lines with words after them or inside a code span; none covers an identifier over a lone END.

Regression vs da9120a: yes, for every form above. Vs 0959181: yes for the Read-tool, `grep -n`, docker-prefixed, JSON Read-tool and string-array forms; the bare and JSON forms were erased by 0959181 as well.
Severity P2: needs a line made only of letters, digits, `/`, `+`, `=` of 16+ characters directly over an END line with nothing else on it; it erases that line and the END line.

## F4 — P3 — A sentence becomes a line prefix when the line above starts with the same words

`secret-scrub.mjs:767-768`. `prefixed` compares the END line's text before the END (digits free, `:`/`-` interchangeable) with the start of the line above. Lines that open with the same words (bullets, a repeated sentence stem, a chat log with one speaker) pass that test, so the sentence is not a sentence any more: the span runs to `ee`, and a clean END makes one 16-39 line enough.

```
=== repeated sentence stem, identifier 40+
IN : "The last line is ThisIsAVeryLongIdentifierNameThatExceedsForty\nThe last line is -----END RSA PRIVATE KEY----- in every PEM file."
cur: "The last line is ***PEM_KEY*** in every PEM file."   old, rel: (unchanged)
=== bullet sentences
IN : "- see ThisIsAVeryLongIdentifierNameThatExceedsForty\n- see -----END RSA PRIVATE KEY----- too"
cur: "- see ***PEM_KEY*** too"   old, rel: (unchanged)
=== repeated stem, clean END
IN : "The footer: parsePrivateKeyPemString\nThe footer: -----END RSA PRIVATE KEY-----\n"
cur: "The footer: ***PEM_KEY***\n"   old, rel: (unchanged)
=== chat log same speaker
IN : "[12:00:01] alice: parsePrivateKeyPemString\n[12:00:02] alice: -----END RSA PRIVATE KEY-----\n"
cur: "[12:00:01] alice: ***PEM_KEY***\n"   old, rel: (unchanged)
```

With words after a non-clean END and a single line under 40 characters, nothing is erased (`[12:00:02] alice: -----END … is the footer` kept in all three).
Regression vs da9120a and vs 0959181: yes. Severity P3: needs repeated line openings plus an identifier-shaped line.

## F5 — P3 — `X-*` and `CRL` header names make prose after a lone BEGIN line into armor headers

`secret-scrub.mjs:380-381`. `ARMOR_HEADER_RE` now accepts `X-<anything>:` and `CRL:` case-insensitively. In `cutOffKeyEnd`, one header line sets `armors > 0`, and then one 16+ line under it is a key, so the BEGIN line, the prose "header" line and the identifier line are all erased.

```
=== X- HTTP headers after BEGIN, identifier under
IN : "-----BEGIN RSA PRIVATE KEY-----\nX-Request-Id: 42\nContentSecurityPolicyReport\nmore prose here"
cur: "***PEM_KEY***\nmore prose here"   old, rel: (unchanged)
=== X-ray prose after BEGIN
IN : "-----BEGIN RSA PRIVATE KEY-----\nx-ray: the header above opens a key\nparsePrivateKeyPemString\nand so on"
cur: "***PEM_KEY***\nand so on"   old, rel: (unchanged)
=== CRL prose
IN : "-----BEGIN RSA PRIVATE KEY-----\ncrl: see RFC 5280\nparsePrivateKeyPemString\n"
cur: "***PEM_KEY***\n"   old, rel: (unchanged)
=== X- then long word 40
IN : "-----BEGIN RSA PRIVATE KEY-----\nX-Note: docs\nThisIsAVeryLongIdentifierNameThatExceedsForty\n"
cur: "***PEM_KEY***\n"   old, rel: (unchanged)
```

The same erasure already existed for `Version:`/`Comment:` (`-----BEGIN…\nVersion: see below\nparsePrivateKeyPemString` is erased by all three), so this widens an existing shape rather than adding a new mechanism.
Regression vs da9120a and vs 0959181: yes for the new names. Severity P3: needs a BEGIN line alone, then a line starting `X-…:` or `CRL:`, then a 16+ base64-alphabet line.

Still not covered (not a regression): an unlisted header name between `Proc-Type` and `DEK-Info` stops the walk and the whole body is stored in cur, old and rel (`${H}\nProc-Type: 4,ENCRYPTED\nFoo-Bar: x\nDEK-Info: AES-128-CBC,00\n\n${B}\n${B}`: cur/old unchanged, rel erased only the BEGIN line).

## F6 — P3 — A clean END followed by a closing tag or a comment is not clean, so a 16-39 tail line is kept

`secret-scrub.mjs:391`. `CLEAN_AFTER_END_RE` allows only `[ \t"'`,;)\]}]` before the break. `lineCore` accepts a closing tag after a key line, but an END followed by `</key>` or ` # footer` is not clean.

```
=== tail with closing tag after END
IN : "<key>\nXq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\n-----END RSA PRIVATE KEY-----</key>"
cur: (unchanged)   old: (unchanged)   rel: "<key>\n***PEM_KEY***</key>"
=== tail END followed by comment
IN : "Xq9ZbT2kLp8WvR4nYc7MfH1sJd6GaU\n-----END RSA PRIVATE KEY----- # footer\n"
cur: (unchanged)   old: (unchanged)   rel: "***PEM_KEY*** # footer\n"
```

Regression vs da9120a: no. Vs 0959181: yes. Severity P3: tail-only view, last line 16-39 characters, and a tag or comment after the END.

## F7 — P3 — The F2 prefix repair needs the line above to repeat the END line's prefix exactly outside digits

`secret-scrub.mjs:767`. A prefix that changes in letters or spacing between the last key line and the END line fails `shape.test(above)`, the words make it a sentence, `shape` is dropped, and the prefixed key lines above read as OTHER. The whole tail stays.

```
=== syslog day width change   ("Sep  9" -> "Sep 10")
IN : "Sep  9 23:59:59 host app[1]: Xq9Zb…NtVy\nSep  9 23:59:59 host app[1]: Xq9Zb…NtVy\nSep 10 00:00:00 host app[1]: -----END RSA PRIVATE KEY-----"
cur, old, rel: (unchanged)
=== request-id prefix varies
IN : "[req a1f3] Xq9Zb…NtVy\n[req b2c4] Xq9Zb…NtVy\n[req c3d5] -----END RSA PRIVATE KEY-----"
cur, old, rel: (unchanged)
=== log level changes on the END line
IN : "2026-09-28 12:00:01 INFO Xq9Zb…NtVy\n2026-09-28 12:00:01 INFO Xq9Zb…NtVy\n2026-09-28 12:00:02 WARN -----END RSA PRIVATE KEY-----"
cur, old, rel: (unchanged)
```

Prefixes with regex metacharacters (`(a|b) [x]* `), non-ASCII (`日志 → `) and JSON-escaped docker/Read-tool lines are handled (all erased by cur). A prefix body over 256 characters gets no shape and the tail stays in all three (`'p '.repeat(140)`).
Regression: no, vs either. Severity P3.

## Q5 — Growth, throws, idempotence

Timings (`.d3/perf.mjs`, one run each, ms; cur vs old at 100k / 200k / 400k chars):

| Shape | cur 100k/200k/400k | old 100k/200k/400k |
|-------|-------------------|-------------------|
| prefixed ENDs (`a b c d e f g ` prefix on both lines) | 15 / 6 / 10 | 5 / 3 / 6 |
| sentence ENDs | 3 / 5 / 11 | 2 / 3 / 8 |
| 240-char word prefix on every line | 2 / 3 / 6 | 1 / 2 / 4 |
| END + 500 spaces + `x` (CLEAN_AFTER_END_RE backtrack) | 3 / 5 / 9 | 2 / 2 / 4 |
| END + one backslash run of n | 1 / 1 / 3 | 1 / 1 / 2 |
| END + 300-backslash runs repeated | 1 / 2 / 4 | 1 / 2 / 4 |
| quote walk over `a'` x n before an escaped BEGIN | 7 / 11 / 21 | 4 / 8 / 15 |
| many escaped BEGINs after `a'b'c'` | 5 / 6 / 12 | 4 / 4 / 8 |
| alternating depth 1 / depth 2 BEGINs | 6 / 9 / 15 | 4 / 6 / 10 |
| one huge line then a tail | 2 / 5 / 10 | 2 / 5 / 9 |
| END after an n-char word prefix | 1 / 3 / 5 | 2 / 3 / 5 |
| `a b END` repeated on one line | 3 / 5 / 11 | 2 / 3 / 6 |
| `X-A:`/`X-B:`/`CRL:` headers repeated | 4 / 6 / 11 | 3 / 4 / 7 |
| `X-` + n letters header name | 4 / 7 / 14 | 3 / 7 / 14 |

Every shape roughly doubles per doubling of input; max 21 ms at 400k. The cur/old ratio is at most about 2x on the prefixed-END shape (single runs, not stamped as a benchmark).

Throws: none. Idempotence: `.d3/fuzz.mjs` seeds 1 and 7, 30 000 inputs each (random joins of BEGIN/END/key lines/headers/prefixes/quotes/escapes/`***PEM_KEY***`), `scrubSecrets(scrubSecrets(x)) === scrubSecrets(x)` held for 60 000 / 60 000, with 0 throws. Since `scrubSecrets` loops to a fixed point, this also shows none of these inputs reached the 32-pass cap.
