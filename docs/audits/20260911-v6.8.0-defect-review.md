**Files.** `lib/import-jsonl.mjs:44-47` (`importedObsTitle`), `:172-183` (storage), `:316`
(preview); `lib/scrub-record.mjs:76-90`; `secret-scrub.mjs:277-286`.

**Mechanism.** The round consolidated the title into one function, and the docblock states the
guarantee that is supposed to buy:

> `lib/import-jsonl.mjs:43` — *"One home, scrubbed here, so the two can no longer drift apart."*

The two sites are still not the same expression:

- **preview** (`:316`): `importedObsTitle(useEv)` → `scrubSecrets(x)` — **one** pass.
- **storage** (`:183`): `title: importedObsTitle(toolUse)` is passed into
  `scrubRecord('observations', {...})`, and `title` is in `TEXT_FIELDS_BY_TABLE.observations`
  (`lib/scrub-record.mjs:19`), so the stored string is `scrubSecrets(scrubSecrets(x))` — **two**

They agree iff `scrubSecrets` is idempotent. It is not. Three deterministic counter-examples, run
against `$D/secret-scrub.mjs`:

```
"AccountKey=-?postgres://@&"
  pass1 "AccountKey=-?postgres://***"      pass2 "AccountKey=***"
"AccountKey=https://a:b@h"
  pass1 "AccountKey=https://***:***@h"     pass2 "AccountKey=***"
"Bash: az storage blob list --account-key AccountKey=x/postgres:///"
  pass1 "… AccountKey=x/postgres://***"    pass2 "… AccountKey=***"
```

### The mechanism, stated exactly: it is pattern ORDER, not pattern content

Non-idempotence needs a length-floored rule that sits **earlier** in `SECRET_PATTERNS` than a rule
that **lengthens** the value that floor is measuring. `scrubSecrets` (`secret-scrub.mjs:283-285`)
applies the array in order, once, top to bottom:

| role | line | pattern |
|---|---|---|
| consumer, runs **first** | `secret-scrub.mjs:173` | `/\b(AccountKey\|SharedAccessSignature)=[^\s;&'"]{16,}/gi` |
| consumer, runs **first** | `secret-scrub.mjs:174` | `/([?&]sig=)[^\s;&'"]{16,}/gi` |
| grower, runs **later** | `secret-scrub.mjs:185` | `/(https?\|ftps?):\/\/[^@/\s:]+:[^@/\s]+@/gi` → `'$1://***:***@'` — `https://a:b@` (12) → `https://***:***@` (16), **+4** |
| grower, runs **later** | `secret-scrub.mjs:193` | the db-connection-string rule — `postgres://x` (12) → `postgres://***` (14), **+2** |

Pass 1: `:173` sees a 12-character value, the `{16,}` floor rejects it, and nothing re-runs `:173`
after `:185` rewrites the same span to 16. Pass 2: `:173` runs first again, the value now clears
its own floor, and it fires. `secret-scrub.mjs:69` already reasons about exactly this hazard for
the `{6,}` KV arms ("Both arms emit `***` (3 chars, under the `{6,}` floor), so they cannot
double-apply") — the `{16,}` arms were never given the same treatment, and unlike the `{6,}` arms
their floor can be cleared from **below** by a later rule.

### Why a character-level fuzz over the four real prefixes returns zero

A 300,000-draw fuzz over `[a-zA-Z0-9-_=/+.:]` in the `Bash: ` / `Edit: /repo/` /
`NotebookEdit: /home/u/` / bare prefixes finds nothing, and that is a property of the instrument,
not evidence of idempotence. Three independent reasons, each sufficient on its own:

1. **That alphabet has no `@`** (verified: 69 characters, `@` absent, `&` absent). The +4 grower at
   `:185` requires a literal `@`, so it can never fire.
2. **The other grower needs a literal scheme token** — `postgres`, `mysql`, `rediss`, `mongodb+srv`
   — i.e. 8-11 specific consecutive characters. At 69 symbols a character-level generator does not
   emit one in 300,000 draws.
3. **The value has to be SHORT (12-15 chars) to survive pass 1.** A targeted `AccountKey=`
   construction using an opaque or realistic value lands on the idempotent side by construction: a
   real Azure account key is 88 base64 characters, which `:173` catches on pass 1. The bug lives
   only in the narrow band where the value is under the floor *before* the rewrite and over it
   *after*.

My own sweep found it because its alphabet carried `@`, `&`, `postgres://` and `AccountKey=` as
whole tokens — it was sampling token sequences, not characters. This is the repo's own
"a NEUTRAL from a structurally blind ruler says nothing" rule (`findings.md` doctrine 9) rather
than a disagreement about the fact.

### Verbatim reproductions

All four verified against `secret-scrub.mjs` at HEAD; the first two are in the `Bash: ` prefix so
they drop straight into the existing fuzz harness.

```
"Bash: AccountKey=https://a:b@h"
  pass1 "Bash: AccountKey=https://***:***@h"
  pass2 "Bash: AccountKey=***"

"Bash: curl \"?sig=https://a:b@h\""                       <- the :174 arm
  pass1 "Bash: curl \"?sig=https://***:***@h\""
  pass2 "Bash: curl \"?sig=***\""

"AccountKey=-?postgres://@&"                             <- the :193 grower instead of :185
  pass1 "AccountKey=-?postgres://***"
  pass2 "AccountKey=***"

"Bash: az storage blob list --account-key AccountKey=x/postgres:///"
  pass1 "Bash: az storage blob list --account-key AccountKey=x/postgres://***"
  pass2 "Bash: az storage blob list --account-key AccountKey=***"
```

A ready-to-paste vitest case covering all four, with a premise assertion so it cannot pass
vacuously if a pattern edit stops the fixtures reaching the mechanism, is at
`scratchpad/scrub-idem-case.mjs` (runs green against HEAD: 2 tests).

Original framing, kept for the record: the mechanism is a first-pass rewrite that **grows** a value past a later pattern's length floor.
The basic-auth URL rule (`secret-scrub.mjs:184`) turns `https://a:b@` into `https://***:***@`, four
characters longer; the DB-URL rule (`:193`) does the same for `scheme://…`. That pushes the run
following `AccountKey=` over the `{16,}` floor at `:172`, so pass 2 matches what pass 1 did not.
`secret-scrub.mjs:69` already reasons about exactly this hazard for the `{6,}` KV arms ("Both arms
emit `***` (3 chars, under the `{6,}` floor), so they cannot double-apply") — the `{16,}` arms
(`AccountKey=`, `[?&]sig=`) were never given the same treatment. Rate on a seeded sweep, quoted with
its population so it is reproducible: **10 / 300,000** strings of 2-9 tokens drawn uniformly from a
30-token credential-shaped alphabet, `mulberry32(20260911)`.

**Reproduction status.** Reproduced at the function level (above). **Not reproduced** on a realistic
transcript title: every non-idempotent shape needs a credential key immediately followed by a URL
inside the first 80 characters, and a real Azure `AccountKey` (88 base64 chars) is already caught on
pass 1. So the shipped symptom — a row that re-imports on every run — is not reachable today as far
as I could push it. What is wrong is that the fix's stated invariant is conditional on a property
nothing asserts, and CHANGELOG item 4 describes the failure as fixed unconditionally.

**Fix (one line, no behaviour change).** Put the preview through the *same* choke point so both
sides are literally the same two function applications and no idempotency claim is needed:

```js
const titlePreview = scrubRecord('observations', { title: importedObsTitle(useEv) }).title;
```

(Dropping `title` from the `scrubRecord` call at `:172` also works but silently weakens the
table-level failsafe, so prefer the above.) A guard for it: assert
`scrubRecord('observations', {title: t}).title === t` for `t = importedObsTitle(fixture)` — which is
the property the docblock is actually claiming.

**P3-6 — backfill cost and the retry loop on a large store.** Measured from `$D`'s sources on a
file-backed WAL database: **100,000 observations × 2 paths → 462.6 ms, 200,000 edges, rss 132 MB**;
the next (marked) open costs **0.125 ms**. One-time, so acceptable, and `UNIQUE(obs_id, filename)`
(`schema.mjs:813`) indexes the `NOT EXISTS` probe. The sharp edge: `.all()` at
`schema.mjs:1065-1071` is **outside** the transaction, so a failure there — or any rollback of the
transaction at `:1076-1091` — leaves the marker unset (`schema.mjs:1200-1203`) and the full scan
repeats on **every** `ensureDb`, i.e. every hook fire, until it succeeds. Note also that
`INSERT OR IGNORE` does **not** suppress FOREIGN KEY violations in SQLite, and `initSchema`
re-enables `foreign_keys` before `runDeferredCleanups` runs (`tests/schema-fk-warmstart.test.mjs`),
so an observation deleted between the SELECT and the INSERT aborts the whole pass. Self-healing, but
on a big store it is a repeated half-second tax rather than a cheap one. Consider batching (e.g.
`LIMIT 5000` per pass, marker set only when a pass returns zero rows), or at minimum moving the
SELECT inside the transaction.

**P3-7 — `tests/schema-backfill-observation-files.test.mjs:157` passes `includeNoise: true`, so the
headline case does not exercise the default recall predicate.** `recallByFile`'s default applies

not use. Drop the flag.
