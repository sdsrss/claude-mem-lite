# D#593 测量：重建前查页的第二次尝试（2026-11-01）

> 这次改动没有发布，也没有合进 main：代码留在本地分支 `feat/d593-page-check`（代码 b6628ea7，文档 e5e50611），没有推送。
> 发版前 r1 两个盲审报了一个 P0、两个 P1：
>
> - 页检查用 `openSync` 打开 `-shm`、主文件和 `-wal`，读完就 `closeSync`。POSIX 的 fcntl 锁按"进程 × 文件"记，关掉任何一个
>   描述符，本进程在这个文件上的锁全部释放，包括调用方连接持有的主文件 SHARED 锁和 `-shm` 的 DMS 锁。一个长寿连接跑过检查以后，
>   别的进程关闭时以为自己是最后一个连接，检查点并删掉日志；这个连接之后的提交写进已删除的文件，再在它关闭时被旧页盖掉。
>   复现：`mem_fts_check rebuild` 之后 hook 提交的行丢失，integrity_check 仍是 `ok`（defects P0-1）。同一原因让检查在读事务
>   期间没有读锁，跨进程写者 + 检查点下，好库被判 damaged（defects P2-2：轮换检查点的四组各约 11,500–12,700 次提交，每组 2–7 个）。
> - doctor 先跑 `claude mcp list`，它会启动 MCP 服务器，服务器读写打开库并写入，发生在页检查之前（claims P1-1：日志内夹具 300 → 288 行）。
> - 库文件本身是符号链接时，复制命令的副本里没有 `-wal`（claims P1-2 = defects P2-1：库 70 行、副本 50 行）。
>

## 测量过程中的事故

原型阶段（同一天，nBackfill 规则加入前后）的并发探针没有上限地跑，单进程长到 20.6 GiB 物理内存 + 4.1 GiB swap（用户实测），
虚拟机内存和 swap 用光。原因：better-sqlite3 把 `serialize()` 的整库副本和语句对象交给 JS 时挂的是原生终结器，Node 要等事件循环
转一轮才执行；探针的主循环同步跑 60 秒，GC 收得掉 JS 对象，SQLite 那块内存一块都没释放。1 GiB 上限下对照：`serialize()` × 300
（约 4 MB 的库）不让出事件循环时每次 +3.85 MB，过 1 GiB 被结束；每 20 次让出一次，峰值 157 MB。此后所有尺子都封顶跑，
没有封顶时拒绝启动（`tasks/d593/guard.mjs`），循环每轮让出事件循环。产品不受这个机制影响：doctor 和 hook 跑一次就退出，
MCP 服务器在请求之间转事件循环，页检查也不再用 `serialize()`。
