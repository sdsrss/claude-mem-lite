# Pre-release claims review: claude-mem-lite 6.35.0 (90de5127)

Reviewer: independent, fresh context. Tree: `git archive 90de5127` + copied node_modules at
/home/ai/.cache/tmp/agent-tmp-rv-6350-claims/tree (verified byte-equal to the archive after all runs,
`diff -rq` exit 0). 90de5127 resolves to 90de51277d8ca5bf4fe62fa90a9cd850d364a696. No model calls; LLM keys
and proxies unset; every purge/install run used HOME, CLAUDE_MEM_DIR and cwd inside the work dir, `env -i`,
PATH=/usr/bin:/bin (no `claude` binary reachable).

## Verdict

**P1: 0. P2: 2. P3: 8.** Every number in the release text recomputes exactly from the data and code
(11/60, 23/60, 936, 635, "no other count rose by more than 1", the prompt hash pins, "unchanged byte for byte").
The two P2s are both in the purge prose: the "does not / no longer deletes through a symbolic link" headline
is false in both directions, and the new README sentence "With CLAUDE_MEM_DIR set, it removes only what
claude-mem-lite writes there" drops the runtime/ caveat.

## Findings

### P2-1 — "no longer deletes through a symbolic link" / "does not delete through a symbolic link" is false both ways

Sentences:
- CHANGELOG.md:19 — "`uninstall --purge` no longer deletes through a symbolic link, and prints `Done!` only when `~/.claude-mem-lite` is gone."
- README.md:250 — "**`uninstall --purge` does not delete through a symbolic link.**"
- README.md:1081 — "`--purge` does not delete through a symbolic link: when `~/.claude-mem-lite`, or an entry at its top level ..."
- README.zh-CN.md:209 and :822 — "`uninstall --purge` 不会穿过符号链接删除。" / "`--purge` 不会穿过符号链接删除：…"
- Commit 90de5127 message — "`uninstall --purge` no longer deletes through a symbolic link".

Why false:
1. 6.34.0 never deleted through these links. It removed the link itself and left the target, which CHANGELOG.md:21-22
   itself says ("removed the link, printed `Done!` and left the store where the link pointed"). Sandbox runs of
   `node install.mjs uninstall --purge` on the v6.34.0 tree:
   - E1 `~/.claude-mem-lite` -> ext/store: rc=0, "✓ Data purged (~/.claude-mem-lite/)", "Done!"; ext/store/claude-mem-lite.db, hook.mjs and runtime/r.json all still there.
   - E3 real `~/.claude-mem-lite`, `runtime` -> ext/rt: rc=0, "Done!"; ext/rt/r.json still there.
   - E8 `~/.claude-mem-lite/claude-mem-lite.db` -> ext/claude-mem-lite.db: rc=0, "Done!"; ext/claude-mem-lite.db still there.
2. 6.35.0 still deletes through a link when CLAUDE_MEM_DIR is one, the same as 6.34.0.
   E6, no `~/.claude-mem-lite`, CLAUDE_MEM_DIR=ext/memlink -> ext/realstore, on 90de5127: rc=0,
   "✓ Relocated data purged from …/ext/memlink", "Done!". ext/realstore was emptied (claude-mem-lite.db and runtime/ gone)
   and the link was left. The v6.34.0 tree gives the same result.

What actually changed: when there is a link at `~/.claude-mem-lite` or directly inside it, the purge no longer
removes that link and no longer reports Done! with data left. Effect: minor, because --purge is meant to delete.
But a user whose CLAUDE_MEM_DIR is a symlink, reading README.md:1081 as written, would expect the linked store to
survive, and it does not.

### P2-2 — "With `CLAUDE_MEM_DIR` set, it removes only what claude-mem-lite writes there" (new in this release)

Sentences: README.md:1083-1084; README.zh-CN.md:822 "设了 `CLAUDE_MEM_DIR` 时，只删 claude-mem-lite 在那里写的东西。"
Both were added by 90de5127.

Why false: `runtime/` and `managed/` are removed whole when nothing unrecognised sits at the top level, and that
includes any user file inside them (install.mjs:2181-2186 OWNED_WHOLE_DIRS; :2281-2282 `remove(name)` for `whole`).
- E9 on 90de5127: CLAUDE_MEM_DIR store with runtime/my-notes.txt (a user file) and nothing else of the user's →
  rc=0, "✓ Relocated data purged (…/ext/reloc)", "Done!", and my-notes.txt is gone.
- The behaviour predates this release. The 6.33.0 note in the same README (line 272ff; zh :224) states the
  runtime/ managed/ exception, but the new Uninstall-section sentence drops it.
- Effect: minor (rare population), but it is a deletion claim.

### P3-1 — README's "it removes nothing" reads as the whole command

Sentence: README.md:250-252 "When `~/.claude-mem-lite`, … is a link, it removes nothing and exits 1." The subject is
`uninstall --purge`. The same holds for README.zh-CN.md:209 "它什么都不删".

E1b on 90de5127 (link at `~/.claude-mem-lite` plus an installed footprint): before the link line, the same run printed
"✓ CLI symlink removed", "✓ Removed from installed_plugins.json", "✓ Hooks and plugin settings cleaned",
"✓ Plugin cache removed" and "✓ Marketplace cache directory removed". It exited rc=1, with the final line
"✗ Uninstalled, but the purge is incomplete". Only the purge step removes nothing. CHANGELOG.md:22 (subject: the purge)
and README.md:1081 (subject: `--purge`) are scoped correctly.

### P3-2 — "exits 1" is 3 when the MCP registration remains

Sentences: CHANGELOG.md:23, :25, :28; README.md:252, :1082-1083; README.zh-CN.md:209, :822.

When `claude` cannot remove the registration, uninstall returns EXIT_MCP_UNREGISTERED = 3 (install.mjs:1715;
branch :2133-2139). That branch runs before the purge-incomplete line.
- E1m (link, and ~/.claude.json still registers mem-lite, `claude` not on PATH): rc=3. The final line is "✗ Uninstalled, but the MCP server is still registered…".
- The "purge is incomplete" summary line is not printed. The link warning above it is.
- The exit code is non-zero either way.

### P3-3 — "other than a development install's code links": the exemption is by name, in any install

Sentences: CHANGELOG.md:23-24; README.md:251, :1082; README.zh-CN.md:209, :822.

install.mjs:609 exempts any top-level link named after a SOURCE_FILES top segment, `scripts` or `node_modules`
(lib, cli, server, package.json, hook.mjs, …). It does not check whether this is a dev install or where the link
points.
- E4 (copy-style install, `lib` -> ext/lib): rc=0, "Data purged", "Done!", the link was removed, and ext/lib/a.mjs was kept.
- Nothing is deleted through the link. The code means "links with those names", which is wider than "a development install's code links".
- E10 (a real dev-style layout) behaves as described: rc=0, Done!, and the repo is intact.

### P3-4 — "(another process wrote into it)" names the wrong cause

Sentence: CHANGELOG.md:27-28.

The code comment (install.mjs:2020-2021) and commit e375b8ab both say the cause is another process *deleting* files.
Probe on Node 26.8.1, 6 runs per arm, with a churn process in runtime/ beside 3000 files (race.sh, churn.mjs in the work dir):

| Churn arm | "still there when the removal returned" | Other outcomes |
|---|---|---|
| write only | 0/6 | 5 "Data purged", 1 "Could not remove ~/.claude-mem-lite (ENOTEMPTY)" |
| write + unlink | 2/6 | 2 ENOTEMPTY, 2 "Data purged" |
| unlink only | 6/6 | — |

A writer alone lands in the named-failure branch. The described behaviour itself (the run says so and exits 1) is true.

### P3-5 — zh says more than en about Done!

- README.zh-CN.md:209 "只有 `~/.claude-mem-lite` 确实删掉了，才打印 `Done!`" means "only when it was actually deleted".
- README.md:252 and CHANGELOG.md:19-20 say "only when `~/.claude-mem-lite` is gone".
- With no `~/.claude-mem-lite` at all (E6, relocated purge only), the run prints Done! although nothing was deleted
  there. The English holds; the Chinese does not. Wording like "已不存在" would match.

- **Purge, link case** (CHANGELOG.md:21-24):
  - E1 and E2 at 6.34.0: link removed, "Done!", rc=0, store left behind the link. E2 also purged the CLAUDE_MEM_DIR store.
