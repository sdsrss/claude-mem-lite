## Findings: 0 P1, 0 P2, 10 P3

F1 P3 (pre-existing, also at a122250): the legacy ~/claude-mem-lite migration never runs in the default (non-relocated) shape.
  install.mjs:3571 runLockedInstall calls acquireLock(MEM_DATA_DIR/runtime/install.lock) BEFORE install().
  lib/proc-lock.mjs:123 does mkdirSync(dirname(lockPath), {recursive:true}), which creates ~/.claude-mem-lite.
  So by the time install.mjs:490 checks `!existsSync(DATA_DIR) && existsSync(oldUnhidden)`, the condition is already false.
  The new comment at install.mjs:485-486 ("arming first would create ~/.claude-mem-lite and the migration
  below would never see it absent"), and the test "install() deploys ... after the directory migration",
  both protect an ordering that has no effect in the default shape.
  Repro: temp HOME containing ~/claude-mem-lite/legacy-marker.txt, fake `npm`/`claude` on PATH,
  `node install.mjs install` (it stops at the binding check after the migration step):
    d3acaaa, default:      "legacy dir still present: yes; migrated marker in hidden dir: no"
    a122250, default:      same
    d3acaaa, CLAUDE_MEM_DIR=$H/data (lock lives elsewhere): "Migrating ~/claude-mem-lite/ → ~/.claude-mem-lite/ ... ✓ Directory migrated"
  Effect: a user still on the unhidden layout gets a fresh empty install, and the old data sits unread.

F2 P3: the barrier expires 2 minutes after install arms it. npm install and the binding verify/rebuild are not bounded by that.
  scripts/hook-launcher.mjs:170 sets SWAP_MAX_MS = 2 min, and :175 drops a marker whose ts is older than that.
  install.mjs:470 writes ts once and never refreshes it. execSync(NPM_INSTALL_CMD) at :587 has no timeout.
  The comment at install.mjs:581-586 records compiles from source long enough to hang a 5-minute Bash timeout.
  So when an install runs longer than 2 minutes, hooks fire unbarriered while node_modules is being rewritten.
  The CHANGELOG Unreleased bullet says, with no qualifier, that hooks starting "while the files and their npm
  dependencies are being replaced skip that one run". That holds only for the first 2 minutes.

F3 P3 (by code reading; same split as the pre-existing install.lock): where the barrier lives depends on the installer's env.
  install.mjs:465 puts the marker under resolveDataDir(CLAUDE_MEM_DIR) of the INSTALLER's env.
  The launcher (hook-launcher.mjs:44,67) reads it under the HOOK's env.
  Suppose CLAUDE_MEM_DIR is set only where Claude Code passes env to hooks, and the user runs install from a terminal.
  The marker then lands in ~/.claude-mem-lite/runtime while hooks look in $CLAUDE_MEM_DIR/runtime.
  The code being swapped is always ~/.claude-mem-lite (INSTALL_DIR), which does not move with the env.
  A background repair inherits the hook env, so it is unaffected.

F4 P3 (maintainer path): `install --dev` deploys by rm + symlink, not by rename.
  install.mjs:513/519/523: clearLinkPath (rmSync recursive) then symlinkSync, for each source file, for scripts/ and for node_modules/.
  A reader in that window sees no file (ENOENT). For scripts/ that includes hook-launcher.mjs itself, so the swap
  barrier, which lives inside the launcher, cannot intercept the fire.

F5 P3: tests do not pin the marker's location under relocation or a runtime override.
  Each mutation below leaves tests/install-atomic-deploy.test.mjs at 8/8 passing:
    M7  install.mjs:465 → join(MEM_RUNTIME_DIR, 'swap-in-progress')        (wrong under CLAUDE_MEM_RUNTIME_DIR)
    M8  install.mjs:465 → join(DATA_DIR, 'runtime', 'swap-in-progress')    (wrong under CLAUDE_MEM_DIR)
  HEAD itself is correct (see claim 2). The gap is in the guard, not the code.

F6 P3: "tolerated errors are still printed" is not guarded.
  Deleting the print at scripts/validate-plugin-manifests.mjs:130-131 (V5) leaves tests/validate-plugin-manifests.test.mjs at 12/12 passing.
  The tests check classifyReport().allowedErrors, not main()'s output.

F7 P3: the README / README.zh-CN "Headless runs" paragraph (README.md:537-546, README.zh-CN.md:442-448) is narrower than it reads.
  (a) The rule `mcp__plugin_claude-mem-lite_mem-lite` covers only the plugin install.
      Method 2 (npx) and Method 3 (git clone + `node install.mjs install`) register the server with
      `claude mcp add -s user ... mem-lite` (install.mjs:785), so their tools are mcp__mem-lite__*, which this rule does not allow.
  (b) "Claude Code refuses every mem_* call until the plugin's tools are allowed" is stated as a general fact.
      The cited audit observed it on one version (2.1.292). docs/audits/20261006-d212-ab.md:44 itself says the
      2026-09-29 eval with the same parameters did save to the DB, so this is version-dependent behaviour.
  The 13/13 refusals, the 88 sessions, 0 CLI fallbacks and the allow-rule smoke all match the audit doc (:34-42, :57-58, :80).

F8 P3: three new comments credit all three red runs with one error signature. The CI logs show it in only one run.
  docs/measurement/findings.md:179-182, tests/install-atomic-deploy.test.mjs:5-8 and tests/sandbox/phaseB-npm.mjs:577-581
  say B10 went red on 09-14, 09-28 and 10-05 "with" `... 'buildNotLowSignalSql'`.

  The warning stays true and offers unadopt, but it is not "newly".

F10 P3 (minor): an interrupted install can leave temp files in the code tree that nothing removes.
  atomicCopyFileSync (lib/atomic-write.mjs:110-123) stages files as `<dst>.tmp-<pid>` inside the code tree
  (e.g. lib/x.mjs.tmp-1234). A SIGKILL or power loss mid-copy leaves one behind.
