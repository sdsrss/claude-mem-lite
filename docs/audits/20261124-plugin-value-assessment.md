## 0. 结论

**有用，但有用的部分很窄；项目的投入与它测得出的价值严重不成比例。**

1. **核心价值已证实，而且在当前宿主和当前最强的常用模型上仍然很大。** 工作跨会话、需求只在对话里说过、用户只说"继续"时：
   - 不装插件，Opus 5.5 有 **7/8** 次漏掉剩余需求，并且报告"做完了"；装插件 **0/8**（完整接续 8/8 对 1/8，Fisher p=0.0014）。
   - Sonnet 5.5：4/4 对 0/4（p=0.029）。
   - 你的真实工作方式正是这一类：65 个会话里 50 个从 `/clear` 开始接着做。
2. **"模型变强"不会自动消除这个价值。** 缺的是信息，不是能力：需求不在仓库里，再强的模型也推不出来。宿主自带的 auto-memory 本该补上，但它只在 **1/8** 条 Opus 轨迹里存了计划（09-29 那一轮是 4/4），不稳定。真正会让插件变得多余的，是 Claude Code 自己做出可靠的会话交接，而不是模型变强。
3. **没有发现"装了反而更差"的质量证据。** 两组 S1 当期目标全过、没有回归、没有引入依赖；R4 盲评里自动注入误导 0 次，插件 hook 报错 0 次。代价是成本和注意力：短会话费用 +26.5%、耗时 +28.5%（Opus，同一任务）；真实长会话约占输入 token 的 2%（估算）、每活跃小时约 1 秒延迟、每个会话约 42 个注入块，其中约 87% 当下用不上。
4. **价值集中在三个小功能上**：会话交接（SessionStart 的 Last Session）、待办账本、显式存取。注入量最大的几个面——文件教训（PreToolUse）、错误召回——在盲评里约 1/8 的块当下用得上、从不误导（R3、R4），但没有任何一次对照实验测出它们改变了结果；相似问题提示连盲评都没做过。而最近 30 天的 336 个提交、22 次发版，大部分花在这些面上。（本条 2026-11-25 更正：初稿把错误召回、相似问题提示写成"没有测出收益"，依据只是引用率，而引用率不是有用性的尺子，见 §4 注。）
5. **对你个人的增益比对默认用户小**：你自己有规格文件、宿主记忆，还会手动把"遗留"贴回来（182 条手打消息里 52 条）。插件交接对你的汇报格式一直读不出来，到今天的 v6.35.6 才修好。

**建议**：不要停，也不要照现在的节奏继续；收缩到核心，转入维护模式（§6 方案 C）。

### 1.4 接续靠的是什么

- **对照组**：唯一成功的 o-c-5，是宿主 auto-memory 在 S1 自己写了计划文件。冒烟里也一样：存了计划的接上了（4/4），没存的没接上（1/4）。所以对照组能不能接上，取决于模型在 S1 是否碰巧决定存计划。
- **插件组**：靠 SessionStart 注入的 `Last Session`，它带着上一轮的 Request 原话和 Remaining。
  - Sonnet 插件组在 S1 一次插件工具都没调用（与 09-29 的观察一致：Sonnet 不执行保存引导），仍然 4/4 接上。所以起作用的是**被动交接**，不依赖模型配合。
- **替代效应**：插件组的宿主 auto-memory 都是空的（0/8），模型把计划交给了插件的待办。卸载插件后，这些计划宿主那边没有。

## 3. 成本换算：短会话和长会话不一样（估算）

- **沙箱里的短会话**：每次请求的上下文约 18k token，插件固定多 3.4k，所以相对开销大（Opus +26.5%）。
- **你的真实会话**：R4 窗口里 5.63B cache read 分摊到 19,577 次 API 请求，平均每次约 288k token。固定 3.4k 约占 1.2%，加上 hook 注入的 0.64%–0.85%（R4），**合计约 2% 的输入 token**。大部分按 cache read 计价。
- 所以在长会话里，插件的费用开销很小；短的一次性会话里比例高。真正的成本在注意力：每个会话约 42 个注入块。这些块有没有让模型多走步骤，transcript 里看不出来，**待验证**。

## 5. 判断

1. **不是可装可不装。** 跨会话接着做事是你最常见的工作方式。在这类任务上，插件把"静默漏需求并报告完成"从 7/8 降到 0/8。这一点在当前宿主、当前模型上重新测过，不是两个月前的旧结论。
2. **价值来源与模型强弱无关，与宿主是否做好交接有关。** 要盯的信号是 Claude Code 的版本说明和本实验的对照组接续率：如果对照组达到 ≥7/8（预先登记里"测不出价值"的线），核心价值就没有了。
3. **项目的大部分面积没有测出结果上的价值。** pretool（7.11）、PostToolUse 两面（1.75）、UserPromptSubmit 检索面（1.35）合计 10.21 KB/会话，占插件注入的 66%。盲评里它们约 1/8 的块当下用得上、从不误导，但没有一次对照实验测出它们改变了结果；测出因果收益的会话交接在 SessionStart 里，只是其中一段。
4. **投入与价值不成比例。** 项目从 2026-02-08 起有 2,617 个提交、437 个 tag，发布源码 7.85 万行、测试 18.1 万行、审计文档 9.2 万行；最近 30 天 336 个提交、22 次发版。今天的 v6.37.0 改的是 pretool 的排序，而这个面的引用率是 0.4%。

## 7. 局限

- **场景只有一个，而且是专门挑出来测已知价值的**。它不衡量长期积累的教训（数月）、多项目、大仓库下的价值。09-29 测过的其余 6 类任务两组没有差别，本轮没有重测。
- **`-p` 模式下模型不能中途追问**。交互模式里，用户可能发现遗漏，但 4/7 的 Opus 失败回复没有任何提示，要靠用户自己发现。
- **为模拟交互里的批准，两组都放行了 Bash**（冒烟后修订，判定规则没变）。
- **种子项目形态**：`package.json` 有 `bin`、没有 `private`，插件把它判为可发布的 npm 包根，引导走注入而不是 `CLAUDE.local.md`。这是已发布行为；对普通私有仓库，引导会写进 `CLAUDE.local.md`，主动记录会更多（09-29 §8.5）。
- **样本量**：Opus 每组 8、Sonnet 每组 4。真实会话数据只来自一台机器、一个维护者、4 个项目。
- **费用是名义值**：`total_cost_usd`，Max 订阅不实际扣费。
