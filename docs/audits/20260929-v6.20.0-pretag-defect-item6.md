# Review item 6 — one-shot wide event-edge prune (lib/maintain-core.mjs, cc71b6c)

Scope: `pruneWideEventEdges` / `runWideEdgeCleanupOnce` (lib/maintain-core.mjs:986-1082), call site
hook.mjs:1995-2005, test tests/wide-event-edges-cleanup.test.mjs. Tree: 80335a4. Date 2026-09-29.
Mutations run only in a throwaway clone (deleted). The live DB was opened read-only once, plus one
`VACUUM INTO` copy into the temp dir; nothing was written to the live DB.

Verdict: no P1 or P2. The design matches the spec: a hub edge is never an event's last one removed,
transient paths go even when they are the last, the pass runs in the auto-maintain worker, and it is
idempotent. Two failure/scope gaps (P3) and three test gaps.

## What holds (evidence)

- Placement: only caller is `runSessionStartAutoMaintain` (hook.mjs:1998), and that is reached only
  from `handleAutoMaintain` (hook.mjs:2273), which runs under the proc-lock `AUTO_MAINTAIN_LOCK`
  (hook.mjs:2262). It is not called from ensureDb or from a foreground hook. It is not inside a
  transaction, so VACUUM INTO can run.
- Concurrency with hooks: the only writer of `events.file_paths` is the INSERT in
  lib/activity.mjs:79 (`grep -rn file_paths … | grep -i "UPDATE\|INSERT"`), and nothing UPDATEs it.
  Rows inserted between the plan's SELECT and the UPDATE transaction are not in the plan, and
  UPDATE-by-id cannot lose a concurrent write. Two workers are serialised by the proc-lock. A stolen
  stale lock (10 min) followed by a second run finds 0 changes.
- FTS: `events_fts_au` is `AFTER UPDATE OF title, body` (schema.mjs:829), so the UPDATE does not
  touch FTS.
- Idempotent and marker-gated, measured on a copy of the live DB (5130 events, 4968 with
  file_paths): run1 `{ran:true, changed:1185, removed:1831}` in 51.2 ms including the snapshot;
  run2 `{ran:false}`; a dry run afterwards gives `changed:0`; a dry run on the `.pre-edge-prune-*.bak`
  gives `changed:1185`, so the snapshot holds the pre-image.
- Failure paths: an UPDATE that throws rolls back its transaction, the catch returns
  `{ran:false}`, and the marker stays unset, so the pass retries on the next daily run. A marker
  INSERT that throws after the prune gives the same result, and the retry is a 0-change pass. The
  pass never throws into the rest of auto-maintain.
- The last edge: `kept = nonHub.length > 0 ? nonHub : real` (maintain-core.mjs:1039). A hub is
  removed only when a non-hub, non-transient edge remains.

## Findings

### P3-1 A failed snapshot does not stop the pass, which still marks itself done
maintain-core.mjs:1069-1077. `snapshotDb` is best-effort and returns null on any error
(lib/db-backup.mjs `snapshotDb` catch). `runWideEdgeCleanupOnce` ignores the null, rewrites the rows
and sets the marker. The edges are then gone with no pre-image and no retry. The spec requires a
snapshot "before an irreversible write". The v6.20.0 CHANGELOG entry (working tree, line ~51 of the
section) says "The database is snapshotted first".
The best-effort rule in db-backup exists so that a disk-full purge is never blocked. This one-shot has
no urgency, and deferring it by a day costs nothing.
Repro (clone, vi.mock of `snapshotDb` → null, file-backed DB, one `saveEvent` with
`['/p/package.json','/p/src/x.mjs']`):
`RESULT {"ran":true,"changed":1,"removed":1,"snapshot":null} files ["/p/src/x.mjs"] marker true baks 0`.
Realistic trigger: VACUUM INTO needs free space equal to a full copy of the DB.
Suggested fix: `if (!snapshot && db.name !== ':memory:') return { ran: false };`. With that
mutation applied (M12) the existing 6 tests stay green, so the fix is compatible with the suite.
Severity P3: only recall keys are lost, not memory content.

### P3-2 The pass is not limited to old or machine-written events
maintain-core.mjs:1026-1028 scans every event (`WHERE file_paths IS NOT NULL AND file_paths != '[]'`)
with no `created_at_epoch` bound and no source filter. Two groups the rationale ("provably not the
subject") does not cover lose their hub edges:
(a) events the user wrote on purpose: `claude-mem-lite activity save --files package.json,src/x.mjs`
(cli/activity.mjs:58-86, used by /bug and /lesson) store user-chosen edges. No column tells them
apart from Haiku-written episodes (schema.mjs:788-803). Probe above: a `lesson` with
package.json + src/x.mjs lost package.json.
(b) events written by the new capture (edited files only) between the upgrade and the first daily
maintain run. An episode that edited both package.json and src/app.js is written correctly and then
narrowed. The window is up to 24 h, longer if the worker is skipped.
There is also a converse gap. Sessions still running the old plugin root after the marker is set keep
writing wide edges, and nothing ever cleans them.
Severity P3: recall-key narrowing only, and the hub edge survives when it is the only edge.

### P3-3 The transient rule is not relative to the project, so a project under /tmp/claude-N loses its own edges
`isTransientPath` (lib/bash-file-targets.mjs:39-48) matches `^/tmp/claude-\d+/` absolutely. Unlike
`isScratchCommandPath`, it does not spare paths inside the project dir. The prune applies it
retroactively and removes the edge even when it is the last one. Live DB, read-only:
project `scratchpad--loop-smoke` has events 1912 and 1914, and every edge of each is that project's
own file (`/tmp/claude-1000/.../scratchpad/loop-smoke/.loop/state.md`). Both would become
`file_paths = NULL`.
This matches the spec wording ("a path the capture now drops"), so it is a design edge case rather
than a code defect. Population on the live DB: 675 events emptied in total. Their transient
elements break down as 1079 tmp-claude, 481 host `~/.claude/projects`, 14 node_modules and
1 tool-results. Only 2 of the 675 events are the project-under-/tmp case.

### P3-4 "Bounded" is not enforced
The spec's 9-D constraint says the pass is "bounded". The pass reads every matching row into memory
and updates all of them in one transaction, with no cap. The practical impact is nil at the
measured scale (4968 rows, 51.2 ms end-to-end with the snapshot). I did not measure a DB 10x or
100x larger.

## Test strength (tests/wide-event-edges-cleanup.test.mjs, 6 tests; baseline 6/6 green in the clone)

Mutations; each one was confirmed applied (`landed=true`) and reverted before the next:
- CAUGHT: hub removed even if last (M2); transient kept if last (M3); no marker insert (M4); no marker
  check (M5); dryRun writes (M6); snapshot even when 0 changes (M7); no snapshot (M8); emptied list
  stored as `[]` instead of NULL (M9).
- NOT CAUGHT, 6/6 green:
  - M1: snapshot moved AFTER the prune, so the .bak holds the post-image. The test only checks that
    a `.pre-edge-prune-*.bak` exists and never checks its content. This is the pass's only recovery
    route.
  - M10: marker written BEFORE the prune. Nothing tests the docstring's "a failure leaves the
    marker unset so the next run retries".
  - M11: per-row UPDATEs without the transaction. Atomicity is not tested.
  - multi-hub-only event: `kept = … : real.slice(0, 1)` (keep one hub of two). Only a single lone
    hub is fixtured, so "all hubs kept when nothing else remains" cannot say NO.
- Not guarded: that the pass stays out of ensureDb and the foreground hooks. No test reads the
  call placement. Only the e2e test checks that the worker runs it.
- A side note on the e2e test: it does not set HOME. `pluginDisabledHere()` (hook.mjs:252-263) reads
  the real `~/.claude/settings.json`, so the test exits 0 without doing anything, and fails, on a
  machine where the plugin is disabled. This shape already existed before this range.
