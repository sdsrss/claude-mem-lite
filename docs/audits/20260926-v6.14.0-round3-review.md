No P1. Real-data correctness is better than d9ea38d on every change I judged (40/40), and nothing throws.

slowdown is a regression against the released version.

## P2-1: node-side resolution in scriptTargets is quadratic on unbalanced list bindings and loop headers

`lib/bash-file-targets.mjs:370` (LIST_BINDING_RE) + `:372` closeBracket; `:547-548` loopRes; `:559-576` forEach
back-walk; `:522` helperRe (`[^)]*`).

- Each `name = [` / `(` / `{` calls `closeBracket`, which scans to the END of the program when the bracket
  never closes: O(bindings × program). This runs whenever the program has any path literal. It does not need
  an unresolved identifier.
- The loop regexes use a lazy `[^:\n]*?` / `[^\n]*?` up to ` in ` / ` of `, and the forEach back-walk goes to
  index 0 when there is no matching `[`. Both are O(n²) on one long line.

Repro: `node /tmp/claude-1000/-home-ai-dev-claude-mem-lite/c1d0431d-2267-4ec2-a67d-1dc1df78abd0/scratchpad/perf.mjs <tree>` (kept; payload builder `mkpay.mjs`, changed-set `changed.json` also kept) (python heredoc `open(p, 'w')\nx = 'lib/a.mjs'\n` + repeated fragment):

End to end through the real hooks (sandbox DB created first; without a DB pre-tool-recall.js exits at its
`existsSync(DB_PATH)` gate before parsing, and the result is a false 64 ms):
- PreToolUse `scripts/pre-tool-recall-bash.sh`, listBindUnclosed: 12 KB 336 ms vs 59 ms (d9ea38d);

  **60 KB 6450 ms vs 111 ms**. The timeout is 5 s, so the host kills the hook and the episode entry is lost.

The commit's "unbalanced brackets 12 ms at 200 KB" is true for whichever shape it timed, but `x=[`×N at
200 KB takes 71.8 s. The bound test (tests/bash-file-targets.test.mjs, "200 KB of helper definitions") covers
same-name `def f` only.
Suggested fix: give scriptTargets one budget, for example skip indirect resolution (lists, loops, forEach,
helpers) above ~16 KB of program, or cap closeBracket / back-walk distance, and add a bound test per shape above.

## P2-2: BACKUP_MARK's `/tmp/` alternative backtracks cubically inside RESTORE_CMD_RE / BACKUP_CMD_RE

`lib/episode-input-filter.mjs:40` (BACKUP_MARK third alternative `\/tmp\/[^\s"';|&()]*(?:bak|…)[^\s"';|&()]*`),
nested between `[^\s"';|&()]*` stars at `:44` and `:57`. It runs in hook.mjs:732 `entryInputTags` on EVERY
PostToolUse Bash call. The command is not length-capped; only the response is windowed.

Repro: `entryInputTags('Bash', {command}, '')`:
- `'mv ' + '/tmp/bak'×N + ' /tmp/z.bak'`: e51f6cb 414 B 340 ms · 814 B 357 ms · **1614 B 5077 ms** ·
  ~2 KB 12,118 ms. d9ea38d: 0 to 1 ms at every size.
- `'echo mutation; cp a ' + '/tmp/'×N + 'x'` (BACKUP_CMD_RE): 50 KB 550 ms · 100 KB 1980 ms · 200 KB 8002 ms;
  d9ea38d 0 ms.
- The cubic case needs many `/tmp/` + `bak` in one token AND a backup-marked destination (the negative
  lookahead fails, so everything backtracks). With one `/tmp/` or a plain destination it stays ≤104 ms at
  1.2 KB. Over 18,119 real Bash calls (178 transcripts incl. subagents) the maximum was 2.5 ms.

Suggested fix: make the /tmp alternative non-overlapping (e.g. anchor it at the token start: `(?<=^|["'\s])\/tmp\/…`
with no enclosing `[^…]*` before it), or cap `cmd` length for the tag regexes (e.g. 8 KB of words).

## P2-3 (pre-existing in this delta; new since v6.13.6): the prefilter bash regex is still quadratic on non-heredoc shapes

`scripts/pre-tool-recall-bash.sh:82-89` (`start`/`wrap`/`prog_re`). The P2-B fix makes tokens stop at `\`, which
fixes JSON-escaped heredocs. A whitespace-free, backslash-free run with many command-start characters still
restarts the match at each `;` / `(` and scans to the end of the run. d9ea38d and e51f6cb time the same
(test copy `_probe.sh` with the node handoff replaced by `echo HANDOFF`):

| payload command | 30 KB | 120 KB |
|---|---|---|
| `echo a.mjs ` + `;x=`×N | 5474 ms | 78,663 ms |
| `echo a.mjs ` + `( -a(`×N | 3895 ms | 63,632 ms |
| `echo a.mjs ` + `;/x`×N | 1447 ms | 22,938 ms |
| `echo a.mjs ` + `;a/python`×N | 629 ms | 9687 ms |
| `\n` + `-a -b `×N / `sudo -u 5 `×N | 72 ms | 931 ms |
| tab heredoc (the fixed P2-B shape) | 24 ms | 58 ms |

The real data never reaches this: 911 distinct transcript commands over 2 KB, max 34 ms (16.8 KB).
The commit message does not claim these shapes. I list it because the hook is new in 6.14.0 and the timeout is 3 s.
Suggested fix: cap the scanned `cmd` (e.g. the first 16 KB) or bound the number of start positions.

## P3-1: loop targets are matched by variable NAME across the whole program (contradicts the commit claim)

`lib/bash-file-targets.mjs:545-577`. `unresolved` is program-global. Any loop whose first variable shares a name
with a write target has its list heads marked written, even when that loop only reads. The commit body says
"each indirect target resolves only where the write provably flows", and that is true for helpers (their body
is checked) but not for loops or forEach.

Repro (writes, e51f6cb vs d9ea38d):
- `checks=[('lib/a.mjs','pat')]; edits=[('lib/b.mjs','x','y')]; for f, pat in checks: assert pat in open(f).read()`
  `for f, a, b in edits: open(f,'w')…` → NEW `[a.mjs, b.mjs]` (a.mjs false) | OLD `[]`
- node: `['lib/a.mjs'].forEach(f => console.log(fs.readFileSync(f)))` + `for (const f of ['lib/b.mjs']) fs.writeFileSync(f,…)`
  → NEW `[b.mjs, a.mjs]` (a.mjs false) | OLD `[b.mjs]`
- `for f in ['lib/a.mjs']: print(open(f).read())` + `for f in ['lib/b.mjs']: open(f,'w')` → false a.mjs in BOTH trees.

Effect: pre-tool-recall picks "the first file it WRITES", so a false write can steer edit-mode recall to the wrong
file, and bashWrites mis-attributes. None appear among the 40 real changed commands (below).

## P3-2: the 64-helper cap silently drops real writes past the 64th distinct helper

`lib/bash-file-targets.mjs:529`. The cap is deliberate. Its cost: 200 KB of distinct `def fN(path, x)` +
calls records 64 writes vs 2710 at 4cdfa89 / d9ea38d. No real script comes near 64 helpers. No action needed,
beyond recording the trade-off in the comment.
