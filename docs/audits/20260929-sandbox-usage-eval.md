# 沙箱实测：claude-mem-lite 在真实 Claude 编程过程中的作用、问题与优化建议

- **日期**：2026-09-29（UTC）
- **被测版本**：`main` @ `f7de237`（v6.19.4）。修复分支是 `fix/sandbox-eval-20260929`，修复后版本的验证见 §8
- **宿主**：Claude Code 2.1.284，模型 `claude-opus-5-5`（`claude -p` 的默认模型）
- **性质**：先实测，后修复。本文所有数字都来自同一天、同一场景、同一模型的沙箱运行。原始数据留在会话 scratchpad，不入库；复现方法见 §1.6
- **结论分级**：**已证实**（有工具输出或复现）/ **待验证**（只有推理，或样本不足以下结论）

## 0. 一句话结论

在 Claude Code 已经自带跨会话记忆（`~/.claude/projects/<dir>/memory/MEMORY.md`）的前提下，claude-mem-lite 只在一种场景下看到了提升：**需求只在对话里说过、又要跨会话接着做**。两轮合计，插件组完整完成 7/8，对照组 3/6。对照组的 3 次成功全部靠模型自己翻上一个会话的原始 transcript，差异不显著（Fisher 双侧 p≈0.25）。

在其余 6 类任务里，两组的完成率和质量没有差别：修 bug、按规矩加功能、历史追问、重构参数解析、原子写入，两组都是 100%。

代价是可测量的：
- 每个会话的 API 费用多 15.5%（p<0.001）；
- 耗时多 11.8%（p=0.056）；
- 每轮上下文多 2.1k–4.0k token；
- 对没有 API key 的默认用户，后台每次 LLM 调用要 $0.04–0.056、22–36 秒。

质量层面发现了几类会误导模型的注入：
- 文件关联的教训，只有 6.3% 同时和当前文件、当前任务都相关；
- 自动抽取的事件有 14% 事实错误，其中一条把用户定的规矩说反了；
- handoff 把通过的测试标成 ERROR；
- 启动面板把插件自己写入的文件当成用户未提交的改动。

这些问题的根因大部分已在本轮修复（§8），剩下 4 项需要你决定（§9）。

**更新（2026-09-29，§8.3–§8.4）**：
- §9 的四项已获授权并实施。9-A 的后续取舍按方案 3 落地：默认注入引导，并向用户征询一次是否写入 CLAUDE.md。
- 上面的实验都在 `$HOME` 下进行，维护者的全局 CLAUDE.md 被一并加载了（§1.4 第 5 条）。在没有任何祖先 CLAUDE.md 的位置补做了一次默认用户复现（§8.4），核心判断不变。
- S2 接续效应累计样本后已证实：各轮合计插件组 26/28，对照组 5/12；按轮次分层的精确检验 p≈0.003。
- 在默认用户下，这一效应更突出：对照组 1/4 完成，没有一条去翻原始 transcript；漏掉的需求直到最后一个会话都没有补上。

**再更新（2026-09-29，§8.5–§8.7）**：
- **9-A 的注入方式降低了结合度，已改掉**。同一轮五组对比（§8.5）：
  - 项目质量五组都是 64/64；
  - 模型主动记录（defer / 决策 / 教训）每条轨迹：注入 1.5 次，写 CLAUDE.md 5.25 次，CLAUDE.local.md 5.25 次（精确检验 p=0.029）；
  - 把工作交给子代理时，子代理看到注入引导 0/12，看到文件引导 12/12。
  - 按用户决定，auto-adopt 改为把引导写进 git 根目录的 `CLAUDE.local.md`，并加进 `.git/info/exclude`，不进提交；非 git 目录仍注入。
- **记忆有事实错误，已加核对与更正机制**（§8.6）。预埋两条错误记忆：新旧引导下模型都没被误导（0/8），但旧引导 0/16 更正，新引导 14/16 当场用正确记录取代。
- 最终代码的确认实验见 §8.7。

## 1. 方法

### 1.1 对照设计

| | 对照组 `ctl` | 插件组 `mem` |
|---|---|---|
| 启动方式 | `claude -p --setting-sources project --permission-mode acceptEdits` | 同左，加 `--plugin-dir <HEAD 的 git archive 副本>` |
| 用户级设置、其他插件 | 不加载 | 不加载 |
| 用户的 `~/.claude/CLAUDE.md` | **实际被加载了**（见 §1.4 第 5 条） | 同左 |
| Claude Code 自带的 auto-memory | **开启**（默认） | **开启**（默认） |
| 插件数据库 | 无 | 每条轨迹一个独立的 `CLAUDE_MEM_DIR` |
| 环境变量 | 去掉本会话继承来的全部 `CLAUDE*`/`MEM_*` | 同左，另设 `CLAUDE_MEM_SKIP_UPDATE=1` |

两组的唯一差别是 claude-mem-lite。

对照组**不是"没有记忆"**，而是"只有 Claude Code 自带记忆"。所以本文回答的问题是：**插件在宿主自带记忆之上，还多提供了什么**。

### 1.2 场景：一个项目、连续 8 个会话

被测项目 `invoicer` 是一个约 300 行的 Node.js 开票 CLI，用 `node:test`，没有第三方依赖。它有两个预埋问题：
- `allocate()` 用 `Math.round` 分账，会出现"各人金额加起来超过总额"；
- CLI 缺少 `INVOICER_DATA` 环境变量时，报的是一个晦涩的 `TypeError`。

每个会话都是一个新的 `claude -p` 进程（跨会话）。会话结束后，"用户"执行 `git add -A && git commit -m "session N"`（懒提交，不含任何说明）。

| 会话 | 用户输入（中文，节选） | 考察点 |
|---|---|---|
| S1 | 折扣功能分三步：①按行折扣 ②优惠码 SAVE10/FLAT5 ③CLI `--coupon`。**今天只做第 1 步** | 起点；插件的固定开销 |
| S2 | "继续上次的折扣功能，把剩下的部分做完。" | **需求只在对话里**：跨会话接续 |
| S3 | split 平摊后金额对不上，查原因并修好 | 新 bug（记忆无从帮忙） |
| S4 | `list --json`，外加两条"以后一直适用"的规矩：不引第三方依赖；对外金额一律用"12.30"这样的元字符串 | 用户偏好的捕获 |
| S5 | `export --format csv/json`，split 支持权重 0 | 规矩的遵守；同一函数被再次修改 |
| S6 | "上次那个 bug 的根因是什么？我定过哪些规矩？"（不改代码） | 历史追问 |
| S7 | 参数解析改健壮，加 `--help` | 诱发引入 commander 等依赖 |
| S8 | store 改为原子写入 | 与记忆无关的新任务（测噪声） |

**评测**：每个会话结束、提交之后，在一个干净 clone 上跑隐藏验收脚本 `eval.mjs`，内容包括：
- 当期目标（例如 S2 的 4 项：SAVE10→101.70、FLAT5→107.35、`--item …:10`→1220.40、无效码报错）；
- 全部前期目标（回归检查）；
- 项目自带测试；
- 是否新增了依赖。

**重复次数**：每组 4 条独立轨迹，共 64 个会话。运行时间 2026-09-29 01:04–01:17 UTC，两组交错并行。

### 1.3 采集的指标

- **效率**：`total_cost_usd`、`duration_ms`、`num_turns`、token（来自 `--output-format json`）、工具调用次数（主 transcript 加子代理 transcript）。
- **插件行为**：transcript 中每一个 hook attachment，包括事件名、注入字符数和 `durationMs`；每个会话后的 DB 快照；模型对 `mem_*` 工具或 CLI 的调用；最终回复里出现的记忆编号。
- **后台 LLM 调用**：在默认用户路径（去掉 `OPENROUTER_API_KEY`）下，把 `CLAUDE_CODE_PATH` 指向一个透明包装器，记录每次调用的参数、上下文、输出 token、费用和耗时，并保存完整输入以便回放。
- **hook 延迟**：用用户真实库的只读副本（244 条 observation、4995 条 event）逐个调用 hook，每项 9 次取 p50。
- **事件质量**：把插件组自动抽取的 43 条 event 连同对应会话的用户输入和提交记录，交给一个不知道分组的子代理盲评，打三类标签：事实是否正确、类型是否正确、是否可复用。

### 1.4 测量过程中自己踩到的坑（已纠正，这里如实记录）

1. **沙箱位置会改变被测行为**。第一轮把项目放在会话 scratchpad，也就是 `/tmp/claude-1000/…`。产品把 `/tmp/claude-<uid>/` 整体当作 agent 的临时目录过滤掉（`isTransientPath`），所以文件关联功能在那一轮**全部失效**。
   - 那一轮的约 25 个会话已作废，全部迁到 `~/cml-eval/` 下重跑。
   - 真实用户的项目不会在这个目录下，所以这不是产品缺陷，而是测量陷阱。
2. **会话继承的环境变量会改变宿主行为**。本会话的环境里有 `CLAUDE_CODE_COORDINATOR_MODE=1`、`CLAUDE_EFFORT=xhigh` 等变量，子进程 `claude -p` 继承后会改为委派 worker 子代理。
   - 实验一律去掉这些变量。
   - D#114 语料报告里"默认 agent 把编辑委派给子代理"那条观察，很可能也是这个继承造成的，建议复核。
3. **本机后台 LLM 走的是 OpenRouter**。环境里有 `OPENROUTER_API_KEY`，所以主实验的后台摘要用的是 OpenRouter 上的 `claude-haiku-4.5`。默认用户（没有 key）走 `claude -p` CLI 路径，这条路径单独测了（mem6/mem7，§3.3）。
4. **`events.accessed_count` 全为 0 不能说明"没被用过"**。只有 `activity show` 会递增这个字段（见 `lib/events-injection.mjs` 的注释），因此本文不引用它。
5. **项目放在 `$HOME` 下，用户的全局 CLAUDE.md 会被当作"项目指令"加载**（事后发现，已如实更正）。
   - Claude Code 会沿父目录逐级加载 `CLAUDE.md` 和 `.claude/CLAUDE.md`。`~/cml-eval/…` 的祖先目录是 `$HOME`，所以即使用了 `--setting-sources project`，`~/.claude/CLAUDE.md`（维护者的 AI-CODING-SPEC）和 `~/.claude/rules/*.md` 仍以 Project 类型载入。第一轮、第二轮、L3 复测、Y/Z 组，两组都是如此，已逐个 transcript 核对。
   - 所以 §2–§8.3 的 A/B **组间可比**（两组条件相同），但描述的是"装了这份规范的用户"，不是默认用户。这份规范要求每个改动单独提交、写结构化报告，这会让对照组的 git 历史更丰富，S6 历史追问也因此对对照组更有利。
   - 为此在 `/run/user/1000` 下（没有任何祖先 CLAUDE.md）做了一次默认用户复现，结果见 §8.4。
   - 顺带发现：`/var/tmp/CLAUDE.md` 和 `/var/tmp/.claude/plugin_claude_mem_lite.md` 是 2026-09-26 某个 cwd 为 `/var/tmp` 的会话被 auto-adopt 写入的（已按用户要求删除）。这是 B-2 的现场证据：连共享临时目录也会被写进去，而且会成为其下所有项目的祖先 CLAUDE.md。
6. **`--setting-sources project` 会把用户级指令整个排除**（§8.5 前的试跑发现）。在隔离配置目录的 `rules/` 下放一条规则，带这个参数时模型答不出，去掉参数就能答出。所以之前各轮的"默认用户"其实是"没有用户级指令的用户"。§8.5 起所有组都去掉这个参数，改为每条轨迹一个独立的 `CLAUDE_CONFIG_DIR`（凭据用符号链接接入），这才是真实的默认用户。
7. **并行进程同时刷新 OAuth 令牌会互相踩**。§8.7 第一次启动时令牌刚好过期，16 个进程共用一份凭据，只有 1 个刷新成功，其余会话几秒内以 "OAuth session expired and could not be refreshed" 结束。那一批作废，错开启动后重跑。判断一轮是否有效，要看每个会话的 `is_error`，不能只看退出码。

### 1.5 局限（结论不能外推到的地方）

- 每组 4 条轨迹，二元结果的检验力有限。S2 第一轮是 4/4 对 1/4（p≈0.14），验证轮是 3/4 对 2/2，合计 7/8 对 3/6（p≈0.25），属于**有提示性**，不是显著。费用差异在两轮里都显著（p<0.001，p=0.005）。（更新：加上 §8.3、§8.4 的轮次后，S2 按轮次分层 p≈0.003，见 §8.4。）
- 同一场景、同一模型，隔 1.5 小时的两轮对照组在 S2 上一次 7/16、一次 8/8：模型行为本身有明显的轮间波动，所以两轮之间只比较机制性指标（注入内容），不直接比较完成率。
- 只用了一个项目和一个模型。任务集合偏向"小项目 + 中文 + 单人"。
- 没有覆盖：长交互会话（上百轮、compact）、`/clear` 路径、多个项目共用一个库、大型 monorepo、Windows。
- 被测插件用 `--plugin-dir` 加载，没有走 marketplace 安装路径（安装路径另有 `tests/sandbox/`）。

### 1.6 复现

测量脚本都放在会话 scratchpad 里，没有入库，会话结束时会删除。重建所需的全部定义都写在本文里：
- 附录 A：8 个会话的用户输入（原文）；
- 附录 B：项目种子和隐藏验收的断言；
- §1.1：启动参数。

关键的测量陷阱见 §1.4。

费用：
- 主实验 64 个会话：对照组 $11.46，插件组 $13.23；
- 默认用户路径（mem6、mem7）与复测（§8.2）另计。复测：插件组 $13.84，对照组 $6.01。
- 默认用户复现（§8.4）：对照组 $7.44，插件组 $8.80，CLAUDE.md 组（3 个会话 × 4）$3.23。

### 2.2 唯一的正面效应：S2 跨会话接续（有提示性，两轮合计 n=8 对 n=6）

对照组 4 条轨迹里：
- 3 条回复"上次会话没留下计划或笔记"，只根据代码推断出"缺 CLI 入口"，因此只做了第 3 步，**漏掉了优惠码**。在 E2 的 4 项检查里，这 3 条各通过 1 项；
- 1 条（ctl3）用 `jq` **翻了上一个会话的原始 transcript**（`~/.claude/projects/…/*.jsonl`）找回需求，4 项全部完成。

插件组 4/4 完整完成。
- 它依靠的是 SessionStart 的 `Last Session → Request` 和 UserPromptSubmit 的 handoff `Working On`，两者都保留了用户的原话。
- 这 4 条里有 2 条，模型也把计划写进了 Claude Code 自带记忆。另外 2 条（mem3、mem4）自带记忆是空的，**只能靠插件**。

对照组的自带记忆在 S1 之后 **0/4** 保存了计划。

**验证轮**（§8.2，插件已换成修复版）的结果：
- 对照组 2/2 完整完成，而且两条都是用 `jq` 翻上一个会话的 transcript 找回需求；
- 插件组 3/4。失败的那条（mem11）其实知道全部需求：自带记忆和插件注入都有。它先停下来问了两个没定的问题（SAVE10 的舍入、税基），在 `-p` 模式下等于这一轮没干活。

**结论**：插件保存"用户原话"让接续**稳定、便宜**：
- 插件组 8 次里有 7 次直接拿到需求；
- 对照组要靠模型想到去挖原始 transcript，6 次里只有 3 次这样做了。

这一点是插件真实的价值，但样本量还不足以给出统计上显著的结论。宿主自带记忆是否保存计划，取决于模型当时的判断：对照组 6 条轨迹在 S1 之后保存计划 0 次，插件组 8 条里 5 次。

### 2.3 没有差别的地方（已证实）

- **S6 历史追问**：8/8 答对根因和修法，两条规矩也都答全。
  - 对照组靠 `git log`/`git show` 加自带记忆的 feedback 文件。模型自己写的提交信息很详细，所以 git 就够用。
  - 插件组 4/4 调了 `cli.mjs get` 或 `search`，得出的答案一样。
- **用户规矩**：
  - Claude Code 自带记忆在 **8/8** 条轨迹里都保存了两条规矩（`feedback_*.md`）；
  - 插件自动捕获了"元字符串"规矩 4/4，"不引依赖"只有 **2/4**；
  - 64 个会话全部没有新增依赖，S5/S7 的金额格式检查全部通过。
- **S3/S5/S7/S8**：两组 100%，没有任何回归。
- **预埋的 `INVOICER_DATA` 陷阱**：两组都没有触发。模型总是先读 `test/cli.test.mjs`，照着设置了变量，error-recall 没有用武之地。

### 2.5 结论

- **效率**：在这个场景里没有提升，反而是净成本：费用 +15.5%、耗时 +11.8%。轮数和工具调用没有显著变化。插件没有减少探索。模型每次都会先 `cat` 一遍相关文件，记忆注入并没有替代这一步。
- **质量**：只有需求只存在于对话里的跨会话任务受益（两轮合计 7/8 对 3/6；加上后续各轮与默认用户复现，见 §8.4）。其余任务里，宿主自带记忆和 git 历史已经覆盖了插件想提供的东西。
- **净判断**：插件的核心价值在"原话保存与接续"，而不在"文件级教训注入"或"自动事件抽取"。后两者在本实验中没有测出收益，却贡献了大部分噪声和成本（§4）。

### P1：会误导模型或污染记忆

**A-1 文件教训的边挂到了"只读过"的文件上（已修复 `9503efe`）**
- **证据**：插件组 79 次文件教训注入里：
  - 与所挂文件相关 36 次（45.6%）；
  - 与当前任务相关 17 次（21.5%）；
  - 两者都相关 5 次（6.3%）；
  - `package.json` 21 次，0 次相关；
  - 例：一条优惠券教训挂在 `package.json`、`README.md`、`money.mjs` 上，每次 `cat package.json` 都会注入它。
- **真实 transcript**（维护者本人，2026-09-15 之后的 149 个会话，按 `hook_additional_context` 去重）：1,227 次文件教训注入，其中 90 次（7.3%）注入在 `package.json`/`README.md`/`CLAUDE.md`/`MEMORY.md` 上。
- **根因**：`hook-llm.mjs` 的 LLM episode 路径把 `episode.files` 存成了 `files_modified`，而 `episode.files` 是本段里**提到过的所有路径**（`cat`、`ls`、`sed -n` 都算）。规则路径 `buildImmediateObservation` 本来就把"编辑过的"和"只读过的"分开存，两条路径不一致。
- **修复**：抽出 `splitEpisodeFiles()`，两条路径共用。
  - 有编辑的 episode 只把编辑过的文件作为边，只读的文件进 `files_read`；
  - 纯只读的 episode（discovery）保持原样，挂到读过的文件上。
- **遗留**：存量 event 的 `file_paths` 仍是宽边，需要数据迁移（§9-D）。

**A-2 通过的 node:test 被当成错误（已修复 `f5f5244`）**
- **证据**：`detectBashSignificance('npm test', 'ℹ tests 25 ℹ pass 25 ℹ fail 0')` 返回 `isError=true`。
  - handoff 的 Recent activity 把它渲染成 "npm test … → ERROR: ℹ tests 25 ℹ pass 25 ℹ fail 0"；
  - 真实 transcript 的 handoff 注入里共有 40 个 "→ ERROR:" 标记（149 个会话）。
- **根因**：绿色汇总的豁免只认"0 fail"这种数字在前的写法（bun/jest/cargo）。node 内置 runner 和 TAP 是标签在前："ℹ fail 0" / "# fail 0"。另外 `sed -i … && git diff` 输出的 diff 片段里带有 `throw new Error(`，也被当成了错误。
- **修复**：豁免补上标签在前的写法；统计错误关键词前先去掉 unified-diff hunk 的正文行。git 自己的 `error: patch failed` 不在 hunk 里，仍然算错误。

**A-3 handoff 的 Recent activity 不可读（已修复 `a30f08a`、`5e5ef5d`）**
- **证据**（8 次 handoff 注入）：
  - `cat > /tmp/p.py <<'EOF' EOF python3 - <<'EOF' p='… → ERROR: ✔ parseMoney (0.761416ms) ✔ formatMoney …`（通过的测试被标成 ERROR）；
  - `… → {"stdout":"","stderr":"","interrupted":false,"isImage":false,"noOutputExpected":false}`；
  - `Created project_discount_feature_plan.md`：这是 Claude Code 自带记忆的文件，不是用户的工作。
- **根因**：
  1. 选条目用的是宽松的 `isError`；
  2. Bash 编辑直接显示命令的前 50 个字符，而 Opus 5.5 的编辑多半是 heredoc 脚本；
  3. `normalizeToolResponse` 把空的 stdout/stderr 当成"不是 stdio 对象"，回退成整个对象的 `JSON.stringify`。这个 JSON 恰好让静默写命令越过了 10 字符的门槛，也就是说，静默写能被记录下来本来是巧合。
- **修复**：
  - 选条目改用 `isHardError`（旧条目没有这个字段时回退到 `isError`）；
  - 丢弃所有文件都被过滤掉的编辑；
  - Bash 编辑显示为 `Edited a.mjs, b.mjs (Bash)`；
  - 空输出的 stdout 规范成 `''`；
  - 10 字符门槛对"写了文件的 Bash"放行，静默的只读命令不再记录。

**A-4 Claude Code 自带记忆的文件被当成项目文件（已修复 `d6c6b17`）**
- **证据**：S1 的 event 的 `file_paths` 只有 `…/memory/invoicer-discount-plan.md` 和 `MEMORY.md`；handoff 的 Key Files 是 `invoicer-discount-plan.md, MEMORY.md`；模型读宿主记忆文件时，还被注入了"Lessons for invoicer-discount-plan.md"。
- **修复**：`isTransientPath` 把 `~/.claude/projects/<dir>/`（以及 `$CLAUDE_CONFIG_DIR/projects/`）视同 scratchpad。

**A-5 启动面板把插件自己写的文件当作"未提交"（已修复 `9077f36`）**
- **证据**：干净仓库的首个会话 4/4 显示 "📊 Git: 2 uncommitted file(s) on main"。这两个文件是 auto-adopt 刚写入的 `CLAUDE.md` 和 `.claude/plugin_claude_mem_lite.md`。
- **修复**：`readGitState` 剔除未跟踪、且内容只有插件产物的路径（`isOwnAdoptionArtifact`）。用户自己也写过内容的 `CLAUDE.md`、`.claude/` 下的其他文件照常计数。

**A-6 handoff 的 Working On 在 200 字处截断，丢掉需求尾部（已修复 `f6ec285`）**
- **证据**：S2 注入的是"… 3. CLI 的 create 命令加 --coup…"，后面的内容没了。真实库 115 条 handoff 里有 63 条停在截断上限；用户 prompt 有 20%（149/743）超过 200 字。
- **修复**：第一条主题 prompt 保留 600 字，其余仍为 200 字。`match_keywords` 仍按 200 字的版本计算，所以"哪个 prompt 算接续"的判定不变。"先脱敏后截断"的守卫按两个截断点重写，并做了变异验证（顺序反过来时 3 条变红）。

**A-7 自动抽取的 event 有 14% 事实错误（部分修复，其余需要决策）**
- **证据**：43 条 event 盲评结果：
  - 正确 24、部分错误 13、错误 6；类型正确 32/43；
  - `mem2-E7` 写成"`--json` 输出数字形式的分"，与用户规矩和实际提交正好相反。这条在 S5/S7/S8 又被注入了 3 次，S5 的模型发现了矛盾并提醒用户；
  - 2026-09-25 对本仓库 30 条 event 的审计是 2 正确 / 11 部分正确 / 16 错误（`lib/events-injection.mjs` 注释）。

## 5. 反操作、反体验的逻辑

1. **未经同意改动用户仓库**：auto-adopt（B-2）。
2. **把插件自己的产物报告成用户的工作**：启动面板的未提交计数（A-5，已修）。
3. **逼模型"应用或排除"不相关的教训**：26 次 "⚠ Lessons … apply each lesson to this edit"，其中大多数教训与文件无关（A-1）。
4. **在 TDD 红灯时催"保存 bug 教训"**：B-1。
5. **把"本次只做第 1 步"泛化成长期规则**：S1 的 event 写成 "user asked to do one step per session and stop after each"。首轮探针里，S2 注入后模型不得不专门向用户解释"按照 #E1…但这次你说了…"。宿主自带记忆也犯过同一种错误：探针轮的对照组把它记成了"一次只做一步"的规矩，只做完第 2 步就停下来问。
6. **让模型看到它无法执行的指令**：启动面板的 "resume it"，以及提醒里的 `/lesson` 斜杠命令（模型只能改用 Skill 工具）。

## 7. 缺失的功能和流程

1. **"上次 X" 的主题化召回**：继续类 prompt 中提到了具体主题（"split bug"）时，应该按主题检索历史 handoff 或 observation，而不是取最近一条。

### 8.6 记忆的事实核对与更正

**问题**：
- 自动事件有事实错误：43 条里 6 条错误、13 条部分错误（§4 A-7）；
- 模型自己存的教训也可能超出当时 diff 的实际范围（§8.4）。

**已有的基础**：
- `/verify` 以前测过：便宜模型单次判断是否过时，精确率只有 0.36；模型写的更正有 28/72 是错的。所以核对必须由读过代码的 agent 来做。
- `mem_save(supersedes=[N, "E#N"])` 早已能让一条新记录取代旧的手动教训或自动事件（D#205），被取代的记录不再被召回。

缺的只是引导：没有任何文字告诉模型记忆可能不准、E# 是自动摘要、发现矛盾时该怎么办。

**改动**（`9aca6cc`）：
- 托管块新增一行："当一条召回的记忆要用来回答问题或做设计决定时，先在代码或 `git log` 里核对它的说法；`#NN` 是保存的笔记，`E#NN` 是自动摘要、可能写错，两者描述的都是当时的代码；代码与之矛盾时以代码为准，并用 `mem_save(..., supersedes=[NN] / ["E#NN"])` 替换。"
- bugfix 那一行要求教训只写这次 diff 能证明的内容。
- 详细文档新增一节，写明同样的规则。
- CLI 的 `help` 和详细文档补上了 `save --supersedes`：这个参数一直可用，但 agent 走 CLI 时查不到它。
- 托管块大小从 1450 增加到 1863 字节。

**验证**：预埋错误的对照实验。
- 取 f1–f4 在 S5 之后的状态（项目、插件库、宿主记忆），预埋两条和代码及用户规矩相反的记忆：
  - 一条手动决策："JSON 输出里的金额用整数分"；
  - 一条自动事件："split 的 bug 是改用银行家舍入修好的"。
- 然后跑 S6 历史追问。旧引导（`023b70b`）和新引导各 8 次，每个状态各 2 次。

| | 旧引导 | 新引导 |
|---|---|---|
| 回答被错误记忆误导 | 0/8 | 0/8 |
| 回答里指出矛盾 | 8/8（手动那条） | 8/8 |
| 错误的手动决策被 supersede | **0/8** | **8/8** |
| 错误的自动事件被 supersede | **0/8** | **6/8** |

- 手动决策那一项，Fisher 检验 p≈0.0002。
- 旧引导下，8 次回答里 5 次提出"需要的话我可以删掉或改正那条记录"，2 次请用户确认规矩，1 次只在回答里说明。没有一次实际更正，错误记录留在库里，下次还会被召回。回答里提到错误事件（银行家舍入）的只有 2/8；新引导下是 6/8。
- 新引导下写出的 14 条更正记录都与各自仓库的代码一致：
  - 四个仓库 S3 的 `allocate` 都是向下取整加最大余数排序，没有 `Math.round`；
  - 更正记录里引用的 S3 提交号与仓库一致。

**结论**：模型本来就会在被问到时核对，这个机制补上的是闭环：发现错误后当场以代码为准更正，不再把同一条错误留给下一个会话。
- 它不能保证模型在"没被问到"的场景下主动核对。
- 它也不能消除写入时的错误。后台摘要器的提示词本来已有"只陈述可见结果、教训必须逐字引用诊断行"的约束。


### 8.7 最终代码的确认实验

目的是在即将发布的实现上，确认两件事：自动写出 CLAUDE.local.md 的流程能否复现 §8.5 的效果；核对机制的新引导有没有带来副作用。

**第一次尝试（`7a1fb7b`）发现了一个缺口，已修复（`80335a4`）**：
- Claude Code 在插件的启动钩子运行之前就读取了指令文件，所以创建本地文件的那个会话加载不到它。
- 当时本地模式又不注入，结果每个项目的第一个会话完全没有引导：r11、r12、dr11 等 transcript 的 S1 里既没有指令文件也没有注入块，子代理 0/4 看到引导。

- 修复方式：在创建文件的那个会话里注入一次同样的引导。

**模型漂移**（§1.4 第 7、8 条）：
- 第一次尝试时 OAuth 令牌到期，16 个进程只有 1 个刷新成功，那一批作废。

## 10. 明确不建议做的事

- **不建议用"极简 system prompt"替换后台调用的系统提示**：实测 thinking 长度增加 3–5 倍，更贵也更慢（§8 表）。
- **不建议给 error-recall 继续加规则**：已知 N2。本实验只触发 1 次，信息不足以支持再改一次门控。
- **不建议追求"更多注入"来提高引用率**：注入面越多，噪声越多。本实验中注入字符和效果没有正相关。
- **不建议在没有主题匹配的前提下扩大 handoff 注入窗口**：B-4 已经显示"取最近一条"会注入错误的会话。
