### F2 — P1 — "now loses the word, as the same line in plain text does" is false when the value ends its line

- **Sentence.** "A line in a JSON string that starts with a label and a word (`password: instructions`) now loses the word, as the same line in plain text does."
- **What is false.** The value class `[^\s,;'"}\]]` does not stop at the escaped break `\n`. A value that ends its line runs on through the following lines up to the first space, `,`, `;`, quote, `}` or `]`. In plain text it stops at the real break.
  - `Reset the\npassword: instructions\nare in the wiki` in a JSON string becomes `password: *** in the wiki` in 6.30.12, losing `instructions\nare`. Plain text gives `password: ***\nare in the wiki`.
  - A Write tool response for a .env: `{"type":"create","filePath":"/repo/.env","content":"# env\nAPI_KEY=<V>\nDEBUG=true\nPORT=3000\nNODE_ENV=production\nLOG_LEVEL=info\nFEATURE_FLAGS=a,b\n",…}`.
    - 6.30.12 leaves the content as `# env\nAPI_KEY=***,b\n`: of 7 lines, 2 remain.
    - Plain text loses only the value.
    - `password=` and `SECRET=` behave the same. `token: <V>\nregion: eu-west-1` becomes `token: *** eu-west-1`.
  - The value also takes the backslash of an escaped quote right after it, and the JSON stops parsing. Example: `{"filePath":"/repo/x","content":"const help = \"Usage: tool\\ntoken: <V>\";\n"}` becomes `…token: ***";\n"}`. The Python `MSG = "Reset the\npassword: <V>"` breaks the same way. 6.30.11 left both valid.
- **Repro.** `node scripts/p7-textloss.mjs`, `node scripts/p8-run-through.mjs`, `node scripts/p17-escape-loss.mjs`.
- **6.30.11:**
  - It did not match these line-start labels at all: it stored the credential and lost no text.
  - For names it already caught (`DB_PASSWORD=`, `GITHUB_TOKEN=`) it ran on the same way (`# env\nDB_PASSWORD=***,b\n`), so the run-on itself is old behaviour.
  - What is new is its reach: `API_KEY=`, `password=`, `SECRET=`, `token:` and the rest now run on at every JSON line start. The entry calls this losing "the word".
- **Population note.** On 344 public config and doc files under node_modules (56,740 lines), JSON-wrapped and plain scrubbing gave the same result in both trees (p19). Those files have no credentials at line starts, so they cannot show this; the shape is credential-bearing config, which is what the change targets.
- **Grading note.** The release spec's own pre-registered rule counts "text lost beyond what is written, in a real shape" as P0/P1. I graded under that reading.

### F6 — P3 — after an escaped tab mid-line, a JSON string now loses words plain text keeps

- **Sentences.** D#663 bullet: "also after an escaped tab or carriage return, while the same line in plain text was erased". Claim-5 bullet: "as the same line in plain text does".
- **What is false.**
  - In JSON the prose guard `(?<![A-Za-z][ \t]…)` sees the two characters `\` and `t`, not a letter and a tab, so it does not hold back a label that follows a word and an escaped tab.
  - `see the<TAB>token: alicebob below`: plain text is kept by both trees. In JSON, 6.30.11 keeps it and 6.30.12 gives `token: *** below`.
  - `Reset the<TAB>password: instructions are…` becomes `password: *** are…` in JSON only.
  - The entry does not state this loss.
- **Repro.** `node scripts/p7-textloss.mjs` (the "tab mid-line" rows).

### F7 — P3 — plain text with a literal `\n` also loses words

- **Sentence.** "A line in a JSON string … now loses the word". The change is not limited to JSON strings.
- **What is false.**
  - The new anchor `(?<=\\[nrt])` matches the characters `\` and `n` in any text, not only in JSON-encoded text.
  - Source code read as plain text, such as `console.log("Usage:\ntoken: required\n");` from Bash `cat` or grep, becomes `token: ***");` in 6.30.12; 6.30.11 leaves it unchanged.
  - The commit message says this ("An escaped backslash before an n … is taken for a break as well"); the CHANGELOG does not.
  - The commit's own lost-word case, `'Reset the\npassword: instructions…'`, is a JS source fixture, not a JSON string.
- **Repro.** `node scripts/p7-textloss.mjs` (last row).

### F8 — P3 — commit and code comment: "Its value never starts with `-`, so the key passes always had that BEGIN"
