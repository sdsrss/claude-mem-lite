## 8. "`maintain`'s `dedup` op, which is in its default set, supersedes near-identical observations" — **FALSE, both halves**

**Quoted** (`CHANGELOG.md:47-48`, item 4): "Rows already duplicated are not cleaned up by this

This is the remediation advice the entry gives a user who already has duplicate rows, so it

```
dedup in default set? false
dedup in ALL set?     true
```

`lib/maintain-core.mjs:59` is the single definition, and it is the one every face uses:

So a user who runs `maintain` gets no dedup at all.

**Half two — "supersedes near-identical observations". Also FALSE for that op.**
`lib/maintain-core.mjs:952`:

```js
if (ops.includes('dedup') && mergeIdsProvided) {
```

The op is gated on the caller supplying explicit merge groups (`keepId:removeId[:removeId…]`),

The very next block (`:962`) is a warning for `merge_ids` passed without `dedup`, and
`tests/maintain-ops-sequence.test.mjs:115-133` pins both branches. So even
`maintain --ops dedup` with no `--merge-ids` supersedes nothing.

```
runSessionStartAutoMaintain (hook.mjs:1746-2001)
  → selectFuzzyDedupeIds (lib/maintain-core.mjs:126)  → bodiesSimilar (Jaccard floor)
```

**So the reassurance survives, the mechanism named does not.** Duplicate imported rows do get

## 9. "A bump locks every older code home out of the database permanently" — **TRUE**

**Quoted** (`schema.mjs:1052-1054`, and the same claim in `0dc0a92` and `CHANGELOG.md:60-61`):
"Deliberately NOT a schema-version bump. A bump locks every older code home out of the
database permanently (see lib/schema-skew.mjs), and on a plugin install that is reached
routinely — far too much to charge for a derived table."

**Verified against the mechanism, not the prose.** `schema.mjs:470-486`, inside `initSchema`:

```js
if (row.version > CURRENT_SCHEMA_VERSION) {
  const err = new Error(`DB schema is v${row.version} but this claude-mem-lite binary supports up to v${CURRENT_SCHEMA_VERSION}. …`);
  err.code = SCHEMA_SKEW_CODE;  …  throw err;
}
```

Unconditional — no env escape, no flag, and the outer catch at `:488-491` explicitly
re-throws it (`if (e.message?.startsWith('DB schema is v')) throw e`). `CURRENT_SCHEMA_VERSION`
is 49 (`schema.mjs:173`), so a bump to 50 makes every currently-shipped home throw on every
open.

- **"every older code home"** — accurate. The guard is evaluated per open, against whatever
  `CURRENT_SCHEMA_VERSION` that home was built with, so every home below the DB's version is
  caught.
- **"permanently"** — accurate in the sense that matters: migrations are forward-only
  (`README.md:605`), nothing lowers the persisted version, and the two exits the thrown
  message offers are *upgrade that home* or *abandon the data* (`point CLAUDE_MEM_DIR to a
  fresh directory`). The lockout never lifts on its own. It is not "unrecoverable" — an
  upgraded home opens it fine — and the comment does not claim that.
- **"on a plugin install that is reached routinely"** — supported by an independent measured
  note in `lib/schema-skew.mjs:7-12`: 2026-09-08, DB v49 against a live plugin cache at 5.6.0
  (supports v48); every `openDb()` threw, ≥648 copies of one sentence in one day's
  `runtime/hook-errors/*.jsonl`, the MCP server dying before its handshake.

The decision the comment justifies — deferred cleanup marker instead of a version bump — is
the right one on these facts.

## (b) The replacement sentence — **FINDING: over-broad, and item 6 contains a false parenthetical**

**Quoted** (`406ab7a`): "the v6.7.2 upgrade note said observations imported before that release
stay unreachable by file and that the fix was forward-only. **Item 6 makes them reachable.**"

**Quoted** (`CHANGELOG.md:56-58`, item 6): "so one real `mem_save` disabled it forever, and
**everything** imported before v6.7.2 stayed unreachable by file **with no way to repair it
(re-importing skips the row at the dedup step, before the edge is written)**."

The backfill recovers edges from the `files_modified` JSON column, and its own `WHERE` excludes
`files_modified = '[]'`. So the claim is only true of rows that *have* a path in that column.
The question nobody asked is whether every pre-v6.7.2 import wrote one. It did not.

**Counter-measurement.** I extracted the pre-v6.7.2 tree (`84c3976^`, i.e. v6.7.1) and ran its
real `importJsonl` over a two-tool-use transcript, then ran HEAD's backfill and recall over the
resulting rows in one process:

```
pre-v6.7.2 import (84c3976^):
   id=1 title="NotebookEdit: "          files_modified=[]                    ← no path recorded anywhere
   id=2 title="Edit: /repo/alpha.mjs"   files_modified=["/repo/alpha.mjs"]

after runDeferredCleanups(db)  — item 6, the backfill:
   edges = 1

after re-importing the same transcript with HEAD:
```

1. **"Item 6 makes them reachable" is over-broad.** It makes the `files_modified`-bearing

## The amendment

`importedObsTitle` no longer scrubs. It returns the RAW title, and both call sites scrub it
exactly once through `scrubRecord`:

```js
// before (committed at 06303a6 / HEAD)
function importedObsTitle(toolUse) { … return scrubSecrets(`${name}: ${detail}`); }
const titlePreview = importedObsTitle(useEv);
// storage: scrubRecord('observations', { title: importedObsTitle(toolUse) })  → scrubbed TWICE

// after (uncommitted)
function importedObsTitle(toolUse) { … return `${name}: ${detail}`; }
const titlePreview = scrubRecord('observations', { title: importedObsTitle(useEv) }).title;
// storage: scrubRecord('observations', { title: importedObsTitle(toolUse) })  → scrubbed ONCE
```

The committed version scrubs the **storage** side twice (once in `importedObsTitle`, again
inside `scrubRecord`, which scrubs `title`) against the **preview** side's once. Those two are
equal only if `scrubSecrets` is idempotent.

## FINDING: `scrubSecrets` is not idempotent, and the committed fix therefore still duplicates

**Counterexample, 63 characters, an ordinary shell command:**

```
Bash: deploy --token ghp_1234567890abcdefghijk secret: hunter2correct
  once : Bash: deploy --token *** secret: hunter2correct
  twice: Bash: deploy --token *** secret: ***
  idempotent? false
```

**Mechanism, and it is general.** The `token`/`bearer`/`secret` `:` pattern carries a prose
guard, `(?<![A-Za-z][ \t])`, so `<word> secret: value` is treated as English and left alone.
Before the first pass the character before ` secret:` is `k` — a letter — so the guard fires
and nothing is scrubbed. The first pass replaces `ghp_…k` with `***`; now the character before
` secret:` is `*`, the guard no longer fires, and the second pass scrubs the value. **A
replacement destroys the letter the lookbehind keys on.** Any input of the shape
`<scrubbable-token-ending-in-a-letter> <noun>: <value≥6>` drifts.

I found it by fuzzing first, then derived the title-shaped case from the mechanism:
**4 non-idempotent inputs in 1,132,050 checked** (an exhaustive grid over credential keywords ×
separators × values × prefixes × suffixes, plus 400,000 random concatenations of those tokens).

**End-to-end consequence — the committed code still has the bug it claims to have fixed.**
Importing one transcript carrying that command, three times, in an extracted copy of each tree:

```
committed HEAD (406ab7a — scrub inside importedObsTitle):
    run1 +1   run2 +1   run3 +1     COUNT(*) observations = 3
    titles: "Bash: deploy --token *** secret: ***"  ×3        ← stored double-scrubbed
            (the preview computed "… secret: hunter2correct" — single-scrubbed — so it never matched)

amended worktree (raw title, one scrubRecord per side):
    run1 +1   run2 +0   run3 +0     COUNT(*) observations = 1
```

So `06303a6`'s headline claim — "`importedObsTitle` is now the single home for that string,
scrubbed once, so the two sites cannot drift" — **is false as committed.** The two sites drift
for any input in the class above, because one of them scrubs twice. The amendment fixes it;
it is not a stylistic refactor and should not be dropped as one.

The round's own guard did not catch this because its fixture (`SECRET_CMD`, a bearer token in a
`curl`) is idempotent under the scrubber — I re-measured that specific string: `drift = false`.
The test passed for a reason narrower than the claim it was written to support.

## FINDING: the amendment's own justification is inaccurate on two points

Both are in text that will ship (a docblock and a test comment), and both understate rather
than overstate the problem — but they are claims, so they are in scope.

**(i) "no input is known that makes the difference observable: 300,000 fuzzed titles plus six
constructions aimed at the mechanism pre-ship review named all came back stable"**
(`tests/import-jsonl-dedup-scrub.test.mjs`, justifying a source scan over a behavioural case).
**FALSE** — one is known, above. The test states its own remedy: *"If a drifting string is ever
found, add it here as a case and this scan becomes the belt rather than the braces."* That
condition is met. The title above reds the committed code behaviourally and passes on the
amendment, so it is exactly the case the comment asks for.

**(ii) "equal only while `scrubSecrets` is idempotent, which is an assumption about the pattern

It asserts `x === x` on strings the scrubber never touches — it never reaches the substitution
