## Findings

### C1 — P2 — the switch offered for the new default leaves the new on-disk record on, and is not a revert
- Sentences:
  - CHANGELOG.md:9-10 "One default changes: the session summary model reads each turn's last reply. `CLAUDE_MEM_SKIP_SUMMARY=1` turns that model call off."
  - README.md:249-250 "Stop keeps each turn's last reply, scrubbed, in `runtime/`; … `CLAUDE_MEM_SKIP_SUMMARY=1` turns the model summary off."
  - README.zh-CN.md:208 "…设 `CLAUDE_MEM_SKIP_SUMMARY=1` 可关闭摘要模型。"
- Why: each sentence is literally true about the model call, but it is placed as the switch for "One default changes" (the project's own convention, e.g. 6.18.0's "One default changes, with a switch", README.md:469-481, names a switch that restores the old behaviour). This one does not:
  1. With it set, Stop still writes every turn's last reply (scrubbed, cut to 12,000 code points) to `runtime/turn-replies-<session>.json`. `recordStopTurnReply` runs in the `finally` of handleStop, ungated; only `spawnBackground('llm-summary', …)` is gated (tree/hook.mjs:1938 vs :1958-1959). Nothing reads the file when the summary is off; it stays until the 24 h sweep.
  2. It turns off the whole model summary (Next / Lessons / Decisions), which 6.33.0 had on, so it is not 6.33.0's behaviour either. No switch keeps the model summary without the replies; only pinning 6.33.0 does.
  A user who sets it to keep assistant replies out of claude-mem-lite's files still gets them written each turn.
- Evidence (probes/sbx.sh, all hooks with CLAUDE_MEM_SKIP_SUMMARY=1):
  ```
  [stop rc=0] … [stop rc=0]
  -rw------- 1 ai ai  111 … turn-replies-hook-sbx1--proj-223908e2.json
  {"turns":[[1,"Turn 1: parser fixed, tests 10/10 passed. key *** groq ***"],[2,"Turn 2: committed as abc123."]]}
  shim log: (not called)
  ```
- Severity note: P2 because the sentence is true as written; if the maintainer reads "One default changes: X. <var> turns that off" as the opt-out for the change (as 6.18.0 used it), it is a P1 opt-out/data-handling claim.

The sentence right before (CHANGELOG.md:13-15) describes 6.33.0 ("It read the session's observations and prompts only"), so a reader takes 4,383 as today's prompt. For cost, the number a 6.33.0 user needs is 6.33.0's prompt on the same sessions.
- Evidence: probes/prompt-len.mjs builds, for reading 5's 30 sessions (collectSessions at the reading's `now`, same sample 30/30), 6.33.0's call, arm A and arm C, and checks A and C against the measured `promptChars`:

### C3 — P2 — the release text presents the next-session defect as fixed; the change does not reach 43% of sessions, and not a final-reply report

The D22 spec's census (tasks/specs/d22-summary-turn-replies.md, "并行路径") counts 39 of 147 multi-turn sessions on the report path and 29 on the tail path.
  rulers.md:90 states both ("Not modelled: … both still keep only the last turn's account (D23)"); the CHANGELOG and READMEs do not.

### C4 — P3 — "every turn's last reply" / "each turn's last reply" overstates
- Sentences: CHANGELOG.md:5 (heading "reads every turn's last reply"), :12, :15-17 ("Stop records each turn's last reply … under its session"); README.md:244, :248-249; README.zh-CN.md:206, :208; commit 22b0dff2 subject.

  3. A turn ended by an API error fires StopFailure, which is not hooked; it records nothing (rulers.md says so; the CHANGELOG does not).
