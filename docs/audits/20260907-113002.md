## 2. 三条关键流(按代码实际实现,不按文档)

### 2.1 检索流水线

两个面(CLI `cmdSearch`、MCP `runSearchPipeline`)进入同一个 `coreRunSearchPipeline`(`lib/search-core.mjs:621`),只差 14 个具名 policy opt(`:651-662`)。顺序:`sanitizeFtsQuery` → obs 腿(FTS+八乘子 → **AND→OR 回退 ×0.5** → 概念共现扩展 ×0.7 → PRF 扩展 ×0.6 → 向量 RRF)→ tier 过滤 → sessions/prompts/events 三腿 → **类型列表回退(仅 MCP)** → 跨源归一化 → 上下文重排 → `applyUserSort` → `finalizeSearchPage`。

**文档漂移**(A-P3-1):四处 docblock 把流水线写成 "…context re-rank **+ supersede** → tier filter…",全树 grep `markSupersede|supersedeMark|markSuperseded` **零命中**。淘汰行的排除完全发生在 SQL 层的 `liveObsFilterSql`。这不是缺失的功能,是会让下一个读者试图"恢复"一个从未存在的阶段的措辞。

### 2.2 Stop 引用回路

一次 `Stop` → `trackCitationsAtStop`(`hook.mjs:1142-1499`)内部**四条互相独立、无外层节流的写路径**:

| # | 通道 | 幂等键 | 守卫用例 |
|---|---|---|---|
| 1 | access(`bumpCitationAccess`) | **无** | **无**(唯一的多次调用用例断言的正是累加) |
| 2 | decay(`applyCitationDecay`) | `last_decided_session_id` + `last_cited_session_id` | `tests/citation-decay.test.mjs:435,488,590` |
| 3 | cite-recall 提示(`nextCiteLowStreak`) | **无** | **无** |
| 4 | surface 计量(`recordCitationSurfaces`) | 覆盖写 | `tests/citation-surface-funnel.test.mjs:259` |

读侧只有一把尺:`citationIdRe()` = `/#(\d{1,7})\b/g`。**关键不对称**:注入侧(分母)对表命名空间 `E#`/`P#`/`D#`/`S#` 逐面做了锚定防御,被引用侧(分子)与 access 允许表**完全没有**。

### 2.3 每日无人值守 optimize

`handleLLMOptimize` → `optimizeRun(db, {reenrichScope:'wide'})`,四个 task **按 `allTasks` 顺序串行**(`hook-optimize.mjs:1474` / `:1484`):`re-enrich → normalize → cluster-merge → smart-compress`。re-enrich 内部再拆四个池(main/aliases/concepts/scopes)。**这个顺序本身产生了 C-P2-1**:re-enrich 的输出列正是 cluster-merge 的输入谓词,同一次进程里前者盖章、后者失明。

## 4. 待验证疑点(有代码证据,未复现,不计入已证实)

- **`assertRelevanceCoversAllFaces()` 的默认调用是同义反复**(`citation-tracker.mjs:350-360`):默认 `sourced` = `ATTACHMENT ∪ NON_ATTACHMENT`,而 `buildCitationRelevanceSet` 实际走 `ATTACHMENT 减去 DECAY_EXCLUDED_SURFACES`。一个被论证进 `DECAY_EXCLUDED_SURFACES` 的面会**失去 access 提升通道而这条守卫不响** —— 正是它 docblock 宣称防住的事。`DECAY_EXCLUDED_SURFACES` 今天是空集,故潜伏。
- **pretool 面的 lesson 不折叠换行**:实测 `"  #4242 [bugfix] first line\n#4243 [decision] SECOND line"` 提取出 `[4242, 4243]`,第二个是别人的 id。孪生面 `error_recall` 走 `truncate`(折叠 `\n`)因而安全 —— **两个孪生面在同一件事上不一致,只有一个是安全的**。能否在真实语料命中未查。
- **narrow re-enrich 可能把 narrative 砍到 100 字符以下**(`hook-optimize.mjs:546-550`),四个回填池都要求 `> 100` ⇒ 同时落出两个池。SQL 侧已走通,未构造真实 LLM 实例。
- **wide re-enrich 重建手工 save 行的 `text`**(`:557`):R10-P1-4 保住了 title 和 narrative,`text` 仍是重建而非追加。方向**可能是好的**(消掉一份重复计数),判断需要一次 denoise-ab。

## 7. R10-P3-11 的冲突,以及为什么本轮不修

`rebuildObservationDerived`(`lib/observation-write.mjs:276-312`)用**两份不同的字段表**做两件事:**写** `derivedText`(`:229-243`,含 title + narrative),**认** `looksAlreadyDerived`(`:258-274`,已知集**不含** narrative)。"认"是把 `text` 提升进 `narrative` 那条分支的唯一闸门,其假阳性方向**不可逆**(误判 ⇒ 正文被派生结果覆盖,`update` 不拍快照)。

- **出路 A(收窄写者)**:去掉 title+narrative 后,对手工 save 形状的行(`text`=正文,其余列空)`derivedText` 求值为**空字符串** ⇒ `update --importance 3` 会把 `text` 清空;且只消掉 5 份重复中的 2 份,只在 `update` 一条路径上。
- **出路 B(索引侧去重)**:一次消掉全部 5 份、对每条写路径生效、`looksAlreadyDerived` 一字不改;但 `text` 是唯一装着 import-jsonl 与手工 save 正文的列,把它移出索引会让这两类行不可检索,所以 B 的正确形态要求**每条写路径都把正文写进 `text`**。
- **A 要求 `text` 是子集,B 要求 `text` 是超集。两条路不能各走一半。**

**结论:本轮不修,改判为"口径问题,先决条件是决定 `text` 的定义"**。今天 `text` 有四种互不相容的含义(ingest 关键词 blob / 手工 save 正文 / `derivedText` 全列超集 / import-jsonl 原始载荷)。可做的是把 §6.3 的方向更正写进 CLAUDE.md,并把三词方向断言固化成一个**能说 NO** 的测试。
