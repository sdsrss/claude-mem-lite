# v6.23.0 pre-tag review: DEFECTS lens

Range `ee5bb00..1a89f8b` (6 commits). Reviewed on an isolated worktree fast-forwarded to
`1a89f8b`. The worktree had been created at `0ab2849`, so I ran `git merge --ff-only 1a89f8b`
before reading anything. Node v26.8.1, bundled SQLite 3.53.4, Linux. Date 2026-10-07.

## Verdict

No P1 and no P2 findings. There are 7 P3 findings. Two of them are in code that predates this
range but that this release makes newly reachable.
The three in-house commits do what they say, with one exception: a claim in 7cffde0's docstring
(the analysis limit) is false. Its measured cost is small. From the defects lens, the release is
safe to tag.

## Findings

### P3-1: `refreshPlannerStats` runs ANALYZE with NO analysis limit, but the docstring says it has one
- `schema.mjs:1342-1346` is the docstring that says "under SQLite's own temporary
  analysis_limit". `schema.mjs:1372` is the call, `db.pragma('optimize=0x10002')`. 7cffde0's
  commit body makes the same claim.
- In the bundled SQLite source, `node_modules/better-sqlite3/deps/sqlite3/sqlite3.c:147337` reads
  `if( (opMask & 0x10)==0 ){ nLimit = 0; }`. The 0x10 bit turns on the temporary limit, and
  0x10002 does not set it. So the ANALYZE scans every index in full.
- Measured with a scratch probe on a copy of a synthetic DB, warm page cache, first call / second call:
  - 44k obs: `0x10002` took 16.8 ms / 0.21 ms, and stat1 holds `44000 44000 1`. Exact counts
    mean a full scan. `0x10012` took 8.1 ms / 0.10 ms, and stat1 holds `44000 2001 1`. Sampled
    counts mean the limit applied.
  - 400k obs: `0x10002` took 103.3 ms / 0.27 ms. `0x10012` took 31.1 ms / 0.14 ms.
  - Changing the mask has a cost: on the 44k DB, `0x10012` writes **0** `sqlite_stat4` rows,
    against **93** with `0x10002`.
- Impact: the cost grows linearly with index size. The call runs synchronously at
  `server.mjs:244`, before the MCP handshake, and holds the write lock while it runs. At
  realistic store sizes the cost is small, so the statement is wrong but the behaviour is not.
  Either correct the comment (it is a one-off full ANALYZE, measured at about 0.1 s per 400k
  observations) or switch to 0x10012, knowing that stat4 is lost.
  A smaller mismatch: the docstring says "costs ~0.1 ms when there is nothing to do", but I
  measured 0.21-0.27 ms with 0x10002.

### P3-2: on the direct path, `doctor` reports an IPv6-literal ANTHROPIC_BASE_URL as unreachable when it is reachable (false red)
- `lib/llm-provider-probe.mjs:61` returns `u.hostname`, which keeps the brackets (`[::1]`).
  The direct probe `tcpReachable` then calls `net.connect({ host: '[::1]' })` at `:79`, which
  does a DNS lookup on the bracketed string.
- Evidence from a scratch probe (listener on `::1`, no proxy, fake key): for `https://[::1]:41647`
  doctor warns "api key set but unreachable direct (ENOTFOUND) — every background LLM call
  fails ...". It gives the same warning for `http://[::1]:41647`. The product's own transport
  does reach the listener: `fetch http://[::1]:41647` connected, and the `UND_ERR_SOCKET` it
  returned came from the test server closing at once.
- 49de57a stripped the brackets for the tunnel's TLS host. This direct probe is the parallel
  path that commit did not cover. The proxy branch is correct (the CONNECT path is
  `[::1]:port`). Fix: strip `^\[|\]$` before calling `_probe`.

### P3-3: NO_PROXY matching now decides where the user's gateway traffic goes, and it misses common forms
- `lib/proxy-fetch.mjs:51` accepts only an exact match or a suffix written with a leading dot.
  The code is identical at `ee5bb00:lib/proxy-fetch.mjs:43`, so it predates this range. Before
  #33 it only ever saw public hosts. Now it routes user-chosen gateways, and those are the
  internal hosts that NO_PROXY usually lists.
- Evidence with `HTTPS_PROXY=http://127.0.0.1:9 NO_PROXY='localhost,127.0.0.1,::1'`:
  `https://[::1]:8443/...` goes through the proxy, and it should not, because the hostname
  carries brackets. `127.0.0.1` and `localhost` both bypass the proxy as expected. With
  `NO_PROXY='*'`, `https://gw.internal:8443/...` still goes through the proxy.
  curl's documented convention also treats `corp.example.com` as covering its subdomains. This
  code only does that when the entry is written `.corp.example.com`.
- Impact: Claude Code reaches such an internal gateway directly, but the direct leg sends it
  through the corporate proxy. The request fails, and every call falls back to `claude -p`.
  doctor uses the same function, so it warns instead of reporting a false green.

### P3-4: "Deleting an observation clears its stored title" holds only for the explicit delete path
- A grep of the shipped `.mjs/.js` files for `search_results` finds one writer to
  `search_results.snapshot_label` outside the telemetry module: `lib/delete-core.mjs:89-93`.
  These hard deletes bypass it: `purgeStale` (`lib/maintain-core.mjs:761`), `cleanupBroken`
  (`:422`), `hook-llm.mjs:100`, and any delete that a 6.22.1 code home runs on the same DB.
- This only affects users who opt in. In issue #31 the maintainer wanted labels to survive
  *compression*, so keeping them through a purge may be intended. If so, the sentence in the
  commit and PR promises more than the code does.

### P3-5: `0.0.0.0` and `localhost.` gateways are refused as "plain http to a non-loopback host"
- `lib/anthropic-base-url.mjs:21-31`. Evidence: `http://0.0.0.0:4000` is refused with
  "...non-loopback host (0.0.0.0); refusing...", and `http://localhost.:4000` is refused too.
  `http://[0:0:0:0:0:0:0:1]:4000` and `http://127.1:4000` are accepted. The refusal is
  conservative by design. The user gets a doctor warning and the CLI fallback, so no request
  goes anywhere it should not.

### P3-6 (pre-existing): if a gateway drops mid-body, the call never rejects, and the unref'd timer can let the process exit with the call unsettled
- At `lib/proxy-fetch.mjs:248-259`, `resp` has only `data` and `end` listeners. Node does not
  emit `error` on an IncomingMessage that has no error listener, so a premature close never
  settles the promise. The overall timer is `unref`'d at `:221`.
- Scratch probe: a TLS gateway behind a real CONNECT proxy sends headers and `partial`, then
  destroys the socket 50 ms later. When something else keeps the event loop alive, the caller
  gets `proxy request timeout` only after the full 3000 ms budget, not at about 50 ms. When
  nothing else is alive, the child process exits without printing a result line, and stderr
  shows Node's unsettled-top-level-await caret. The code is identical at
  `ee5bb00:lib/proxy-fetch.mjs:228`. #33 makes it easier to hit, because the tunnel now points
  at user gateways. Fix: have `resp.on('aborted'|'error')` call `finish(reject, ...)`.

### P3-7: issue #41 asked for ANALYZE in `maintain`'s default ops, and that was not done; two bulk paths leave stats stale
- The release refreshes statistics in only three places, per grep: server open
  (`server.mjs:244`), the daily worker (`hook.mjs:2242`) and after import-jsonl
  (`mem-cli.mjs:3499`). `claude-mem-lite maintain` / `mem_maintain` (`mem-cli.mjs:2624`) do not
  refresh them. Restoring a pre-6.23 snapshot doesn't either, and such a snapshot has no
  `sqlite_stat1`. The stats stay stale until the next session's server start or the next daily
  pass. The `restore` case is reasoning only; I did not run it.

## Questions answered with evidence

1. **Can `refreshPlannerStats` throw, block, write on a read-only handle, or break an older code home?**
   - It never threw in any probe. On a read-only handle it returns false (covered by a suite
     case). On a closed DB it returns false. With an iterator open on the same connection it
     returns false and leaves `busy_timeout` at 5000. On `:memory:` it returns true. ANALYZE
     also covers the FTS5 shadow tables: `observations_fts_data`, `_idx`, `_docsize` and
     `_config` all got stat1 rows, with no defensive-mode error.
   - Startup bound: the 250 ms override bounds the lock wait (covered by a suite case). Nothing
     bounds the ANALYZE itself (P3-1). It took 16.8 ms at 44k and 103 ms at 400k.
   - Older code home: I took a 44k DB, analyzed it with 6.23 and recorded one telemetry search.
     Then the **6.22.1 tree** (`git archive ee5bb00`) ran `stats`, `search` and a `delete`
     preview on it, and all three worked. 6.22.1's own UPS `searchByFts` returned 10 rows in
     73 ms on that DB, because it also uses the new stats. No production code enumerates
     `sqlite_master` beyond lookups by name.
   - WAL, VACUUM INTO and the skew guard: the pragma runs after `ensureDbWithWalRecovery`
     returns, so the skew guard is not affected. The worker takes its VACUUM INTO snapshot
     before the refresh, and the snapshot copies the stat tables. WAL mode makes no difference
     to this call.
2. **Call sites.** Production reaches all three:
   - `scripts/launch.mjs` → the `server.mjs` module body.
   - SessionStart `spawnBackground('auto-maintain')` → `hook.mjs:3967` → `handleAutoMaintain`
     → `runSessionStartAutoMaintain` (gated to once per 24 h).
   - `cli.mjs import-jsonl`.

   No hot path pays for it. Hook entry A/B on a 44k store (same DB, stats off vs on, sandboxed
   HOME, min of 3 runs):
   - `user-prompt-search.js`: **80,978 → 165 ms**
   - `pre-tool-recall.js` (Read): 68 → 66 ms
   - `hook.mjs session-start`: 117 → 111 ms, with the same 1182-byte output

   In-process, UPS `searchByFts` went from 74,662 / 18,160 / 21,632 / 17,212 / 2,054 ms to
   65.6 / 24.4 / 27.6 / 20.3 / 0.5 ms. The MCP/CLI hybrid path did not change (for example
   80.4 → 73.6 ms).

   Stats do not change rankings. On the benchmark corpus I ran all 42 benchmark queries (main
   and vocab-mismatch fixtures) before and after `refreshPlannerStats`. The hybrid top-10, and
   the UPS top-10 for each of the 5 projects, came back with identical id lists. Note that
   `benchmark/` never runs ANALYZE, so the gate measures the stat-less plan while production
   now runs with stats. The A/B above is the only evidence that this does not move the numbers.
   Gaps: P3-7.
3. **db7b04a.**
   - I created a DB with the **6.22.1 CLI** (`save`), then ran 6.23 `stats --search-telemetry`
     in text and `--json` modes. Both reported zeros, and afterwards `sqlite_master` still had
     no `search_%` table.
   - One-table state (only `search_runs`, holding a row): the report says 0 stored. This state
     is reachable only briefly or by a manual DROP, so it is not a defect. The brief case is the
     multi-statement `db.exec` failing between the two CREATEs, and then `search_runs` is still
     empty.
   - Flag turned off after being on: the report still reads the tables, because the CLI is not
     flag-gated by design.
   - Locking: `ensureSearchTelemetrySchema` on existing tables needs no write lock. It passed
     with a peer holding `BEGIN IMMEDIATE` at `busy_timeout=0`. `recordSearch` under a held
     lock fails in 6 ms and restores `busy_timeout` to 5000.
4. **49de57a SNI.** Each call went through a real CONNECT proxy, in a child that trusts the
   fixture CA.
   - Shapes that connect: DNS name in upper case, DNS name with a trailing dot, IPv6 with a
     matching cert, IPv4 written as the integer `2130706433`.
   - Refusals are intact. These four cases all failed with `ERR_TLS_CERT_ALTNAME_INVALID`:
     - DNS name against an IP-only cert
     - DNS name with a trailing dot against an IP-only cert
     - IPv4 against a DNS-only cert
     - IPv6 against a cert without `::1`
   - Reject paths:
     - On a cert mismatch the child exits in about 58 ms, with no hang.
     - A handshake that never completes rejects with `proxy request timeout` at 2504 ms, and
       the child exits at 2557 ms.
     - A non-200 CONNECT destroys the socket (code read).
   - IDN was not run. URL parsing hands punycode to both SNI and the identity check (code read).
   - Mid-body drop: see P3-6 (pre-existing).
5. **Other.** See P3-2 to P3-5. When telemetry is enabled, `countMcpEligibleCorpus` adds a median
   21.7 ms per `mem_search` on 44k rows (35 ms with a tier filter). That is acceptable for an
   opt-in feature.
