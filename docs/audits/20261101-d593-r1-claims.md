## 发现

### P1-1　doctor 查页之前，它自己的 `claude mcp list` 步骤已经启动了 claude-mem-lite 的 MCP 服务器，服务器以读写方式打开数据库并写入

- **被审的说法**：
  - `CHANGELOG.md:28` "**doctor checks the pages before anything opens the database for writing.**"
  - `README.md:962-964` "Before anything opens the database for writing, doctor checks its pages … When they are damaged it … writes nothing to the database"
  - `README.zh-CN.md:738`（同一说法）
  - `install.mjs:3154` 的代码注释
- **实际情况**：
  - doctor 在 `install.mjs:3044` 无条件运行 `claude mcp list`，在数据库一节之前（数据库一节从 3130 开始，页检查在 3148–3160）。
  - 仓库自己说这一步会启动每个服务器：`install.mjs:3035-3036` "health-checks — i.e. STARTS — every MCP server configured"；README 写 "briefly launches each one"。
  - `server.mjs:204` 在导入时以读写方式打开库（`ensureDbWithWalRecovery`），`:272` 接着写入（`PRAGMA optimize=0x10002`）。收到 SIGTERM/SIGINT 时，`:2332-2344` 先跑 `wal_checkpoint(TRUNCATE)` 再关闭。
  - R3 的 doctor 面（`r3.mjs:60`）和门禁测试（`tests/claude-stub.mjs:16`）都看不到这一点：两者用的都是 exit 0 的 `claude` 桩。
- **证据**：用日志内交叉链接夹具（`writeCrossLinkedStore({inLog:true})`，300 条真值行）。
  - 启动服务器、发 `initialize`，然后：

    | 结束方式 | 主文件 sha1 | 日志 | 能读出的行（含日志 / 只主文件） |
    |---|---|---|---|
    | 之前 | `62b4fa9087f6` | 103,032 字节 | 300 / 300 |
    | SIGTERM | `143042f798d3` | 没了 | 288 / 288 |
    | SIGKILL | 不变 | 长到 226,632 字节 | 288 / 300 |

    光是启动时的写入就会覆盖行，不需要检查点。
  - 完整的 `install.mjs doctor`，用一个 `mcp list` 时同样启动服务器的桩：主文件 sha1 从 `62b4fa9087f6` 变成 `2b3ec4f04f99`，日志变成 0 字节，能读出的行 300 → 288。doctor 随后打印 `✗ Database pages: damaged — Tree 5 page 5 cell 3: Rowid 48 out of order`，这处损坏是它自己前一步写出来的。
  - 对照组用 exit 0 的桩（R3 的设置）：sha1 不变，300/300。
- **不确定之处**：没有跑真的 `claude` 二进制（沙箱规则不允许）。"它会启动插件服务器"来自仓库自己的注释和 README。SIGKILL 那一行说明，即使真实客户端不发 SIGTERM，行也会丢。

### P1-2　数据库文件本身是符号链接时，复制命令得到的副本里没有日志

- **被审的说法**：
  - `CHANGELOG.md:30-31` "the command copies the files themselves when the directory or the database file is a symlink (`cp -aL` of the real directory)"
  - `lib/db-unusable.mjs:150-151` "or a store file that is one, is copied as data"
- **实际情况**：
  - SQLite 按解析后的路径给日志命名，`store-pages.mjs:204` 自己也这么写。
  - 命令复制的是 `realpath(dirname(db))`。`-L` 会解引用主文件，但 `-wal` 在链接目标旁边，从来不会被复制。
  - 门禁测试（`store-pages-gate.test.mjs:251-267`）用的是已检查点的库，只比主文件的 sha1，所以看不到这一点。
- **证据**（`scripts/copytest.mjs`：主文件里 50 行，另有 20 行只提交在日志里，然后用 `sh` 跑打印出的命令）：

  | 布局 | 命令退出码 | 副本里有什么 | 行数（库 / 副本） |
  |---|---|---|---|
  | 真目录 | 0 | db、-shm、-wal | 70 / 70 |
  | 数据目录是符号链接 | 0 | db、-shm、-wal | 70 / 70 |
  | 数据库文件是符号链接（`…/disk/real.db`） | 0 | 只有 `claude-mem-lite.db`；`real.db-wal` 留在 `disk/` | 70 / 50 |

## P3

1. **"Four bytes of memory per page"**：
   - 位置：`CHANGELOG.md:21`、`store-pages.mjs:191`、f806b6b4。
   - 这句漏了两样东西。日志页号映射对日志帧里每个不同的页有一个 Map 条目（`:149`）。`lines` 在填充时从不设上限（`:289` 每个未使用的页加一行，截断只在返回时做，`:306`），所以 `:193` 的 JSDoc（"at most max lines are kept"）也不对。
   - 实测：577 MB 的库 +29 MB，2.254 GiB 时峰值 81 MB；按"每页 4 字节"算分别是 0.56 MB 和 2.4 MB。
2. **"On a read-only connection"**（`CHANGELOG.md:21`）只对两个预检（doctor、`fts-check rebuild`）成立。每次重建里面的检查跑在调用方的连接上，而打开器、`mem_fts_check`、doctor 的 FTS 步骤、打开器之后的 `fts-check`、快照探针用的都是读写连接。
3. **"6.30.8's … `fts-check rebuild`"**（`CHANGELOG.md:23`）实际测的是 6.30.8 的 `rebuildIndexes` 这一步，跑在新打开器打开过的 s0 副本上（`r3.mjs:7, 171-173`），不是 6.30.8 的整条命令。文档表格里的标签 "OLD rebuildIndexes" 才是准确的。
4. **耗时范围** "0.43 to 0.44 s / 2.09 to 2.10 s" 是负载 1.5–1.8 下一次运行的离散度：

   | 运行 | 负载 | 热 | 冷 |
   |---|---|---|---|
   | `r4.txt`（被引用的那次） | 1.5–1.8 | 433–441 ms | 2,087–2,099 ms |
   | `r4b.txt`（早 49 秒） | 2.3–3.0 | 444–511 ms | 2,150–2,268 ms |
   | 我的重跑（`out/r4-rerun.txt`） | 3.1–4.3 | 436–581 ms | 2,123–2,276 ms |

   +29 MB 和 FTS5 自检的 2.2–2.3 s 在我的重跑里复现。CHANGELOG 没写负载。
5. **"59 个 serialize 自己抛"**（文档 `:16`）：这 59 个样本上，产品检查的第一行是同一个错误，其中 29 个是 "malformed database schema"，在 `beginPinnedRead` 的第一次 prepare 就抛了，在 `serialize()` 之前。两边的读取器都没有读到页。
6. **"两个面都拒绝了这 1,507 个"**（文档 `:45`）：其中 59 次 doctor 运行没有走到页检查（`pagesLine: null`，正好是 59 个读不出的库）；1,448 次打印了 ✗。1,507 个的 sha1 都没变。
7. **R2 的上限**：文档（`:22`）写 `capped.sh 2G 180`；预登记（`:29`）写 `2G 120`，`race.mjs:1` 写 `<secs+60>`。没有任何产物记录实际的调用。"33 MB"也没有地方记录。
8. **"没有碰到那个窗口"**（文档 `:24`，b6628ea7）：竞态输出里没有这个窗口的计数器，只能说明没有出现症状。
9. **噪声的措辞**（文档 `:67-68`）：`noisy` 标志的意思是"s0 自己两次读不同，或这个臂自己两次读不同"（`r3.mjs:114`），不是"和 s0 的读不同"。219 个里 156 个来自 s0 自己的噪声。74 × 4 是 296，不是 219。预登记的"两次读不一致的臂次"在所有臂上是 407，文档没有给出。
10. **预登记的"一次只跑一个总体"没有遵守**：R1 重跑和 R5 都和三个 R3 分片同时跑。上限加起来 8 GiB，在约定允许的范围内。
11. **"和第一次尝试逐行相同"只在同一进程内成立**：`exact.mjs:120-129` 在同一个连接上先跑 NEW 再跑 OLD。跨进程时，字节相同的输入会给出不同的 `lines`：
    - p2-v1 跑 4 次，主文件、日志和 -shm 的 sha1 都相同：第一行有 2 次是 "Tree 2 page 2 cell 1: Offset 65535…"，2 次是 "database disk image is malformed"。
    - 全部 869 个 plant 跑 3 次：18 个 plant 的 lines 不同；state 0 个不同。
    - 我完整重跑 R1：118 个 plant 的 lines 和测量那次不同；state 0 个不同。

    这支持文档的假设：噪声来自 SQLite 读坏页，不是尺子。
12. **查询时的补救文字**（`db-unusable.mjs:135`）："doctor checks the pages and rebuilds it too" 没有条件，但页坏、库忙或写被挡住时 doctor 不会重建。
13. **打开器**在一次它随后会拒绝的重建之前，仍然记 "FTS index corruption detected, rebuilding indexes"（`schema.mjs:1876`）。
14. **升级说明**（`CHANGELOG.md:7-10`）只列了 "on damaged pages"；检查跑不了时重建也会被拒绝，这一点只出现在第一条的标题里。说明的其余部分准确：钉版本的写法是标准的，schema 仍是 49，没有跳过开关。
15. **"Whenever it checks the database"**（`CHANGELOG.md:8`）比代码宽：`doctor --benchmark / --metrics / --session-audit` 走的是读写打开器，没有页检查（`cli.mjs:256`）。
