# 6.35.0 release text, round 2: claims delta review (c6f49ad0 vs 90de5127)

Verdict: no P1. Two P2 findings: one headline is broader than the code, and one prompt claim leaves out a condition. Three P3 findings. Every purge claim in the bullets held when run.

Setup: `tree/` is `git archive c6f49ad0` with node_modules copied in. `tree-634/` is v6.34.0 and `tree-pre/` is 9da56038 (the parent of 1cf1ceae). Every run used `env -i` with HOME and CLAUDE_MEM_DIR inside this dir, PATH=/usr/bin:/bin plus a dir that holds only node (v26.8.1), no `claude` on PATH, no keys and no proxies. Scripts are in `probe/` and each scenario's output is in `s/<name>/out.txt`.

## Findings

### P2-1: the purge headline claims more than the code does
- Where: CHANGELOG.md:19, README.md:250, README.zh-CN.md:209 and the c6f49ad0 message all say: "`uninstall --purge` no longer says `Done!` when data stayed behind a symbolic link." (数据留在符号链接后面时，… 不再打印 `Done!`)
- Why it is wrong: only links in `~/.claude-mem-lite` are checked. Links in a relocated `CLAUDE_MEM_DIR`, and links one level down, are unlinked. The run then says Done! and exits 0, and the data behind the link stays. For the relocated store, 6.34.0 does exactly the same thing, so "no longer" is false there too. The bullets underneath are scoped correctly; the headline is not.
- Evidence (scenario E-claude-mem-lite.db): `$H/reloc/claude-mem-lite.db -> $H/elsewhere/real.db`, CLAUDE_MEM_DIR=$H/reloc. Output: `✓ Relocated data purged ($H/reloc)` … `Done!`, `exit=0`. Afterwards `elsewhere/real.db` is still there. The same run on tree-634 (E-634) gives the same output.
- Same result for these shapes:
  - `reloc/runtime` as a link: Done!, exit 0.
  - `reloc/metrics` as a link: "Kept 1 entry … metrics", then Done!, exit 0.
  - In a real `~/.claude-mem-lite`, `runtime/turn-replies-s1.json` or `backups/verify-…json` as a link (scenario F): Done!, exit 0, the target files stay.
  - A user's own link such as `research -> userdata` (scenario C): Done!, exit 0. This is intended, but the headline's bare word "data" also covers it.
- Suggested fix: scope the headline to the bullet's rule, e.g. "…when claude-mem-lite's data in `~/.claude-mem-lite` stayed behind a symbolic link". Change the ZH line to match.

### P2-2: the order-by-importance sentence is only sent when there is a reply
- Where:
  - CHANGELOG.md:8-9: "One default changes: the session summary prompt asks the model to order the work it lists as completed by importance."
  - README.md:247-249 and README.zh-CN.md:208.
  - The c6f49ad0 message.
  - The same claim, outside the diff: CHANGELOG.md:14, "The summary prompt now asks for the most important finished outcome first".
- Why it is wrong: `SUMMARY_COMPLETED_ORDER` is added only inside the turns rule or the final-reply rule. The hook-llm.mjs comment above it says: "The prompt without a reply does not carry it." A session with no recorded reply gets the 6.33-era prompt, which has no ordering request. That happens when every Stop had empty text and there is no transcript tail.
- Evidence (`probe/prompt.mjs` calls the shipped `buildSessionSummaryPrompt`):
  ```
  no reply         carries-order-sentence=false
  finalReply only  carries-order-sentence=true
  one turn reply   carries-order-sentence=true
  two turns        carries-order-sentence=true
  empty reply      carries-order-sentence=false
  ```
- Effect: small. Stop falls back to the transcript tail (hook.mjs:1289-1296), so few sessions have no reply.
- Suggested fix: add "when it has the session's replies".

### P3-1: the README no longer states the exit code
The earlier draft said "exits 1" in both READMEs. The new README.md:250-252 and :1081-1082 (ZH :209, :822) only say "removes nothing and names the link". A user who scripts `uninstall --purge && …` has only the CHANGELOG ("None of these ends in `Done!` or exit 0") to go by.

### P3-2: the Uninstall section lost the CLAUDE_MEM_DIR sentence
The earlier draft's README Uninstall paragraph said "With `CLAUDE_MEM_DIR` set, it removes only what claude-mem-lite writes there". In ZH it was "设了 `CLAUDE_MEM_DIR` 时，只删 claude-mem-lite 在那里写的东西". Both are gone. 6.34.0's Uninstall section never had it, so this is not a regression. The information now appears only in the 6.33.0 upgrade note (README.md:272). Meanwhile README.md:1074 says "Deletes ~/.claude-mem-lite/ and its data", which says nothing about the relocated directory.

### P3-3: the 1cf1ceae message lists the names as if complete
The message says a link counts only under "the store and its files, snapshots, runtime/, managed/, metrics/, errors/, backups/". The matcher also covers `resource-registry.db`, `plugin_claude_mem_lite.md`, `.corrupt`, legacy backups, `.snapshot-check-*` and `.update-staging/backup-*`; all were tested in scenario B. The CHANGELOG version adds "among others"; the commit message does not.

## Claims checked and true
- **"With ~/.claude-mem-lite a link, the purge removed the link, printed Done!…"** True. On tree-634 (A-634) the link went, Done! printed, exit 0, and `target/claude-mem-lite.db` stayed.
- **"It now removes nothing, CLAUDE_MEM_DIR included, and names the link."** True (A). Output: `⚠ ~/.claude-mem-lite is a link to $H/target. … removed nothing (CLAUDE_MEM_DIR $H/reloc included).`, exit=1. Both the target and reloc were untouched.
- **"The same holds when … one of the entries … is a link (…)"** True for all 11 names tried. Each gave exit=1, no Done!, the link named, and both the home dir and reloc kept: runtime, managed, metrics, errors, backups, claude-mem-lite.db, -wal, a pre-delete snapshot, plugin_claude_mem_lite.md, resource-registry.db, .corrupt. A dangling `~/.claude-mem-lite` link is also refused with exit 1.
- **Code links and user links are unlinked, never followed** (C). Links tried: registry.mjs, .mcp.json, commands, scripts, server.mjs, node_modules and research. Result: Done!, exit 0, all targets intact, and none of the 48 SOURCE_FILES top-level names is an owned name. Pre-fix tree-pre with a `registry.mjs` link: exit 1 and reloc left. 6.34.0: purged, exit 0. This confirms the 1cf1ceae account.
- **"A removal … that fails is named, where it printed a stack trace; the relocated purge still runs"** (D, a chmod 555 subdir). Current: `⚠ Could not remove ~/.claude-mem-lite (EACCES).` then `✓ Relocated data purged`, exit 1. tree-634 printed an `Error: EACCES … at rmSync` stack trace and the reloc store stayed.
- **"still there after the removal returned, the run says so"** True. A concurrent deleter during the purge produced "still there when the removal returned" in 6 of 6 runs, each exit=1 with no Done!.
- **"None of these ends in Done! or exit 0"** True. All of A, B×11, D, the race runs and the dangling link exited 1 with no Done!. If the MCP server is still registered, the exit code is 3 (`EXIT_MCP_UNREGISTERED`).
