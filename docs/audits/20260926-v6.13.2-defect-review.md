## Findings

### P3-1. A red run that ends as `interrupted` (`--bail`, Ctrl-C) leaves the older green stamp reusable
- scripts/green-stamp-reporter.mjs:70 clears only on `reason === 'failed' || unhandledErrors.length > 0`. vitest 5 reports a run as `'interrupted'` whenever `vitest.isCancelling`, and it checks that before it checks for failures (node_modules/vitest/dist/chunks/index.B89dZ0-N.js:19979: `this.vitest.isCancelling ? "interrupted" : this.hasFailed(modules) ? "failed" : "passed"`). `--bail=N` cancels the run on its N-th failure, so a red bail run reports `interrupted`.
- Reproduced on the SAME tree: a stamp from a full green run, followed by an env-dependent failure (I reset the clone's origin URL, which is not part of the tree key):
  ```
  node scripts/green-stamp.mjs check          -> "full suite passed on this exact tree at 2026-09-26T06:38:22Z"
  npx vitest run --bail=1 tests/suite-touches-no-repo-files.test.mjs  -> exit 1, "Tests 1 failed | 1 passed (4)"
  node scripts/green-stamp.mjs check          -> "full suite passed on this exact tree ..."  exit 0  (pre-commit would REUSE)
  npx vitest run tests/suite-touches-no-repo-files.test.mjs           -> exit 1
  node scripts/green-stamp.mjs check          -> "no green stamp" exit 1   (control: without --bail it clears)
  ```
- Scenario: this is the same shape as defect-review P3-1, which the reporter comment says is closed ("A red run is evidence against any stamp, whatever its filter"). A flaky or env-dependent test goes red under `--bail`, or the user hits Ctrl-C after seeing a FAIL. The next `git commit` then skips the suite. CI still runs on push.
- Fix direction: clear when `reason !== 'passed'`, or when any module is not ok, whatever the reason.

### P3-2 (regression, fails open). An unquoted heredoc body is dropped even though bash expands `$(…)` and backticks inside it
- bash-utils.mjs:179-204 (`stripNonCommands`) removes every heredoc body. For `<<EOF` (unquoted) and `<<-EOF`, bash performs command substitution in the body. Checked here: `bash -c 'cat <<EOF\nx \`echo EXECUTED\`\nEOF'` prints `x EXECUTED`.
- Repro, `detectBashSignificance({command}, RED).isHardError` where RED contains a TypeError plus a stack frame:
  - `cat > notes.md <<EOF\n$(npm test)\nEOF`: old **true** → new **false**
  - `cat > notes.md <<EOF\nrun \`npm test\` first\nEOF`: old other → new read
  - Same shape on another path: `awk -f /dev/stdin f <<'EOF'\nBEGIN{system("npm test")}\nEOF`: old other → new read. The `WRITES_OR_RUNS.awk` test sees only the statement text, and the program has been stripped out of it.
- The same function's own `<<"EOF"` (quoted) case is now correctly read. The defect is that the quoted and unquoted delimiters get the same treatment.
- Corpus: 0 of the 53 other→read flips in this project's transcripts have an unquoted delimiter (15,617 Bash results, 151 files, 2026-09-26 ~06:50Z).
- Fix direction: when the delimiter is unquoted, pass the body's `$(`, `` ` `` and `$((` spans to `subs` instead of dropping them.

### P3-3 (regression, fails open). An arithmetic shift `<<` opens a phantom heredoc that swallows the following lines
- bash-utils.mjs:179. `stripNonCommands` knows nothing about `$(( ))` or `(( ))`, so in `$((1<<2))` it reads `<<2` as a heredoc with delimiter `2`. At the next newline it skips every line until one equals `2`, which in practice means the rest of the command.
- Repro: `grep -c x $((1<<2)) f\nnpm test`: old other/hard **true** → new read/hard **false**. Also `(( x <<= 2 ))\nnpm test`, which opens delimiter `=`, and `cat <<E"OF"\nbody\nEOF\nnpm test`, where a partly quoted delimiter is parsed as `E` and never closes. Both swallow `npm test`.
- Corpus: 0 occurrences of `$((…<<…))` among the flips.

### P3-4 (regression, fails closed). A variable assigned from any substitution makes the whole line "not read-only"
- bash-utils.mjs:253/260 write the placeholder as `' SUBST '`, with a leading space. In `f=$(…)` that splits `f=` from its value, so `classifySimpleCommand` (:141) skips `f=` as an env assignment and takes `SUBST` as the verb, which gives `'other'`. `x="$(…)"` goes the same way.
- Repro: `f=$(git ls-files lib | head -1); grep -n TypeError $f` → isHardError **true**. It was false at ff62955, because `f=$(git` was skipped as an assignment and `grep` was the verb. The substitution body here is itself read-only.
- Corpus: this is 1 of 3 substitution-caused `isError` false→true flips in 15,617 results. The instance is `f=$(git grep -l … | sed …); … git show … | awk …`, which is purely reads. hardError: 0 false alarms in the corpus. All 9 newly-firing hard errors are real: 8 heredoc-then-run, and 1 backtick inside double quotes that bash executed.
- Related fail-closed shapes, which are by design but not tested: `cd "$(git rev-parse --show-toplevel)" && grep …`, `grep x "$(date +%F)".log`, `code-graph-mcp outcome` and `code-graph-mcp snapshot inspect f.db`. The last two are read-only per `code-graph-mcp --help` (0.157.0) but are missing from `CODE_GRAPH_READ_SUBCMDS`. Also `grep $'a\'b' f`: ANSI-C quoting unbalances the quote parser and the new parse-failure rule gives `'other'`, where the old code gave read.

### P3-5 (gap in the claimed coverage, not a regression). A command substitution inside `$(( ))` is never judged
- bash-utils.mjs:256-258 drop the whole arithmetic body (`if (!arithmetic) subs.push(...)`), including any `$(…)` nested inside it.
- Repro: `grep x $(( $(npm test) + 1 )) f` → isHardError false, both old and new. The commit body says the bodies of `$(...)` "are now judged as commands of their own". This one is not.

### P3-6 (new failure mode, no realistic input). Unbounded recursion throws RangeError, and the call site has no guard
- `commandKind` (bash-utils.mjs:336/341) recurses once per nesting level, and `closingParen` rescans the body at every level. A command of 3000 nested `$(` throws `RangeError`: at depths 1000/3000/6000/12000 I measured ok 14 ms / RangeError 61 ms / 164 ms / 369 ms. `isReadOnlyCommand` runs for EVERY Bash command. hook.mjs:677 calls `detectBashSignificance` without a guard, and the comment at bash-utils.mjs:364-369 says a throw there drops the whole tool event. The old code did not recurse.
- Fix direction: a depth cap that returns `'other'`.

### P3-7 (the D#40 shape, only partly closed). key_files still spends its 10-row cap on rows that contribute only files already listed
- hook-handoff.mjs:372-375. A row counts as "contributing" whenever it has at least one valid file, even when every such file is already in `fileSet`. Repeated edits to one file (the common case) use up the 10 rows.
- Measured on a copy of the live DB (2026-09-26T06:35Z). Population: 311 windows = (user_prompts.content_session_id, cc_session_id) pairs joined to sdk_sessions.project, window start = MIN(prompt epoch). This is NOT the commit's 14-window population.
  - The fix vs the old `LIMIT 10 → filter`: 176 windows gain files, 918 in total.
  - The fix vs "count rows that add a NEW file": 146 windows still lose files, 288 in total.
- Not a regression. It is the same eviction mechanism, reached through a second kind of row that contributes nothing. The renderer (hook-handoff.mjs:979-986) has no cap of its own, so the lost files are simply never shown.
